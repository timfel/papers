Regarding this issue and how this affects what the solver can do with
respect to adding/removing fields, we have made an effort to make this
clearer. First, we added the key property that all variables can be
used in constraints and potentially solved for when first introducing
the example in Listing 1:
\begin{quote}

\DIFdelbegin \DIFdel{at least }%DIFDELCMD < \verb!minBal!%%%
\DIFdel{.  }\DIFdelend \DIFaddbegin \DIFadd{above the minimum balance
  required by the plan.  Note that the plan's minimum balance is the
  result of a message send---it does not matter if it is calculated or
  a field access. }\DIFaddend If the constraint is already satisfied

\DIFdel{properties }\DIFdelend \DIFaddbegin \DIFadd{fields }\DIFaddend

  that these variables and fields are not special ``constraint

free. However, our rules allow passing such functions to a solver,
which can then give up. We have reworked this section of the text:
\begin{quote}
\DIFaddbegin \DIFadd{A method }\verb|m| \DIFadd{that is used in a multi-way constraint in the above
manner is ultimately exploded into a set of primitive constraints that
correspond to the primitive operations performed by }\verb|m| \DIFadd{and its
callees, which are then handed to the solver.  However, if the
resulting constraints are not supported by the solver, then even

\paragraph{Primitive values versus objects}
Some languages do not have primitive values, and one reviewer asked if
this means that our rules cannot provide value constraints in these
languages. We have included a clarification in our overview of
existing Babelsberg languages ins Section 2:
\begin{quote}
\DIFadd{Babelsberg implementations allow any object or value to occur in a
constraint and (given capable solvers) be solved for---there is no
distinction between }\emph{\DIFadd{constrainable}} \DIFadd{variables and }\emph{\DIFadd{ordinary}}
\DIFadd{variables. However, during solving there is a distinction between objects for
which identity is significant and those for which it is not. For
example, booleans and small integers are true objects in Ruby and
Smalltalk, but their identity is determined by their value, so
variables referring to such objects can be re-assigned by the
solver. Variables that refer to objects for which identity is
significant, however, cannot simply be re-assigned---in Babelsberg,
these may only be re-assigned by the solver to satisfy constraints
over object identities.}
\end{quote}

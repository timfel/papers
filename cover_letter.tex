\paragraph{Connection between constraint variables and ordinary variables}
Regarding this issue and how this affects what the solver can do with
respect to adding/removing fields, we have made an effort to make this
clearer. First, we added the key property that all variables can be
used in constraints and potentially solved for when first introducing
the example in Listing 1:
\begin{quote}
The constraint on line 2 ensures that \verb!acc.balance! remains
\DIFdelbegin \DIFdel{at least }%DIFDELCMD < \verb!minBal!%%%
\DIFdel{.  }\DIFdelend \DIFaddbegin \DIFadd{above the minimum balance
  required by the plan.  Note that the plan's minimum balance is the
  result of a message send---it does not matter if it is calculated or
  a field access. }\DIFaddend If the constraint is already satisfied
at that point, then nothing need be done; otherwise the solver will
modify the values of variables and their \DIFdelbegin
\DIFdel{properties }\DIFdelend \DIFaddbegin \DIFadd{fields }\DIFaddend
in order to satisfy the constraint. \DIFaddbegin \DIFadd{Note also
  that these variables and fields are not special ``constraint
  variables''---any variable can appear and potentially be solved for
  in a constraint. }\DIFaddend  
\end{quote}
We think some of the confusion may have also been due to the fact
that, in the semantics, we simply replace the entire heap and
environment with those generated by the solver - this is just for
simplicity and really an implementation detail, so we removed
this. Instead, we have attempted to clarify that the issue really
arises when we allow any kind of constraints without type-checking
them. A relevant text was added in Section 2.1:
\begin{quote}
Specifically, suppose the object \verb!acc! has no \verb!balance!
field.  In earlier versions of Babelsberg\DIFaddbegin \DIFadd{, }\DIFaddend the solver could silently
invent such a field \DIFdelbegin \DIFdel{and then constrain it. }\DIFdelend \DIFaddbegin \DIFadd{to satisfy the constraint on line 2, and that field
would be added to the object when the solution is used to update the
heap---after all, we did ask in our constraint that such a field exist
and be equal to the minimum balance. (Similarly, if we created a
constraint that the account be equal to an object with only a balance
field and if the account previously had additional fields, the superfluous
fields could be removed.) 
}\DIFaddend While one might argue that such behavior is desirable in \DIFdelbegin \DIFdel{this case}\DIFdelend \DIFaddbegin \DIFadd{these
cases}\DIFaddend , it is a slippery slope.  For example, consider a constraint of
the form \verb!p.x > 0 || p.y > 0!  on a point \verb!p!.  There is
inherent nondeterminism here --- the solver can choose which \DIFdelbegin \DIFdel{property }\DIFdelend \DIFaddbegin \DIFadd{field }\DIFaddend to
update if the constraint does not hold.  But if \verb!p! lacks an
\verb!x!  \DIFdelbegin \DIFdel{property }\DIFdelend \DIFaddbegin \DIFadd{field }\DIFaddend should it be invented?  If \verb!p! lacks both \DIFdelbegin \DIFdel{properties }\DIFdelend \DIFaddbegin \DIFadd{fields
}\DIFaddend which one should be invented?
\end{quote}

\paragraph{Lifetime of always constraints}
\label{sec:lifet-always-constr}
Regarding the asymmetry of always constraints only applying from the
point at which they are executed (but not retroactively), and
semantically persisting forever (implying interaction with automatic
garbage collection), we have added a clarifications around Listing 1:
\begin{quote}
An \verb!always! constraint is required to
hold for the rest of the execution; Babelsberg/JS therefore \DIFaddbegin \DIFadd{re-creates
and }\DIFaddend re-solves the constraint as part of the execution of each
subsequent statement if it may have become invalidated.  In contrast,
a \verb!once! constraint is solved once and then immediately
\DIFdelbegin \DIFdel{redacted. }\DIFdelend \DIFaddbegin \DIFadd{retracted. Semantically, }\verb!always!  \DIFadd{constraints persist for the
rest of the execution, but the practical implementations garbage
collect constraints if all variables that they transitively refer to are no longer
accessible.
}\DIFaddend 
\end{quote}
\begin{center}
[\dots]
\end{center}
\begin{quote}
  Because this is an \verb!always! constraint, it will be re-checked,
  and if necessary re-solved, \DIFdelbegin \DIFdel{after }\DIFdelend
  \DIFaddbegin \DIFadd{as part of executing }\DIFaddend each
  subsequent statement \DIFdelbegin \DIFdel{.  It is }\DIFdelend
  \DIFaddbegin \DIFadd{as well.$^1$}\vskip0.3\baselineskip
  {\footnotesize \DIFadd{$^1$The constraint is active from the point
      at which it is created and onwards, but does not retroactively
      apply prior to the execution.  In a graphical application, for
      example, the user may have already seen previous results.}}
  \DIFaddend
\end{quote}

\paragraph{Distinct identity constraints}

There was a question of whether it is possible to express that two
variables must not refer to the same object. It is not, because this
leads to identity non-determinism:

\begin{quote}
  Finally, the solver \DIFdelbegin \DIFdel{can }\DIFdelend
  \DIFaddbegin \DIFadd{could }\DIFaddend also satisfy the identity
  constraint by assigning both variables to yet a third
  object\DIFaddbegin \DIFadd{$^1$}
  \vskip0.3\baselineskip
  {\footnotesize \DIFadd{$^1$One could also imagine a
    }\emph{\DIFadd{distinct}} \DIFadd{identity constraint to express
      that two variables should not refer to the same
      object---however, this will almost always lead to
      non-determinism as the solver is free to pick any object to
      re-satisfy the constraint if one of the variables is assigned to
      be identical to the other.}} \DIFaddend
\end{quote}

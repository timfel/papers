\authorinfo{Stefan Lehmann\and Tim Felgentreff\and Robert Hirschfeld}

\begin{abstract}
  \acrlong{cop} extends object-oriented languages with a mechanism to
  dynamically adapt behavior. \acrlong{ocp} orthogonally extends
  object-oriented run-times by integrating constraints, including
  support for constraints over mutable state, object identity, and the
  results of message sends. Using these two language extensions in
  conjunctions offers interesting opportunities.

  In this paper, we report on new mechanisms involving layers and
  constraints that evolved from our experiences with combining
  Babelsberg/JS, an Object-Constraint Language, and ContextJS, an
  implementation of \acrlong{cop} in JavaScript. First, our experience
  shows that it is desirable to dynamically adapt declarative
  constraints, which offer an orthogonal mechanism to the definition
  of imperative behavior, likewise at runtime. In this work, we show
  an extension to ContextJS to scope activation or refinement of
  constraints dynamically using layers.  Second, ContextJS already
  provides different activation mechanisms for layers, including
  dynamically or structurally scoped, or globally through system
  generated events. Constraints provide an activation mechanism based
  on arbitrary boolean expressions changing their value, allowing for
  interesting applications of behavioral adaption based on certain
  conditions.
\end{abstract}

\section{Introduction}

Many mechanisms exist that extend the toolbox of the object-oriented
programmer with features such as pattern matching\cite{}, functional
cores\cite{}, multi-dimensional dispatch\cite{}, and more. Among those
mechanisms are \gls{cop}\cite{}, which add dynamic adaption of
behavior based on layers, and \gls{ocp}\cite{}, which adds constraints
over mutable objects and on the results of message sends. Using these
two language extensions in conjunctions offers interesting
opportunities to address shortcomings in each language, and thus make
both extensions useful for a wider variety of problems. In this paper,
we present two such extensions, which we call \emph{Layer Activators}
and \emph{Constraint Layers}.

\paragraph{Layer Activators}
\label{sec:constr-based-adapt}
\gls{cop} layers adapt behavior at runtime when they are
activated. There are many activating strategies in \gls{cop}
languages, including dynamically scoped\cite{} or scoped to object
structure\cite{} and event-based\cite{} or reactive
activation\cite{}. While first two mechanisms offer explicit control
over the activation time of layers, the latter two are particularly
interesting for our discussion, because of their declarative
nature.

Event-based activation uses system-generated events to activate or
deactivate a layer during the event loop. Reactive activation is based
on similar principles as Aspect-oriented Programming: whenever a
message is sent that matches a \emph{pointcut}, an associated
condition is evaluated. If that condition evaluates to true, a layer
is activated for the duration of the method activation.  

A limiting factor of both mechanisms is their granularity. Event-based
activation relies on the creating appropriate events that indicate a
change in the system state to activate layers. In JavaScript, for
example, common system generated events indicate user input or network
activity. However, it is not possible to tell the system to generate
an event whenever an arbitrary condition changes. Similarly, reactive
activation focuses on message sends. The conditions for layer
activation are only checked at join-points, and thus the burden is on
the programmer to ensure that their pointcuts match all message sends
that may be relevant.

With Babelsberg, any constraint expression can be continuously
monitored, thus, we argue, providing a flexible constraint activation
mechanism. In essence, any boolean expression in the source language
can be associated with the activation state of a layer. We call these
kinds of constraints \emph{Layer Activators}.

\paragraph{Constraint Layers}
\label{sec:constraint-layers}
\gls{ocp} languages are motivated by the observation that some issues
in software development lend themselves to a declarative
specification, while others are more directly expressed using
imperative constructs. The goal is to provide both paradigms in a
cleanly integrated fashion within an object-oriented language in a way
that supports messages, encapsulation, inheritance, mutable objects,
and object identity in constraints. In \gls{ocp}, constraints can be
defined, activated, and retracted at runtime. A meta-level protocol
exists using which constraints can be activated and retracted at
arbitrary points during the execution. In addition, various \gls{ocp}
systems offer explicit scoping mechanisms for constraints.

Babelsberg \cite{FelgentreffJOT14} is a design for \gls{ocp}
languages, and this work is based on its JavaScript implementation,
Babelsberg/JS \cite{FelgentreffECOOP14}. Babelsberg defines three
types of scopes for constraints: \emph{always}, which defines and
activates a constraint for the entire rest of the execution;
\emph{once}, which activates a constraint, solves it, and then
immediately retracts it; and \emph{assert--during}, which activates a
constraint for the duration of a code block.

An issue with these scoping mechanisms is that they effectively allow
the activation of constraints with global effects at any point in
time. It is not possible to add restrictions on when constraints can
be activated, making reasoning about a program difficult. Because
constraints are, by their nature, multi-directional, any method may
add a constraint involving its arguments and thus calling any method
may affect the objects created by its caller.

To alleviate this problem and provide control over when constraints
are active, we use \gls{cop} to provide a convenient scoping mechanism
to add, modify, or suppress constraints using layers. We call such
layers that adapt declarative constraints in addition to behavior
\emph{Constraint Layers}.

The work presented here was done as a result of our experience in
developing a browser-based clone of the game \emph{Wii Play/Tanks!},
which provided opportunities to use both constraints and layers, but
also exposed shortcomings of these language extensions in our use-case
(\autoref{sec:game}). Since our target platform is the browser, our
approach extends Babelsberg/JS and ContextJS, implementations of
\gls{ocp} and \gls{cop} in the browser (\autoref{sec:solution}), but
may also be useful on other platforms with similar language extensions
(\autoref{sec:related-work}). While we have found our mechanisms to be
useful in developing our game clone, we also report on open questions
and future work in that direction (\autoref{sec:conclusion}).

\section{Motivation and Problems}
\label{sec:game}

We set out to create a clone of the game \emph{Wii
  Play/Tanks!}\footnote{\textcopyright 2007 by
  Nintendo\textregistered,
  \url{http://www.nintendo.com/sites/software_wiiplay.jsp}, accessed
  March 30, 2015} that runs in the browser. The game is top-down, with
the players controlling toy-tanks that shoot rubber bullets at each
other. The tanks can move about the field and turn their turrets
independently. The field contains obstacles such as walls and holes in
the ground which the tanks cannot cross, but bullets can ricochet off
walls and fly over holes. As an extension to the original, we added
power-ups which give the tanks' bullets additional behavior such as
flying faster or ricocheting more often.

  \caption{WePlayTanks with Babelsberg and ContextJS}

The finished game is shown in \autoref{fig:game}. From our experience
with both ContextJS and Babelsberg/JS, we realized there are multiple
opportunities to use constraints and layer-based behavioral
adaption. Power-ups change the behavior of bullets, and, during
development, an alternative drawing mode is desirable for
introspection. These can be conveniently encapsulated using
layers. Additionally, there are UI elements that have constraints on
them, such as the target following the mouse, or that a tank cannot
drive into a wall or over a hole. We encapsulated these using
constraints.

\subsection{Desired Form of Layer Activation}

Consider the use of layers for non-permanent power-ups, which are
collected and activated in the game, and should be deactivated after
some time. Activating the layers imperatively is straightforward: when
the player drives the tank over the power-up, the corresponding layer
becomes active. The case for deactivating the constraint, however, is
not as clear.

To later deactivate the constraint, we could create a timeout which
fires later to deactivate the layer
\cite[App.B]{taeumel2014applying}. This, however, makes the
implementation to accumulate the times for multiple power-ups more
difficult, as each timeout would have to check if the layer should
indeed be deactivated or if more power-ups of the same type have
extended the timeout. Alternatively, we could use a variable that
remembers the last time the player found a power-up, and find a
convenient place in the game loop to insert a check if the layer
should be deactivated, with the drawback that we mingle different
concerns into our game loop.

Instead, we would like to re-use the existing game loop time and
decide if a layer is active based on the time difference between the
last collected power-up and the current game time. Intuitively, we
might have a declarative definition of when the layer should be
active, given a variable $lastCollectionTime$ which holds the last
time the player collected a power-up:
\[
   lastCollectionTime + timeOut \leq gameTime
\]
Given this definition, we can control both activation and deactivation
of the layer. When the player drives over the power-up, we set
$lastCollectionTime$ to $gameTime$, which, for a non-zero $timeOut$,
implicitly activates the layer. As time progresses, the inequality
will become false and implicitly, the layer is deactivated.

Constraints in Babelsberg/JS are ordinary JavaScript expressions that
are introduced using the keywords \verb!always! or \verb!once!, the
constraint being that the expression evaluates to true. A translation
mechanism executes constraint expressions while keeping track of the
dependencies between encountered variables and fields. Babelsberg
abstracts from the details of the underlying solvers and can translate
constraints in different ways to hand to different solvers.

As long as a constraint is active, the system keeps track of the
objects that relate to it and, if the constraint becomes invalidated
through modifications to those objects, triggers the solver to find a
solution that satisfies them. If no solution can be found, the
modification that invalidated the constraints is rejected and an
exception is generated. Constraints in Babelsberg/JS are thus useful
to encapsulate \emph{system maintained assumptions}, and ensure that
these assumptions cannot be quietly invalidated.

As a simple example, suppose we want to specify that the \texttt{y}
coordinate of a point object \texttt{pt} is twice as big as its
\texttt{x} coordinate:
\begin{lstlisting}[label=lst:implementation-cassowaryexample,caption={~},]
always: { solver: new ClSimplexSolver()
          pt.x * 2 == pt.y }
\end{lstlisting}

Line 1 specifies that we want to use the Cassowary solver to satisfy
this constraint. Line 2 is the boolean expression that will be
converted by the framework to be solved. Although this code is valid
JavaScript, if executed directly, no constraints will be
created. Babelsberg/JS uses a source-to-source transformation to
convert the above constraint expression into the following JavaScript:
\begin{lstlisting}[label=lst:implementation-cassowaryexamplesourcetransformed,caption={~},]
bbb.always({
  solver: new ClSimplexSolver() 
  ctx: {
    pt: pt
  }
}, function() {
  return pt.x * 2 == pt.y
});
\end{lstlisting}

Besides allowing for a more convenient syntax, the source code
transformation creates a context object that contains all variables
that are directly referenced by the function. The framework requires
this context object in order to interpret and transform the constraint
expression.

In order to maintain constraint, Babelsberg intercepts accesses and
assignments to relevant variables while the constraint is active. As
part of the transformation, each constraint expression is interpreted
using a modified pure-JavaScript interpreter which wraps all object
fields with \emph{property accessors}. From then onward, to get the
value of a field the accessors returns the appropriate value from the
constraint solver. When a field is written, the update is passed to
the constraint solver as a temporary new constraint, triggering the
solving process. If the constraints can still be satisfied using the
new value, the constraint system is updated, otherwise the update is
rejected.

\subsection{Layer Activators}

Games frequently involve dynamic changes of the system's behavior depending on various conditions. Certain functionality can be restricted to a specific game mode, e.g. velocities are only rendered in debug mode.
%example
%- debugmode
%- editor or game mode
%- timer -> power up
As with trigger constraints, we want to specify the relation between the behavior adaption and the condition explicitly.
So, we introduce the concept of \emph{activator constraints}.
Using activator constraints one can specify that a certain adaption in behavior applies as long as a given condition holds.

%\paragraph{Explain cop + why cop for the job?}
Note, that activator constraints rely on an additional concept to
dynamically adapt behavior. The concept of
\acrlong{cop}~\cite{costanza:2005:language, hirschfeld:2008:cop}
provides such a mechanism.  \gls{cop} provides means to associate
partial behavior definitions with explicit context objects,
\emph{layers}.  Layers can be activated or deactivated during the
execution of a program, usually based on the control flow.  When a
layer is activated, the partial behavior definitions become part of
the respective objects and classes until the deactivation of the
layer.  \gls{cop} enables dynamic adaption and variation in behavior
based on the current context.  To illustrate this, consider the spring
power up described in \autoref{sec:application-description}. The
spring power up causes all bullets of the affected tank to bounce off
walls once more.  This functionality can easily be expressed using
layers as in \autoref{lst:design-coplayerexample}. Line 1 creates a
layer and associates a partial object definition to this layer. Lines
2 to 4 augment the method \texttt{getBulletRicochets} of the
\texttt{tank} object by incrementing the result of the original
function by one.  In addition to the definition of the layer and the
partial behavior, one has to activate the layer in order for the
adaption to take place.  A layer is typically de-/activated globally
or for the dynamic extent of a function invocation. Such mechanisms
only allow control flow-specific scoping. However, adaptions can also
depend on scopes other than control flow, such as conditions on the
current state of the program.
%However, contexts are often bound to certain conditions that hold.
%However, these acvivation methods are control flow-based ...
As with trigger constraints, we want to treat the condition associated
with a context explicitly. We imagine activator constraints to
activate a given layer as long as the associated constraint expression
is fulfilled, as illustrated by \autoref{fig:design_activate}. Once we
reach a state in which the constraint expression is fulfilled, the
layer is activated until the constraint expression evaluates to
false. Then, we deactivate the respective layer again.

\begin{figure}
\centering
\includegraphics[width=\linewidth]{ppt/design_activate.png}
\caption{System state trajectory augmented by an activator constraint}
\label{fig:design_activate}
\end{figure}

\begin{lstlisting}[label=lst:design-coplayerexample,caption={Constructing a \gls{cop} layer with partial behavior}]
var powerUpLayer = new Layer().refineObject(tank, {
  getBulletRicochets: function() {
    return cop.proceed() + 1;
  }
});
\end{lstlisting}

As continuation of the spring power up example, suppose the benefit of the power up is of limited duration. So, the power up is only active until its time is running out. We use a dedicated \texttt{Timer} class to keep track of time in our example. Using activator constraints we can connect an instance of this class with the previously defined \texttt{powerUpLayer}, as shown in \autoref{lst:design-activatorexample}. In line 2 we define the condition that the \texttt{remainingTime} attribute of the \texttt{timer} is greater than zero. Next, we connect this condition with the \texttt{powerUpLayer} and, thereby, create the desired relation in line 3.

\begin{lstlisting}[label=lst:design-activatorexample,caption={Activator constraint to activate a power up for a specific amount of time}]
predicate(function() {
  return timer.remainingTime > 0;
}).activate(powerUpLayer);
\end{lstlisting}

We use layers as units of dynamic behavior adaption because of the
following reasons:
\begin{itemize}
\item \gls{cop} treats context objects, layers, explicitly.  These
  context objects can easily be activated based on a condition. \item
  \gls{cop} is no special solution dedicated to JavaScript, but has
  been implemented in many other languages such as Lisp, Smalltalk,
  Python, Java, and Ruby. So, Babelsberg implementations in languages
  other than JavaScript can also base on the very concept of
  \gls{cop}.
%, not special-library solution
\item Aside partial object and class definitions \gls{cop} layer can
  act as units of scoping for constraints as well, as described in
  \autoref{sec:design-scopedconstraints}. Being able to use
  constraints to activate layers and layers to scope constraints
  provides additional synergy effects between both concepts.
\end{itemize}

\subsubsection*{Implementation}
In order to implement the above concept, we extend the existing
Babelsberg library. Babelsberg is built to use use multiple solvers,
and let them cooperate to solve constraints.  We can view the
condition to activate a layer as a constraint of the form
\[
  booleanExpression? = isActive(Layer)
\]
The questionmark means that the solver is not allowed to change the
condition, and thus must change the activation state of the layer when
the condition changes. Accordingly, we implement a
\texttt{ReactiveSolver}, which re-uses the Babelsberg framework for
interpreting the condition expression. Whenever a variable that
participates in the boolean expression changes, the framework asks our
solver to \verb!solve! the constraint.  To do so, our custom solver
checks whether the evaluation result of the condition coincides with
the layer activation status and if not, activates or deactivates the
layer as necessary (see \autoref{lst:implementation-activator}).

\section{Related Work}
\label{sec:related-work}

We discuss work related to our layer activation mechanism. To our
knowledge, there is no previous work related to our second
contribution, to allow \gls{cop} layers to add, modify, or suppress
constraints using layers. Neither do we know of related work that
combines \gls{cop} and \acrlong{cp}.

\emph{EventCJ}~\cite{kamina:2011:eventcj} separates the control of
layer activation and the execution of context-dependent behavior using
two language constructs, \emph{event declarations} and \emph{layer
  transition rules}. An event declaration specifies a named event,
when the event is triggered, and to which objects the event is sent. A
layer transition rule specifies the activation and deactivation of
layers in a declarative manner. EventCJ events rely on a subset of
AspectJ~\cite{kiczales:2001:aspectj} pointcuts. However, the pointcut
has to be specified explicitly. In contrast, our Layer Activators
allow to specify an arbitrary condition and, thereby, abstract from
concrete point of execution to activate the layer.  A benefit of
EventCJ is that it provides instance-specific layer activation, while
our work activates layers globally.

\emph{PyContext}~\cite{vonLoewis:2007:implicitactivation} introduces
implicit layer activation, to address the issue that, similar to our
observations, layers are often activated depending on a condition. If
this condition changes frequently, the condition and activation may be
scattered across the code. Each PyContext layer may define the
\texttt{active} method and, if this method evaluates to true, the
layer is active.  Whenever a layered method is called, PyContext first
determines which layers are active using those methods. In contrast,
our work determines the composition when the condition
changes. Depending on the frequency, one or the other implementation
may incur more overhead.

\emph{ServalCJ}~\cite{kamina:2015:servalcj} attempts to unify
different layer activation methods by introducing two concepts:
\emph{contexts} specify the duration of a layer activation and
\emph{subscribers} specify which computations are affected by the
layer activation.  The unified model allows to represent all
previously existing \gls{cop} activation mechanisms.


\section{Discussion and Conclusion}
\label{sec:conclusion}

We have presented a novel \gls{cop} layer activation mechanism related
to reactive and event-based layer activation techniques, and a novel
use of layers as a scoping and control mechanism for constraints in
\gls{ocp} languages. These mechanisms resulted from our experience in
creating an interactive game using both constraints and layers.

This work is practical, and open issues remain regarding semantics
that were not relevant for our use-case.

First, it is currently not clear what happens when two conflicting
Layer Activators refer to the same layer. The layer may active if one
or more of the activator constraints evaluate to true, or only if all
associated activator constraints evaluate to true. Alternatively, we
may detect a conflict when trying to define an Activator for a layer
that already has one. As a final option, we could ask the system to
solve for all Activator expressions to be equal, when multiple
expressions are defined.\footnote{The semantics of the first two
  issues are clear when using the layer activation semantics of
  ContextJ~\cite{appeltauer:2011:contextj}. In this implementation,
  multiple activations cause the behavioral variations to be applied
  multiple times.  This, activating a layer twice through manual
  activation or multiple Layer Activators simply applies the behavior
  adaption twice.}

Second, how do Layer Activators and control flow-based activations of
a layer interact? If a layer that is associated with an activator
constraint is activated manually, we may raise an error or just fail
silently if the activator expression is not true (the latter option
being the practical expression of an assumed artifically small time
between the imperative activation and the time when the Activator
deactivates the layer). Alternatively, we may propagate the layer
activation and prompt the framework to solve for the Activator
expression to be true.\footnotemark[\value{footnote}]

Third, consider a Layer Activator that is part of a Constraint Layer,
and both are active. What happens if the Constraint Layer is
deactivated, and thus the Layer Activator as well. We see two options:
1) disabling the Activator deactivates the layer regardless of the
current value of the Activator expression, or 2) disabling the
Activator leaves its layer active.

Despite these open questions, our practical implementation of these
mechanisms enabled us to construct a usable game. We were able to use
our mechanisms to make use of \gls{ocp} constraints and \gls{cop}
layers in a way which improved the clarity and conciseness of our
code, and believe that further work in this direction may benefit
other application domains.

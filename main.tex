\begin{abstract}
  We present an approach and extension to an object-oriented language
  to solve generic constraints on messages between objects. These
  constraints describe equalities and inequalities between the results
  of message that are continuously maintained by the system.

  Constraints are expressed as anonymous functions that contain
  constraint expressions. To maintain a constraint, our approach
  chooses a constraint solver based on the return types of the
  messages sent in the dynamic extent of the expression execution.
  Solvers can be flexibly bound to types such as reals or strings, but
  also complex objects such as files or methods. Furthermore,
  constraint solvers are implemented in application code, so
  programmers can add domain specific solvers for their use cases.

  Our system solves constraints by modifying objects that determine
  the results of messages sent during the constraint expression
  execution. Whenever imperative code changes these objects, the
  appropriate solvers are triggered to maintain the constraints.

  Our approach is superior to existing approaches because it relies on
  object-oriented message sends instead of paths between objects or
  special constraint method definitions. This property ensures both
  encapsulation and supports the uniform access principle. This, in
  turn, allows programmers to change the implementation of objects
  without breaking constraint code, as well as applying groups of
  constraints to different objects that implement the same
  interface. Since programmers can extend the available solvers, they
  can choose the solver that gives the best results or provides the
  best performance to their specific application.

  We argue that using our approach, constraint solving becomes a
  generic tool that is not limited to specific domains. Using a
  Ruby-based implementation, we show example applications that apply
  constraints to interesting new domains such as performance
  assurances and configuration file handling.
\end{abstract}

\section{Introduction}

  % % Context
  % Imperative object-oriented programming languages are ill-suited to
  % describe constraints between objects. They require programmers to
  % maintain the constraints explicitely through assignments and control
  % flow scattered throughout the code, rather than declare them in one
  % place. For some specific problem domains---such as graphical
  % layouting or musical harmonization ---specialized constraint
  % libraries provide solutions to this issue. For general purpose
  % applications, constraint-oriented extensions to imperative languages
  % have been explored.

  % % Problem
  % However, current approaches result in unsatisfactory trade-offs
  % between constraint-oriented and object-oriented programming. They
  % either violate object encapsulation by defining constraints only on
  % state, do not integrate constraint solving and the object-oriented
  % behavior definition into one language, and/or are limited to
  % specific domains. Consequently, current approaches increase coupling
  % in the system, duplicate definitions of relations across behavior as
  % well as constraint-expressions, and/or are not directly reuseable
  % for new domains.

  % % Solution
  % We present an extension to an object-oriented language that allows
  % developers to apply constraints to complex objects and the results
  % of message sends to them. Our approach preserves encapsulation and
  % re-uses the existing object-oriented method definitions for the
  % constraint declarations. Our system can deal with constraints on
  % complex objects (by automatically destructuring them) and provides
  % extension points so users can define specialized constraint solvers
  % for specific domains.

Constraints are a useful concept to specify program behavior in a
number of domains, such as graphical layouting, musical harmonization,
or game rules~\todo{cite}. Such constraints are equalities and
inequalities between objects, their parts, and the results of message
sends to them. A common example are constraints on the minimum
distance between visible elements in a layout that have to be
considered when resizing the interface~\todo{citeosx}.

Programmers that imperatively ensure constraints in their programs
often write assertions to fail early if these constraints are
unexpectedly not satisfied~\todo{cite}. However, using constraint
solvers it is often possible to correct the faulty program state
automatically and continue running~\todo{rinard}. Replacing assertions
with constraints, undesirable program states can be corrected by the
runtime.

Constraints are difficult to express in purely imperative
object-oriented programming languages~\todo{cite}. Programmers satisfy
constraints using tests, branching, and destructive
assignment. Although constraints can be expressed using constraint
libraries, programmers need to write code to explicitly copy
object-oriented state between to the constraint solver and back
whenever it changes, which is cumbersome and error
prone. Consequently, explicit language support is desirable to express
constraints in imperative object-oriented languages.

State of the art solutions to express constraints for specific domains
domains in imperative program exist in the form of \acp{dsl} (both
external~\todo{css,osx} and internal~\todo{bloom?}), constraint
libraries~\todo{backtalk}, language extensions~\todo{javadingens}, and
dedicated languages~\todo{kaleidoscope}. However, constraint solving
is not yet a general purpose tool, as we will show in
section~\ref{sec:background}.

We think that the state of the art approaches result in unsatisfactory
trade-offs between constraint-oriented and object-oriented
programming:
\begin{itemize}
\item They violate either object encapsulation or the uniform access
  principle by defining constraints only on state~\todo{cite} or only
  on special constraint behavior definitions~\todo{cite}. This leads
  to problems as programs grow and implementations of objects change,
  as the constraints have to be kept up-to-date regarding the internal
  state of the domain objects.
\item They use special types that tie objects to the domains of
  constraint solvers. This means that objects have to be mapped to
  those types either through transformations that have to be triggered
  whenever the program state changes or the objects have to be
  built entirely from those types.
\item They provide no mechanism for programmers to add solvers for
  both finite and infinite domains.
\end{itemize}

\section{Background}
\label{sec:background}
Consider a rectangle implemented as a pair of points as in
listing~\ref{fig:lst:rectangle}. This rectangle is displayed in an
application window which the user can resize. Suppose this rectangle
encompasses some information that we want to make sure remains
visible. We want to make sure the area of the rectangle is never less
than 100 square pixels and that its origin is always within display
bounds, i.e. positive.

\begin{figure}
  \centering
  \begin{lstlisting}
class Rectangle
  attr_accessor :origin, :extent

  def visible?
    origin.x > 0 and origin.y > 0
  end

  def area
    extent.x * extent.y
  end
end
  \end{lstlisting}
  \caption{A rectangle implemented as a pair of points, with a predicate to test it starts within display bounds and a method to calculate the area}
  \label{fig:lst:rectangle}
\end{figure}

Imperatively, we can use, for example, aspects to satisfy these
constraints explicitly whenever the rectangle changes:
\begin{lstlisting}
class RectAspect < Aspect
  def ensure_constraints(method, rect, status, *args)
    rect.origin.x = 0 if rect.origin.x < 0
    rect.origin.y = 0 if rect.origin.y < 0
    rect.extent.x = 100.0 / rect.extent.y if rect.area < 100
  end
end

RectAspect.new.wrap(Rectangle, :postAdvice, /(origin|extent)=/)
\end{lstlisting}

The above code has a number of problems:
\begin{itemize}
\item The original constraints are expressed in a form that makes them
  harder to understand
\item Advice code is required to capture all modifications that may
  invalidate the constraints - if the advice is insufficient or not
  triggered often enough, the constraints may be violated through
  parts of the execution
\item It is not trivial to tell whether the solution for the
  constraints is optimal. In the presence of competing constraints,
  this becomes even harder.
\end{itemize}

In this section, we will compare how state of the art approaches to
constraint programming in imperative programs solve our problem.  The
approaches are presented in four groups:
\begin{inparaenum}
\item constraint solver libraries that are used directly from
  imperative code,
\item constraint solver \acp{dsl} that exist for special domains,
\item \emph{DataFlow} and \ac{frp} languages, and
\item constraint-imperative programming that combines constraints and
  imperative statements in the one language
\end{inparaenum}.

\subsection{Constraint Solver Libaries}
When realizing they are dealing with a constraint problem, programmers
may choose to include a constraint solver library in their
program. (Examples of solvers with implementations or bindings in a
variety of languages are Cassowary~\todo{cite}, DeltaBlue~\todo{cite},
or \zcubed~\todo{cite}.)

The following code adapts the previous, purely imperative solution to
use the \zcubed constraint solver to solve our constraints:
\begin{lstlisting}
class RectAspect < Aspect
  def ensure_constraints(method, rect, status, *args)
    ctx = Z3::Context.new
    ctx << Z3::Variable.new("extent_x", rect.extent.x)
    ctx << Z3::Variable.new("extent_y", rect.extent.y)
    ctx << Z3::Constraint.new("extent_x * extent_y > 100")
    # ... same for origin constraint
    ctx.solve
    rect.extent.x = ctx["extent_x"]
    rect.extent.y = ctx["extent_y"]
  end
end
# boilerplate code as for purely imperative approach
\end{lstlisting}

Using a solver allows programmers to express constraints about the
system in terms of a ``primitive'' domain (i.e. reals, booleans,
uninterpreted function symbols) the solver understands. If the problem
is expressible in a domain for which a solver is available (as the
above code is) the constraints can be clearly written.

This approach, while clearly expressing the constraints, is not
satisfactory for two reasons:
\begin{itemize}
\item constraints are expressed on object state, which has to be
  copied between objects and the solver
\item advice code is still required to capture all modifications that
  may invalidate the constraints to trigger the solver
\end{itemize}

\subsection{Domain-specific Languages for Constraints}
For specialized domains such as user interface layouting, constraints
are available as separate \ac{dsl}s that describe relations between
visible objects that can be automatically maintained by the
runtime. Examples of such \acp{dsl} are \textsc{css}~\todo{cite}, the
\emph{Mac OS X}~\todo{cite} layout specification language, and the
Python GUI framework \emph{Enamel}~\todo{cite}. These allow
programmers to express relations such as distances between objects or
parent/child alignments. These constraints are automatically
re-satisfied by the runtime when imperative code changes the user
interface.

The following is an example of an \emph{Enamel} specification for our
problem:
\begin{lstlisting}[language=python]
enameldef Main(Window):
    Container:
        constraints = [
            # the rectangle area is called contents in enamel
            contents_top > 0, contents_left > 0,
            (contents_bottom - contents_top) *
              (contents_right - contents_left) > 100
        ]
\end{lstlisting}

This approach allows programmers to specify constraints and avoid
boilerplate code to trigger constraint solving. However, two different
problems arise:
\begin{itemize}
\item constraints can be expressed only on state which is exposed to
  the constraint \ac{dsl}
\item because the constraints are specified in separate languages,
  they are hard to reason about in imperative code and it becomes easy
  to accidentally write imperative code that will interfere with the
  layout engine
\item constraint \acp{dsl} such as these offer a predetermined set of
  constraints for only a few special domain objects, so this approach
  cannot be generalized
\end{itemize}

\subsection{DataFlow Constraints and FRP}
Some languages have built-in support for data flow, which allows
programmers to express unidirectional constraints between objects and
their parts. Examples of such systems are ThingLab~\todo{cite},
Scratch~\todo{cite}, the LivelyKernel/Webwerkstatt~\todo{cite}, or
KScript~\todo{cite}. (Of these, only ThingLab includes a planner for
propagation that breaks cycles automatically. In the other systems the
programmer has to break cycles explicitely.)

The following uses LivelyKernel connections to observe changes to
\texttt{origin} and \texttt{extent} in a Rectangle \texttt{rect}.  On
each change, the transformation function is executed with the current
and the previous value and returns the new value for the
field. Programmers can thus directly express relations between objects
and parts of objects.
\begin{lstlisting}[language=java]
connect(rect, "origin", rect, "origin",
        function(origin, prevOrigin) {
            if (this.isVisible()) return prevOrigin;
            else return origin;
        })
connect(rect, "extent", rect, "extent",
        function(extent, prevExtent) {
            if (this.area() < 100) return prevExtent;
            else return extent;
        })
\end{lstlisting}

Although these systems are not constraint solvers, programmers can use
constraint solvers in the function (and some systems, like
\emph{KScript} already integrate a constraint solver to use in the
connection). This solves the question when to trigger constraint
solving.

The problems with these approaches are:
\begin{itemize}
\item relations are uni-directional and binary, so \emph{m:n}
  relations cannot be expressed and have to be satisfied by some other
  mechanism
\item connections observe state changes and trigger further state
  changes. For the second constraint, it would be better if the
  connection could be between the (dynamic) result of the
  \texttt{area} method
\end{itemize}

\subsection{Constraint-Imperative Programming}
The \ac{cip}~\todo{kaleidoscope,turtle} and related
languages~\todo{SOUL} tried to address the aforementioned
issues. Their main goals were:
\begin{itemize}
\item Unify state for constraint solvers and imperative runtime
\item Automatically re-satisfy constraints when they are invalidated
\item Linguistic symbiosis between declarative and imperative
  statements
\item Provide additional abstractions to enable developers to express
  constraints on complex objects
\end{itemize}

Our problem as it could be expressed using Kaleidoscope:
\begin{lstlisting}
class Rectangle
  constructor area = (n: Integer)
    always: extent.x * extent.y = n
  end

  constructor visible?
    always: origin.x > 0
    always: origin.y > 0
  end
end

rect = Rectangle.new
always: rect.area = 100
always: rect.visible?
\end{lstlisting}

The above code states constraints clearly. The abstraction of what it
means for a rectangle to have an area of size $n$ and to be visible is
modularized in the Rectangle class using \emph{constraint
  constructors}. However, through these constructors a two problems
appear:
\begin{description}
\item[Behavior is duplicated] Developers have add \emph{constraint
    constructors} to their objects before they can be used in
  constraints. If they want to constrain the area and also access it in
  from imperative code, they have to duplicate code.
\item[Solvers are predetermined] Due to the deep integration \ac{cip}
  languages offer only a fixed set of solvers, and are thus only
  usable for certain domains.
\end{description}

We propose an integration of constraint-solvers with \ac{oo} languages
that we call \emph{\ac{ocp}}. \ac{ocp} keeps desirable properties from
other approaches and is, for the most part, a continuation of the
\ac{cip} work originally presented
in~\todo{cite}. Table~\ref{tab:cmp-constraint-lang-approaches} shows
these properties and compares \ac{ocp} to the approaches presented in
section~\ref{sec:background}.

As a continuation of \ac{cip}, \ac{ocp} shares some desirable
properties with the \ac{cip} languages \emph{Kaleidoscope}\todo{ref}
and \emph{Turtle}\todo{ref}:

\paragraph{Encapsulation}
Encapsulation in user code is preserved if appropriate constraint
constructors are used to abstract instance variable access.  In
\emph{type I} object-oriented languages such as Smalltalk or Ruby,
object state is always private and cannot (without meta-programming)
be modified from the outside. So to apply constraints in those
languages, constraint constructors are required decompose objects
appropriately. In \emph{type II} languages such as, for example, Java
or JavaScript outside access to state can be allowed, so these
languages can be used for \ac{cip} directly. However, even in those
languages direct access to object state is discouraged as it increases
coupling in the system, and constraint constructors should be used.

The \ac{vm}, on the other hand, can ignore encapsulation when it
solves constraints (similar to how a \ac{jit} compiler ignores
encapsulation when it inlines methods). We have found this idea to be
useful to allow solvers to directly modify objects, but also provide
hooks in \ac{ocp} so developers can require solvers to go through
accessors when applying new solutions.

\paragraph{An Object-Oriented Programming Style}
Programs appear as ordinary \ac{oo} programs if no constraints are
used, but can be easily adapted to use constraints where it makes
sense. If constraints are used, the programmer does not need to
manually trigger solvers. Furthermore, object-oriented techniques such
as inheritance and dynamic-typing work correctly with constraints.

\paragraph{A Declarative Semantics}
Kaleidoscope answers some important questions how imperative and
declarative code interacts on the same objects. The declarative
semantics for assignments to constrained variables in
Kaleidoscope---as a one-time equality constraint---appear intuitive
and have worked well in~\todo{cite} and for us. Object identity vs
equality constraints were discussed in~\todo{cite} and we also be
adopted them in \ac{ocp}.

The following properties of \ac{cip} languages need improvement:

\paragraph{Violation of the Uniform Access Principle}
Constraint constructors, or \emph{user-defined constraints}, allow
objects to decompose themselves into elements for which a constraint
solver is available. However, these constructors require multi-method
dispatch semantics. Also, normal methods can only be used as constants
in constraints, and constraint constructors cannot be called from
imperative code. This means that developers have to duplicate behavior
definitions if an interface is needed both in constraints and
imperative code (as the \emph{area} method is, above). This, in turn,
requires developers to anticipate whether certain behavior may be used
in constraints or imperative code by clients. If they do not
anticipate it, clients have to revert to accessing state directly if
possible. Table~\ref{tab:cmp-ocp-cip} shows how this limits the
applicability of \ac{cip} to languages with only private state. In
\ac{ocp}, constraints use the same behavior definitions as imperative
code, so the problem does not arise.

\paragraph{Limited Solver Domains}
\ac{cip} languages come with a fixed set of embedded solvers. In
Kaleidoscope and Turtle, for example, this precludes adding
constraints on strings or complex objects such as Files or Method
objects, because no appropriate solver is available. In \ac{ocp},
however, all solvers use the same interface to communicate with the
\ac{vm} so developers can add new solvers for their domain objects.

Three goals have guided us in creating this language:
\begin{enumerate}
\item[Unchanged \ac{oo} semantics] We have not changed the execution
  semantics of the underlying \ac{oo} language. The integration of
  constraint-oriented programming consists solely of an additional
  primitive. The \ac{oo} runtime has an \emph{object view} on its data
  that consists only of objects with state and behavior.
\item[Constraints specified using \ac{oo} interface] A constraint
  declaration in our system is an expression passed to a primitive
  method unevaluated in form of a anonymous function closure. That
  closure is executed immediately in the \emph{constraint
    interpreter}. The constraint interpreter executes the code as
  normal \ac{oo} code, but, during execution, constructs a
  \emph{constraint view} for the solvers.

  To construct the constraint view, variables encountered during the
  execution are replaced by the interpreter with their solver variable
  counterparts. If no solver is active in the system that can work
  with the variable encountered, that variable is replaced with a
  placeholder constraint variable that delegates to the original
  object, but serves as a placeholder for constraint invalidation.

  The constraint view is complete when the anonymous function
  returns. The constraint view then consists of a number of a)
  primitive values that are in the domain of the solver and are
  connected in a constrainable way (e.g. through in/equalities,
  arithmetic, boolean logic) and b) a number of complex objects that
  are constrained to their identity.

  The solver operates on this view directly to solve the
  constraint. Changes made by the solver to the variables show up in
  the \ac{oo} view.

  When imperative code changes a primitive value in that appears in
  this view (for example through assignment~\todo{cite kaleidoscope}),
  that change triggers the solver to re-satisfy the constraint.

  When imperative code changes a complex value that is constrained to
  its identity, all constraints asserted based on this value are
  removed from the solver, and the constraint expression is
  automatically re-evaluated to assert new constraints ... here we
  need the example with the arch point
\end{enumerate}

\section{Implementation}
- pypy is ..., topaz is ..., topaz architecture

modes:
  - normal execution
    LOAD\_* -> check if constrainted variable -> get value from solver
    STORE\_* -> check if constrainted variable
               a) is associated with a solver: suggest\_value
               b) was on the path during constraint construction:
                  - get constraint block for this variable
                  - disable all constraints that got created during
                    execution of the constraint block
                  - re-execution constraint block to build new constraints
  - constraint construction
    LOAD\_* -> create constraint variable for the storage cell
              a) new constraint variable associated with solver
                 -> continue working with that (all sends go to the solver variable)
              b) new constraint variable is not assiciated (only on the path)
                 -> store currently executing constraint block on constraint variable
                 -> work with the value as in normal execution
    JUMP\_AND -> enable left-hand side (if a constraint)
             -> continue working on rhs
    ... (could add more, JUMP\_IF, JUMP\_OR ...)
  - constraint execution
    ... special mode we execute the solver/suggest\_value in (in case it is
    written in Ruby, this musn't enter any of the other modes)

- thoughts on implementation:
  - normal execution changes should be aspects that come with the language extension
    (role is basically to observe variable access)
  - constraint construction/execution should be a COP layer

  - Constraints module exposes ObjSpace interface
  - ConstraintObject is marker superclass to ``seal'' solver implementations
  - ConstraintVariable is attached to (locals, ivars, cvars)
    - triggers the specific ``solve'' on STORE and ``set!'' on LOAD

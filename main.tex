\begin{abstract}
  \acrlong{cop} extends object-oriented languages with a mechanism to
  dynamically adapt behavior. \acrlong{ocp} orthogonally extends
  object-oriented run-times by integrating constraints, including
  support for constraints over mutable state, object identity, and the
  results of message sends. Using these two language extensions in
  conjunctions offers interesting opportunities.

  In this paper, we report on new mechanisms involving layers and
  constraints that evolved from our experiences with combining
  Babelsberg/JS, an Object-Constraint Language, and ContextJS, an
  implementation of \acrlong{cop} in JavaScript. First, our experience
  shows that it is desirable to dynamically adapt declarative
  constraints, which offer an orthogonal mechanism to the definition
  of imperative behavior, likewise at runtime. In this work, we show
  an extension to ContextJS to scope activation or refinement of
  constraints dynamically using layers.  Second, ContextJS already
  provides different activation mechanisms for layers, including
  dynamically or structurally scoped, or globally through system
  generated events. Constraints provide an activation mechanism based
  on arbitrary boolean expressions changing their value, allowing for
  interesting applications of behavioral adaption based on certain
  conditions.
\end{abstract}

\section{Introduction}

Many mechanisms exist that extend the toolbox of the object-oriented
programmer with features such as pattern matching\cite{}, functional
cores\cite{}, multi-dimensional dispatch\cite{}, and more. Among those
mechanisms are \gls{cop}\cite{}, which add dynamic adaption of
behavior based on layers, and \gls{ocp}\cite{}, which adds constraints
over mutable objects and on the results of message sends. Using these
two language extensions in conjunctions offers interesting
opportunities to address shortcomings in each language, and thus make
both extensions useful for a wider variety of problems. In this paper,
we present two such extensions, which we call \emph{Layer Activators}
and \emph{Constraint Layers}.

\paragraph{Layer Activators}
\label{sec:constr-based-adapt}
\gls{cop} layers adapt behavior at runtime when they are
activated. There are many activating strategies in \gls{cop}
languages, including dynamically scoped\cite{} or scoped to object
structure\cite{} and event-based\cite{} or reactive
activation\cite{}. While first two mechanisms offer explicit control
over the activation time of layers, the latter two are particularly
interesting for our discussion, because of their declarative
nature.

Event-based activation uses system-generated events to activate or
deactivate a layer during the event loop. Reactive activation is based
on similar principles as Aspect-oriented Programming: whenever a
message is sent that matches a \emph{pointcut}, an associated
condition is evaluated. If that condition evaluates to true, a layer
is activated for the duration of the method activation.  

A limiting factor of both mechanisms is their granularity. Event-based
activation relies on the creating appropriate events that indicate a
change in the system state to activate layers. In JavaScript, for
example, common system generated events indicate user input or network
activity. However, it is not possible to tell the system to generate
an event whenever an arbitrary condition changes. Similarly, reactive
activation focuses on message sends. The conditions for layer
activation are only checked at join-points, and thus the burden is on
the programmer to ensure that their pointcuts match all message sends
that may be relevant.

With Babelsberg, any constraint expression can be continuously
monitored, thus, we argue, providing a flexible constraint activation
mechanism. In essence, any boolean expression in the source language
can be associated with the activation state of a layer, and the system
ensures that they are equal. We call these kinds of constraints
\emph{Activators}.

\paragraph{Constraint Layers}
\label{sec:constraint-layers}
\gls{ocp} languages are motivated by the observation that some issues
in software development lend themselves to a declarative
specification, while others are more directly expressed using
imperative constructs. The goal is to provide both paradigms in a
cleanly integrated fashion within an object-oriented language in a way
that supports messages, encapsulation, inheritance, mutable objects,
and object identity in constraints. In \gls{ocp}, constraints can be
defined, activated, and retracted at runtime. A meta-level protocol
exists using which constraints can be activated and retracted at
arbitrary points during the execution. In addition, various \gls{ocp}
systems offer explicit scoping mechanisms for constraints.

Babelsberg \cite{FelgentreffJOT14} is a design for \gls{ocp}
languages, and this work is based on its JavaScript implementation,
Babelsberg/JS \cite{FelgentreffECOOP14}. Babelsberg defines three
types of scopes for constraints: \emph{always}, which defines and
activates a constraint for the entire rest of the execution;
\emph{once}, which activates a constraint, solves it, and then
immediately retracts it; and \emph{assert--during}, which activates a
constraint for the duration of a code block.

An issue with these scoping mechanisms is that they effectively allow
the activation of constraints with global effects at any point in
time. It is not possible to add restrictions on when constraints can
be activated, making reasoning about a program difficult. Because
constraints are, by their nature, multi-directional, any method may
add a constraint involving its arguments and thus calling any method
may affect the objects created by its caller.

To alleviate this problem and provide control over when constraints
are active, we use \gls{cop} to provide a convenient scoping mechanism
to add, remove, or suppress constraints using layers. We call such
layers that adapt declarative constraints in addition to behavior
\emph{Constraint Layers}.

\subsection{Constraint Declaration and Solving in Babelsberg}
\label{sec:implementation-babelsberg-ccm}
Babelsberg/JS extends and integrates both semantically and
syntactically with JavaScript. Constraints are ordinary JavaScript
expressions that are introduced using the keywords \verb!always! or
\verb!once!, the constraint being that the expression evaluates to
true. A translation mechanism executes constraint expressions while
keeping track of the dependencies between encountered variables and
fields. Babelsberg abstracts from the details of the underlying
solvers and can translate constraints in different ways to hand to
different solvers. 

As long as a constraint is active, the system keeps track of the
objects that relate to it and, if the constraint becomes invalidated
through modifications to those objects, triggers the solver to find a
solution that satisfies them. If no solution can be found, the
modification that invalidated the constraints is rejected and an
exception is generated. Constraints in Babelsberg/JS are thus useful
to encapsulate \emph{system maintained assumptions}, and ensure that
these assumptions cannot be quietly invalidated.

As a simple example, suppose we want to specify that the \texttt{y}
coordinate of a point object \texttt{pt} is twice as big as its
\texttt{x} coordinate:
\begin{lstlisting}[label=lst:implementation-cassowaryexample,caption={},]
always: { solver: new ClSimplexSolver()
          pt.x * 2 == pt.y }
\end{lstlisting}

Line 1 specifies that we want to use the Cassowary solver to satisfy
this constraint. Line 2 is the boolean expression that will be
converted by the framework to be solved. Although this code is valid
JavaScript, if executed directly, no constraints will be
created. Babelsberg/JS uses a source-to-source transformation to
convert the above constraint expression into the following JavaScript:
\begin{lstlisting}[label=lst:implementation-cassowaryexamplesourcetransformed,caption={},]
bbb.always({
  solver: new ClSimplexSolver() 
  ctx: {
    pt: pt
  }
}, function() {
  return pt.x * 2 == pt.y
});
\end{lstlisting}

Besides allowing for a more convenient syntax, the source code
transformation creates a context object that contains all variables
that are directly referenced by the function. The framework requires
this context object in order to interpret and transform the constraint
expression.

When calling Babelsberg's \texttt{always} method, the given function
is delegated to a JavaScript interpreter alongside contextual
information.  Thereby, the normal execution by the interpreter is
adapted using a layer, the \texttt{ConstraintConstructionLayer},
provided by the Babelsberg library.  In order to intercept accesses
and assignments to relevant variables later during execution the
constraint construction mode wraps properties with property
accessors. For example, to get the value of a variable, the accessors
returns the appropriate value from a constraint solver.  However,
during constraint construction Babelsberg does not use these
accessors, but returns a \texttt{ConstrainedVariable} object
instead. To get a specialized \texttt{ConstrainedVariable} for a
concrete solver, its \texttt{constrainedVariableFor} method is
invoked. The solver returns a \texttt{ConstrainedVariable} if the
interpreter tries to access a value of a type supported by the
specific solver. For instance, when accessing the \texttt{x}
coordinate of the point object, Cassowary returns a
\texttt{ConstrainedVariable} as a stand-in for the \texttt{Number}
value.  Now, messages are sent to this object instead of calculating
values.  Each \texttt{ConstrainedVariable} has a set of supported
methods. These methods are used to create primitive constraint objects
that can be satisfied using the solver. As a consequence, the
interpreted constraint expression returns a specific constraint object
that supports the \texttt{enable} and \texttt{disable} methods.  When
a constraint was successfully created, this constraint is immediately
enabled and, in turn, solved.

Besides constructing and solving a constraint once, another important
feature of the always statement is the automatic maintenance of the
desired relation.  To do so, Babelsberg installed property accessors
during the interpretation of the constraint expression.  When a new
value is assigned to a property wrapped with a property accessor, the
\texttt{suggestValue} method of the corresponding
\texttt{ConstrainedVariable} object is called.  To solve the
assignment Babelsberg creates a temporary equality constraint between
the variable and its new value. However, this change could affect the
whole constraint system. So, Babelsberg finds all constraints with the
modified variable. Babelsberg repeats this process for all variables
of all constraints found in the previous step, and so on. This process
stops once the convex hull of the assignment is found.  In order to
solve the constraints, Babelsberg sorts all participating solvers
according to their weight.  Then, the solver with the highest weight
solves all of its constraints using its specialized solving algorithm.
Babelsberg continues to solve the constraint system with the next
solver. However, all variables referenced by previous solvers are
marked as read-only. As a consequence, a solver cannot modify
variables assigned by previous solvers. This process continues for all
remaining solvers. As a result, the constraint system is satisfied and
the regular program execution can proceed with the next statement.

\paragraph{\emph{Limitations of the current implementation.}}
Babelsberg/JS is an implementation of the \gls{ocp} paradigm provided
as a library without any VM support. Such an implementation has
several requirements on the host
language~\cite{Felgentreff:2014:babelsbergjs}. One of those
requirements is that the host language must support means to intercept
variable lookup. Babelsberg/JS uses property accessors to meet this
requirement. However, this technique only supports object fields, and
cannot intercept local variables. Additionally, some fields of
built-in types, such as the \texttt{length} attribute of
\texttt{Arrays}, do not support property accessors.  Another
requirement is that the host language must provide means to modify the
interpretation of a block.  As described in this section,
Babelsberg/JS uses a augmented JavaScript interpreter for constraint
construction.  Yet, this interpreter cannot access any variable scoped
in a closure.  As a consequence, Babelsberg/JS cannot instrument any
method refined by ContextJS, because ContextJS employs scoped
variables. In addition, current state of the art browser-based
JavaScript modules, asynchronous module definitions, cannot be
instrumented if the module definition uses locally scoped variables.

\subsection{Activators}

Games frequently involve dynamic changes of the system's behavior depending on various conditions. Certain functionality can be restricted to a specific game mode, e.g. velocities are only rendered in debug mode.
%example
%- debugmode
%- editor or game mode
%- timer -> power up
As with trigger constraints, we want to specify the relation between the behavior adaption and the condition explicitly.
So, we introduce the concept of \emph{activator constraints}.
Using activator constraints one can specify that a certain adaption in behavior applies as long as a given condition holds.

%\paragraph{Explain cop + why cop for the job?}
Note, that activator constraints rely on an additional concept to dynamically adapt behavior. The concept of \acrlong{cop}~\cite{costanza:2005:language, hirschfeld:2008:cop} provides such a mechanism.
\gls{cop} provides means to associate partial behavior definitions with explicit context objects, \emph{layers}.
Layers can be activated or deactivated during the execution of a program, usually based on the control flow.
When a layer is activated, the partial behavior definitions become part of the respective objects and classes until the deactivation of the layer.
\gls{cop} enables dynamic adaption and variation in behavior based on the current context.
To illustrate this, consider the spring power up described in \autoref{sec:application-description}. The spring power up causes all bullets of the affected tank to bounce off walls once more.
This functionality can easily be expressed using layers as in \autoref{lst:design-coplayerexample}. Line 1 creates a layer and associates a partial object definition to this layer. Lines 2 to 4 augment the method \texttt{getBulletRicochets} of the \texttt{tank} object by incrementing the result of the original function by one.
In addition to the definition of the layer and the partial behavior, one has to activate the layer in order for the adaption to take place.
A layer is typically de-/activated globally or for the dynamic extent of a function invocation. Such mechanisms only allow control flow-specific scoping. However, adaptions can also depend on scopes other than control flow, such as conditions on the current state of the program.
%However, contexts are often bound to certain conditions that hold.
%However, these acvivation methods are control flow-based ...
As with trigger constraints, we want to treat the condition associated with a context explicitly. We imagine activator constraints to activate a given layer as long as the associated constraint expression is fulfilled, as illustrated by \autoref{fig:design_activate}. Once we reach a state in which the constraint expression is fulfilled, the layer is activated until the constraint expression evaluates to false. Then, we deactivate the respective layer again.

\begin{figure}
\centering
\includegraphics[width=.45\linewidth]{ppt/design_activate.png}
\caption{System state trajectory augmented by an activator constraint}
\label{fig:design_activate}
\end{figure}

\begin{lstlisting}[label=lst:design-coplayerexample,caption={Constructing a \gls{cop} layer with partial behavior}]
var powerUpLayer = new Layer().refineObject(tank, {
  getBulletRicochets: function() {
    return cop.proceed() + 1;
  }
});
\end{lstlisting}

As continuation of the spring power up example, suppose the benefit of the power up is of limited duration. So, the power up is only active until its time is running out. We use a dedicated \texttt{Timer} class to keep track of time in our example. Using activator constraints we can connect an instance of this class with the previously defined \texttt{powerUpLayer}, as shown in \autoref{lst:design-activatorexample}. In line 2 we define the condition that the \texttt{remainingTime} attribute of the \texttt{timer} is greater than zero. Next, we connect this condition with the \texttt{powerUpLayer} and, thereby, create the desired relation in line 3.

\begin{lstlisting}[label=lst:design-activatorexample,caption={Activator constraint to activate a power up for a specific amount of time}]
predicate(function() {
  return timer.remainingTime > 0;
}).activate(powerUpLayer);
\end{lstlisting}

We use layers as units of dynamic behavior adaption because of the
following reasons:
\begin{itemize}
\item \gls{cop} treats context objects, layers, explicitly.  These
  context objects can easily be activated based on a condition. \item
  \gls{cop} is no special solution dedicated to JavaScript, but has
  been implemented in many other languages such as Lisp, Smalltalk,
  Python, Java, and Ruby. So, Babelsberg implementations in languages
  other than JavaScript can also base on the very concept of
  \gls{cop}.
%, not special-library solution
\item Aside partial object and class definitions \gls{cop} layer can
  act as units of scoping for constraints as well, as described in
  \autoref{sec:design-scopedconstraints}. Being able to use
  constraints to activate layers and layers to scope constraints
  provides additional synergy effects between both concepts.
\end{itemize}

\subsubsection*{Implementation}
In order to implement the above concept, we extend the existing
Babelsberg library. Babelsberg is built to use use multiple solvers,
and let them cooperate to solve constraints.  We can view the
condition to activate a layer as a constraint of the form
\[
  booleanExpression? = isActive(Layer)
\]
The questionmark means that the solver is not allowed to change the
condition, and thus must change the activation state of the layer when
the condition changes. Accordingly, we implement a
\texttt{ReactiveSolver}, which re-uses the Babelsberg framework for
interpreting the condition expression. Whenever a variable that
participates in the boolean expression changes, the framework asks our
solver to \verb!solve! the constraint.  To do so, our custom solver
checks whether the evaluation result of the condition coincides with
the layer activation status and if not, activates or deactivates the
layer as necessary (see \autoref{lst:implementation-activator}).

\item[2) ] The manual layer activation fails silently.
\item[3) ] The activator constraint is modelled as an always constraint. The manual activation causes Babelsberg to solve the constraint expression of the activator constraint.

For the third issue, suppose an activator constraint refers to a layer. The constraint expression of the activator constraint evaluates to true and, therefore, the layer is active. What should happen when the activator constraint is now disabled?
\begin{itemize}
\item[1) ] Disabling an activator constraint deactivates the layer.
\item[2) ] Disabling the activator constraint has no effect on the layer. The layer holds its current state and stays active even if the constraint expression of the activator constraint becomes false, because the activator is disabled.

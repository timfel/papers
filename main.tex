\begin{abstract}
  % Context
  Imperative object-oriented programming languages are ill-suited to
  describe constraints between objects. They require programmers to
  maintain the constraints explicitely through assignments and control
  flow scattered throughout the code, rather than declare them in one
  place. For some specific problem domains---such as graphical
  layouting or musical harmonization ---specialized constraint
  libraries provide solutions to this issue. For general purpose
  applications, constraint-oriented extensions to imperative languages
  have been explored.

  % Problem
  However, current approaches result in unsatisfactory trade-offs
  between constraint-oriented and object-oriented programming. They
  either violate object encapsulation by defining constraints only on
  state, do not integrate constraint solving and the object-oriented
  behavior definition into one language, and/or are limited to
  specific domains. Consequently, current approaches increase coupling
  in the system, duplicate definitions of relations across behavior as
  well as constraint-expressions, and/or are not directly reuseable
  for new domains.

  % Solution
  We present an extension to an object-oriented language that allows
  developers to apply constraints to complex objects and the results
  of message sends to them. Our approach preserves encapsulation and
  re-uses the existing object-oriented method definitions for the
  constraint declarations. Our system can deal with constraints on
  complex objects (by automatically destructuring them) and provides
  extension points so users can define specialized constraint solvers
  for specific domains.
  % Constraints are re-useable on objects that respond to the same messages.
  % Constraints appear in various domains (esp. modeling real-world behaviour?)
  % object-oriented languages are widespread for implementation of many of these domains
  % they have no good support for constraints
  %    constraint extensions to imperative languages tried to address this problem
  %    they either:
  %        - violate/ignore encapsulation by using path specifiers
  %        - only support constraints within one objects' primitive state
  %        - require a different kind of method definition
  %    we provide seamless application to constraints on objects and the results of
  %    their methods, our constraint system uses the message sending mechanism of
  %    the OO paradigm and cannot look inside objects
\end{abstract}

\section{Introduction}

In a number of domains, such as graphical layouting, musical
harmonization, or product lines, acceptable program behavior is
partially specified in terms of constraints~\todo{cite}. (Specifically
in domains that have an acceptability envelope\todo{cite} or need to
optimize values based on competing inputs, constraint solving is a
natural fit.)  Such constraints may be invariants or (in-)equalities,
for example minimum and maximum distances between visible elements in
a layout that have to be considered when resizing~\todo{citeosx}, or
correspondence between the contents of a file, the display, and a
programmatic value.

Constraints are difficult to express in purely imperative
object-oriented programming languages~\todo{cite}. Programmers satisfy
declarative constraints using tests, branching, and destructive
assignment. In the case of temporal constraints, constraint checking
is a cross-cutting concern and programmers have to structure control
flow so the constraints can be re-checked whenever they may have been
invalidated~\todo{cite}.  There are two problems with this approach:
\begin{enumerate}
\item Explicitely solving constraint satisfaction problems using
  imperative code may not find an optimal solution or may not find a
  solution even if one exists.
\item Aspects can only capture one dimension of this cross-cutting
  concern. Constraints cross-cut both across control flow and data
  structures. Aspects can capture control flow cross-cutting and
  preserve encapsulation, but support code for constraint satisfaction
  code still has to be scattered across all classes that participate
  in constraints. If encapsulation is ignored to modularize constraint
  satisfaction, tight coupling is introduced between the constraint
  satisfaction module and the rest of the system.
\end{enumerate}

Programmers solve the first problem by using constraint
solvers~\todo{cite}. A solver suited to the domain of the problem.

Explicit use of constraint libraries only solves
the optimization part, but still requires aspects/observers/scattered
code to trigger solving and copy values between the solver and the OO
program

Using constraint extensions for specialized domains alleviates this
problem for these domains ... e.g. cassowary solver for osx
layouting. the constraints are automatically maintained, as long as
imperative code does not interfere with the layout engine. However,
the interaction between the layout engine and the imperative code is
hard to reason about, as they are in separate source code files and
operate on different objects/levels of abstractions ...

Finally, the family of constraint-imperative languages tried to
address these issues. Problems with these approaches are specific to
the trade-offs of each approach. Some break encapsulation, because
constraints can only be applied to the primitive leaves of explicitely
stated object paths. Others require developers to add
constraint-method definitions to their objects before they can be used
in constraints, duplicating behaviour definitions for another
paradigm.

\section{Background}

In the following section, we will explore the related approaches to
constraint solving in imperative languages in more detail.

\subsection{Constraint Solver Libaries}
Simplex-based (Cassowary), Propagation (DeltaBlue, SkyBlue), SMT (Z3)
\begin{itemize}
\item[advantages]
  \begin{itemize}
  \item solve problems over ``primitive'' domains
  \item fast for specialized problems (but sometimes very slow in the worst case)
  \item some have constraint hierarchies
  \item bidirectional by default
  \item easy to changing solvers in application code or per object type
  \end{itemize}
\item[problems]
  \begin{itemize}
  \item no general solver over multiple domains that is also fast
  \item trigger code is scattered through program
  \item no language integration (different variables)
  \end{itemize}
\end{itemize}

\subsubsection{DataFlow}
ThingLab, Scratch, LivelyKernel
\begin{itemize}
\item[advantages]
  \begin{itemize}
  \item can naturally work on results of object-oriented message sends
  \item automatically watch for value changes in objects
  \end{itemize}
\item[problems]
  \begin{itemize}
  \item uni-directional, have to break cycles explicitely
  \item explicit relations instead of constraints leave no
    ``wiggle-room'' => no dealing with conflicting requirements
  \end{itemize}
\end{itemize}

\subsection{Constraint-Imperative Programming}

by default, so CIP has to either modify the language or constraints
can only be private to an object. This means either constraints on
complex objects explicitely specify the path (Turtle, ... increases
coupling), or need ``constraint methods'' ...

Type 2 languages (Java, JavaScript) allow outside access to state, but
that increases coupling, so constraints on behaviour are also
desirable here... see above ...

\section{Contribution: Object-Constraint Programming}
- integration of solver with OO language

- OO semantics unchanged
  - OO world has a view on the data that consists of objects
    with state and behaviour
  - primitive to register reaction to state changes was added

- constraints specified using OO interface
  - a constraint is a closure passed to a primitive method
  - that primitive is gateway to the constraint world
  - the primitive activates the constraint interpreter for the closure
  - constraint interpreter is (conceptually) a COP layer on the interpreter
    that records additional information to construct the constraint view

- constraint interpreter constructs ``constraint view'' during closure evaluation
  - the constraint view is the Set of primitive values that partake in a
    constraint in a constrainable way (in/equalities, arithmetic, boolean logic)
  - Solver sees the constraint view on the data, that consists of primitive
    types in the object-graph
    - the solver/constraint view is consistent subset of OO state data
    - changes in the OO object graph/state update the solver/constraint view
  - solver operates on its view of state directly
  - change shows up in the OO object state

    5. assignments show up in OO view
       (and assignments possibly trigger constraint solver)

\section{Implementation}
- pypy is ..., topaz is ..., topaz architecture
- extensions:
  constraint interpreter
    - ``COP like'', activated for constraint frames
    - changes LOAD\_* instructions (locals, ivars, cvars)
    - ``layer'' is deactivated for objects of type Constraint
      - this way, solver can again be implemented in OO language itself,
        otherwise it would see (and potentially modify) it's own state
  objspace primitive to register solvers
    - triggered on state change (STORE\_*) and state read (LOAD\_*)
      - TODO: maybe register should just work both ways?
        e.g.: STORE -> solve(stored\_variable, previous\_value, new\_value)
              LOAD  -> readout(loaded\_variable, current\_value)
  - Constraints module exposes ObjSpace interface
  - ConstraintObject is marker superclass to ``seal'' solver implementations
  - ConstraintVariable is attached to (locals, ivars, cvars)
    - triggers the specific ``solve'' on STORE and ``set!'' on LOAD

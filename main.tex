\begin{abstract}
% \AEBadge{}
  Systems that integrate constraint solving with general purpose
  programming languages must strike a balance between exposing the
  full power of solvers and how aware the programmer needs to be of
  the solving process in order to write understandable and correct
  programs.  To integrate with imperative languages, this balancing
  act extends to how freely programmers can express constraints versus
  how aware they need to be of the transition between the imperative
  and declarative parts of the program in order to understand its
  limits.

  Babelsberg is a design to integrate constraints with a standard
  object-oriented language. Experience with Babelsberg, as well as
  with earlier constraint imperative languages, revealed the potential
  for complex interactions between the object-oriented core and
  constraints, in particular powerful constraints involving object
  identity, multiple types, or change over time.  Programmers needed
  to be aware of these complications to make effective use of
  constraints, and sometimes refactor the constraint expressions or
  the structure of objects in response. Otherwise, the system might
  come up with surprising solutions, or none at all.
  
  In this paper we present design principles that tame the power of
  the constraint solver and of the translation between imperative and
  declarative expressions, avoiding difficult corner cases and
  surprising solutions while retaining the key features and
  capabilities of the approach. We provide an informal description of
  the resulting language, and a formal semantics for a useful subset
  of it, with the full semantics given in a companion technical
  report. We validate the utility of this semantics with an executable
  version that allows us to run test programs in it and to verify that
  they provide the same results as our actual implementation in
  Babelsberg/JS.

  \textbf{Keywords:} Constraints, Object Constraint Programming,
  Constraint Imperative Programming, Executable Semantics Test Suites
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Babelsberg \cite{FelgentreffJOT14} is a family of object constraint
languages, with current instances being Babelsberg/R (a Ruby
extension) \cite{felgentreff+:2014:babelsberg}, Babelsberg/JS (a
\javascript extension) \cite{FelgentreffECOOP14}, and Babelsberg/S (a
Squeak extension) \cite{GraberREBLS2014}. The Babelsberg design
integrates constraint satisfaction with ordinary object-oriented
constructs such as inheritance and polymorphism, and inherits many
traits from the earlier Kaleidoscope \cite{lopez1994kaleidoscope} and
Turtle \cite{grabmuller2004turtle} constraint-imperative programming
languages.  It is motivated by the observation that a number of key
aspects of interactive applications can be elegantly and concisely
specified using constraints, but that other aspects are more easily
specified using standard imperative constructs (assignment, loops, and
so forth).  Its goal is to provide both paradigms in a cleanly
integrated fashion, within an object-oriented framework that respects
standard object-oriented features such as messages, encapsulation, and
inheritance. However, experience with Babelsberg has shown that
interactions between the object-oriented core and constraints can be
difficult to understand --- it is easy to formulate constraints that
allow the system to come up with surprising solutions, but also to
write constraints that produce no solutions at all, because they would
need to be formulated differently for the translation from imperative
code to constraints to work as intended.

In this paper we formalize restrictions on the solver and rules for
the translation from methods to constraints that help programmers
understand how constraints in Babelsberg will work and what the
properties of the solutions will be, as well as providing guidance to
language implementors. Our restrictions make the solving
process more deterministic, offer guidance how to express valid
constraints, and thus give enough freedom to express many interesting
problems. The main contributions are:
\begin{itemize}
\item A non-standard form of structural type-checking paired with soft
  constraints to restrict the power of the solver and to define how
  constraints interact with object identity and structure.
\item A formalization of prior work on object constraint programming
  to integrate objects, methods, classes, and constraints in a way
  that is backwards compatible with the existing object-oriented
  paradigm. Of particular interest here is the way we explode
  constraints involving methods and how we restrict side effects in
  constraint expressions.
\item An executable version of our semantics to automatically verify a
  suite of example programs that illustrate the problems we address.
\item A framework to generate language test suites from our suite of
  example programs, so Babelsberg implementations can be tested for
  conformance to this semantics.
\item An adapted version of the Babelsberg/JS implementation that
  passes the generated test suite, and our experiences which existing
  Babelsberg/JS applications no longer run with the our semantics.
\end{itemize}

The rest of this paper is structured as follows:
\autoref{sec:example-programs} presents example programs in
Babelsberg, both ones that illustrate the expressiveness that comes from
integrating support for object-oriented programming with constraints,
and also ones that exhibit the kind of surprising behavior that we
address in this work.  \autoref{sec:informal-solution} gives an

rules. \autoref{sec:semantics} presents the semantics for a small

semantics. \autoref{sec:related-work} gives an overview of related
work, and \autoref{sec:conclusions} concludes.

\section{Example Programs}
\label{sec:example-programs}

Example programs written in one or more of the Babelsberg implementations
include a graphical application for building and simulating electrical
circuits, a GUI for a color picker, interactive games, programs to
solve logic puzzles, and simple mobile applications on a smart phone.
These programs illustrate the division of labor and interplay between
the imperative object-oriented portions of the code and the constraint
parts, as well as the different kinds of constraints and solvers that
can be employed.  The electrical circuit editor and simulator
\cite{FelgentreffECOOP14}, for example, uses constraints and an
appropriate solver to capture the relevant laws of physics such as
Ohm's Law and Kirchhoff's Current Laws and to solve the resulting sets
of simultaneous linear equations, and imperative constructs to support
actions such as making new resistor, battery, and meter instances, and
placing and connecting them.  The logic puzzle applications
\cite{GraberREBLS2014} --- for Sudoku, cryptarithmetic, Pentominoes,
and Star Battle --- use a different class of constraints and solver,
namely constraints over finite domains and a SAT solver, but similarly
have a division of labor into a constraint part for the constraints
that define the Sudoku rules and an imperative part to control the
interaction.  The color picker \cite{FelgentreffECOOP14} illustrates
hard and soft constraints, as well as support for fast incremental
re-solving of the constraints during interactive editing.  Finally,
the mobile application illustrates the use of identity constraints
(constraints that two variables refer to the same identical object) to
connect the UI and the underlying model.

As a smaller example, suppose that we may want to express the
requirement that a window in a graphical application stay centered on
a particular point.  We will use Babelsberg/JS for the code (\ie
\javascript syntax).  Babelsberg/JS provides the keyword label
\verb!always:! to declare constraints on the return values of ordinary
object-oriented expressions that then hold for the rest of the
execution.  The constraint can then be defined as:
\begin{lstlisting}[language=JavaScript,caption={Constraining a window to be centered on a point},label=lst:window]
var window = new Window(0,0,100,100);
always: { window.getCenter().equalsPoint(Point(150,150)) }
\end{lstlisting}

After running this code, the system will ensure that the window is
centered on the point $(150,150)$. If it is resized or dragged by the
title bar, the system will either adjust other parts of the window to
keep the center at the desired position, or, if that is not possible,
prevent the interaction. It does not matter if \verb!getCenter!
is just an accessor or a calculated property. Babelsberg traces into
the method and creates the correct relations between the actual parts
of the window and the point.

Next, as an example to illustrate some of the kinds of surprising
behavior that can arise when integrating constraints with an object
oriented language, consider a bank account application in which we
want to prevent changes that would make the account balance drop below
a certain threshold. Additionally, we want to track the current
interest the account produces, but not allow it to rise above 1000.
(This example is simple enough that we can show the listing easily,
but is designed to illustrate some complexities around object
identity, as well as constraint features such as soft constraints and
read-only annotations on variables.)
\begin{lstlisting}[language=JavaScript,caption={Ensuring domain requirements on a bank account},label=lst:account]
var acc = new Account(), minBalance = 100, curInterest = 0;
always: { acc.balance >= minBalance? }
always: { priority: "medium"
          curInterest == acc.balance? * 0.01 }
always: { curInterest <= 1000 }
\end{lstlisting}

\begin{sloppypar}
Here, the solver will ensure the property \verb!balance! remains
larger than \verb!minBalance! after line 2. The read-only annotation
on \verb!minBalance! (indicated by the question mark)
prevents the solver from changing it
to satisfy the constraint. Thus, any change to the account that
would drop the result of \verb!balance! below
\verb!minBalance! is rejected by the system. Conversely, the
system is not allowed to change the result of \verb!balance! to
satisfy the second constraint. The current interest is always
determined from the current balance, but not vice-versa. Note also
that we assign a priority to the second constraint. This tells the
system that is should satisfy this relation if possible, but it is no
error not to do so. Due to the third constraint, if the interest were
to rise above 1000, the system can leave the second constraint
unsatisfied.
\end{sloppypar}

Experience with Babelsberg has shown that their design requires
programmers to consider the solving process as well as the
implementation of the framework to use constraints effectively; even
the small examples above contain the potential for surprising
solutions. Programmers have to be careful to express constraints in a
manner so that the solver will find the desired solution. To
understand what kind of solutions are available to the solver,
programmers additionally have to consider how the framework translates
constraints and how they are passed to the solver.

\subsection{Weeding Out Unintuitive Solutions}
\label{sec:find-desir-solut}

% \ab{commented out the part about problems that are too hard for one
%   solver and cooperating solvers, since that seems orthogonal to the
%   issues here}
%% It is easy to formulate a problem that is too hard for any one solver,
%% and it is easy to specify a problem that allows the solver to find
%% undesired solutions. To mitigate the first problem, Babelsberg/JS
%% implements a design for cooperating constraint solvers
%% \cite{FelgentreffECOOP14}. To address the second problem, we propose
%% to restrict the solvers to favor solutions that are less surprising
%% for imperative programmers.

We sometimes discovered that Babelsberg would find an unintuitive
solution that the human programmer didn't even consider, and which was
not a desired one.  To help address this, in this work we define a set
of restrictions on the language to rule out a significant number of
such solutions.  For example, in \autoref{lst:account}, we intuitively
expect the solver to reason about the balance of the newly created
\verb!Account! object. However, there are other valid solutions:
\begin{inparaenum}
\item[first,] the solver might change the variable \verb!acc! to point
  to another object that has the right balance.
\item[Second,] the solver may correct the balance, but also add or remove
  fields from the account that are not relevant to the constraint.
\item[Third,] even if the initial balance was already higher than
  \verb!minBalance!, the solver may still choose to make it equal
  to \verb!minBalance!, as this also satisfies the constraint.
\end{inparaenum}

All three solutions are clearly undesired: imperative programmers do
not expect the identity of the \verb!acc! variable to change or
the solver to change the object structure. Neither do they expect the
property to change, if the constraint is already satisfied.

To address this problem, we restrict the power of the solver so it
finds the expected solution in cases such as these.\footnote{The
  formulation of the first two restrictions is new in this work; the
  third has been present in Babelsberg since the original language
  definition, as well as in the earlier Kaleidoscope design.}
\begin{inparaenum}
\item[First,] we separate constraints involving object identity from
  those involving only values, and solve those independently, so that
  a solution that changes the identity of \verb!acc! is not valid.
\item[Second,] we use structural type-checking to ensure the solver
  cannot add or remove fields from objects.
\item[Third,] we implicitly add a low priority ``stay'' constraint to
  each variable, so that its value only changes if required to do so
  by some higher-priority constraint.
\end{inparaenum}

% The Kaleidoscope language, particularly the early versions, was
% arguably too complex in part because it was too powerful in ways that
% were interesting, but not useful in practice. This made it difficult
% to understand what the result of a program might be and also difficult
% to implement efficiently. A heuristic for the present work is that
% when there is a choice, we favor simplicity over power.

\subsection{Clear Rules for Writing Valid Constraints}
The second issue is that the programmer needs to be aware of some
restrictions on how objects can be used in constraints. Kaleidoscope
and Turtle distinguish imperative and declarative behavior definitions
that are used depending on whether an object is used in an imperative
or a declarative context. This means that programmers have to consider
both interfaces of an object, depending on what they want to
express. Babelsberg unifies the behavior definition and allows the
programmer to express constraints directly using imperative
methods. However, this creates a different set of problems, as not all
methods work equally well in constraints. Consider the
\verb!getCenter! method from \autoref{lst:window}. Because it is
dynamically bound, in general a programmer will 
not know its implementation when
writing the constraint. The method may simply return a field, but it
may also calculate the center from other fields on the object. If the
latter, the method may also cache that calculation for faster
retrieval. Regardless, the programmer expects the system to adjust
whatever parts of the window contribute to the result of
\verb!getCenter! so that the center stays at $(150,150)$. If the
system fails to satisfy this constraint, it is not clear to the
programmer which of the operations -- the check for cache
invalidation, storing the result, or the calculation itself -- does
not work as part of the constraint.

Earlier work on Babelsberg enumerated a set of informal rules for when an
expression could be used to define a constraint. However, there were
some confusing edge cases involving object identity and constraints,
and regarding when methods called from a constraint expression could
be used multi-directionally.

In the work reported here, we have developed and formalized a
simple-to-understand set of restrictions on the expressions that
define constraints, and when they can be used multi-directionally.
\begin{inparaenum}
\item[First,] if the method consists solely of a single return
  statement (for example, an expression that is a calculation on the
  object's fields) it can work multi-directionally.
\item[Second,] if a method has any statements before returning, it can
  only be used in the forward direction.
\item[Third,] if the method has any side effects, such as writing to a
  non-local location or generating a random number, it cannot be used
  in a constraint in any direction.
\end{inparaenum}

\section{Solution Overview}
\label{sec:informal-solution}

A goal of this work is to clarify design decisions of Babelsberg to
guide language users and implementers.  However, it is not intended to
be a complete description of a practical object constraint language,
and we omit aspects of the language that are inherited from the host
language, such as class and method definitions, exception handling, or
\textsc{IO}.

A guiding principle in our design has been to adhere to the original
goal of Babelsberg that, in the absence of constraints, it should be a
standard object-oriented language. This work focuses on how standard
object-oriented constructs need to be modified to support the
Babelsberg design. Where there is a choice, we aim to make the
smallest possible changes while still accommodating constraints in a
clean and powerful way. Beyond this, we favor simplicity of the rules
over the power to support interesting, but in practice rarely used
features.

This section consists of two parts: the first presents how we restrict
the power of the solver to be deterministic with regards to objects'
identities and structure. The second part presents how we restrict the
translation from object-oriented methods to constraints to avoid
corner-cases and give simple rules for programmers to follow when they
express constraints.

\subsection{Restricting the Solver}
\label{sec:restricting-solver}

At the core of our design is the idea that the solver determines the
entire heap and environment after each statement. However, for an
imperative programmer it would be surprising if variables change more
than they have to or if objects loose or gain fields or unnecessarily
change their types -- the solver should always pick a solution that is
close to the current state of the system.

\subsubsection{Object Structure}
\label{sec:object-structure}

In \autoref{lst:account} we have seen a constraint on a
field. However, in the absence of other constraints, nothing is
preventing the solver from adding or removing unrelated fields to the
object. Consider setting the \verb!acc! variable to an empty
object and asserting the constraint. Should the solver invent a
balance field and constrain it?

To tame the power of the solver so that it does not (for example)
invent new fields for objects, we add
\emph{structural compatibility checks} that are dynamically
asserted before sending the constraints involving objects to the
solver. They ensure, for example, that field accesses occur only on
objects (and not primitive values), and that those objects have the
necessary fields. These assertions, unlike constraints, are only
checked --- if one is violated it is an error and the constraint
solving fails. The programmer must ensure that objects used in
constraints have all the required fields.

\subsubsection{Object Identity}
\label{sec:determ-object-ident}

A central issue in the design of an object constraint language is the
interaction between constraints and object identity.  Object identity
plays an essential role when using an object-oriented language to
model aspects of the real world and so, in a language that integrates
constraints with object-oriented features, we need to resolve the
tensions between these fundamental features \cite{lopez-ecoop-1994}.
Additionally, making explicit identity constraints available to the
programmer allows for useful capabilities such as specifying two
variables refer to the same identical object, or describing circular
structures.  However, experience with Kaleidoscope in particular
suggests that allowing powerful constraints on object identity and
types can lead to non-obvious consequences. As an example, consider
the following program:

\begin{lstlisting}[language=JavaScript,caption={Constraining two variables to be identical},label=lst:identity]
var account1 = {credit: 10}, account2 = {debit: 100};
always: { account1 === account2 }
always: { account1.debit >= 0 }
\end{lstlisting}

This adds a constraint on line 2 that \verb!account1! and
\verb!account2! be identical. However, it is not clear if
\verb!account1! and \verb!account2! will afterwards refer to an
account with debit balance or an account with credit balance. If the
latter, the constraint on line 3 will not pass our structural
compatibility checks. The choice of identity in one place would thus
determine the validity of the second constraint. This makes programs
more difficult for the programmer to understand.

To tame the power of constraints on object identity and type, we set
the following goals for this aspect of our design:
\begin{enumerate}[a)]
\item Constraints on object identity must be declared explicitly using
  the host languages identity check method (\verb!===! in the case of
  \javascript). They cannot be hidden within a method.
\item\label{item:deterministic} The solution to the constraints is
  deterministic as far as object identity and type are concerned ---
  there should never be multiple correct solutions in which a given
  variable refers to objects with different identities in the
  different solutions. Thus, the programmer must first ensure the
  identity constraint is already satisfied, before asserting it.
\item Any change to the identities of the objects referred to by
  variables can only flow from an assignment statement --- the
  constraint solver must not be allowed to otherwise alter object
  identities.
\item To make Babelsberg programs more understandable for the
  programmer, we want to reason about identities in value
  constraints. We thus first solve all the identity constraints (with
  a deterministic solution, in keeping with goal
  \ref{item:deterministic}), and then the value constraints. In the
  second step, identities are fixed, and thus method lookup follows
  ordinary object-oriented semantics. This requires all identity
  constraints to be declared separately from value constraints. We
  disallow non-required identity constraints, to avoid having to
  backtrack when solving value constraints (or otherwise
  non-deterministically failing).
\end{enumerate}

To preview the results of our rules, the program in
\autoref{lst:identity} would then be illegal, since the identity
constraint \verb|account1 === account2| isn't satisfied at the time it
is asserted. If the programmer uses an assignment to first make both
\verb|account1| and \verb|account2| refer to the debit account, the
program succeeds; if the programmer makes them refer to the credit
account, it halts with a structural compatibility check error; in
either case it becomes deterministic and straightforward to reason
about.

\subsubsection{Stay Constraints}
\label{sec:stay-constraints}

As in Kaleidoscope, Babelsberg adds an implicit weak stay constraint
to each variable to keep it at its current value, if possible. This
satisfies the desire that the solver should not change a variable, if
no constraint on it is violated.

\subsection{Rules for Constraint Expressions}
\label{sec:rules-constr-expr}

In Babelsberg, constraints are ordinary expressions in the host
language that evaluate to a boolean --- the constraint being that they
evaluate to true.  In our semantics, we have rules to translate these
expressions into constraints.  Our translation process traces through
methods and effectively unrolls loops, prunes branches, and inlines
method bodies.

%% WAS: ordinary imperative expressions - removed the word imperative
%% since they are side-effect-free and ``imperative'' seems confusing
%% in that context

In prior work, the restrictions on constraint expressions, and
the rules to translate expressions into constraints, evolved alongside
the existing implementations, driven in part by practical
considerations about the expectations of programmers familiar with the
underlying host language. These rules were originally defined as:
\begin{inparaenum}[1)]
\item\label{item:ssa} if there are assignments, variables assigned to
  must be used in \textsc{SSA} form,
\item the constraint expression should either be free of side effects,
  or if there are side effects, they should be benign, and
\item repeatedly evaluating the constraint expression should return
  the same thing, so a method that returns the current system time
  would not qualify.
\end{inparaenum}
In practice, it was not clear which constructs follow these rules, or
what constitutes ``benign'' side effects in a particular language. The
implementations also vary slightly in their wording of the rules and
rule \ref{item:ssa} in particular was omitted for Babelsberg/JS.

In the work reported here, we provide a clear and straightforward set
of restrictions on constraint expressions, which also makes them
amenable to use in proofs.  These restrictions are stronger than the
earlier versions.  They do allow us to express a wide range of useful
programs, but we suspect we can do better, and a direction for future
work (\autoref{sec:conclusions}) is to relax some of them while still
retaining clarity and precision.

\subsubsection{One-Way and Multi-Way Constraints}
\label{sec:transl-multi-way}

We propose a rule that, for simplicity, methods that contain more than
a return statement can only be used in the forward direction. This
includes methods with multiple assignments, which removes the first
older rule that variables assigned to in constraints must be used in
\textsc{SSA} form. Such methods can still be called in the usual way,
including passing any parameters by value with pointer semantics. For
example, suppose we have a constraint \verb|always c=x.m(a,b)|, and
method \verb|m| has multiple statements so that it can only be used in
the forward direction, \ie we can find a value for \verb|c| given
values for \verb|x|, \verb|a|, and \verb|b| but not any other
direction.  In that case, \verb|m| can be called in the usual way,
passing \verb|a| and \verb|b| by value with pointer semantics.  If the
other constraints are such that the correct solution involves finding
a value for \verb|b| given values for \verb|c|, \verb|x|, and
\verb|a|, the implementation should halt with an error that the
constraints are too hard for it to solve, due to a method called from
the constraint that can't be inlined (or in the formal semantics, we
get stuck). Note that in contrast to examples of constraints that are
too hard for the \emph{solver}, the fact that these constraints are
too hard is a limitation of our \emph{transformation} rule.

If method \verb|m| contains only a return statement, it can be used
multi-directionally so that for example we can find a value for
\verb|b| given values for \verb|x|, \verb|a|, and \verb|c|. In our
semantics the method is inlined so that the resulting constraints can
be turned over to the solver, and we can potentially solve for any of
\verb|x|, \verb|a|, \verb|b|, or \verb|c|.  This done by creating an
environment for method \verb|m| and inlining the returned expression
with respect to that environment. The parameters in that environment
are constrained to be identical to \verb|a| and \verb|b| respectively,
and \verb|self| is constrained to be identical to \verb|x|.

\subsubsection{No Side Effects in Constraints}
\label{sec:no-side-effects}

Our rules prevent the programmer from asserting constraints that have
non-benign side effects. We define ``non-benign'' here as side effects
that change the value of existing variables that are visible after the
constraint expression returns (rather than just creating new temporary
variables), the creation of new objects where identity and equality
are not the same (because these could be discerned by identity in
languages that allow reflection on the heap), or system calls other
than ones that return a constant value
(for example calls to a random number generator or the clock).

A particularly thorny issue pertained to creating new objects in
constraint expressions.  As noted in the above paragraph, this is
problematic when the identity of the newly created object could be
significant; yet we found numerous useful examples that involved
creating simple objects such as points and rectangles in constraint
expressions.  To resolve this issue, we add the concept of \emph{value
  classes} to Babelsberg.  Instances of these classes are immutable
after creation, and object identity is not significant for them.  An
example of a value class is the \verb!Point! constructor used in
\autoref{lst:window}.  However, value classes are more than simple
records, since they support methods and inheritance.  A number of
existing languages have proposals to support forms of value classes,
such as Java\footnote{\url{http://openjdk.java.net/jeps/169}} and
Scala\footnote{\url{http://docs.scala-lang.org/sips/completed/value-classes.html}}.

For practical implementations where the host language does not support
value classes, we can allow the creation of instances of ordinary
classes, and assume developers follow conventions about object
creation, modification, and not testing for object identity.

\section{Formalism}
\label{sec:semantics}

For our semantics we use a simple language, Babelsberg/UID, that
includes primitive types (reals, booleans, and strings), as well as
mutable objects that live on the heap and immutable objects on the
stack. 
Its semantic rules are mostly standard imperative rules,
with the addition of rules to assert and maintain constraints. The
semantics for this language, although not object-oriented, illustrates
all our important contributions. Extending it to include all the
essential features of the actual object constraint languages such as
support for classes, methods, messages, and inheritance, along with
constraint definitions that can include method calls is
straightforward, and is presented in the companion technical report
\cite{felgentreff:2014:semantics}.

In addition to a normal imperative language, after every statement
execution the current set of constraints is solved and the environment
and heap are updated from the solution.  The current set of
constraints is determined as follows: If the statement is an
assignment, we evaluate the right hand side and then set up a
constraint that the resulting value and the left hand side be
identical. Otherwise the statement is simply executed. In addition to
any constraint resulting from an assignment statement, each constraint
in the current set of constraints is given to the solver.  If the
solver finds a solution, the environment and heap are replaced by the
model the solver found; but if the constraints have no solution, or if
they are too hard for the solver, the execution implicitly gets
stuck. In the practical languages, a runtime exception will be
generated and the heap and environment remain unchanged.

The semantics treats the solver as a black box, but we assume it
supports our primitive types, records, uninterpreted functions, as
well as hard and soft constraints \cite{borning1992constraint} and
read-only variables. The solver should find a single best solution ---
if there are multiple solutions, the solver is free to pick any one of
them. % Providing answers rather than solutions, \ie results such as
% $10 \leq x \leq 20$ rather than a single value for $x$, and
% backtracking among multiple answers, as available in for example
% constraint logic programming \cite{jaffar-popl-1987}, is left for
% future work.

\subsection{Syntax}

\vskip\baselineskip\noindent We use the following syntax for
Babelsberg/UID: \vskip0.5\baselineskip\noindent
\begin{tt}
\begin{tabular}{lrrl}
{\rm Statement} & s & ::= & skip $\mid$ L := e $\mid$ L := new o $\mid$ always C $\mid$ once C \\
  & & &  $\mid$ s;s $\mid$ if e then s else s $\mid$ while e do s \\
{\rm Constraint} & C & ::= & $\rho$ e $\mid$ C $\wedge$ C\\
{\rm Expression} & e & ::= & v $\mid$ L $\mid$ e $\oplus$ e
$\mid$ e $\olessthan$ e $\mid$ e $\ovee$ e $\mid$ I\\
  & & & $\mid$ o $\mid$ D\\
{\rm Identity} & I & ::= & L == L\\
{\rm Object Literal} & o & ::= &  \{l$_1$:e$_1$,$\ldots$,l$_n$:e$_n$\} \\
{\rm L-Value} & L & ::= & x $\mid$ L.l \\
{\rm Constant} & c & ::= & true $\mid$ false $\mid$ nil $\mid$ {\rm base type constants}\\
{\rm Variable} & x & ::= & {\rm variable names} \\
{\rm Label} & l & ::= & {\rm record label names} \\
{\rm Reference} & r & ::= & {\rm references to heap records} \\
{\rm Dereference} & D & ::= & \H(e) \\\\

{\rm Value} & v & ::= & c $\mid$ r $\mid$ \{l$_1$:v$_1$,$\ldots$,l$_n$:v$_n$\} \\
\end{tabular}
\end{tt}\vskip0.5\baselineskip

Metavariable {\tt c} ranges over the {\tt nil} value, booleans, and
primitive type constants. A finite set of arithmetic operators on
expressions is ranged over by $\oplus$, $\olessthan$ ranges over a set
of {\em predicate} operators, and $\ovee$ ranges over logical
operators for combining boolean expressions. $\olessthan$ includes at
least an equality operator {\tt =} for each primitive type, and
$\ovee$ includes at least conjunction {\tt $\wedge$}. The operator
{\tt ==} tests for identity -- for primitive values and immutable
objects this is the same
as {\tt =}. The symbol $\rho$ ranges over constraint {\em priorities}
and is assumed to include a bottom element {\em weak} and a top
element {\em required}. The syntax requires the priority to be
explicit; for simplicity we sometimes omit it in the rules and assume
a {\em required} priority.

In the syntax, we treat \H as a keyword used for dereferencing.
Source programs will not use expressions of the form \texttt{\H(e)},
but they are introduced as part of constraints given to the solver,
which we assume will treat \H as an uninterpreted function.

\subsection{Operational Semantics}

The semantics includes an environment \E and a heap \H. The former is
a function that maps variable names to values, while the latter is a
function that maps mutable references to ``objects''. When convenient,
we also treat both \E and \H as a set of pairs ({\tt \{(x,v),...\}}
and {\tt \{(r,o),...\}}, respectively). The currently active value
constraints are kept as a compound constraint \C; identity constraints
are kept as a compound constraint referred to as \I.

\judgment{\evalH{\E}{\H}{e}{v}}

``Expression {\tt e} evaluates to value {\tt v} in the context of
environment \E~and heap \H.''

The rules for evaluation are mostly as expected in an imperative
language. We do not give rules for expressions of the form {\tt
  \H(e)}, because they are not meant to appear in source. For each
operator {\tt op} in the language we assume the existence of a
corresponding semantic function denoted
$\llbracket {\tt op} \rrbracket$.

  1 $\leq$ $i$ $\leq$ $n$
}{

}

\judgment{\tcH{\E}{\H}{e}{T}}
\judgment{\tcHC{\E}{\H}{C}}

``Expression {\tt e} has type {\tt T} in the context of environment
{\tt \E} and heap \H.''

``Constraint {\tt C} is well formed in the context of environment
{\tt \E} and heap \H.''

We use a notion of typechecking to prevent undesirable non-determinism
in constraints.  Specifically, we want constraint solving to preserve
the structure of the values of variables, changing only the underlying
primitive data as part of a solution, in support of the goals listed
in \autoref{sec:object-structure}.  We formalize our notion of
structure through a simple syntax of types:
\vskip0.5\baselineskip\noindent\begin{tt}
\begin{tabular}{lrrl}
{\rm Type} & T & ::= & PrimitiveType $\mid$ \{l$_1$:T$_1$,$\ldots$,l$_n$:T$_n$\}
\end{tabular}
\end{tt}
\vskip0.5\baselineskip

The typechecking rules are mostly standard. We check expressions
dynamically just before constraint solving, so we typecheck in the
context of a runtime environment. As with the evaluation rules,
expressions of the form {\tt \H(e)} do not typecheck. Note that we do
not include type rules for identities. This ensures that constraints
involving them do not typecheck, so identity checks cannot occur in
ordinary constraints.

\judgment{\solveH{\E}{\H}{C}}

% ``Environment \E and \H represent a solution to constraint {\tt C}''

This judgment represents a call to the constraint solver, which we
treat as a black box.  The proposition \mbox{\solveH{\E}{\H}{\C}}
denotes that environment \E~and heap \H~are an \emph{optimal solution}
to the constraint {\tt C}, according to the solver's semantics.

\judgment{\stay{\E}{C}}
\judgment{\stay{\H}{C}}
\judgment{\istay{e}{C}}
\judgment{\istay{\E}{C}}
\judgment{\istay{\H}{C}}

% ``{\tt C} is a conjunction of weak stay constraints on the variables in \E''

% ``{\tt C} is a conjunction of weak stay constraints on the objects in \H''

% ``{\tt C} is a stay constraint for expression {\tt e}''

% ``{\tt C} is a conjunction of weak stays on primitive values and
% required stays on references in \E''

% ``{\tt C} is a conjunction of weak stays on primitive fields and
% required stays on reference fields on the objects in \H''

As in Kaleidoscope, the semantics ensure that each variable has a
 stay constraint to keep it at its current value, if
possible. To ensure that the solver cannot invent new fields on
objects, we create required stays on the heap that assert the
structure of the objects. The first two stay rules assert only weak
stays on all variables. The \istay{\E}{C} and \istay{\H}{C} rules use
the \istay{e}{C} rule to create weak stays on primitive values, 
but they create required stays for
references as well as for the structure of objects. 
These latter rules are used when solving value
constraints, and ensure that value constraints cannot affect object
identities and structures.

To properly account for the heap in the constraint solver, we employ
an uninterpreted function {\tt \H} that maps references to objects
(i.e., records).  The rules below employ this function in order to
define stay constraints for references.

    \istay{x$_{r0}$==v$_0$}{C$_{r0}$} $\cdots$ \istay{x$_{rn}$==v$_n$}{C$_{rn}$}}
}{\mbox{
  \istay{\H}{C$_0$ $\wedge$
    {\tt required \H(r)==\{l$_0$:x$_{r0}$,$\ldots$,l$_n$:x$_{rn}$\}} $\wedge$

    $\ldots$ $\wedge$
    C$_{rn}$ }

\judgment{\combine{\E}{\H}{C}{C$'$}}
\judgment{\combine{\E}{\H}{I}{C$'$}}

We use these judgments to translate a constraint into a
constraint suitable for the solver. Specifically, each occurrence of
an expression of the form
{\tt L.l}, where {\tt L}
refers to a heap reference {\tt r}, is translated  into {\tt \H(L).l}
(recursively, as required). We do not give rules, because they are
straightforward. The full Babelsberg/Objects language includes a
similar judgment that also inlines method calls, given in its
entirety in a companion technical report.

\judgment{\stepH{\E}{\H}{\C}{\I}{s}{\E$'$}{\H$'$}{\C$'$}{\I$'$}}

``Execution starting from configuration {\tt <\E|\H|\C|\I|s>} ends in
the state {\tt <E$'$|\H$'$|C$'$|\I$'$>}.''

A ``configuration'' defining the state of an execution includes a
concrete context, represented by the environment and heap, a symbolic
context, represented by the constraint and identity constraint stores,
and a statement to be executed. The environment, heap, and statement
are standard, while the constraint stores are not part of the state of
a computation in most languages.  Intuitively, the environment and
heap come
from constraint solving during the evaluation of the immediately
preceding statement, and the constraint records the \verb|always|
constraints that have been declared so far during execution. Note that
our execution implicitly gets stuck if the solver cannot produce a
model. 

The first two rules below describe the semantics of assignments.  We
employ a two-phase process.  First the identity constraints are solved
in the context of the new assignment.  This phase propagates the
effect of the assignment through the identities, potentially changing
the structures of objects as well as the relationships among objects
 in the environment and heap.  
In the second phase, the value constraints
are typechecked against the new environment and heap resulting from
the first phase.  If they are well typed, then we proceed to solve
them.  This phase can change the values of primitives but will not
modify the structure of any object.

Implicitly these rules get stuck if either a) the identity constraints
cannot be solved, b) the value constraints do not typecheck, 
or c) the value constraints cannot be solved. A
practical implementation would add explicit exceptions for these cases
that the programmer could handle.

  \mbox{

    \stay{\E}{C$_{E_s}$} \andalso
    \stay{\H}{C$_{H_s}$}}\\
  \mbox{
 \andalso
    \combine{\E}{\H}{\I\,$\wedge$\,L==v}{C$_I$} \andalso
    \solveH{\E$'$}{\H$'$}{(C$_I$ $\wedge$ C$_{E_s}$ $\wedge$ C$_{H_s}$)}}\\
  \mbox{
    \istay{\E$'$}{C$_{{E'}_s}$} \andalso
    \istay{\H$'$}{C$_{{H'}_s}$}} \\
  \mbox{
    \combine{\E}{\H}{\C\,$\wedge$\,L==v}{C$_C$} \andalso
    \tcHC{\E$'$}{\H$'$}{C$_C$} \andalso

\subsection{Properties}

Here we state two key theorems about our formalism.  The proofs for
these theorems can be found in our companion technical report.  The
first theorem formalizes the idea that any solution to a value
constraint preserves the structures of the objects on the
environment and heap:

\begin{theorem} (Structure Preservation)
 If \stepH{\E}{\H}{\C}{\I}{(once|always)
   C$_0$}{\E$'$}{\H$'$}{\C$'$}{\I$'$}, then 
  % $dom(\E) = dom(\E')$\\
  % $\wedge dom(\H) = dom(\H')$\\
  $\forall {\tt x}\in dom(\E):$ \tcH{\E}{\H}{x}{T} $\Rightarrow$
  \tcH{\E$'$}{\H$'$}{x}{T}. 
\end{theorem}

The second theorem formalizes the idea that all solutions to an
assignment will produce structurally equivalent environments and heaps:

\begin{theorem} (Structural Determinism)
  If
  \stepH{\E}{\H}{\C}{\I}{L := e}{\E$_1$}{\H$_1$}{\C$_1$}{\I$_1$} and
  \stepH{\E}{\H}{\C}{\I}{L := e}{\E$_2$}{\H$_2$}{\C$_2$}{\I$_2$},
  then
  % $dom(\E) = dom(\E')$\\
  % $\wedge dom(\H) = dom(\H')$\\
  $\forall {\tt x}\in dom(\E_1):$ \tcH{\E$_1$}{\H$_1$}{x}{T} $\Rightarrow$
  \tcH{\E$_2$}{\H$_2$}{x}{T}.
\end{theorem}

\section{Evaluation}
\label{sec:evaluation}

Our aim in developing a formal semantics for Babelsberg has been
primarily a practical one, including clarifying the desired behavior
of the language, providing a guide for language implementors, and
proving useful language properties that then can be relied on by
programmers.  One piece of evidence of success is that we have in fact
clarified the desired behavior of the language, and as discussed in
the introduction, in response have adapted the existing Babelsberg/JS
implementation to conform to it.

Beyond that, we offer two forms of evaluation.  First, we have
implemented our natural semantics in \rml \cite{pettersson1994rml},
yielding an executable semantics.  We then evaluated a set of test
programs in this executable semantics, using the Z3 solver \cite{de2008z3}
to provide heap and environment updates. As an extension to
that, we provide a translation from the test programs in the
executable semantics to a \javascript test suite. We have adapted the
\javascript implementation of Babelsberg and show that the practical
implementation and semantics produce the same results for most of the
tests, except those that test features of value classes which we do
not emulate in \javascript.

As a second form of evaluation, we have adapted the currently existing
suite of example programs for Babelsberg/JS to the revised
language. We demonstrate that nearly all of the programs continue to
work without modification, or work with minimal adjustments.  (These
adjustments are described below.)  Those programs that do not work
anymore stopped doing so because they use constructs we explicitly
decided to disallow.

\subsection*{An Executable Semantics}
\label{sec:an-exec-semant}

\rml is a programming language to generate executables from natural
language specifications. It provides \emph{relations} as basic
building blocks for the semantics and translates these to C\@. It was
possible to implement our semantics exactly in \rml.  As the semantics
does not model the solving process, we have added a translation from
our constraint syntax to Z3, which solves the
constraints and generates a model of the new heap and
environment. Because our semantics requires on soft constraints, we
use an experimental version of Z3 that supports them
\cite{bjornernuz}.

Z3 types expressions. Our structural typing rules, however, allow
variables to change their type. Consequently, we declare variables in
Z3 with a union type \verb!Value!, and define the operation,
comparison, and combination functions on that union type. \verb!Value!
variables have a real, boolean, reference, and value class
component. The latter is encoded as a Z3 array that maps \emph{labels}
to reals. Labels and references are declared as finite domain types
that range over the existing references and record labels
respectively.

In a companion technical report \cite{felgentreff:2014:semantics}, 
we provide 45 example programs that
illustrate various concerns of the semantics (including the examples
given in this paper). Of those 45 programs, 3 use constraints on
strings, which are not supported in the version of Z3 we used. The
remaining 42 all run and produce the expected results at each step of
the execution.

As an extension to the \rml implementation, we add a module to
transform the example code into test cases for the various
implementations of Babelsberg. This may provide an avenue for future
development of Babelsberg --- as the semantics evolve, test cases for
the existing implementations can be generated and the implementations
adapted to pass the generated tests. To generate the tests, we use the
executable semantics to execute our examples, translate the syntax
into the syntax of the target language using a simple mapping provided
for each language, and use a test scaffold (also specific to each
language) to embed the examples and execute them in each
implementation.

All of the existing implementations must be adapted to pass the tests,
because all deviate from our proposed semantics in one way or
another. We have modified the \javascript implementation, as it is the
most advanced. After modification, of the 42 test cases that work in
the \rml semantics, 39 produce the expected results. The remaining
three all specifically test properties of value classes in
constraints. Since \javascript does not support value classes (and we
do not emulate them in some way in the scaffolding code) these 3 tests
fail, in one case producing no result when there is a solution, and
the other two producing a solution when solving should fail. We have
also tested, but not adapted, the Ruby and Squeak
implementations. Both Babelsberg/R and Babelsberg/S pass 26 out of 42
tests. In addition to the value class failures, these implementations
also fail some tests concerning object identity, have insufficient
support for explicit identity constraints, and support only an older
version of Z3 that does not include soft constraints. A
proof-of-concept Python implementation exists, but was not tested.

\subsection*{Applying the Semantics to Babelsberg/JS}
\label{sec:apply-semant-babelsb}

% Notes on specs in Babelsberg/JS:
% 39/45 tests pass.
% tests 9,10,11 do not work because they include strings
% test 15 uses irecord == which we do not have
% tests 32,32b test for something that shouldn't work b/c of irecords, but it works with heap objects

Modifying Babelsberg/JS to follow the semantics presented here
required changes to both to the translation from imperative
expressions to constraints (called \emph{constraint construction} in
Babelsberg/JS) and to the way in which the solvers are
called. Additionally, we had to update some of the existing example
programs that break with the new semantics.

\subsubsection{Modifications to the Implementation}
\label{sec:modif-impl}
First, we modified the code that translates \javascript expressions
into constraints to not inline methods that have more than a simple
return expression. Methods that have any other statements in them are
executed and their result returned, so they can only be used in the
forward direction. We did not modify the translation to disallow
creating new objects --- as described in \ref{sec:no-side-effects}, we
allow these since \javascript does not include value classes, and
assume that, when new objects are created in constraints, our
conventions on object creation, modification, and not testing for
identity are followed. As an optimization, Babelsberg/JS omits
re-translating expressions if no dependent variables changed. We have
left this optimization in place.

The second change adds support for our restricted form of identity
constraints. Before, users of Babelsberg/JS could use identity checks
as part of ordinary constraints, as long as they used an appropriate
solver. We now disallow this, and add a restricted form of identity
constraints. In the executable semantics, identity constraints can be
solved using Z3 by reasoning over the finite domain of available
references and updating the environment. However, in \javascript we
cannot reflect on the heap or use first-class references, so identity
constraints cannot be solved in the same way. Instead, we use the
DeltaBlue local propagation solver \cite{freeman1989deltablue} to
propagate identity changes as they occur, and call any solvers for
value constraints after that. Babelsberg/JS, through its
implementation of a cooperating solvers architecture
\cite{FelgentreffECOOP14,borning2012architectures}, already supports
solving in multiple phases. The two-phase solving of identity and
value constraints in the formalism is thus implemented simply by
ensuring that the DeltaBlue solver for identity constraints is always
run before any other solvers. Note in particular that this still
allows the developer to use other instances of the DeltaBlue solver
for value constraints, but, just as with all solvers for value constraints, 
it will be called after all the object identities are determined.

\subsubsection{Modifications to Existing Programs}
\label{sec:exist-appl}
Our changes break a number of existing programs in Babelsberg/JS.
These programs are mostly written in the LivelyKernel
\cite{lively-kernel-2008} \javascript environment and publicly
available from the Babelsberg/JS repository and as part of a published
artifact \cite{FelgentreffECOOP14}. For our adaption, we used the
versions from the repository.

\paragraph{Argument Checking.}
\label{sec:argument-checking}
One issue we encountered frequently is that many existing \javascript
methods have, besides
a return statement, a statement that checks the number, types, or
structure of arguments. As per our semantics, such methods do not work
multi-directionally. In fact, allowing them to be truly
multi-directional would allow the solver to change the number, types,
or structure of arguments, which is the kind of surprising behavior we
want to avoid. As an example, consider the frequently used method to
add two points in LivelyKernel:
\begin{lstlisting}[language=JavaScript,caption={The {\tt lively.Point.addPt} method},label=lst:addPt]
function addPt(p) {
    if (arguments.length != 1) throw ('addPt() only takes 1 parameter.');
    return new lively.Point(this.x + p.x, this.y + p.y);
}
\end{lstlisting}
A practical solution to this issue that stays close to the semantics,
but increases the compatibility with existing applications, is to
allow ``hoisting'' of statements that simply do argument checking
outside of the constraint. This is unclean, because the resulting
constraints are not truly multi-directional -- but in practice, we
think it exhibits the expected behavior.

\paragraph{Branching.}
\label{sec:branching}
We encountered a similar issue with methods that return one of two
expressions, depending on a test. The semantics do not allow branching
in constraints. The most frequently encountered such method is
\verb!getPosition!:
\begin{lstlisting}[language=JavaScript,caption={The {\tt lively.morphic.Morph.getPosition} method},label=lst:getPosition]
function getPosition() {
    if (!this.hasFixedPosition() || !this.world()) {
        return this.morphicGetter('Position');
    } else {
        return this.world().getScrollOffset().
                addPt(this.morphicGetter('Position'));
    }
}
\end{lstlisting}
Hoisting the test outside of the method and adding the constraint only
for the branch that is chosen fixes the issue for cases where the
branch condition does not change. In the tested programs this was
always the case. For this particular method, all Morphs we encountered
that are used in constraints execute the first branch.

\paragraph{Benign Side Effects.}
\label{sec:benign-side-effects}
Lazy initialization and caching are used in the constraints in some of the
example applications. Prior work has explicitly allowed such
benign side effects \cite{FelgentreffJOT14,FelgentreffECOOP14},
but our formal semantics disallows them.  (We believe that this is an
appropriate simplification to the formal semantics, preferring to
leave this issue to clear but less formal guidance to programmers and
language implementors.)  For example, the LivelyKernel method
\verb|Morph.getBounds| is used (often indirectly) in many of the
examples.  The code below was adapted to focus on the caching -- the
method also uses branches and local variables, which are also
disallowed now:
\begin{lstlisting}[language=JavaScript,caption={Shortened {\tt lively.morphic.Morph.getBounds} method},label=lst:getBounds]
function getBounds() {
    if (this.cachedBounds && !this.hasFixedPosition())
        return this.cachedBounds;
    // ... other code paths guarded with branches
    return this.cachedBounds = this.innerBounds();
}
\end{lstlisting}
A workaround that we use here is to call
\verb|innerBounds| directly, and circumvent the caching. For Morphs
for which all child Morphs are contained within the bounds of their
parent, this returns the same result.

Another method directly uses lazy initialization in example code:
\begin{lstlisting}[language=JavaScript,caption={A temperature getter that initializes from a Web service},label=lst:getCelsius]
function getCelsius() {
    if (!this.updater)
        this.updater = setInterval(this.updateCelsiusFromWeb.bind(this), 1000);
    return this.Celsius;
}
\end{lstlisting}
A workaround here is to move initializers into separate methods and
run them before using the field in a constraint.

\paragraph{Local Variables.}
\label{sec:local-variables}
Some methods we encountered declared local variables to split up
calculations or name constants. For such methods, manual inlining of
the split up calculation into the return expression was required. The
original Babelsberg design explicitly allows such methods, as long as
the variables are used in static single assignment fashion
\cite{FelgentreffJOT14}.
\begin{lstlisting}[language=JavaScript,caption={A split-up calculation},label=lst:airPressure]
function pressure() {
   var gasConstantDryAir = 287.058, // J/(kg*K)
       density = 1.293, // kg/m^3
       entropyPerVol = gasConstantDryAir * density; // J/K/m^3
   return entropyPerVol * this.K / 1000;
}
\end{lstlisting}

\paragraph{Edit Constraints.}
\label{sec:edit-constraints}
Edit constraints \cite{freeman1989deltablue,freeman1990incremental}
support the efficient updating of a solution to the current
constraints as a set of input values changes, for example, as a point
in a diagram is dragged with the mouse.  Edit constraints are
supported in the Ruby and \javascript implementations of Babelsberg,
but are not yet accounted for in our formal semantics.  Adding them to
the semantics should be straightforward.

Overall, we think these changes, although they represent additional
work for the programmer, make the code clearer, and the interactions
between the object-oriented part and the constraints more
comprehensible. A future goal will be to see which of these
workarounds can be removed while maintaining a clean and
comprehensible set of rules for the interaction of the object-oriented
core and constraints.

\section{Application to Related Work}
\label{sec:related-work}

There are a large number of related systems that integrate constraints
with imperative languages, ranging from \acp{dsl}, to constraint
satisfaction libraries, and to syntactic and semantic integration
similar to Babelsberg. How these systems choose to balance the power
of solvers and how aware the programmer needs to be of the solving
process differs greatly, as does their balance between how freely
programmers can express new constraints versus how aware they need to
be of the fact that they are writing constraints rather than ordinary
statements in the host language.

Kaleidoscope \cite{freeman1990kaleidoscope} was an early \ac{cip}
language, and as such had to address many of the issues that arise
when integrating declarative
constraints with an imperative system that includes mutable state.
Kaleidoscope uses soft constraints to ensure that, in the absence of
other constraints, the solver does not change the values of existing
variables. Babelsberg adapted this and we have expressed it in our
semantics. In contrast to the semantics presented here, Kaleidoscope
separates methods that generate constraints from ordinary methods.
This avoids having to give rules for when a method may work
multi-directionally or only in the forward direction as we have
done. The disadvantage is that it puts the burden on the programmer to
develop and maintain two sets of interfaces, one for use in
constraints and one for use in imperative statements.

Kaleidoscope'93 \cite{lopez1994kaleidoscope} also adds support for
identity constraints, to express the distinction in object-oriented
languages between object equality and identity. However, the
Kaleidoscope system still allowed the solver to determine the identity
of method arguments when solving value constraints, and it used
multi-method dispatch to decide which methods to call in a constraint.
In combination, while this gave the system much power, it also made it
sometimes hard in practice to understand which solution the system
might come up with. Babelsberg does not use multi-method dispatch,
removing one dimension of freedom from the solver (as well as
conforming to a more standard semantics for an object-oriented 
language).  Furthermore, with
our semantics, the solver cannot change the identity or structure of
arguments for value constraints, because identities are fixed and
structure is typechecked before value constraints are interpreted. We
believe the same solution could be applied to the Kaleidoscope design.

Turtle \cite{grabmuller2004turtle} is a more recent \ac{cip} language
developed from scratch, while Kaplan \cite{koksal2012constraints}
provides constraints in Scala \cite{odersky-scala-book}. Both separate
the declaration of ``constrainable'' variables from ordinary variables
to make it clearer what may happen when a variable is used.  Neither
addresses issues of object identity, however.  Like Kaleidoscope, the
Turtle system provides constraint priorities; Kaplan does not. Because
ordinary variables in Turtle are not determined by the solver, only
constrainable variables have low-priority stay constraints on them.
(Kaplan does not currently support constraints over mutable data
types, so stay constraints are not relevant for it.)  Also analogous
to Kaleidoscope, both languages separate constraint functions from
ordinary functions. In Kaplan, only such specifically annotated
functions can be used in constraints. Turtle does allow ordinary
methods and variables to be used in constraints; however, their
values are treated as constants, making all ordinary methods work only
in the forward direction. We believe the simple rules for method
inlining in our semantics could be used with these systems as
well to allow a restricted set of ordinary object-oriented methods 
to be used in constraints.

BackTalk \cite{pachet1995} and
\textsc{Squander} \cite{Squander} explicitly allow the constraint solver
to determine object structure, and even to create new objects that
satisfy a set of constraints. While these systems have many
differences, they are more similar to each other than to
Babelsberg. Both use object-oriented methods in constraints merely as
tests for the backtracking algorithm as it tries different objects and
object structures as assignments for the constrained variables. Thus, it
is a basic property of these systems
to allow actions that we prohibit in Babelsberg.  However, this
does not represent such a
problem in those systems, because the transition from declarative
variables to ordinary variables is explicit, so the programmer can
check for surprising results at that time.

Finally, $\alpha$Rby\cite{alloyRuby2014} is a language that embeds the
Alloy specification language \cite{DBLP:journals/tosem/Jackson02} in
Ruby. Its goal is to allow Alloy users to easily pre- or post-process
their models using imperative libraries, for example to experiment
with visualizations for Alloy models. $\alpha$Rby translates Ruby
programs into Alloy, but the programs consist not of ordinary Ruby
classes and methods. Instead, they are written in a \ac{dsl} that
closely mimics the Alloy language. In contrast to Babelsberg, Alloy
aims to provide imperative constructs to Alloy users, whereas
Babelsberg provides declarative constructs to object-oriented
programmers.

\section{Conclusions and Future Work}
\label{sec:conclusions}

We have presented design principles to tame the power of the solver in
object-constraint programming languages to avoid surprising or
non-deterministic behavior, and a set of simple rules that guide
developers in expressing constraints. Our principles are formalized in
a natural semantics for a useful subset of an object-constraint
language that preserves key properties of existing object-constraint
implementations. For this semantics we presented proof that our rules
remove non-determinism and surprising behavior, in that they never
allow the solver to find solutions that would add or remove fields
from existing objects. Our rules also ensure that the only way for a
variable to change its structure is through an assignment statement --
thus, solving constraints outside of an assignment can never lead to
solutions where variables change their types.

The semantics given here defines a useful subset of the language. A
full object-constraint language that supports standard classes and
methods is given in a companion technical report
\cite{felgentreff:2014:semantics}.  It includes formal rules for
defining constraints on the results of message sends that implement
our informal description in \autoref{sec:transl-multi-way}. Its
restrictions are easy to understand, but may be too conservative, as
shown by our experiences with existing Babelsberg example
programs. One avenue for future work will be to allow somewhat more
general kinds of expressions in methods called from constraints to be
used multi-directionally.

We also presented an executable semantics that can run a suite of
example programs, provided a mechanism to generate a language test
suite to check the implementations' conformance to the semantics, and
modified one existing implementation to follow our design, thus
demonstrating its practicality. Another avenue for future work is to
use this test suite to move other implementations closer to conforming
with the semantics, to further test its practicality.

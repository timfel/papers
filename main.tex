\begin{abstract}
% \AEBadge{}
  Systems that integrate constraint solving with general purpose
  programming languages must strike a balance between exposing the
  full power of solvers and how aware the programmer needs to be of
  the solving process in order to write understandable  and correct
  programs.  In systems that integrate constraints with imperative
  languages, this balancing act extends to how freely programmers can
  express constraints versus how aware they need to be of the
  translation process between the imperative and declarative parts of
  the language in order to understand the limits of this translation.

  Babelsberg is a design to integrate constraints with a standard
  object-oriented language. Experience with Babelsberg, as well as
  with earlier constraint imperative languages, revealed the potential
  for complex interactions between the object-oriented core and
  constraints, in particular among constraints, object identity, and
  change over time.  Programmers needed to be aware of these
  complications to make effective use of constraints, and sometimes
  refactor the constraint expressions or the structure of objects in
  response. Otherwise, the system might come up with surprising
  solutions, or none at all.
  
  In this paper we present design principles that tame the power of
  the constraint solver and of the translation from imperative to
  declarative expressions, avoiding difficult corner cases and
  surprising solutions while retaining the key features and
  capabilities of the approach.  We also provide an informal
  description of the resulting language, and a formal semantics for a
  useful subset of it.  (A companion technical report provides the
  complete formal semantics.)  We validate the utility of this
  semantics with an executable version that allows us to run test
  programs in it and to verify that they provide the same results as
  our actual implementation in Babelsberg/JS.

  \textbf{Keywords:} Constraints, Object Constraint Programming
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Babelsberg \cite{FelgentreffJOT14} is a family of object constraint
languages, with current instances being Babelsberg/R (a Ruby
extension) \cite{felgentreff+:2014:babelsberg}, Babelsberg/JS (a
\javascript extension) \cite{FelgentreffECOOP14}, and Babelsberg/S (a
Squeak extension) \cite{GraberREBLS2014}. The Babelsberg design
integrates constraint satisfaction with ordinary object-oriented
constructs such as inheritance and polymorphism, and inherits many
traits from the earlier Kaleidoscope \cite{lopez1994kaleidoscope} and
Turtle \cite{grabmuller2004turtle} constraint-imperative programming
languages.  It is motivated by the observation that a number of key
aspects of interactive applications can be elegantly and concisely
specified using constraints, but that other aspects are more easily
specified using standard imperative constructs (assignment, loops, and
so forth).  Our goal is to provide both paradigms in a cleanly
integrated fashion, within an object-oriented framework that respects
standard object-oriented features such as messages, encapsulation, and
inheritance. 

Example programs that we have implemented include a graphical
application for building and simulating electrical circuits, a GUI for
a color picker, interactive games, programs to solve logic puzzles,
and simple mobile applications on a smart phone.  These programs
illustrate the division of labor and interplay between the imperative
object-oriented portions of the code and the constraint parts, as well
as the different kinds of constraints and solvers that can be
employed.  The electrical circuit editor and simulator, for example,
uses constraints and an appropriate solver to capture the relevant
laws of physics such as Ohm's Law and Kirchhoff's Current Laws and to
solve the resulting sets of simultaneous linear equations, and
imperative constructs to support actions such as making new resistor,
battery and meter instances, and placing and connecting them.  The
logic puzzle applications \cite{GraberREBLS2014} --- for Sudoku,
cryptarithmetic, Pentaminos, and Star Battle --- use a different class
of constraints and solver, namely constraints over finite domains and
a SAT solver, but similarly have a division of labor into a constraint
part for the constraints that define the Sudoku rules and an
imperative part to control the interaction.  The GUI for a color
picker (described in \cite{FelgentreffECOOP14}) illustrates some
additional desirable kinds of constraints, namely both hard and soft
constraints, and also support for fast incremental re-solving of the
constraints during interactive editing.  Finally, the mobile
application illustrates the use of identity constraints (constraints
that two variables refer to the same identical object) to connect the
UI and underlying model.

As an example constraint, suppose that we may want to express the
requirement that a window in a graphical application stay centered on
a particular point.  We'll use Babelsberg/JS for the code (i.e.,
Javascript syntax).  Babelsberg/JS provides the keyword \verb!always! to
declare constraints on the return values of ordinary methods that then
hold for the rest of the execution.  The constraint can then be
defined as:
\begin{lstlisting}[language=JavaScript,caption={Constraining a window to be centered on a point},label=lst:window]
var window = new Window(0,0,100,100);
always: { window.getCenter().equalsPoint(Point(150,150)) }
\end{lstlisting}

After running this code, the system will ensure that the window is
centered on the point $(150,150)$. If it is resized or dragged by the
title bar, the system will either adjust other parts of the window to
keep the center at the desired position, or, if that is not possible,
prevent the interaction. It does not matter if \verb!getCenter!
is just an accessor or a calculated property. Babelsberg traces into
the method and creates the correct relations between the actual parts
of the window and the point.

As another example, consider a bank account application in which we
want to prevent changes that would make the account balance drop below
a certain threshold. Additionally, we want to track the current
interest the account produces, but not allow it to rise above 1000.
(This example is simple enough that we can show the listing easily,
but is designed to illustrate some complexities around object
identity, as well as constraint features such as soft constraints and
read-only annotations on variables.)
\begin{lstlisting}[language=JavaScript,caption={Ensuring domain requirements on a bank account},label=lst:account]
var acc = new Account(), minBalance = 100, curInterest = 0;
always: { acc.balance >= minBalance? }
always: { priority: "medium"
          curInterest == acc.balance? * 0.01 }
always: { curInterest <= 1000 }
\end{lstlisting}

Here, the solver will ensure the property \verb!balance! remains
larger than \verb!minBalance! after line 2. The question-mark
after \verb!minBalance! prevents the solver from changing it
to satisfy the constraint. Thus, any change to the account that
would drop the result of \verb!balance! below
\verb!minBalance! is rejected by the system. Conversely, the
system is not allowed to change the result of \verb!balance! to
satisfy the second constraint. The current interest is always
determined from the current balance, but not vice-versa. Note also
that we assign a priority to the second constraint. This tells the
system that is should satisfy this relation if possible, but it is no
error not to do so. Due to the third constraint, if the interest were
to rise above 1000, the system can leave the second constraint
unsatisfied.

Experience with Babelsberg has shown that their design requires
programmers to consider the solving process as well as the
implementation of the framework to use constraints effectively. First,
the programmer has to be careful to express constraints in a manner so
that a constraint solver will find the desired solution. Second, the
programmer has to consider how the framework translates constraints to
the solver in order to understand how a particular constraint
expression is passed to the solver.

\paragraph{Finding the Desired Solution}
\label{sec:find-desir-solut}
It is easy to formulate a problem that is too hard for any one solver,
and it is easy to specify a problem that allows the solver to find
undesired solutions. While we cannot help the former, we can avoid
some surprising solutions by restricting the solver to favor solutions
that are less surprising for imperative programmers.

In \autoref{lst:account}, we expect the solver to reason about the
balance of the newly created Account. However, there are other valid
solutions:
\begin{inparaenum}
\item[first,] the solver might change \verb!acc! to point to another
  object that has the right balance.
\item[Second,] the solver may correct the balance, but also add or remove
  fields from the account that are not relevant to the constraint.
\item[Third,] even if the initial balance was already higher than
  \verb!minBalance!, the solver may still choose to make it equal
  to \verb!minBalance!, as this also satisfies the constraint.
\end{inparaenum}

All three solutions are clearly undesired: imperative programmers do
not expect the identity of the \verb!acc! variable to change or
the solver to change the object structure. Neither do they expect the
property to change, if the constraint is already satisfied.

To address this problem, we restrict the power of the solver so it
finds the expected solution in cases such as these.\footnote{The
  formulation of the first two restrictions is new in this work; the
  third has been present in Babelsberg since the original language
  definition.}
\begin{inparaenum}
\item[First,] we separate constraints involving object identity from
  those involving only values, and solve those independently, so that
  a solution that changes the identity of \verb!acc! is not valid.
\item[Second,] we use structural type-checking to ensure the solver
  cannot add or remove fields from objects.
\item[Third,] we implicitly add a low priority ``stay'' constraint to
  each variable, so that its value only changes if required to do so
  by some higher-priority constraint.
\end{inparaenum}

\paragraph{Formulating Valid Constraints}
The second issue is that the programmer needs to be aware of some
restrictions on how objects can be used in constraints. Kaleidoscope
and Turtle distinguish imperative and declarative behavior definitions
that are used depending on whether an object is used in an imperative
or a declarative context. This means that programmers have to consider
both interfaces of an object, depending on what they want to
express. Babelsberg unifies the behavior definition and allows the
programmer to express constraints directly using imperative
methods. However, not all methods work equally well in
constraints. Consider the \verb!getCenter! method from
\autoref{lst:window}. Because it is dynamically bound, a programmer
cannot know its implementation when writing the constraint. The method
simply return a field, but it may also calculate the center from other
fields on the object. If the latter, the method may cache that
calculation for faster retrieval. Regardless, the programmer expects
this constraint to adjust whatever parts of the window contribute to
the result of \verb!getCenter! so the center is at
$(150,150)$. If it does not, it is not clear to the programmer which
of the operations -- the check for cache invalidation, storing the
result, or the calculation itself -- does not work in a constraint.

In our earlier work on Babelsberg, we enumerated a set of rules for
when an expression could be used to define a constraint, but there
were some confusing edge cases around object identity and constraints,
and around when methods called from a constraint expression could be
used multi-directionally.  Now, in the work reported here, we have
developed a simple-to-understand set of restrictions on the
expressions that define constraints, and when they can be used
multi-directionally. 
\begin{inparaenum}
\item[First,] if the method consists solely of a single return
  statement (for example, an expression that is a calculation on the
  object's fields) it can work multi-directionally.  However, if it
  has additional statements before returning, it can only be used in
  the forward direction.
\item[Second,] if the method has any side-effects, such as writing to
  a non-local location or generating a random number, it cannot be
  used in a constraint in any direction.
\end{inparaenum}
\vskip\baselineskip

In this paper we formalize restrictions on the solver and the
translation from methods to constraints that help programmers
understand how constraints in Babelsberg will work, and what the
properties of the solutions will be. Our restrictions make the solving
process more deterministic, offer guidance how to express valid
constraints, and thus give enough freedom to express many interesting
problems. The main contributions are:
\begin{itemize}
\item A non-standard form of structural type-checking paired with soft
  constraints to restrict the power of the solver and to define how
  constraints interact with object identity and structure.
\item A formalization of prior work on object constraint programming
  to integrate objects, methods, classes, and constraints in a way
  that is backwards compatible with the existing object-oriented
  paradigm. Of particular interest here is the way we explode
  constraints involving methods and how we restrict side-effects in
  constraint expressions.
\item We give an executable version of our semantics that uses the Z3
  \cite{de2008z3} constraint solver to verify our examples.
\item We have adapted the Babelsberg/JS implementation to follow the
  semantics, and can present our experiences with which examples do
  not work anymore.
\end{itemize}

\autoref{sec:informal-solution} gives an informal overview of our

\section{Solution Overview}
\label{sec:informal-solution}

A goal of this work was to clarify design decisions of Babelsberg to
guide language users and implementers. It is not meant to be a
complete description of an object constraint language. Because
Babelsberg is a design to provide object constraint programming in an
object-oriented host language, we omit aspects of a practical language
that are intended to be inherited from the host language, such as
class- and method-definitions, exception handling, or \textsc{IO}.

Babelsberg, in the absence of constraints, should be a standard
object-oriented language. This work focuses on how standard
object-oriented constructs need to be modified to support the
Babelsberg design. Where there is a choice, we aim to make the
smallest possible changes while still accommodating constraints in a
clean and powerful way. Beyond this, we favor simplicity of the rules
over the power to support interesting, but in practice rarely used
features.

This section consists of two parts: the first presents how we restrict
the power of the solver to be deterministic with regards to objects'
identities and structure. The second part presents how we restrict the
translation from object-oriented methods to constraints to avoid
corner-cases and give simple rules for programmers to follow when they
express constraints.

\subsection{Restricting the Solver}
\label{sec:restricting-solver}

At the core of our design is the idea that the solver determines the
entire heap and environment after each statement. However, for an
imperative programmer it would be surprising if variables change more
than they have to -- the solver should always pick a solution that is
close to the current state of the system.

\subsubsection{Object Structure}
\label{sec:object-structure}

In \autoref{lst:account} we have seen a constraint on a
field. However, in the absence of other constraints, nothing is
preventing the solver from adding or removing unrelated fields to the
object. Consider setting the \verb!acc! variable to an empty
object and asserting the constraint. Should the solver invent a
balance field and constrain it?

To tame the power of the solver so that it does not (for example)
invent new fields for objects, we propose all constraints undergo a
\emph{structural compatibility checks}.  These are dynamically
asserted before sending the constraints involving objects to the
solver. They ensure, for example, that field accesses occur only on
objects (and not primitive values), and that those objects have the
necessary fields. These assertions, unlike constraints, are only
checked --- if one is violated it is an error and the constraint
solving fails. The programmer must ensure that objects used in
constraints have all the required fields.

\subsubsection{Object Identity}
\label{sec:determ-object-ident}

A central issue in the design of an object constraint language is the
interaction between constraints and object identity. Identity
constraints have proven useful to express properties on circular
structures \cite{lopez-ecoop-1994}, but experience in particular with
Kaleidoscope suggests that allowing powerful constraints on object
identity and types can lead to non-obvious consequences. As an
example, consider the following program:

\begin{lstlisting}[language=JavaScript,caption={Constraining two variables to be identical},label=lst:identity]
var a = {credit: 10}, b = {funds: 100};
always: { a === b }
always: { a.funds >= 0 }
\end{lstlisting}

This adds a constraint on line 2 that \verb!a! and \verb!b! be
identical. However, it is not clear if \verb!a! and \verb!b! will
afterwards refer to a credits account or a checkings account. If they
are both credit accounts, the constraint on line 3 will not pass our
structural compatibility checks. The choice of identity in one place
would thus determine the validity of the second constraint. This makes
programs more difficult for the programmer to understand.

To tame the power of constraints on object identity and type, we set
the following goals for this aspect of our design:
\begin{itemize}
\item Constraints on object identity must be declared explicitly using
  the host languages identity check method (\verb!===! in the case of
  \javascript). They cannot be hidden within a method.
\item\label{item:deterministic} The solution to the constraints is
  deterministic as far as object identity and type are concerned ---
  there should never be multiple correct solutions in which a given
  variable refers to objects with different identities in the
  different solutions. Thus, the programmer must first ensure the
  identity constraint is already satisfied, before asserting it.
\item Any change to the identities of the objects referred to by
  variables can only flow from an assignment statement --- the
  constraint solver must not be allowed to otherwise alter object
  identities.
\item\label{item:solve-identity-then-values} To make Babelsberg
  programs more understandable for the programmer, we want to reason
  about identities in value constraints. We thus first solve all the
  identity constraints (with a deterministic solution, in keeping with
  goal \ref{item:deterministic}), and then the value constraints. In
  the second step, identities are fixed, and thus method lookup
  follows ordinary object-oriented semantics. This requires all
  identity constraints to be declared separately from value
  constraints. We disallow non-required identity constraints, to avoid
  having to backtrack when solving value constraints.
\end{itemize}

\subsubsection{Stay Constraints}
\label{sec:stay-constraints}

As in Kaleidoscope, Babelsberg adds an implicit weak stay constraint
to each variable to keep it at its current value, if possible. This
satisfies the desire that the solver should not change a variable, if
no constraint on it is violated.


\subsection{Rules for Constraint Expressions}
\label{sec:rules-constr-expr}

In Babelsberg, constraints are ordinary imperative expressions that
evaluate to a boolean --- the constraint being that they evaluate to
true. In our semantics, we have rules to translate imperative
expressions into constraints. Our translation process traces through
methods and effectively unrolls loops, prunes branches, and inlines
method bodies.

The rules to translate expressions into constraints evolved alongside
the existing implementations, driven in part by practical
considerations about the expectations of programmers familiar with the
underlying host language. In prior work, the rules for constraint
expressions in Babelsberg were defined as:
\begin{inparaenum}[a)]
\item if there are assignments, variables assigned to must be used in
  \textsc{SSA} form,
\item the constraint expression should either be free of side effects,
  or if there are side effects, they should be benign, and
\item repeatedly evaluating the constraint expression should return
  the same thing, so a method that returns the current system time
  would not qualify.
\end{inparaenum}
In practice, it was not clear which constructs follow these rules, or
what constitutes ``benign'' side-effects.

\subsubsection{One-Way and Multi-Way Constraints}
\label{sec:transl-multi-way}

For simplicity, methods that contain more than a return statement can
only be used in the forward direction. This includes methods with
multiple assignments, which removes the first older rule that
variables assigned to in constraints must be used in \textsc{SSA}
form. Such methods can still be called in the usual way, including
passing any parameters by value with pointer semantics. For example,
suppose we have a constraint \verb|always c=x.m(a,b)|, and method
\verb|m| has multiple statements so that it can only be used in the
forward direction, i.e., we can find a value for \verb|c| given values
for \verb|x|, \verb|a|, and \verb|b| but not any other direction.  In
that case, \verb|m| can be called in the usual way, passing \verb|a|
and \verb|b| by value with pointer semantics.  If the other
constraints are such that the correct solution involves finding a
value for \verb|b| given values for \verb|c|, \verb|x|, and \verb|a|,
the implementation should halt with an error that the constraints are
too hard for it to solve, due to a method called from the constraint
that can't be inlined (or in the formal semantics, we get stuck). Note
that in contrast to examples of constraints that are too hard for the
\emph{solver}, the fact that these constraints are too hard is a
limitation of our \emph{transformation} rule.

On the other hand, if method \verb|m| can be used multi-directionally,
so that for example we can find a value for \verb|b| given values for
\verb|x|, \verb|a|, and \verb|c|, then in the semantics the method is
inlined so that the resulting constraints can be turned over to the
solver, and we can potentially solve for any of \verb|x|, \verb|a|,
\verb|b|, or \verb|c|.  This done by creating an environment for
method \verb|m| and inlining the returned expression with respect to
that environment. The parameters in that environment are constrained
to be identical to \verb|a| and \verb|b| respectively, and \verb|self|
is constrained to be identical to \verb|x|.

\subsubsection{No Side-Effects in Constraints}
\label{sec:no-side-effects}

Our rules prevent the programmer from asserting constraints that have
non-benign side-effects. We define non-benign as such side-effects
that change the value of existing variables that are visible after the
constraint expression returns (rather than just creating new temporary
variables), the creation of new ordinary objects the heap (because
these could be discerned by identity in languages that allow
reflection on the heap), as well as system calls (for example to a
random number generator or the clock).

The only kinds of objects that can be safely created in constraints
are instances of \emph{value classes} that are immutable after
creation and for which object identity is not significant, that is, it
is a test for field equality. An example for this is the \verb!Point!
constructor used in \autoref{lst:window}. However, value classes are
more than simple records, since they support methods and
inheritance. A number of existing languages have proposals to support
forms of value classes, such as
Java\footnote{\url{http://openjdk.java.net/jeps/169}} and
Scala\footnote{\url{http://docs.scala-lang.org/sips/completed/value-classes.html}}.
For practical implementations where the host language does not support
value classes, we can allow the creation of instances of ordinary
classes, and assume developers follow conventions about object
creation, modification, and not testing for object identity.

\section{Semantics}
\label{sec:semantics}

For our semantics we use a simple language, Babelsberg/UID, that
includes primitive types (reals, booleans, and strings), as well as
mutable objects that live on the heap and immutable objects that are
in the environment. Its semantic rules are mostly standard imperative
rules, with the addition of rules to assert and maintain
constraints. The semantics for this language, although not
object-oriented, illustrates all our important
contributions. Extending it to include all the essential features of
the actual object constraint languages such as support for classes,
methods, messages, and inheritance, along with constraint definitions
that can include method calls is straightforward. We include the
extended language, Babelsberg/Objects, in an appendix.

In addition to a normal imperative language, after every statement
execution the current set of constraints is solved and the environment
and heap are updated from the solution.  The current set of
constraints is determined as follows.  If the statement is an
assignment, we evaluate the right hand side and then set up a
constraint that the resulting value and the left hand side be
identical. Otherwise the statement is simply executed. In addition to
any constraint resulting from an assignment statement, each constraint
in the constraint store is added to the set of constraints as well,
and the resulting set of constraints is given to the solver.  If the
solver finds a solution, the environment and heap are replaced by the
model the solver found; but if the constraints have no solution, or if
they are too hard for the solver, the execution implicitly gets
stuck. In the practical languages, a runtime exception will be
generated and the heap and environment remain unchanged.

The semantics treats the solver as a black box, but we assume it
supports our primitive types, records, uninterpreted functions, as
well as hard and soft constraints \cite{borning1992constraint} and
read-only variables. The solver should find a single best solution ---
if there are multiple solutions, the solver is free to pick any one of
them. % Providing answers rather than solutions, i.e., results such as
% $10 \leq x \leq 20$ rather than a single value for $x$, and
% backtracking among multiple answers, as available in for example
% constraint logic programming \cite{jaffar-popl-1987}, is left for
% future work.

\vskip\baselineskip\noindent We use the following syntax for
Babelsberg/UID: \vskip0.5\baselineskip\noindent
\begin{tt}
\begin{tabular}{lrrl}
{\rm Statement} & s & ::= & skip $\mid$ L := e $\mid$ L := new o $\mid$ always C $\mid$ once C \\
  & & &  $\mid$ s;s $\mid$ if e then s else s $\mid$ while e do s \\
{\rm Constraint} & C & ::= & $\rho$ e $\mid$ C $\wedge$ C\\
{\rm Expression} & e & ::= & v $\mid$ L $\mid$ e $\oplus$ e
$\mid$ e $\olessthan$ e $\mid$ e $\ovee$ e $\mid$ I\\
  & & & $\mid$ o $\mid$ D\\
{\rm Identity} & I & ::= & e == e\\
{\rm Object Literal} & o & ::= &  \{l$_1$:e$_1$,$\ldots$,l$_n$:e$_n$\} \\
{\rm L-Value} & L & ::= & x $\mid$ e.l \\
{\rm Constant} & c & ::= & true $\mid$ false $\mid$ nil $\mid$ {\rm base type constants}\\
{\rm Variable} & x & ::= & {\rm variable names} \\
{\rm Label} & l & ::= & {\rm record label names} \\
{\rm Reference} & r & ::= & {\rm references to heap records} \\
{\rm Dereference} & D & ::= & \H(e) \\\\

{\rm Value} & v & ::= & c $\mid$ r $\mid$ \{l$_1$:v$_1$,$\ldots$,l$_n$:v$_n$\} \\
\end{tabular}
\end{tt}\vskip0.5\baselineskip

Metavariable {\tt c} ranges over the {\tt nil} value, booleans, and
primitive type constants. A finite set of arithmetic operators on
expressions is ranged over by $\oplus$, $\olessthan$ ranges over a set
of {\em predicate} operators, and $\ovee$ ranges over logical
operators for combining boolean expressions. $\olessthan$ includes at
least an equality operator {\tt =} for each primitive type, and
$\ovee$ includes at least conjunction {\tt $\wedge$}. The operator
{\tt ==} tests for identity -- for primitive values this is the same
as {\tt =}. The symbol $\rho$ ranges over constraint {\em priorities}
and is assumed to include a bottom element {\em weak} and a top
element {\em required}. The syntax requires the priority to be
explicit, for simplicity we sometimes omit it in the rules and assume
a {\em required} priority.

In the syntax, we treat \H as a keyword.  Source programs will
not use expressions of the form \H(e), but they are introduced as
part of constraints given to the solver, which we assume will treat
\H as an uninterpreted function.

The semantics includes an environment \E~and a heap \H. The former is
a function that maps variable names to values, while the latter is a
function that maps mutable references to ``objects''. When convenient,
we also treat both \E~and \H~as a set of pairs ({\tt \{(x,v),...\}}
and {\tt \{(r,o),...\}}, respectively). The currently active value
constraints are kept as a compound constraint \C, identity constraints
are kept in \I.

``Expression {\tt e} evaluates to value {\tt v} in the context of
environment \E~and heap \H.''

The rules for evaluation are mostly as expected in an imperative
language. We do not give rules for expressions of the form {\tt
  \H(e)}, because they are not meant to appear in source. For each
operator {\tt o} in the language we assume the existence of a
corresponding semantic function denoted
$\llbracket {\tt o} \rrbracket$.

\judgment{\tcH{\E}{\H}{e}{T}}
\judgment{\tcHC{\E}{\H}{C}}

``Expression {\tt e} has type {\tt T} in the context of environment
{\tt \E} and heap \H.''

``Constraint {\tt C} is well formed in the context of environment
{\tt \E} and heap \H.''

We use a notion of typechecking to prevent undesirable non-determinism
in constraints.  Specifically, we want constraint solving to preserve
the structure of the values of variables, changing only the underlying
primitive data as part of a solution, in support of the goals listed
in \autoref{sec:object-structure}.  We formalize our notion of
structure through a simple syntax of types:
\vskip0.5\baselineskip\noindent\begin{tt}
\begin{tabular}{lrrl}
{\rm Type} & T & ::= & PrimitiveType $\mid$ \{l$_1$:T$_1$,$\ldots$,l$_n$:T$_n$\}
\end{tabular}
\end{tt}
\vskip0.5\baselineskip

The typechecking rules are mostly standard. We check expressions
dynamically just before constraint solving, so we typecheck in the
context of a runtime environment. As with the evaluation rules,
expressions of the form {\tt \H(e)} do not typecheck. Note that we do
not include type rules for identities. This ensures that constraints
involving them do not typecheck, so identity checks cannot occur in
ordinary constraints.

\judgment{\solveH{\E}{\H}{C}}

This judgment represents a call to the constraint solver, which we
treat as a black box.  The proposition \mbox{\solveH{\E}{\H}{\C}}
denotes that environment \E~and heap \H~are an \emph{optimal solution}
to the constraint {\tt C}, according to the solver's semantics.

\judgment{\stay{\E}{C}}
\judgment{\stay{\H}{C}}
\judgment{\istay{e}{C}}
\judgment{\istay{\E}{C}}
\judgment{\istay{\H}{C}}

As in Kaleidoscope, the semantics ensure that each variable has an
implicit stay constraint to keep it at its current value, if
possible. To ensure that the solver cannot invent new fields on
objects, we create required stays on the heap that assert the
structure of the objects. The first two stay rules assert only weak
stays on all variables. The \istay{\E}{C} and \istay{\H}{C} rules use
the \istay{e}{C} rule to create weak stays on primitive values and
immutable objects, but they create required stays for
references. These latter rules are used when solving value
constraints, and ensure that value constraints cannot affect object
identities.

\inferax{StayEmpty}{\stay{$\emptyset$}{true}}

\inferrule{StayOne}{
  \E$({\tt x}) = {\tt v}$ \andalso
  \E$_0 = $\E$ \setminus \{({\tt x},{\tt v})\}$ \andalso
  \stay{\E$_0$}{C$_0$} \andalso
  {\tt C}$ = ${\tt C}$_0$ $\wedge$ {\tt weak x=v}
}{
  \stay{\E}{C}
}

\infrule[StayHeap]{\mbox{
  \H$({\tt r}) = {\tt o}$ \andalso  
  \H$_0 = $\H$ \setminus \{({\tt r},{\tt o})\}$ \andalso
  \stay{\H$_0$}{C$_0$}}\\
\mbox{
  ${\tt o} = $\{{\tt l$_0$:v$_0$,$\ldots$,l$_n$:v$_n$}\} \andalso
  {\tt C} = {\tt weak x$_{r0}$ = v$_0$ $\wedge$ $\ldots$ $\wedge$ weak x$_{rn}$ = v$_n$}}
}{\mbox{
  \stay{\H}{C$_0$ $\wedge$
    {\tt weak \H(r)=\{l$_0$:x$_{r0}$,$\ldots$,l$_n$:x$_{rn}$\}} $\wedge$ C}
}}

    ${\tt o} = $\{{\tt l$_0$:v$_0$,$\ldots$,l$_n$:v$_n$}\}}\\

    \istay{x$_{r0}$=v$_0$}{C$_{r0}$} $\cdots$ \istay{x$_{rn}$=v$_n$}{C$_{rn}$}}
}{\mbox{

    {\tt weak \H(r)=\{l$_0$:x$_{r0}$,$\ldots$,l$_n$:x$_{rn}$\}} $\wedge$
    C$_{r0}$ $\wedge$
    $\ldots$ $\wedge$
    C$_{rn}$ }

\judgment{\combine{\E}{\H}{\C}{C}}
\judgment{\combine{\E}{\H}{\I}{C}}

We use a combination judgment to translate the current constraint into
a constraint suitable for the solver. During this combination all
expressions in parts of the conjunction constraints of the form {\tt
  L.l} where {\tt L} refers to a heap reference {\tt r} are converted
into {\tt \H(L).l} (recursively, as required). We do not give rules,
because they are straightforward. The full Babelsberg/Objects language
includes a similar judgment that also inlines method calls, which is
given in its entirety in the appendix.

\judgment{\stepH{\E}{\H}{\C}{\I}{s}{\E$'$}{\H$'$}{\C$'$}{\I$'$}}

``Execution starting from configuration {\tt <\E|\H|\C|\I|s>} ends in
state {\tt <E$'$|\H$'$|C$'$|\I$'$>}.''

A ``configuration'' defining the state of an execution includes a
concrete context, represented by the environment and heap, a symbolic
context, represented by the constraint and identity constraint stores,
and a statement to be executed. The environment, heap, and statement
are standard, while the constraint stores are not part of the state of
a computation in most languages.  Intuitively, the environment comes
from constraint solving during the evaluation of the immediately
preceding statement, and the constraint records the \verb|always|
constraints that have been declared so far during execution. Note that
our execution implicitly gets stuck if the solver cannot produce a
model. When updating a variable, we solve first for the identity
constraints and then for the value constraints. This propagates any
type changes through the identity constraints. We then type the value
constraints against the environment returned by solving for the
identities.

\infrule[S-Asgn]{
  \mbox{
    \evalH{\E}{\H}{e}{v} \andalso
    \stay{\E}{C$_{E_s}$} \andalso
    \stay{\H}{C$_{H_s}$} \andalso
    \combine{\E}{\H}{\I}{C$_I$}}\\
  \mbox{
    \solveH{\E$'$}{\H$'$}{(C$_I$ $\wedge$ C$_{E_s}$ $\wedge$ C$_{H_s}$ $\wedge$ L=v)}}\\
  \mbox{
    \istay{\E$'$}{C$_{{E'}_s}$} \andalso
    \istay{\H$'$}{C$_{{H'}_s}$} \andalso
    \combine{\E}{\H}{\C}{C$_C$} \andalso
    \tcHC{\E$'$}{\H$'$}{C$_C$}} \\
  \mbox{
    \solveH{\E$''$}{\H$''$}{(C$_C$ $\wedge$ C$_{{E'}_s}$ $\wedge$ C$_{{H'}_s}$ $\wedge$ L=v)}}
}{\mbox{
  \stepH{\E}{\H}{\C}{\I}{L := e}{\E$''$}{\H$''$}{\C}{\I}
}}

Implicitly this rule gets stuck if either a) the identity constraints
cannot be solved, b) the value constraints do not type if the
identities are solved, or c) the value constraints cannot be solved. A
practical implementation would add explicit exceptions for these cases
that the programmer could handle.

\infrule[S-AsgnNew]{
  \mbox{
    \evalH{\E}{\H}{e$_1$}{v$_n$} $\cdots$ \evalH{\E}{\H}{e$_n$}{v$_n$}} \\
\mbox{
    \H({\tt r})$\uparrow$ \andalso {\tt \H$_0$} = {\tt \H}
    $\bigcup$ \{({\tt r}, {\tt \{l$_1$:v$_1$,$\ldots$,l$_n$:v$_n$\}})\}} \\
  \mbox{
    \stay{\E}{C$_{E_s}$} \andalso
    \stay{\H$_0$}{C$_{H_s}$} \andalso
    \combine{\E}{\H}{\I}{C$_I$}}\\
  \mbox{
    \solveH{\E$'$}{\H$'$}{(C$_I$ $\wedge$ C$_{E_s}$ $\wedge$ C$_{H_s}$ $\wedge$ L=r)}}\\
  \mbox{
    \stay{\E$'$}{C$_{{E'}_s}$} \andalso
    \stay{\H$'$}{C$_{{H'}_s}$} \andalso
    \combine{\E}{\H}{\C}{C$_C$} \andalso
    \tcHC{\E$'$}{\H$'$}{C$_C$}}\\
  \mbox{
    \solveH{\E$''$}{\H$''$}{(C$_C$ $\wedge$ C$_{{E'}_s}$ $\wedge$ C$_{{H'}_s}$ $\wedge$ L=r)}}
}{\mbox{
  \stepH{\E}{\H}{\C}{\I}{L := new \{l$_1$:e$_1$,$\ldots$,l$_n$:e$_n$\}}{\E$''$}{\H$''$}{\C}{\I}
}}

The above rule creates a new object on the heap, and assigns the fresh
reference to {\tt L}.

We distinguish value and identity constraints. Note that the rules for
always and once match only constraints that do not include identity
comparisons, because those would not type.  We require that an
identity constraint already be satisfied when it is asserted. So the
rules for identity constraints simply need to check if the expression
is true.

\inferrule{S-OnceIdentity}{
  \evalH{\E}{\H}{L$_0$}{v} \andalso

\section{Evaluation}
\label{sec:evaluation}

Our aim in developing a formal semantics for Babelsberg has been
primarily a practical one, including clarifying the desired behavior
of the language, providing a guide for language implementors, and
proving useful language properties that then can be relied on by
programmers.  One piece of evidence of success is that we have in fact
clarified the desired behavior of the language, and as discussed in
the introduction, in response have adapted the existing Babelsberg/JS
implementation to conform to it.

Beyond that, we offer to forms of evaluation.  First, we have
implemented our natural semantics in \rml \cite{pettersson1994rml},
yielding an executable semantics.  We then evaluated a set of test
programs in this executable semantics, using Z3 \cite{de2008z3} as the
solver to provide heap and environment updates. As an extension to
that, we provide a translation from the test programs in the
executable semantics to \javascript tests. These show that the
practical implementation and semantics produce the same results for
most of the examples, except those that test features of value classes
which we do not emulate in \javascript.

As a second form of evaluation, we have adapted the currently existing
suite of example programs for Babelsberg/JS to the revised
language. We demonstrate that we many of the programs still work or
work with minimal adjustments. Those programs that do not work anymore
work because they use constructs we now decided to disallow.

\subsection*{An Executable Semantics}
\label{sec:an-exec-semant}

\rml is a programming language to generate executables from natural
language specifications. It provides \emph{relations} as basic
building blocks for the semantics and translates these to C. It was
possible to implement our semantics exactly in \rml. As the semantics
does not model the solving process, we have added a translation from
our constraint syntax to Z3 \cite{de2008z3}, which solves the
constraints and generates a model of the new heap and
environment. Because our semantics requires on soft constraints, we
use an experimental version of Z3 that supports them
\cite{bjornernuz}.

Z3 types expressions. Our structural typing rules, however, allow
variables to change their type. Consequently, we declare variables in
Z3 with a union type \verb!Value!, and define the operation-,
comparison, and combination functions on that union type. \verb!Value!
variables have a real, boolean, reference, and value class
component. The latter is encoded as a Z3 array that maps \emph{labels}
to reals. Labels and reference are declared as finite domain types
that range over the existing references and record labels
respectively.

In a companion technical report, we provide 46 example programs that
illustrate various concerns of the semantics (including the examples
given in this paper). Of those 45 programs, 3 use constraints on
strings, which are not supported in the version of Z3 we used. The
remaining 42 all run and produce the expected results at each step of
the execution.

As an extension to the \rml implementation, we add a module to
transform the example code into test cases for the various
implementations of Babelsberg. This may provide an avenue for future
development of Babelsberg --- as the formal and executable semantics
evolve, test cases for the existing implementations can be generated
and the implementations adapted to pass the generated tests.

All of the existing implementations must be adapted to pass the tests,
because all deviate from the semantics in one way or another. We have
modified the \javascript implementation, as it is the most
advanced\footnote{We have also tested, but not adapted two of the
  other implementations. Babelsberg/R passes 26 tests, and
  Babelsberg/S passes 19. A proof-of-concept Python implementation
  exists, but was not run.}. After modification, of the 42 test cases
that work in the \rml semantics, 39 produce the expected results. The
remaining three all specifically test properties of value classes in
constraints. Since \javascript does not support value classes (and we
do not emulate them in some way) these 3 tests fail, in one case
producing no result when there is a solution, and the other two
producing a solution when solving should fail.

\subsection*{Applying the Semantics to Babelsberg/JS}
\label{sec:apply-semant-babelsb}

% Notes on specs in Babelsberg/JS:
% 39/46 tests pass.
% tests 9,10,11 do not work because they include strings
% test 15 uses irecord == which we do not have
% tests 32,32b test for something that shouldn't work b/c of irecords, but it works with heap objects

We modified the existing implementation of object constraint
programming in \javascript, Babelsberg/JS, to follow the semantics
presented here. This required changes to both to the constraint
construction and to the solving process, as well as some changes to
existing programs that break with the new semantics.

\subsubsection{Modifications to the Implementation}
\label{sec:modif-impl}
First, we modified the code that translates \javascript expressions
into constraints to not inline methods that have more than a simple
return expression. Methods that have any other statements in them are
executed and their result returned, so they can only be used in the
forward direction. We did not modify the translation to disallow
creating new objects --- as described in \ref{sec:no-side-effects}, we
allow these since \javascript does not include value classes, and
assume that, when new objects are created in constraints, our
conventions on object creation, modification, and not testing for
identity are followed. As an optimization, Babelsberg/JS already omits
re-translating expressions if no dependent variables changed. We have
left this optimization in place.

The second change adds support for our restricted form of identity
constraints. Before, users of Babelsberg/JS could use identity checks
as part of ordinary constraints, as long as they used an appropriate
solver. We now disallow this, and add a restricted form of identity
constraints. In the executable semantics, identity constraints can be
solved using Z3 by reasoning over the finite domain of available
references and updating the environment. However, in \javascript we
cannot reflect on the heap or use first-class references, so identity
constraints cannot be solved in the same way. Instead, we use the
DeltaBlue local propagation solver \cite{freeman1989deltablue} to
propagate identity changes as they occur, and call any solvers for
value constraints after that. Babelsberg/JS, through its
implementation of a cooperating solvers architecture
\cite{borning2012architectures,FelgentreffECOOP14}, already supports
solving in multiple phases. The two-phase solving of identity and
value constraints in the formalism is thus implemented simply by
ensuring that the DeltaBlue solver for identity constraints is always
run before any other solvers. Note in particular that this still
allows the developer to use other instances of the DeltaBlue solver
for value constraints, but as all other solvers for value constraints,
will be called after all the identities are fixed.

\subsubsection{Modifications to Existing Programs}
\label{sec:exist-appl}
Our changes break a number of existing programs in Babelsberg/JS.
These programs are mostly written in the LivelyKernel
\cite{lively-kernel-2008} \javascript environment and publicly
available from the Babelsberg/JS repository.

\paragraph{Argument Checking.}
\label{sec:argument-checking}
One issue we encountered frequently is that many methods have, besides
a return statement, a statement that checks the argument types or
structure. As per our semantics, such methods do not work
multi-directionally, because we do not want to allow the solver to
change the types and structure of arguments. As an example, consider
the frequently used method to add two points:
\begin{lstlisting}[language=JavaScript,caption={The {\tt lively.Point.addPt} method},label=lst:addPt]
function addPt(p) {
    if (arguments.length != 1) throw ('addPt() only takes 1 parameter.');
    return new lively.Point(this.x + p.x, this.y + p.y);
}
\end{lstlisting}
A practical solution to this issue that stays close to the semantics,
but increases the compatibility with existing applications, is to
allow ``hoisting'' of statements that simply do argument checking
outside of the constraint. This is unclean, because the resulting
constraints are not truly multi-directional -- the solver cannot
change, for example, the types or number of arguments. In practice, we
do not think such behavior would be expected.

\paragraph{Branching.}
\label{sec:branching}
We encountered a similar issue with methods that return one of two
expressions, depending on a test. The semantics do not allow branching
in constraints. The most frequently encountered such method is
\verb!getPosition!:
\begin{lstlisting}[language=JavaScript,caption={The {\tt lively.morphic.Morph.getPosition} method},label=lst:getPosition]
function getPosition() {
    if (!this.hasFixedPosition() || !this.world()) {
        return this.morphicGetter('Position');
    } else {
        return this.world().getScrollOffset().
                addPt(this.morphicGetter('Position'));
    }
}
\end{lstlisting}
Hoisting the test outside of the method and adding the constraint only
for the branch that is chosen fixes the issue for cases where the
branch condition does not change. In the tested programs this was
always the case. For this particular method, all Morphs we encountered
that are used in constraints execute the first branch.

\paragraph{``Benign'' Side-effects.}
\label{sec:benign-side-effects}
Lazy initialization was used in some of the examples. Prior work has
explicitly allowed such ``benign'' side-effects
\cite{FelgentreffJOT14,FelgentreffECOOP14}, but our semantics
disallows them:
\begin{lstlisting}[language=JavaScript,caption={A temperature getter that initializes from a Web service},label=lst:getCelsius]
function getCelsius() {
    if (!this.updater)
        this.updater = setInterval(this.updateCelsiusFromWeb.bind(this), 1000);
    return this.Celsius;
}
\end{lstlisting}
A workaround is to move initializers into separate methods and run
them before using the field in a constraint.

\paragraph{Local Variables.}
\label{sec:local-variables}
Some methods we encountered declared local variables to split up
calculations or name constants. For such methods, manual inlining of
the split up calculation into the return expression was required. The
original Babelsberg design explicitly allows such methods, as long as
the variables are used in static single assignment fashion
\cite{FelgentreffJOT14}.
\begin{lstlisting}[language=JavaScript,caption={A split-up calculation},label=lst:airPressure]
function pressure() {
   var gasConstantDryAir = 287.058, // J/(kg*K)
       density = 1.293, // kg/m^3
       entropyPerVol = gasConstantDryAir * density; // J/K/m^3
   return entropyPerVol * this.K / 1000;
}
\end{lstlisting}

\paragraph{Edit Constraints.}
\label{sec:edit-constraints}
Finally, our semantics does not include support for edit constraints
\cite{freeman1989deltablue,freeman1990incremental}, so existing
programs which use them do not currently work. Although incremental
solving through edit constraints provides performance benefits for
interactive applications, many of the interactive example programs in
Babelsberg/JS seem not to use them, or only use them in such a limited
fashion that refactoring to ordinary constraints was easily
possible. However, performance does suffer in the cases where we
removed edit constraints. A future goal for this semantics is thus to
include support for edit constraints that can be implemented in a
performant manner.

\section{Application to Related Work}
\label{sec:related-work}

There is a large number of related systems that integrate constraints
with imperative languages, ranging from \acp{dsl}, to constraint
satisfaction libraries, and to syntactic and semantic integration
similar to Babelsberg. How these systems choose to balance the power
of solvers and how aware the programmer needs to be of the solving
process differs greatly, as does their balance between how freely
programmers can express new constraints versus how aware they need to
be the fact that they are writing declarative code.

Kaleidoscope \cite{freeman1990kaleidoscope} was the first \ac{cip}
language to name some of the issues when integrating declarative
constraints with an imperative system that includes mutable state.
Kaleidoscope uses soft constraints to ensure that, in the absence of
other constraints, the solver does not change the values of existing
variables. Babelsberg adapted this and we have expressed it in our
semantics. In contrast to the semantics presented here, Kaleidoscope
separates methods that generate constraints from ordinary methods.
This avoids having to give rules for when a method may work
multi-directionally or only in the forward direction as we have
done. The disadvantage is that it puts the burden on the programmer to
develop and maintain two sets of interfaces, one for use in
constraints and one for use in imperative statements.

Kaleidoscope'93 \cite{lopez1994kaleidoscope} also adds support for
identity constraints, to express the distinction in object-oriented
languages between object equality and identity. However, the
Kaleidoscope system still allowed the solver to determine the identity
of method arguments when solving value constraints, and it used
multi-method dispatch to decide which methods to call in a constraint.
Both combined, while they gave the system much power, made it
sometimes hard in practice to understand which solution the system
might come up with. Babelsberg does not use multi-method dispatch,
removing one dimension of freedom from the solver. Furthermore, with
our semantics, the solver cannot change the identity or structure of
arguments for value constraints, because identities are fixed and
structure is typechecked before value constraints are interpreted. We
believe the same solution could be applied to the Kaleidoscope design.

Turtle \cite{grabmuller2004turtle} is a more recent \ac{cip} language
developed from scratch, while Kaplan \cite{koksal2012constraints} provides
constraints in Scala. Both separate the declaration of
``constrainable'' variables from ordinary variables to make it clearer
what may happen when a variable is used. Like Kaleidoscope, the Turtle
system provides constraint priorities, Kaplan, however, does
not. Because ordinary variables are not determined by the solver, only
constrainable variables have low-priority stay constraints on them in
Turtle. Also analogous to Kaleidoscope, both languages separate
constraint functions from ordinary functions. In Kaplan, only such
specifically annotated functions can be used in constraints. Turtle
does allow ordinary methods and variables to be used in constraints,
however --- their values are treated as constants, making all ordinary
methods work only in the forward direction. We believe the simple rules
for method inlining in our semantics could be used applied to these
systems as well to allow some ordinary object-oriented methods to be used in
constraints.

BackTalk \cite{pachet1995} and
\textsc{Squander} \cite{Squander} explicitly allow the constraint solver
to determine object structure, or even to create new objects that
satisfy a set of constraints. While these systems have many
differences, they are more similar to each other than to
Babelsberg. Both use object-oriented methods in constraints merely as
tests for the backtracking algorithm that tries different objects and
object structures as assignments for the involved variables. Thus, it
is in the nature of the system to allow what we prohibit. It is not a
problem in those systems, because the transition from declarative
variables to ordinary variables is explicit, so the programmer can
check for surprising results then.

Finally, $\alpha$Rby\cite{alloyRuby2014} is a language that embeds the
Alloy specification language
\cite{DBLP:journals/tosem/Jackson02} in Ruby. Its goal is to
allow Alloy users to easily pre- or post-process their models using
imperative libraries, for example to experiment with visualizations
for Alloy models. $\alpha$Rby translates Ruby programs into Alloy, but
the programs consist not of ordinary Ruby classes and
methods. Instead, they are written in a \ac{dsl} that closely mimics
the Alloy language. In contrast to Babelsberg, Alloy provides
imperative constructs to Alloy users, whereas Babelsberg provides
declarative constructs to object-oriented programmers.

\section{Conclusions and Future Work}
\label{sec:conclusions}

We have presented design principles to tame the power of the solver in
object-constraint programming languages to avoid surprising or
non-deterministic behavior. Our principles are expressed in an
executable natural semantics that preserves key properties of existing
object-constraint implementations, and we have modified one existing
implementation to follow our design, thus demonstrating its
practicality. Furthermore, we presented proof that the typing rules
for constraints we give as part of our semantics remove
non-determinism and surprising behavior, in that they never allow the
solver to find solutions that would add or remove fields from existing
objects. Additionally, our rules define that the only way for a
variable to change its structure is through an assignment statement --
thus, solving constraints outside of an assignment can never lead to
solutions where variables change their types.

The semantics given here defines a useful subset of the language. A
full object-constraint language that supports standard classes and
methods is given in a companion technical report. It includes formal
rules for defining constraints on the results of message sends that
implement our informal description in
\autoref{sec:transl-multi-way}. Its restrictions are easy to
understand, but may be too conservative. One avenue for future work
will be to allow somewhat more general kinds of expressions in methods
called from constraints to be used multi-directionally.

We also present a mechanism to generate a test suite from the
executable semantics that can be run against the
implementations. Another avenue for future work is to use this test
suite to move the implementations closer to conforming with the
semantics.

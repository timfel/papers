\begin{abstract}
  % Context
  Imperative object-oriented programming languages are ill-suited to
  describe constraints between objects. They require programmers to
  maintain the constraints explicitely through assignments and control
  flow scattered throughout the code, rather than declare them in one
  place. For some specific problem domains---such as graphical
  layouting or musical harmonization ---specialized constraint
  libraries provide solutions to this issue. For general purpose
  applications, constraint-oriented extensions to imperative languages
  have been explored.

  % Problem
  However, current approaches result in unsatisfactory trade-offs
  between constraint-oriented and object-oriented programming. They
  either violate object encapsulation by defining constraints only on
  state, do not integrate constraint solving and the object-oriented
  behavior definition into one language, and/or are limited to
  specific domains. Consequently, current approaches increase coupling
  in the system, duplicate definitions of relations across behavior as
  well as constraint-expressions, and/or are not directly reuseable
  for new domains.

  % Solution
  We present an extension to an object-oriented language that allows
  developers to apply constraints to complex objects and the results
  of message sends to them. Our approach preserves encapsulation and
  re-uses the existing object-oriented method definitions for the
  constraint declarations. Our system can deal with constraints on
  complex objects (by automatically destructuring them) and provides
  extension points so users can define specialized constraint solvers
  for specific domains.
  % Constraints are re-useable on objects that respond to the same messages.
  % Constraints appear in various domains (esp. modeling real-world behaviour?)
  % object-oriented languages are widespread for implementation of many of these domains
  % they have no good support for constraints
  %    constraint extensions to imperative languages tried to address this problem
  %    they either:
  %        - violate/ignore encapsulation by using path specifiers
  %        - only support constraints within one objects' primitive state
  %        - require a different kind of method definition
  %    we provide seamless application to constraints on objects and the results of
  %    their methods, our constraint system uses the message sending mechanism of
  %    the OO paradigm and cannot look inside objects
\end{abstract}

\section{Introduction}

In a number of domains, such as graphical layouting, musical
harmonization, or product lines, acceptable program behavior is
partially specified in terms of constraints~\todo{cite}. (Specifically
in domains that have an acceptability envelope\todo{cite} or need to
optimize values based on competing inputs, constraint solving is a
natural fit.)  Such constraints may be invariants or (in-)equalities,
for example minimum and maximum distances between visible elements in
a layout that have to be considered when resizing~\todo{citeosx}, or
correspondence between the contents of a file, the display, and a
programmatic value.

Constraints are difficult to express in purely imperative
object-oriented programming languages~\todo{cite}. Programmers satisfy
declarative constraints using tests, branching, and destructive
assignment. In the case of temporal constraints, constraint checking
is a cross-cutting concern and programmers have to structure control
flow so the constraints can be re-checked whenever they may have been
invalidated~\todo{cite}. There are two problems with this approach:
\begin{enumerate}
\item Explicitely solving constraint satisfaction problems using
  imperative code may not find an optimal solution or may not find a
  solution even if one exists. Constraint solving between two objects
  is bidirectional~\todo{cite}, but typical change propagation
  approaches using observers~\todo{cite} or pointcuts~\todo{cite}
  requires programmers to explicitely break cycles or only solve
  constraints unidirectionally.
\item Aspects can only capture one dimension of this cross-cutting
  concern. Constraints cross-cut both across control flow and data
  structures. Aspects can capture control flow cross-cutting and
  preserve encapsulation, but support code for constraint satisfaction
  code still has to be scattered across all classes that participate
  in constraints. If encapsulation is ignored to modularize constraint
  satisfaction, tight coupling is introduced between the constraint
  satisfaction module and the rest of the system.
\end{enumerate}

(Programmers can solve the first problem by using constraint solver
libraries~\todo{cite} if their problem can be expressed in the domain
of a solver. However, explicit use of constraint libraries requires
copying state between program and solver and still requires triggers
throughout the program to copy that state as required and re-solve the
constraints. Runtimes with built-in solvers can automatically re-solve
constraints, but only for the domains supported by the built-in
solver.)

\section{Background}

Constraints as we understand them in this paper are assertions about
relations between objects that are maintained by the runtime. Such
assertions may be (in-)equalities between objects or their parts, as
well as assertions about the results of message sends.

Assertions in imperative programming follow the principle to fail
early after undesirable program state has
occurred~\todo{cite}. However, it is often possible to correct the
faulty program state, in which case the program should correct itself
and continue running rather than stop~\todo{cite rinard}. Replacing
assertions with constraints, undesirable program states can be
corrected by the runtime.

In this section, we will explore the related approaches to constraint
solving in imperative languages in more detail.

\subsection{Constraint Solver Libaries}
When realizing they are dealing with a constraint problem, programmers
may choose to include a constraint solver library in their
program. (Examples of solvers with implementations or bindings in a
variety of languages are Cassowary~\todo{cite}, DeltaBlue~\todo{cite},
or Z${}^3$~\todo{cite}.)

This approach requires programmers to express assertions about the
system in terms of a ``primitive'' domain (i.e. reals, booleans,
uninterpreted function symbols) the solver understands. If the program
constraints can be expressed in such terms and a solver library is
available, programmers can replace their assertions with calls to the
constraint solver, and only fail if no solution to the constraint
system is available. (Beispiel)

Advantages of this approach include:
\begin{itemize}
\item free choice of constraint solvers allows programmers to choose
  based on desired properties such as constraint hierarchies, support
  for multiple domains, or performance
\item constraints are bidirectional by default
\item multiple solvers can be used in different parts of the program
  easily
\end{itemize}

In practice however, constraint libraries are often not used, because
of a number of disadvantages:
\begin{itemize}
\item no general solver over multiple domains that is also fast~\todo{cite}
\item solvers do not support complex objects, so programmers have to
  destructure their objects manually and break encapsulation
\item the solver state is not integrated with the object-oriented
  state, so variables have to be copied between the two
  repeatedly. This problem multiplies if more than one solver is used.
\end{itemize}

\subsubsection{Domain-specific Languages for Constraints}
For specialized domains such as user interface layouting, constraints
are available as separate \textsc{dsl}s that describe relations
between visible objects that can be automatically maintained by the
runtime. Examples of such \textsc{dsl}s are \textsc{css}~\todo{cite}
and the \textsc{mac os x} layout specification language, both of which
allow programmers to express relations such as minimum and maximum
distances between objects, parent/child relationships, or alternative
presentations depending on available display space. These constraints
are automatically re-satisfied by the runtime when imperative code
changes the user interface. However, because the constraints are
specified in separate languages, they are hard to reason about in
imperative code, and it is possible to write imperative code that will
interfere with the layout engine. Furthermore, constraint
\textsc{dsl}s such as these only work for specialized domains and on
few objects used in the imperative program.
 
\subsubsection{DataFlow Constraint Languages}
Some languages have built-in support for data flow, which allows
programmers to express unidirectional constraints between objects and
their parts. Examples of such systems are ThingLab~\todo{cite},
Scratch~\todo{cite}, or the LivelyKernel/Webwerkstatt~\todo{cite}. Of
these, only ThingLab includes a planner for propagation that breaks
cycles automatically. In the other two systems the programmer has to
break cycles explicitely.

In these systems, programmers can directly express relations between
objects and parts of objects. For each constrained relation there
exists a function that maintains it~\todo{cite}, and on each change to
an object, that function is triggered with the old and new state and
can decide how to change the downstream object to still satisfy the
constraint.

Although these systems are not constraint solvers, programmers can use
constraint solvers in the function that maintains the relation. This
solves the question when to trigger copying state and constraint
solving. However, because the relations are binary and
uni-directional, conflicting constraints as for example in \emph{n:m}
relations cannot be satisfied in these systems, because the later
change simply overrides the previous. (Beispiel)

\subsection{Constraint-Imperative Programming}

The family of \ac{cip} languages tried to address the aformentioned
issues~\todo{cite}. Problems with this approach are specific to the
trade-offs each language made between object-orientation and
constraint programming, but some problems occur for all languages of
this type.

- integration of solver with imperative language
- Turtle, Kaleidoscope, Java-dingens, C++ constraint dingens, BackTalk
- Advantages:
  - nice semantics (value-streams -> see FRP, time, assignment as one-time constraint)
  - automatic management of solver variables
  - automatic re-solving of constraints
  - semi-automatic constraints for complex objects

\emph{Encapsulation is violated}, either because constraints can only
be applied to the primitive leaves of explicitly stated object
paths~\todo{cite} or because programmers have to expose the structure
of their domain objects to the runtime before they can be used in
constraints~\todo{cite}. (Beispiel?) In either case, the runtime
modifies parts of an object directly.

A result of this problem is that \ac{cip} languages have to make state
accessible from the outside. Table~\ref{tab:cmp-ocp-cip} shows how
this limits these languages.

In \emph{type I} object-oriented languages such as Smalltalk or Ruby,
object state is always private and cannot (without meta-programming)
be modified from the outside. So to apply \ac{cip} to those languages,
they have to be changed to allow access to object state. (either by the
programmer (to state object paths for constraints) or by the
constraint solver (to modify the state directly).)

In \emph{type II} languages such as, for example, Java or JavaScript
outside access to state can be allowed, so these languages can be used
for \ac{cip} directly. However, even in those languages direct access
to object state is discouraged as it increases coupling in the system.

In \ac{ocp}, however, constraints can be specified on the results of
normal object-oriented message sends. This means that both type I and
type II languages can be used with \ac{ocp} directly.

\emph{Behavior is duplicated} in some \ac{cip} languages as they
require developers to add \emph{constraint-method definitions} to
their objects before they can be used in constraints, possibly
duplicating behavior so it can be used in both
paradigms~\todo{cite}.

\emph{Predetermined solvers} integrated into the runtime means that
programmers cannot choose a solver that may be more appropriate for
the problem domain, or explicitly use different solvers for different
parts of the program.

\section{Contribution: Object-Constraint Programming}
We propose an integration of constraint-solvers with \ac{oo} languages
that we call \emph{\ac{ocp}}. (based on Ruby...)

Three goals have guided us in creating this language:
\begin{enumerate}
\item[Unchanged \ac{oo} semantics] We have not changed the execution
  semantics of the underlying \ac{oo} language. The integration of
  constraint-oriented programming consists solely of an additional
  primitive. The \ac{oo} runtime has an \emph{object view} on its data
  that consists only of objects with state and behavior.
\item[Constraints specified using \ac{oo} interface] A constraint
  declaration in our system is an expression passed to a primitive
  method unevaluated in form of a anonymous function closure. That
  closure is executed immediately in the \emph{constraint
    interpreter}. The constraint interpreter executes the code as
  normal \ac{oo} code, but, during execution, constructs a
  \emph{constraint view} for the solvers.

  To construct the constraint view, variables encountered during the
  execution are replaced by the interpreter with their solver variable
  counterparts. If no solver is active in the system that can work
  with the variable encountered, that variable is replaced with a
  placeholder constraint variable that delegates to the original
  object, but serves as a placeholder for constraint invalidation.

  The constraint view is complete when the anonymous function
  returns. The constraint view then consists of a number of a)
  primitive values that are in the domain of the solver and are
  connected in a constrainable way (e.g. through in/equalities,
  arithmetic, boolean logic) and b) a number of complex objects that
  are constrained to their identity.

  The solver operates on this view directly to solve the
  constraint. Changes made by the solver to the variables show up in
  the \ac{oo} view.

  When imperative code changes a primitive value in that appears in
  this view (for example through assignment~\todo{cite kaleidoscope}),
  that change triggers the solver to re-satisfy the constraint.

  When imperative code changes a complex value that is constrained to
  its identity, all constraints asserted based on this value are
  removed from the solver, and the constraint expression is
  automatically re-evaluated to assert new constraints ... here we
  need the example with the arch point
\end{enumerate}

\section{Implementation}
- pypy is ..., topaz is ..., topaz architecture

modes:
  - normal execution
    LOAD\_* -> check if constrainted variable -> get value from solver
    STORE\_* -> check if constrainted variable
               a) is associated with a solver: suggest\_value
               b) was on the path during constraint construction:
                  - get constraint block for this variable
                  - disable all constraints that got created during
                    execution of the constraint block
                  - re-execution constraint block to build new constraints
  - constraint construction
    LOAD\_* -> create constraint variable for the storage cell
              a) new constraint variable associated with solver
                 -> continue working with that (all sends go to the solver variable)
              b) new constraint variable is not assiciated (only on the path)
                 -> store currently executing constraint block on constraint variable
                 -> work with the value as in normal execution
    JUMP\_AND -> enable left-hand side (if a constraint)
             -> continue working on rhs
    ... (could add more, JUMP\_IF, JUMP\_OR ...)
  - constraint execution
    ... special mode we execute the solver/suggest\_value in (in case it is
    written in Ruby, this musn't enter any of the other modes)

- thoughts on implementation:
  - normal execution changes should be aspects that come with the language extension
    (role is basically to observe variable access)
  - constraint construction/execution should be a COP layer

  - Constraints module exposes ObjSpace interface
  - ConstraintObject is marker superclass to ``seal'' solver implementations
  - ConstraintVariable is attached to (locals, ivars, cvars)
    - triggers the specific ``solve'' on STORE and ``set!'' on LOAD

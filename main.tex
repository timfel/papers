\section{Introduction}
\label{sec:introduction}

\ac{ocp} integrates constraint satisfaction with common
imperative and object-oriented features.  
% in its Babelsberg incarnation, inherits many properties from the
% earlier Kaleidoscope \cite{lopez1994kaleidoscope} and Turtle
% \cite{grabmuller2004turtle} constraint imperative programming
% languages, as well as constraint systems such as BackTalk
% \cite{pachet1995}, Kaplan \cite{koksal2012constraints}, and Squander
% \cite{Squander}. 
It is motivated by the observation that a number of
key aspects of interactive applications can be concisely specified
using constraints, but that other aspects are more easily specified
using standard imperative constructs (assignment, loops, and so
forth).  Its goal is to provide both paradigms in a cleanly integrated
fashion, within an object-oriented framework that respects standard
object-oriented features such as messages, encapsulation, and
inheritance.

Experience with \ac{ocp} systems has shown that the solutions to a number of
important problems involve constraints that include mutable objects,
object identity, and message sends. These have the potential for
surprising solutions and non-determinism. If a constraint references a
field that does not exist on an object, should the solver be allowed
to add it? If a constraint requires two variables to refer to the same
object, which variable should be changed? Can methods be used in
constraints?  If so, can they only be used in the ``forward''
direction, to compute a result, or can the solver also use them as
multi-directional constraints?

In this paper we propose a set of design principles to answer these
questions, along with a set of restrictions on the behavior of
\ac{ocp} systems that enforce these principles.  These principles and
restrictions are as follows:
\begin{itemize}
\begin{sloppypar}
\item {\em Structure preservation}: Asserted constraints cannot change
  the structure of any objects.  This property is enforced through a
  form of dynamic structural typechecking, along with extra constraints
  that implement frame axioms.
\todo{Is this rewording ok?  Was ``enforce a frame condition'' --
  ``enforce'' seemed strange to me, since we aren't enforcing these
  constraints (they are soft).}
\end{sloppypar}

\item {\em Identity preservation}: Similarly, adding a constraint
  cannot change the identity of the object stored in a particular
  variable.  This property is enforced by requiring
  constraints on object identity to already be satisfied at the point where they are
  asserted.

\item {\em Structural/identity determinism}:  The structure of objects
  and the identities of objects stored in variables \emph{can}
  change through imperative updates that cause existing constraints to
  be re-solved, but the results are deterministic.  This
  property is enforced through a novel two-phase solving process that first
  deterministically solves identity constraints and then solves the remaining constraints in the
  resulting environment and heap.

\item {\em Syntactic method rules}:  A simple syntactic check suffices
  to determine whether and how a method can be used within constraints.
  In short, methods with side effects (writes other than to local
  variables) cannot be used in constraints.  Other methods whose
  bodies simply compute and return an expression can be used
  multi-directionally in constraints, while the remaining methods can
  be used just in the forward direction.
\end{itemize}

We have instantiated our approach in the context of the Babelsberg
object-constraint language, but the ideas are applicable to such
languages in general.  Indeed, Babelsberg
 inherits the described issues (as well as its overall approach) from the
earlier Kaleidoscope \cite{lopez1994kaleidoscope} and Turtle
\cite{grabmuller2004turtle} constraint imperative programming
languages, and our approach is also useful for constraint systems such as BackTalk
\cite{pachet1995}, Kaplan \cite{koksal2012constraints}, and Squander
\cite{Squander} (see Section~\ref{sec:related-work}).

We describe our approach informally (\autoref{sec:example-programs}) and have evaluated it in several
ways.  First, we have formalized the approach in a
core subset of Babelsberg and proven that it satisfies some key
properties (\autoref{sec:semantics}).  Second, we have developed 
an executable version of our formal semantics to automatically verify a
  suite of example programs, including ones that illustrate the problems we address.
On top of this executable semantics, we have also built a framework
  to generate language test suites from our suite of example programs, to facilitate
  automatically testing Babelsberg implementations for conformance to
  this semantics.
Finally, we have created an updated version of the Babelsberg/JS
implementation using our approach, have verified that it conforms to
the formal semantics on the suite of example programs, and describe
our experience porting existing
  Babelsberg/JS applications to our new version (\autoref{sec:evaluation}).

\section{Ruling Out Surprising Solutions}
\label{sec:example-programs}

Babelsberg, which we will use for our discussion, is a family of
object-constraint languages, with current instances being Babelsberg/R
(a Ruby extension) \cite{FelgentreffJOT14}, Babelsberg/JS (a
\javascript extension) \cite{FelgentreffECOOP14}, and Babelsberg/S (a
Squeak extension) \cite{GraberREBLS2014}. Babelsberg is a recent
\ac{ocp} system which allows developers much freedom in how
constraints can be employed. However, experience with the design has
shown that interactions between the object-oriented core and
constraints could be difficult to understand.  In prior versions of
the language, it was easy to formulate constraints that allowed the
system to come up with surprising solutions, or no solutions at all ---
they would need to be formulated differently for the
translation from imperative code to constraints to work as
intended.

In Babelsberg, the details of the underlying solvers are abstracted so
that constraints can be handed to a number of different solvers, including
ones that can then cooperate to find solutions. We will use Babelsberg/JS for
the code (\ie \javascript syntax).  Babelsberg/JS provides the keyword
labels \verb!always! and \verb!once! to declare constraints on the
return values of ordinary object-oriented expressions and solve them
immediately. An \verb!always!  constraint then holds for the rest of
the execution, whereas a \verb!once!  constraint is redacted after
being solved one time.

This section consists of two parts: the first presents how we restrict
the power of the solver to be deterministic with regards to object
structure and identity. The second part presents how we restrict the
translation from object-oriented methods to constraints to avoid edge
cases and give simple rules for programmers to follow when they define
constraints.

\subsection{Non-determinism in Structure and Identity}
\label{sec:no-non-determinism}

At the core of our design is the idea that the solver determines the
entire heap and environment after each statement. However, for an
imperative programmer it would be surprising if objects unnecessarily
lose or gain fields, if variables change more than they have to, or
non-deterministically change their identity --- the solver should
always pick a solution that is ``close'' to the current state of the
system. To address this problem, we define a set of restrictions on
the language, which result in taming the power of the constraint
solver and ruling out a significant number of such solutions. First,
we use a form of structural typechecking at run time before constraint
solving to ensure that object-structure cannot be modified by the
solver. Second, we only allow changes to object identity to flow from
imperative assignment statements, rather than be determined as part of
the solving process. And third, we implicitly add a low priority
``stay'' constraint to each variable, so that its value only changes
if required by some higher-priority constraint.\footnote{The
  formulation of the first two restrictions is new in this work; the
  third has been present in Babelsberg since the original language
  definition, as well as in the earlier Kaleidoscope design.}

\subsubsection{Object Structure}
\label{sec:object-structure}

As an example to illustrate the non-deterministic and surprising
behavior that can arise when using constraints involving objects with
mutable structure, consider a bank account application in which we
want to prevent changes that would make the account balance drop below
a certain threshold. Additionally, we want to track the daily
interest, but not allow it to rise above 10 euros.  (This example is
simple enough that we can show the listing easily, but is designed to
illustrate some complexities around object identity, as well as
constraint features such as soft constraints and read-only annotations
on variables.)
\begin{lstlisting}[language=JavaScript,caption={~},label=lst:account]
var acc = new Account(), minBal = 100, dailyInterest = 0;
always: { acc.balance >= minBal? }
always: { priority: "medium"
          dailyInterest == (acc.balance? * 0.01) / 365.0 }
always: { dailyInterest <= 10 }
\end{lstlisting}

The desired semantics is that the solver will ensure that
\verb!acc.balance! remains at least \verb!minBal! after line 2. The
read-only annotation on \verb!minBal! (indicated by the question mark)
prevents the solver from changing it to satisfy the constraint. Thus,
any change to the account that would drop the result of
\verb!acc.balance! below \verb!minBal! is rejected by the
system. Conversely, the system is not allowed to change the result of
\verb!acc.balance! to satisfy the second constraint. The daily
interest is always determined from the current balance, but not vice
versa. Note also that we assign a priority to the second
constraint. This tells the system that it should satisfy this relation
if possible, but it is no error not to do so. Due to the third
constraint, if the daily interest were to rise above 10, the system
can leave the second constraint unsatisfied.

Consider the constraint on the \verb!balance! field on line 2. In the
absence of other restrictions, we discovered that Babelsberg as well
as earlier systems that integrate constraints and objects would
sometimes find unintuitive solutions that the human programmer did not
even consider. For example, we intuitively expect the solver to reason
about the balance of the newly created \verb!Account!
object. However, in the absence other restrictions nothing prevents
the solver from considering other solutions:
\begin{inparaenum}[i)]
\item If the \verb!Account! class has no \verb!balance! field, should
  the solver invent a balance field and constrain it? May it then
  remove fields from the account that are not mentioned in the
  constraint?
\item Can the solver change the variable \verb!acc! to point to
  another object that has a balance field with the right value?
\item Finally, if the constraint is already satisfied, is the solver
  allowed to make the balance equal to \verb!minimum!, as this would
  also satisfy the constraint?
\end{inparaenum}

These solutions are clearly undesired: imperative programmers do not
expect the identity or the object structure of the \verb!acc!
variable to change. Neither do they expect the property to change if
the constraint is already satisfied. Yet it is inconvenient to have to
add constraints to prohibit all these solutions. To avoid these
undesired solutions, we add the following restrictions to our design:
\begin{enumerate}[a)]
\item We use a non-standard form of \emph{structural type-checking} at
  run-time before sending constraints to the solver. Our checks
  dynamically assert that field accesses occur only on objects (and
  not primitive values), and that those objects have the necessary
  fields. These assertions, unlike constraints, are only checked ---
  if one is violated it is an error and the constraint solving
  fails. The programmer must ensure that objects used in constraints
  have all the referenced fields. This intentionally restricts the
  power of the constraints in support of our goal of integrating
  constraints with an object-oriented language in a way that reflects
  the expectations of imperative programmers.
\item We furthermore add implicit constraints on the structure of each
  object that is sent to the solver to have the exact same fields,
  thus forcing the solver to keep the object structure, once our
  type-checks have determined the constraint to be valid.
\item Finally, as in Kaleidoscope, Babelsberg adds implicit {\tt weak}
  stay constraints to each variable and field to keep it at its
  current value, if possible. This satisfies the desire that the
  solver should not change a variable if no constraint on it is
  violated.
\end{enumerate}

\subsubsection{Object Identity}
\label{sec:determ-object-ident}

Another issue in the design of an object-constraint language is the
interaction between constraints and object identity.  Object identity
plays an essential role when using an object-oriented language to
model aspects of the real world and so, in a language that integrates
constraints with object-oriented features, we need to resolve the
tensions between these fundamental features \cite{lopez-ecoop-1994}.
Additionally, making explicit identity constraints available to the
programmer allows for useful capabilities such as specifying that two
variables refer to the same identical object, or describing circular
structures.  However, experience with Kaleidoscope in particular
suggests that allowing powerful constraints on object identity and
types can lead to non-obvious consequences. As an example, consider
the following program:

\begin{lstlisting}[language=JavaScript,caption={~},label=lst:identity]
var account1 = {credit: 10}, account2 = {debit: 100};
always: { account1 === account2 }
account1.withdraw(1);
always: { account1.debit >= 0 }
\end{lstlisting}

This adds a constraint on line 2 that \verb!account1! and
\verb!account2! be identical. However, it is not clear if
\verb!account1! and \verb!account2! will afterwards refer to an
account with a debit balance or an account with a credit balance (or both,
or neither).  It is thus not clear which account we withdraw from in line
3, or even if this variable still refers to an account object --- in
the absence of suitable restrictions, the
solver might throw up its hands and set both variables to
\verb|null|.  Assuming we prefer solutions that change as few
variables as possible, both \verb!account1! and \verb!account2! might
refer to a credit account after line 2 is executed. In that case the
constraint on line 4 would not be structurally valid, because no
\verb!debit!  field exists on a credit account. If we let the solver
change identities to satisfy the constraint on line 4, we may have
withdrawn from the credit account and then asserted that the debit
account be above 0. The non-deterministic choice of identity would
thus give rise to multiple possible meanings for the rest of the
program, making it harder to reason about.

To tame the power of constraints on object identity, we set the
following goals for this aspect of our design:
\begin{enumerate}[a)]
\item Constraints on object identity must be declared explicitly using
  the identity test from the host language (\verb!===! in the case of
  \javascript). They cannot be hidden within another method.
\item\label{item:deterministic} The solution to the constraints is
  deterministic as far as object identity is concerned --- there
  should never be multiple correct solutions in which a given variable
  refers to objects with different identities in the different
  solutions. Thus, the programmer must first ensure the identity
  constraint is already satisfied before asserting it.
\item Any change to the identities of the objects referred to by
  variables can only flow from an assignment statement --- the
  constraint solver may not otherwise alter object identities.
\item To make Babelsberg programs more understandable for programmers,
  the identities of objects in value constraints should be clear. We
  thus first solve all the identity constraints (with a deterministic
  solution, in keeping with goal \ref{item:deterministic}), and then
  the value constraints. In the second step, identities are fixed, and
  thus method lookup follows regular object-oriented semantics. This
  requires all identity constraints to be declared separately from
  value constraints.% We
  % disallow non-required identity constraints, to avoid having to
  % backtrack when solving value constraints (or otherwise
  % non-deterministically failing).
\end{enumerate}

To preview the results of our rules, the program in
\autoref{lst:identity} would then be illegal, since the identity
constraint \verb|account1 === account2| is not satisfied at the time it
is asserted. If the programmer uses an assignment to first make both
\verb|account1| and \verb|account2| refer to the debit account, the
program succeeds; if the programmer makes them refer to the credit
account, it halts with a structural compatibility check error.  In
either case it becomes deterministic and straightforward to reason
about.

\subsection{Clear Rules for Writing Valid Constraints}
\label{sec:rules-constr-expr}

Another issue is that programmers need to be aware of certain
restrictions on how methods can be used in constraints. Kaleidoscope
and Turtle distinguish imperative and declarative behavior definitions
that are used depending on whether an object is used in an imperative
or a declarative context. This means that programmers have to consider
both interfaces of an object, depending on what they want to
express.  Babelsberg unifies these definitions, allowing the
programmer to express constraints directly using imperative
methods. However, this creates a different set of problems, as not all
methods work equally well in constraints.

In Babelsberg, constraints are ordinary expressions in the host
language that evaluate to a boolean --- the constraint being that they
evaluate to true.  In our semantics, we have rules to translate these
expressions into constraints.  Our translation process traces through
methods and effectively unrolls loops, prunes branches, and inlines
method bodies.

%% WAS: ordinary imperative expressions - removed the word imperative
%% since they are side-effect-free and ``imperative'' seems confusing
%% in that context

In prior work, the restrictions on constraint expressions, and
the rules to translate expressions into constraints, evolved alongside
the existing implementations, driven in part by practical
considerations about the expectations of programmers familiar with the
underlying host language. These rules were originally defined as:
\begin{inparaenum}[1)]
\item\label{item:ssa} if there are assignments, variables assigned to
  must be used in \ac{ssa} form,
\item the constraint expression should either be free of side effects,
  or if there are side effects, they should be benign, and
\item repeatedly evaluating the constraint expression should return
  the same result, so a method that returns the current system time
  would not qualify.
\end{inparaenum}
In practice, it was not clear which constructs follow these rules, or
what constitutes ``benign'' side effects. The
implementations also vary slightly in their wording of the rules, and
rule \ref{item:ssa} in particular was omitted for Babelsberg/JS.

In the work reported here, we have developed and formalized a set of
restrictions on constraint expressions, which also makes them amenable
to use in proofs.  They are as follows.
\begin{inparaenum}
\item[First,] if the method consists solely of a single return
  statement (for example, returning with an expression that is a calculation on the
  object's fields) it can work multi-directionally.
\item[Second,] if a method has any statements before returning, it can
  only be used in the forward direction.
\item[Third,] if the method has any side effects, such as writing to a
  non-local location or generating a random number, it cannot be used
  in a constraint in any direction.
\end{inparaenum}

These restrictions are stronger than the earlier versions.  They do
allow us to express a wide range of useful programs, but we suspect we
can do better, and a direction for future work
(\autoref{sec:conclusion}) is to relax some of them while still
retaining clarity and precision.

\subsubsection{One-Way and Multi-Way Constraints}
\label{sec:transl-multi-way}

To illustrate this aspect of the restrictions,
suppose that we want to express the
requirement that a window in a graphical application stay centered on
a particular point.  This constraint can then be defined as:
\begin{lstlisting}[language=JavaScript,caption={~},label=lst:window]
var window = new Window(0,0,100,100);
always: { window.getCenter().equalsPoint(Point(150,150)) }
\end{lstlisting}

After running this code, the system should ensure that the window is
centered on the point $(150,150)$. If it is resized or dragged by the
title bar, the system will either adjust other parts of the window to
keep the center at the desired position, or, if that is not possible,
prevent the interaction. It does not matter if \verb!getCenter!  is
just an accessor or a calculated property; in either case, Babelsberg
traces into the method and creates the correct relations between the
actual parts of the window and the point.

Consider the implementation of the \verb!getCenter! method in
\autoref{lst:window}. A simple implementation may be the following:
\begin{lstlisting}[language=JavaScript,caption={~},label=lst:simpleGetCenter]
function getCenter() {
    return Point(
            this.topLeft.x + this.width / 2,
            this.topLeft.y + this.height / 2
    );
}
\end{lstlisting}
The above code has only a simple return statement. The center is
computed from fields, and the systems can solve a constraint involving
this method multi-directionally, that is, it can modify any or all of the
\verb!topLeft!, \verb!width!, and \verb!height! properties of the window to
satisfy the constraint. However consider this alternate implementation:
\begin{lstlisting}[language=JavaScript,caption={~},label=lst:otherGetCenter]
function getCenter() {
    var center = // ... previous code
    if (this.isScaled) {
        center.x = center.x / this.scale;
        center.y = center.y / this.scale;
    }
    return center;
}
\end{lstlisting}
Here, it is difficult to judge which fields the solver would modify to
satisfy the constraint. Besides changing \verb!topLeft!, \verb!width!,
or \verb!height!, the solver might decide to scale the window to keep
the constraint satisfied. In practice, we have found this to lead to
hard to predict solutions.

We impose a simple rule that methods that contain more than a return
statement can only be used in the forward direction, which means that
the result from the method can be used to determine a variable, but
the variable cannot change any variables that participate in creating
said result. This includes methods with multiple assignments, which
removes the earlier rule that variables assigned to in constraints
must be used in \ac{ssa} form. Such methods can still be called in the
usual way, including passing parameters by value (with pointer
semantics for heap objects). Thus, the second implementation of
\verb!getCenter! will not work multi-directionally, and constraint
satisfaction will fail for \autoref{lst:window}, unless the constraint
is already satisfied.

In the semantics, to support methods that can be used
multi-directionally, we create an environment for the activation of
the method and inline
the returned expression with respect to that environment. The
parameters in that environment are constrained to be identical to
their respective argument expressions, and \verb|self| is constrained
to be identical to the receiver of the message. All constraints
created through this transformation are then passed to the solver
simultaneously.

\subsubsection{No Side Effects in Constraints}
\label{sec:no-side-effects}

Our rules prevent the programmer from asserting constraints that have
non-benign side effects. We define ``non-benign'' here as side effects
that change the value of existing variables that are visible after the
constraint expression returns (rather than just creating new temporary
variables), the creation of new objects where identity and equality
are not the same (because these could be discerned by identity in
languages that allow reflection on the heap), or system calls other
than ones that return a constant value
(for example calls to a random number generator or the clock).

A particularly tricky issue relates to creating new objects in
constraint expressions.  This is
problematic when the identity of the newly created object could be
significant (see above); yet we found numerous useful examples that involved
creating simple objects such as points and rectangles in constraint
expressions.  To resolve this issue, we add the concept of \emph{value
  classes} to Babelsberg.  Instances of these classes are immutable
after creation, and object identity is not significant for them.  An
example of a value class is the \verb!Point! constructor used in
\autoref{lst:window}.  However, value classes are more than simple
records, since they support methods and inheritance.  A number of
existing languages support or have proposals for forms of value classes, for example
Scala\footnote{\url{http://docs.scala-lang.org/sips/completed/value-classes.html}}
and Java\footnote{\url{http://openjdk.java.net/jeps/169}}.

%% whereas it's just a proposal in Java.

For practical implementations in which the host language does not
support value classes, we can allow the creation of instances of
ordinary classes, and provide conventions for developers to follow
regarding object creation, modification, and when it is permissible to
test for object identity.

Consider again the \verb!getCenter! method. If the calculation of the
center were expensive, the method might also cache that calculation for
faster retrieval. Regardless, the programmer expects the system to
adjust appropriate parts of the window that contribute to the result
of \verb!getCenter! so that the center stays at $(150,150)$. If the
system fails to satisfy the constraint, it may not be clear to the
programmer which of the operations --- the check for cache
invalidation, storing the result, or the calculation itself --- does
not work as part of the constraint. In such cases the system may
generate a run-time exception to help the programmer better understand
the problem. However, this does not always work reliably (especially
in situations involving side-effects), and the system might continue
running based on an incorrect solution.

Earlier work on Babelsberg enumerated a set of informal rules describing when
an expression could be used in the definition of a constraint. However, there
were some confusing edge cases involving object identity and
constraints, and regarding when methods called from a constraint
expression could be used multi-directionally, \ie to determine all
variables involved in a constraint, versus when system could only
determine one distinguished variable given the values of all others, 
in a data-flow manner (\cf{\autoref{sec:transl-multi-way}}).

\section{Formalism}
\label{sec:semantics}

A goal of this work is to clarify design decisions of Babelsberg to
guide language users and implementers.  However, it is not intended to
be a complete description of a practical object-constraint language,
and we omit aspects of the language that are inherited from the host
language and that are not core to the interaction between constraints
and object-oriented programming, such as class and method definitions,
exception handling, and \textsc{IO}.

For our semantics we use a simple language, called Babelsberg/UID,
that includes primitive types (ints, reals, booleans, and strings), as
well as mutable objects that live on the heap and immutable objects on
the stack. A guiding principle in our design has been to adhere to the
original goal of Babelsberg: in the absence of constraints, it should
behave like a standard imperative language. We focus on how imperative
constructs need to be modified to support the Babelsberg design. Where
there is a choice, we aim to make the smallest possible changes while
still accommodating constraints in a clean and powerful way. Beyond
this, we favor simplicity of the rules over support for interesting
features that are rarely used in practice. The semantics for this
language, although not object-oriented, illustrates our key
contributions. Extending it to include all the essential features of
the actual object-constraint languages, including support for classes,
methods, messages, and inheritance, along with constraint definitions
that can include polymorphic method calls, is straightforward, and we
present this extension in a companion technical report
\cite{felgentreff:2014:semantics}.

In addition to the imperative semantics, after every statement
execution the current set of constraints is solved and the environment
and heap are replaced with the solution.  The current set of
constraints is determined as follows.  
For assignments, we evaluate the right-hand side and then create a
constraint that the resulting value and the left-hand side be
identical. Otherwise the statement is just executed. In addition to any
constraint resulting from an assignment statement, each constraint in
the current set of constraints (e.g, a constraint from an explicit
\verb|always| statement, or from an implicit {\tt weak} stay) is given to
the solver.  If the solver finds a solution, the environment and heap
are replaced by the model the solver found; if the constraints have no
solution (or they are too hard), the execution halts. In practical
languages, a run-time exception would be generated and the heap and
environment remain unchanged.

The semantics treats the solver as a black box, but we assume it
supports our primitive types, records, and uninterpreted functions,
as well as hard and soft constraints and read-only variables
\cite{borning1992constraint}. The solver should find a single best solution ---
if there are multiple solutions, it is free to pick any one of
them.
% Providing answers rather than solutions, \ie results such as
% $10 \leq x \leq 20$ rather than a single value for $x$, and
% backtracking among multiple answers, as available in for example
% constraint logic programming \cite{jaffar-popl-1987}, is left for
% future work.

\subsection{Syntax}

% \vskip\baselineskip\noindent
We use the following syntax for Babelsberg/UID:
\vskip0.5\baselineskip\noindent
{\ttfamily
\begin{tabular}{lrrl}
{\rm Statement} & s & ::= & skip $\mid$ s;s \\
  & & $\mid$ & L := e $\mid$ L := new o \\
  & & $\mid$ & always C $\mid$ once C \\
  & & $\mid$ & if e then s else s \\
  & & $\mid$ & while e do s \\
{\rm Constraint} & C & ::= & $\rho$ e $\mid$ C $\wedge$ C\\
{\rm Expression} & e & ::= & v $\mid$ L $\mid$ e $\oplus$ e $\mid$ e $\olessthan$ e \\
  & & $\mid$ & e $\ovee$ e $\mid$ I $\mid$ o $\mid$ D\\
{\rm Identity} & I & ::= & L == L\\
{\rm Object Literal} & o & ::= &  \{l$_1$:e$_1$,$\ldots$,l$_n$:e$_n$\} \\
{\rm L-Value} & L & ::= & x $\mid$ L.l \\
{\rm Constant} & c & ::= & true $\mid$ false $\mid$ nil \\
  & & $\mid$ & {\rm base type constants}\\
{\rm Variable} & x & ::= & {\rm variable names} \\
{\rm Label} & l & ::= & {\rm record label names} \\
{\rm Reference} & r & ::= & {\rm references to heap records} \\
{\rm Dereference} & D & ::= & \H(e) \\

{\rm Value} & v & ::= & c $\mid$ r $\mid$ \{l$_1$:v$_1$,$\ldots$,l$_n$:v$_n$\} \\
\end{tabular}
}\vskip0.5\baselineskip

Metavariable {\tt c} ranges over the {\tt nil} value, booleans, and
primitive type constants. A finite set of arithmetic operators on
expressions is ranged over by $\oplus$, $\olessthan$ ranges over a set
of {\em predicate} operators, and $\ovee$ ranges over logical
operators for combining boolean expressions. $\olessthan$ includes at
least an equality operator {\tt =} for each primitive type, and
$\ovee$ includes at least conjunction {\tt $\wedge$}. The operator
{\tt ==} tests for identity --- for primitive values and immutable
objects this is the same
as {\tt =}. The symbol $\rho$ ranges over constraint {\em priorities}
and is assumed to include a bottom element {\tt weak} and a top
element {\tt required}. The syntax requires the priority to be
explicit; for simplicity we sometimes omit it in the rules and assume
a priority of {\tt required}.

Finally, in the syntax, we treat \H as a primitive operation for
dereferencing.  Source programs will not use expressions of the form
\texttt{\H(e)}, but they are introduced as part of constraints given
to the solver, which we assume will treat \H as an uninterpreted
function.

\paragraph{Typechecking}
\label{sec:typechecking}
We use a notion of typechecking to prevent undesirable non-determinism
in constraints.  Specifically, we want constraint solving to preserve
the structure of the values of variables, changing only the underlying
primitive data as part of a solution, in support of the goals listed
in \autoref{sec:no-non-determinism}.  We formalize our notion of
structure through a simple syntax of types:
\vskip0.5\baselineskip\noindent\begin{tt}
\begin{tabular}{ll}
{\rm Type} T ::= & PrimitiveType $\mid$ \{l$_1$:T$_1$,$\ldots$,l$_n$:T$_n$\}
\end{tabular}
\end{tt}
\vskip0.5\baselineskip

Our typechecking rules check expression structures dynamically just
before constraint solving, so we typecheck in the context of a
run-time environment. Requiring only structural checks allows our
approach to work on top of both dynamically and statically typed
languages. Note that we do not include type rules for identities. This
ensures that constraints involving them do not typecheck, so identity
checks cannot occur in ordinary constraints.

}

\inferrule{T-Ref}{
  \tcH{\E}{\H}{o}{\{l$_1$:T$_1$,$\ldots$,l$_n$:T$_n$\}} \andalso

}

}

}

\paragraph{Constraint Solving}
\label{sec:constraint-solving}
This judgment represents a call to the constraint solver, which we
treat as a black box.  The proposition \mbox{\solveH{\E}{\H}{\C}}
denotes that environment \E~and heap \H~are an \emph{optimal solution}
to the constraint {\tt C}, according to the solver's semantics.  There
are a number of alternatives for defining what constitutes an optimal
solution \cite{borning1992constraint,felgentreff:2014:semantics}, 
each with their own advantages
and disadvantages.  In the work here, we encode that definition in the
choice of constraint solver, rather than making it a separate part of
the semantic rules.

\paragraph{Stay Constraints}
\label{sec:stay-constraints-1}
The semantics ensures that each variable has a {\tt weak} stay constraint to
keep it at its current value, if possible. To ensure that the solver
cannot invent new fields on objects, we create {\tt required} stays on the
heap that assert the structure of the objects. The first two stay
rules assert only {\tt weak} stays on all variables and are used for
assignment, which can change object identities. The \mbox{\istay{\E}{C}} and
\mbox{\istay{\H}{C}} rules use the \mbox{\istay{e}{C}} rule to ensure that
object identities and structures cannot be affected when solving value
constraints --- they create {\tt weak} stay constraints on primitive values,
but require references and the structure of objects to remain
unchanged.

To properly account for the heap in the constraint solver, we employ
an uninterpreted function {\tt \H} that maps references to objects
(i.e., records).  The following rules employ this function to
define stay constraints for references.

\inferax{StayEmpty}{\stay{$\emptyset$}{true}}

\infrule[StayOne]{
  \mbox{
    \E$({\tt x}) = {\tt v}$ \andalso
    \E$_0 = $\E$ \setminus \{({\tt x},{\tt v})\}$}\\
  \mbox{
    \stay{\E$_0$}{C$_0$} \andalso
    {\tt C}$ = ${\tt C}$_0$ $\wedge$ {\tt weak x=v}}
}{\mbox{
  \stay{\E}{C}
}}

\infrule[StayHeap]{\mbox{
  \H$({\tt r}) = {\tt o}$ \andalso

\paragraph{Constraint Translation}
\label{sec:constr-transl}
We translate constraints into a form suitable for the
solver. Specifically, each occurrence of an expression of the form
{\tt L.l}, where {\tt L} refers to a heap reference {\tt r}, is
translated into {\tt \H(L).l} (recursively, as required). We do not
give rules, because they are straightforward. The full
Babelsberg/Objects language includes a similar judgment that also
inlines method calls, given in its entirety in the companion technical
report \cite{felgentreff:2014:semantics}.

\paragraph{Statement Evaluation}
\label{sec:statement-evaluation}
A ``configuration'' defining the state of an execution includes a
concrete context, represented by the environment and heap, a symbolic
context, represented by the value and identity constraint stores,
and a statement to be executed. The environment, heap, and statement
are standard, while the constraint stores are not part of the state of
a computation in most languages.  Intuitively, the environment and
heap come
from constraint solving during the evaluation of the immediately
preceding statement, and the compound constraint \C\ records the \verb|always|
constraints that have been declared so far during execution. Note that
our execution implicitly gets stuck if the solver cannot produce a
model. 

The first two rules below describe the semantics of assignments.  We
employ a two-phase process.  First the identity constraints are solved
in the context of the new assignment.  This phase propagates the
effect of the assignment through the identities, potentially changing
the structures of objects as well as the relationships among objects
 in the environment and heap.  
In the second phase, the value constraints
are typechecked against the new environment and heap resulting from
the first phase.  If they are well typed, then we proceed to solve
them.  This phase can change the values of primitives but not
the structure of any object.

Implicitly, these rules get stuck if a) the identity constraints
cannot be solved, b) the value constraints do not typecheck, 
or c) the value constraints cannot be solved. A
practical implementation would add explicit exceptions for these cases
that the programmer could handle.

\subsection{Key Properties}
\label{sec:props}
Here we state two key theorems about our formalism.  The proofs for
these theorems can be found in the companion technical report.  The
first theorem formalizes the idea that any solution to a value
constraint preserves the structures of the objects on the
environment and heap:

\begin{sloppypar}
\begin{theorem} (Structure Preservation)\\
 If \stepH{\E}{\H}{\C}{\I}{(once|always)
   C$_0$}{\E$'$}{\H$'$}{\C$'$}{\I$'$} and \\\indent
 \tcHC{\E}{\H}{C$_0$} and \tcH{\E}{\H}{x}{T},\\then
  \tcH{\E$'$}{\H$'$}{x}{T}. 
\end{theorem}
\end{sloppypar}

The second theorem formalizes the idea that all solutions to an
assignment will produce structurally equivalent environments and heaps,
provided we start in a well-formed configuration where all identity
constraints are satisfied:

\begin{sloppypar}
\begin{theorem} (Structural Determinism)\\
  If
  \stepH{\E}{\H}{\C}{\I}{L := e}{\E$_1$}{\H$_1$}{\C$_1$}{\I$_1$} and\\\indent
  \stepH{\E}{\H}{\C}{\I}{L := e}{\E$_2$}{\H$_2$}{\C$_2$}{\I$_2$} and\\\indent
  \evalH{\E}{\H}{I}{true} and {\tt x} in dom(\E),\\
  then
  \tcH{\E$_1$}{\H$_1$}{x}{T} and
  \tcH{\E$_2$}{\H$_2$}{x}{T}.
  % $\forall {\tt x}\in dom(\E_1):$ \tcH{\E$_1$}{\H$_1$}{x}{T} $\Rightarrow$
  % \tcH{\E$_2$}{\H$_2$}{x}{T}.
\end{theorem}
\end{sloppypar}

\section{Evaluation}
\label{sec:evaluation}

Our aim in developing a formal semantics for Babelsberg has been
primarily a practical one, including clarifying the desired behavior
of the language, providing a guide for language implementors, and
proving useful language properties that then can be relied on by
programmers.

One piece of evidence of success is that we have in fact clarified the
desired behavior of the language, and as discussed in the
introduction, in response have adapted the existing Babelsberg/JS
implementation to conform to it.

Beyond that, we offer two forms of evaluation.  First, we have
implemented our natural semantics in \rml \cite{pettersson1994rml},
yielding an executable semantics.  We then evaluated a set of test
programs in this executable semantics, using the Z3 solver
\cite{de2008z3} to provide heap and environment updates. As an
extension to that, we provide a translation framework to generate test
suites for the implementations in \javascript, Ruby, and Smalltalk
from our test programs. We have adapted the \javascript implementation
of Babelsberg and show that the practical implementation and semantics
produce the same results for most of the tests, except those that test
features of value classes, which are not available in \javascript.

As a second form of evaluation, we have adapted the currently existing
suite of example programs for Babelsberg/JS to the revised
language. We demonstrate that nearly all of the programs continue to
work without modification, or work with minimal adjustments.  (These
adjustments are described below.)  Those programs that do not work
anymore stopped doing so because they use constructs we explicitly
decided to disallow.

\subsection{An Executable Semantics}
\label{sec:an-exec-semant}

\rml is a programming language to generate executables from natural
language specifications. It provides \emph{relations} as basic
building blocks for the semantics and translates these to C\@. It was
possible to implement our semantics exactly in \rml.  As the semantics
does not model the solving process, we have added a translation from
our constraint syntax to Z3, which solves the
constraints and generates a model of the new heap and
environment. Because our semantics relies on soft constraints, we
use an experimental version of Z3 that supports them
\cite{bjornernuz}.

Z3 types expressions and does not allow variables to change their
type.  Our structural typing rules, however, do allow variables to change
their type, for example, from a real to an integer or a string. In the
implementation we thus have to reconcile Z3 typing with our
structural typing rules. To do so, we declare variables in Z3 as a
union type \verb!Value! that has real, boolean, reference, and value
class components. The last is encoded as a Z3 array that maps
\emph{labels} to reals. Labels and references are declared as finite
domain types that range over the existing references and record labels
respectively. We define the operation, comparison, and combination
functions on that union type.

In the companion technical report, we provide 47 short test programs
that illustrate various aspects of
the semantics. We use these to validate that our semantics exhibits
the characteristics we want. Of those 47 programs, three use
constraints on strings, which are not supported in the version of Z3
we used.  (A string theory exists for an old version of Z3, but does not
work in recent versions \cite{zheng2013z3}.)  The remaining 44 all run
and produce the expected results at each step of the
execution\footnote{The entire executable semantics and the test
  programs are available at:
  \url{https://github.com/babelsberg/babelsberg-rml}}.

As an extension to the \rml implementation, we add a module to
transform the example code into test cases for the various
implementations of Babelsberg. This will provide an avenue for future
development of Babelsberg --- as the semantics evolve, test cases for
the existing implementations can be generated and the implementations
adapted to pass the generated tests. To generate the tests, we run our
examples through the generated \rml executable, automatically
translate them into the syntax of the target language using a simple
mapping provided for each language, and wrap them in a test scaffold
(also specific to each language) to execute them in each
implementation.%\todo{add a reference to the RML TR}

All of the pre-existing implementations of Babelsberg require
adaptation to pass these tests, because all deviate from our new
semantics in one way or another.  We began with the \javascript
implementation, as it is the most advanced, and updated it based on
the work described here.  After modification, of the 44 test cases
that work in the \rml semantics, 41 produce the expected results. The
remaining three specifically test properties of value classes in
constraints.  Since \javascript does not support value classes, and
since we do not currently emulate them in some way in the scaffolding code,
these three tests fail, in one case producing no result when there is
a solution, and the other two producing a solution when solving should
fail.  We have also tested, but not adapted, the Ruby and Squeak
implementations. Both Babelsberg/R and Babelsberg/S pass 28 out of 44
tests. In addition to the value class failures, these implementations
also fail some tests concerning object identity, due to insufficient
support for explicit identity constraints and use of an older
version of Z3 that does not include soft constraints. A
proof-of-concept Python implementation exists, but was not tested.

\subsection{Applying the Semantics to Babelsberg/JS}
\label{sec:apply-semant-babelsb}

Adapting Babelsberg/JS to follow the semantics presented here required
changes to both the translation from imperative expressions to
constraints (called \emph{constraint construction} in Babelsberg/JS)
and the way in which the solvers are called. Additionally, we had to
update some of the existing example programs that break with the new
semantics.

\subsubsection*{Modifications to the Implementation}
\label{sec:modif-impl}
First, we modified the code that translates \javascript expressions
into constraints to not inline methods that have more than a simple
return expression. Methods that have any other statements in them are
executed and their result returned, so they can only be used in the
forward direction. We did not modify the translation to prohibit
creating new objects --- as described in \autoref{sec:no-side-effects}, we
allow these since \javascript does not include value classes, and
assume that, when new objects are created in constraints, our
conventions on object creation, modification, and not testing for
identity are followed. As an optimization, Babelsberg/JS omits
re-translating expressions if no dependent variables changed. We have
left this optimization in place.

The second change added support for our restricted form of identity
constraints. Before, users of Babelsberg/JS could use identity checks
as part of ordinary constraints, as long as they used an appropriate
solver. We now disallow this, and in its place
add a restricted form of identity
constraints. In the executable semantics, identity constraints can be
solved using Z3 by reasoning over the finite domain of available
references and updating the environment. However, in \javascript we
cannot reflect on the heap or use first-class references, so identity
constraints cannot be solved in the same way. Instead, we use the
DeltaBlue local propagation solver \cite{freeman1989deltablue} to
propagate identity changes as they occur, and call any solvers for
value constraints after that. Babelsberg/JS, through its
implementation of a cooperating solvers architecture,
% removed self-reference - we're citing ourselves a lot...
% \cite{FelgentreffECOOP14,borning2012architectures}
already supports solving in multiple phases. The two-phase solving of
identity and value constraints in the formalism is thus implemented
simply by ensuring that the DeltaBlue solver for identity constraints
is always run before any other solvers. Note in particular that this
still allows the developer to use other instances of the DeltaBlue
solver for value constraints, but, just as with all solvers for value
constraints, they will be called after all the object identities are
determined.

\subsubsection*{Modifications to Existing Programs}
\label{sec:exist-appl}

These programs are written for the LivelyKernel

Ohm's Law and Kirchhoff's Current Laws and to solve the resulting sets
of simultaneous linear equations, and imperative constructs to support
actions such as making new resistor, battery, and meter instances, and
placing and connecting them.  The games combine constraints to encode
the game rules with imperative constructs for the user interface.

\paragraph{Argument Checking }
\label{sec:argument-checking}
One issue we encountered is that many LivelyKernel methods have,
besides a return statement, some statements that check the number,
types, or structure of arguments. As per our semantics, such methods
do not work multi-directionally. In fact, allowing them to be truly
multi-directional would allow the solver to change the number, types,
or structure of arguments, which are examples of the surprising behaviors we
want to avoid. As an example, consider the frequently used method to
add two points in LivelyKernel:
\begin{lstlisting}[language=JavaScript,caption={~},label=lst:addPt]
function addPt(p) {
    if (arguments.length != 1)
        throw ('addPt() only takes 1 parameter.');
    return new lively.Point(this.x + p.x, this.y + p.y);
}
\end{lstlisting}
We almost certainly don't want to satisfy a constraint that calls the
\verb|addPt| method with a bad argument by changing the argument to
be a point.  In the future we plan to revise the semantics to allow
argument checking simply as checks, rather than as parts of the 
constraint that can be used multi-directionally.
For now, although it is not semantically clean,
the practical implementation allows such tests on arguments, because
these checks are so pervasive that working around was very
inconvenient.

\paragraph{Benign Side Effects }
\label{sec:benign-side-effects}
Lazy initialization and caching are used in the constraints in some of the
example applications. Prior work has explicitly allowed such
benign side effects \cite{FelgentreffJOT14,FelgentreffECOOP14},
but our formal semantics disallows them.  (We believe that this is an
appropriate simplification to the formal semantics, preferring to
leave this issue to clear but less formal guidance to programmers and
language implementors.)  For example, the LivelyKernel method
\verb|Morph.getBounds| is used (often indirectly) in many of the
examples.  The code below was adapted to focus on the caching --- the
method also uses branches and local variables, which are also
disallowed now:
\begin{lstlisting}[language=JavaScript,caption={~},label=lst:getBounds]
function getBounds() {
    if (this.cachedBounds && !this.hasFixedPosition())
        return this.cachedBounds;
    // ... other code paths guarded with branches
    return this.cachedBounds = this.innerBounds();
}

contained within the bounds of their parent, this returns the same
result. In the practical applications, this change had the additional
benefit of removing some UI glitches that happened when the solver
changed the cached bounds. The rendering code in the LivelyKernel
expects changes to a Morph's bounds to go through the inner bounds to
trigger re-rendering, but a change to the \verb!cachedBounds!
rectangle did not update the UI unless something else triggered
rendering (in which case the \verb!getBounds!  method would return the
updated \verb!cachedBounds! and the Morph was rendered at the correct
position).

\paragraph{Local Variables }
\label{sec:local-variables}
Some methods we encountered declared local variables to split up
calculations or name constants. For such methods, manual inlining of
the split up calculation into the return expression was required. The
original Babelsberg design explicitly allows such methods, as long as
the variables are used in \ac{ssa} fashion \cite{FelgentreffJOT14}. In
this case, our restrictions may be too strong. However, our experience
with the different languages has shown that to some people it is not
clear if the system can, in such cases, change the value of local
variables hidden within a method, or if these can be regarded as
constants. Thus, we argue that, although sometimes inconvenient, the
restriction not to allow local variables makes it easier to reason
about the program.

\section{Application to Related Work}
\label{sec:related-work}

There are a large number of related systems that integrate constraints
with imperative languages, ranging from constraint satisfaction
libraries and \acp{dsl} to syntactic and semantic integration similar
to Babelsberg. How these systems choose to balance the power of
solvers and how aware the programmers need to be of the solving
process differs greatly, as does their balance between how freely
programmers can express new constraints versus how aware they need to
be of the fact that they are writing constraints rather than ordinary
statements in the host language.

The work presented here allows object-constraint languages to use different
constraint solver libraries as black-box solvers and
ensures that using a different solver does not introduce the kinds of
non-deterministic and surprising behaviors that we address. A large
number of constraint satisfaction libraries exist\footnote{See, for
  example, this catalog:
  \url{http://openjvm.jvmhost.net/CPSolvers/sssss}, accessed March 9,
  2015}, however, these systems do not integrate
syntactically or semantically with the host language. They require
explicit action by the developer to copy and convert variables between
the imperative and declarative systems, require the developer to
explicitly ensure that the solver is called at appropriate times, and
require explicit action to deal with updates to the object
graph. Thus, our work is not directly relevant to those systems by
themselves.

Kaleidoscope \cite{freeman1990kaleidoscope} was an early \ac{cip}
language, and had to address issues that arise from integrating
declarative constraints and imperative code with mutable state.
Kaleidoscope uses soft constraints to ensure that, in the absence of
other constraints, the solver does not change the values of existing
variables, as does Babelsberg. In contrast to Babelsberg, Kaleidoscope
separates methods that generate constraints from ordinary methods.
This avoids having to give rules for how a method can be used
in constraints, but it puts the burden on the programmer to develop
and maintain two sets of interfaces, one for use in constraints and
one for use in imperative statements.

Kaleidoscope'93 also included support for identity constraints
\cite{lopez1994kaleidoscope}, to express the distinction in
object-oriented languages between object equality and
identity. However, Kaleidoscope'93 allowed the solver to determine the
identity of method arguments when solving value constraints, and used
multi-method dispatch to look up methods in a constraint.  In
combination this gave the system much power, but also made it hard
to understand which solution the system might select.  Babelsberg
does not use multi-method dispatch, removing one dimension of freedom
from the solver (as well as conforming to a more standard semantics
for an object-oriented language).  Furthermore, with our semantics,
the solver cannot change the identity or structure of arguments for
value constraints.  We believe the
same solution could be applied to the Kaleidoscope design.

Turtle \cite{grabmuller2004turtle} is a more recent \ac{cip} language,
while Kaplan \cite{koksal2012constraints} provides constraints in
Scala. Both separate the declaration of \mbox{\emph{constrainable}}
variables from ordinary variables to make it clearer what may happen
when a variable is used.  Neither includes support for identity
constraints, however.  Like Babelsberg, the Turtle system provides
constraint priorities; Kaplan does not. Because ordinary variables in
Turtle are not determined by the solver, only constrainable variables
have low-priority stay constraints on them. Kaplan does not currently
support constraints over mutable types, so stay constraints are not
relevant for it.  Analogous to Kaleidoscope and in contrast to
\ac{ocp}, both languages separate constraint functions from ordinary
functions. In Kaplan, only such specifically annotated functions can
be used in constraints. Turtle does allow ordinary methods and
variables in constraints; however, their values are treated as
constants, making all ordinary methods work only in the forward
direction. We believe the simple rules for method inlining in our
semantics could be used with these systems as well to allow a
restricted set of ordinary object-oriented methods to be used in
constraints.

BackTalk \cite{pachet1995,roy2000framework} and \textsc{Squander}
\cite{Squander} explicitly allow the constraint solver to determine
object structure, and even to create new objects that satisfy a set of
constraints. While these systems have many differences, both use
object-oriented methods in constraints as tests for a backtracking
algorithm that tries different objects and object structures as
assignments for the constrained variables. Thus, it is a basic
property of these systems to allow actions that we prohibit in
Babelsberg. In those systems, constraints are most useful when the
concrete identity of an object is not relevant. When declarative code
interacts with imperative code, however, this may not be the case,
especially in dynamic languages such as JavaScript, where libraries
add and remove properties to specific instances at runtime and check
for object identity rather than properties.

Finally, $\alpha$Rby \cite{alloyRuby2014} is a language that embeds the
Alloy specification language \cite{DBLP:journals/tosem/Jackson02} in
Ruby. Its goal is to allow Alloy users to easily pre- or post-process
their models using imperative libraries, for example to experiment
with visualizations for Alloy models. $\alpha$Rby translates Ruby
programs into Alloy, but the programs  are written in a \ac{dsl} that
closely mimics the Alloy language rather than using ordinary Ruby
classes and methods.  In contrast to Babelsberg, $\alpha$Rby
aims to provide imperative constructs to Alloy users, whereas
Babelsberg provides declarative constructs to object-oriented
programmers.

\section{Conclusion and Future Work}
\label{sec:conclusion}

We have presented design principles to control the power of the solver in
object-constraint programming languages to avoid surprising or
non-deterministic behavior, and a set of simple rules that guide
developers in expressing constraints. Our principles are formalized in
a natural semantics for an object-constraint
language that preserves key properties of existing object-constraint
implementations. For this semantics we presented two theorems that
formalize two key properties of our rules, namely that they
remove non-determinism and surprising behavior, in that they never
allow the solver to find solutions that would needlessly add or remove fields
from existing objects. Our rules also ensure that the only way for a
variable to change its structure is through an assignment statement ---
thus, solving constraints outside of an assignment can never lead to
solutions in which variables change their structure.

The semantics given here defines a useful subset of the language. A
full object-constraint language that supports standard classes and
methods is provided in the companion technical report.
It includes formal rules for
defining constraints on the results of message sends that implement
our informal description in \autoref{sec:transl-multi-way}. Its
restrictions are easy to understand, but may be too conservative, as
shown by our experiences with existing Babelsberg example
programs. One direction for future work will be to allow somewhat more
general kinds of expressions in methods called from constraints to be
used multi-directionally.

We also presented an executable semantics that can run a suite of
example programs, provided a mechanism to generate a language test
suite to check the implementations' conformance to the semantics, and
so far modified one existing implementation to follow our design, thus
demonstrating its practicality. Another direction for future work is to
use this test suite to move other implementations closer to conforming
with the semantics, to further test its practicality.

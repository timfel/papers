\begin{abstract}
Constraints provide a useful technique for ensuring that desired
properties hold in an application, and have been used in a wide range
of applications, including graphical layout, simulation, scheduling,
and problem-solving.  At the same time, very lightweight, web-based
applications have become increasingly prominent.  We describe a design
and implementation of an \acrlong{ocp} language, an object-oriented
language that cleanly integrates constraints with the underlying
language, in a way that respect encapsulation and standard
object-oriented programming techniques, and that runs in browser-based
applications.  Prior work on \acrshort{ocp} languages has relied on
modifying the underlying \acrlong{vm}, but that is not an option for
such browser-based applications.  In this paper, we present an
approach to implementing \acrlong{ocp} without \acrlong{vm} support,
along with an implementation as a \javascript extension.  We
demonstrate the resulting language, \langname/JS, on a number of
applications and provide performance results.  Programs in
\langname/JS without constraints run at essentially the same speed as
pure \javascript, while programs that do have constraints can still be
run quite efficiently.  Our design and implementation also supports
cooperating constraint solvers, which allow multiple solvers to work
together to solve a more difficult problem, as well as incremental
re-solving to support interaction.
\end{abstract}

\section{Introduction}

Constraints are relations among objects that should hold. This could
be that all parts in an electrical circuit simulation obey the laws of
physics, that the rows in a Sudoku include each digit from 0 to 9, or
that a streamed video play smoothly in the presence of changing CPU
and network load.  It is useful to extend the constraint formalism to
allow soft constraints as well as required ones, where the system
should try to satisfy the soft constraints if possible, but it is not
an error if they cannot be satisfied.  The streaming video example
illustrates the need for this: we might have a soft constraint for
video quality that we are willing to relax if necessary, given the
current network load.  In the work reported here, we want to support
such constraints in a clean way in an object-oriented language that
can also be used in a very lightweight, web-based programming
environment.

\autoref{fig:colorchooser} shows a color chooser from the parts bin
\cite{lively-partsbin-2012} that can be used to create a color palette
for a website.  Users can specify the desired average hue and
luminance using the sliders, as well as change each color individually
using a color chooser. The system automatically updates the colors and
sliders according to user input -- for example, the hue slider adjusts
when the user changes the luminance slider. Edit constraints are used
for incremental resolving, so colors change smoothly when dragging the
sliders. Furthermore, the constraints on hue, luminance, and specific
color selection have different priorities. Changes to individual
colors may be slightly adjusted by the system or cause changes to
other colors to keep the average hue and luminance constant, whereas
dragging the sliders forces the system to use the new value. There are
additional constraints that luminance and hue of each individual color
must be at least 80\% of the average luminance and hue, and that the
system cannot set red, green, and blue values outside the value range
(0--1 in Lively).

\autoref{fig:wheatstone} shows a constraint-based simulation of
Wheatstone Bridge being constructed.  Parts representing batteries,
resistors, and meters are copied from the parts bin on the right,
dropped into the circuit on the left, and wired together.  These parts
carry constraints representing Ohm's Law, Kirchhoff's Current Law, and
so forth.  The system automatically solves the constraints when the
parts are first connected, and re-solves them if the battery's supply
voltage or a resistance is edited, updating the amperes displayed by
the meter.

While the capability to graphically construct constraint-based
simulations dates back to Sketchpad \cite{sutherland-ifips-1963} and
ThingLab \cite{borning-toplas-1981}, in the current work we want to do
a true integration of the constraints with the host object-oriented
programming language, and further support this in a web-based
environment.  To accomplish this, we build on recent work by
Felgentreff et al.~\cite{FelgBorningJot2014-submitted} on Babelsberg,
a a language framework that supports an integration of constraint
satisfaction with objects and their methods.  Babelsberg in turn
builds on earlier work on constraint-imperative programming in
Kaleidoscope \cite{lopez1994kaleidoscope} and Turtle
\cite{grabmuller2004turtle}. In \langname, constraints are expressed
as predicates using the underlying object-oriented language. The
constraint is that the predicate evaluates to true, and the system
maintains this constraint automatically whenever objects that
participate in the constraint change.

\langname improves on related approaches to constraint satisfaction in
object-oriented programs, which use
libraries \cite{badros2001cassowary,de2008z3,torlak2007kodkod},
domain-specific languages \cite{AppleCocoaAutoLayout,Enaml}, or (more
recently) functional-reactive
programming \cite{ohshima2012report,meyerovich2009flapjax} to specify
and solve
constraints. These approaches do not need special runtime support, but
require the programmer to call specific \acp{api} or follow certain
rules to not accidentally circumvent the constraints.

Felgentreff et al.\ first implemented the \langname design as a
prototype in Ruby \cite{flanagan2008ruby}, called \langname/R.  This
implementation depends on extending the Ruby \ac{vm}.  However, in our
current environment, \javascript applications typically have to work
on a variety of client \acp{vm} included in different Web
browsers. This makes it infeasible to implement \langname in a
\javascript \ac{vm}. \javascript is currently of considerable interest
in the industry and research communities.  Thus, an implementation as
an extension written entirely in \javascript enables us to apply
constraint programming to a variety of existing problems, and to
compare it directly with alternative solutions on a variety of
platforms.  Another goal for our design is good performance.  As with
the original \langname/R implementation, we want the extension to have
at most minimal impact on speed for programs without constraints; and
for programs with constraints, we still want to have good performance
for interactive graphical applications, which generally implies the
need to support incremental constraint solvers.

In addition to the goal of good performance, a useful Object
Constraint Language requires sufficiently powerful constraint solving
capabilities.  Felgentreff et al.\ \cite{FelgBorningJot2014-submitted}
identify an important requirement here that was not yet implemented in
their system, namely support for \emph{cooperating constraint
  solvers}.  The motivation for this is that it is often infeasible to
provide a single constraint solver that works well for all aspects of
a problem; instead, different solvers may be more appropriate than
others for some aspects, and which need to work together to solve the
problem.  Our design and implementation in \langname/JS provides this
capability, in a way that supports incremental re-solving of
constraints without requiring access to the \ac{vm}.

\section{Background and Related Work}
\label{sec:background}

Programs frequently have some set of constraints that should hold. 
In a standard imperative language, the usual approach to
dealing with such constraints is to leave it entirely up to the
programmer to ensure that they are satisfied --- the constraints may
be implicit in the code and just expressed explicitly in comments and
documentation, or perhaps in the form of machine-checkable
assertions.

For some constraints, programmers may write assertions to fail early
if the constraints are unexpectedly not satisfied
\cite{rinard2005exploring}, other constraints describe invalid system
states that can be automatically corrected, for example when the user
selects a specific color that does not meet the luminance
constraints. To deal with the latter, programmers may write corrective
code that is executed at various times (for example, color adjustments
may run while the user is dragging the luminance slider). This code
uses branches and state changing operations to check and correct
invalid state. However, these statements are order dependent, and the
branching code expresses the constraints implicitly. Furthermore, it
is unclear whether a solution is complete in that it covers all
possible cases or optimal.  As argued by Felgentreff et 
al.~\cite{FelgBorningJot2014-submitted}, it is usually clearer to express
and satisfy constraints explicitly, rather than encoding them in
control flow.

One approach to make the constraints explicit is to use a library that
provides one or more constraint solvers. A large number of solvers
that cover a wide range of type domains (such as reals, booleans, or
finite sets) is available for imperative languages and can be called
from imperative code
\cite{badros2001cassowary,de2008z3,torlak2007kodkod,freeman1989deltablue}. For
more specialized domains such as user interface layout, some libraries
provide separate \acp{dsl} to express for example minimal distances
between graphical objects. Prominent examples here include the Mac OS
X layout specification language \cite{AppleCocoaAutoLayout} or the
\textsc{Squander} framework \cite{Squander}. For our example, these
approaches replace the branching and state changing code with
declarative constraints. However, these constraints are expressed in
the language of the library, using solver-specific types and
expressions. To interact with the imperative state of the system,
the solver must be called explicitly, and the constrained values
must be copied between the solver and runtime data
structures whenever either imperative code or the solver update
them.  Further, because solvers operate on a limited number of domain-specific
primitive types, object-oriented abstractions cannot be used to
express constraints.

An alternative approach, however, is to integrate a means to express
and maintain constraints with the language itself. Some languages such
as Scratch \cite{resnick2009scratch}, LivelyKernel
\cite{lively-kernel-2008}, and KScript \cite{ohshima2012report} have
built-in support for data flow, which allows programmers to express
unidirectional constraints among objects. To support a broader set of
constraints, some languages directly integrate one or more solvers
into their execution model. Again, there is a huge body of prior art
in this area, examples include Constraint Logic Programming
\cite{jaffar-popl-1987}, Constraint Imperative Programming
\cite{lopez1994kaleidoscope,grabmuller2004turtle}, and Object
Constraint Programming, of which \langname is an instance.  Object
Constraint Programming differs from the former in that it focuses on
object-orientation as the main paradigm. It seeks to integrate
declarative constraints in a way that does not compromise the
expectations of imperative object-oriented programmers and that
provides a declarative semantics that is compatible with these
expectations.

\langname is a design for a family of object constraint languages that
integrate constraints with an existing object-oriented language. Its
goals include:
\begin{itemize}
\item a syntax and semantics that are a strict superset of and fully
  compatible with the base language
\item a unified mechanism for abstraction shared between constraints
  and object oriented code, so that constraints can re-use
  object-oriented methods and respect encapsulation
\item performance that is competitive with the base language for
  standard object-oriented code without constraints
\item support for required and preferential constraints, constraints
  on object identity, variables that are read-only to solvers or
  imperative code, as well as incremental re-solving for use in
  interactive applications
\item an \ac{api} for constraint solvers that makes it straightforward
  to add new solvers and does not privilege the solvers provided with
  the implementation, to make it easy to use different solvers in
  different programs
\end{itemize}

\subsection{\langname/R}
\label{sec:babelsberg-approach}

Felgentreff et al.~\cite{FelgBorningJot2014-submitted} 
describe \langname/R, an implementation of \langname based on a
modified Ruby \ac{vm}. The modifications are almost all semantic
extensions, with only one minor syntactic extension, plus 
libraries for constraint satisfaction.  The semantic
model is also an extension of Ruby's, and supports all of the existing
Ruby constructs such as classes, instances, methods, message sends,
blocks (closures), object identity, and the language's control
structures.

All these Ruby constructs are also supported in constraints. However,
there are two important restrictions:
\begin{itemize}
\item The expression that defines a constraint should return a
  boolean, just like an assertion. The constraint is that the boolean
  is \emph{true}.
\item Constraints can be placed on the results of message sends, as
  long as the execution of these messages does not have side-effects
  (or those side-effects are benign, like caching), and repeated
  execution of the expression produces the same result, as long as no
  variables participating in the constraint have changed (so system
  calls for example to a random number generator or a file stream do
  not qualify)
\end{itemize}

For example, the constraint that each color should have a luminance
at least 80\% of the global targeted average could be
expressed a concise manner with \langname/R:
\begin{lstlisting}[language=ruby]
colors.each do |color|
  always { palette.target_luminance * 0.8 <= color.luminance() }
end
\end{lstlisting}
What looks like an assertion on all elements in the \lstinline{colors}
collection is actually a constraint. Whenever any color or the target palette
luminance changes, the system will automatically adapt to ensure that
this expression is always satisfied. This snippet also shows that
constraints can be used within imperative constructs and constrain the
values of properties (the \lstinline{target_luminance} as well as the
results of object-oriented message sends (the result of the calculated
\lstinline{luminance} of colors).

Given a set of constraint expressions, \langname can choose among
multiple solvers to find a solution to them. An architecture to add
multiple solvers makes it straightforward to add new solvers, and does
not privilege the solvers provided with the language (they are merely
the ones that come with the standard library). However, the programmer
has to indicate which solver is available to the runtime, and there
may be constraints that are too difficult for any one
solver. Additionally, features such as incremental
solving \cite{freeman1990incremental}, read-only variables, soft- and
stay-constraints \cite{borning1992constraint} are only available with
some solvers.

The \langname/R design allows programmers to express constraints
concisely using the abstractions of the Ruby language, however, it
only runs on a modified Ruby \ac{vm}. To express constraints in this
way in existing environments where \ac{vm} modifications are not
feasible, the design has to be extended to support an \langname-style
constraints without \ac{vm} support.

\section{Object Constraint Programming Without VM Support}
\label{sec:design}

\javascript is currently of great interest to the research
community. In the industry, it has become the de-facto standard for
Web programming and a huge amount of code exists in the
language. \javascript's unique language design and its execution
environment in the Web browser currently prompt much research to
revise and adapt existing features of other
systems\cite{vancutsem-proxies-2010,kang-jsmodules-2012}

To provide practical support for object-constraint programming in
\javascript, we adapt the \langname design to not require support from
the underlying \ac{vm}. This enables us to run \langname/JS in modern
browsers and use it in a variety of practical Web applications.

The original \langname/R system employs two interpretation modes:
imperative evaluation mode and constraint construction mode.  The
interpreter normally operates in imperative evaluation mode.  In the
absence of constraints, this is the standard Ruby \ac{vm}.  However,
if the interpreter encounters a \load or \store instruction for a
variable with a constraint on it, rather than directly loading or
storing into the variable, it calls the appropriate constraint solver
to retrieve the variable's value or to solve an equality constraint
between the variable and the new value.  When a constraint is being
added, the interpreter switches to constraint construction mode.  It
continues to evaluate expressions using message sends, but rather than
computing the result, it builds up a network of primitive constraints
that represent the constraint being added, keeping track of the
dependencies in the process.

For \langname/JS, since we don't have access to the virtual machine,
another technique is needed.  Instead, the underlying \javascript
interpreter is used for imperative evaluation mode.  To intercept
accesses and assignments to constrained variables, we replace the
normal property accessors with new ones that interact correctly with
the constraint solvers, again calling the appropriate constraint
solver to solve an equality constraint between the variable and the
new value for a store, or getting the value from the solver for that
variable for a load.  When a constraint is being added, we evaluate
the constraint expression to build up the network of primitive
constraints by using a modified \javascript interpreter (written in
\javascript) --- since this is a much less common activity, and one
that doesn't occur in inner loops, the performance penalty from using
an interpreter written in an interpreted language is not an issue.


\subsection{Babelsberg/JS}
\label{sec:vm-support}

\langname/R was built as an extension to a Ruby \ac{vm}. The extension
is two-fold:
\begin{itemize}
\item The \ac{vm} was extended to support \emph{constrained
    variables}. These variables refer to different objects depending
  on the context they are used in. One is the normal object-oriented
  binding used in the host language execution. The other is a
  constraint object that can be used by a solver for constraint
  construction and solving. Variables become constrained variables
  only when they are used in a constraint, minimizing the performance
  impact for parts of the program where only normal variables
  are accessed.
%% ALAN TODO: check for overlap with new paragraphs in intro
\item The \langname/R interpreter distinguishes between different
  execution modes: normal \emph{imperative execution} and
  \emph{constraint construction}. A primitive --- \lstinline{always}
  --- was added to execute a closure in constraint construction
  mode. In this mode, the bytecodes for \load and \store were modified
  to refer to the constraint objects of constrained variables. Normal
  variables are automatically promoted to constrained variables in
  this mode. During imperative execution, assignments to constrained
  variables trigger recalculation of the constraints.
\end{itemize}

We have thus identified the following requirements for implementing
the \langname scheme without \ac{vm} support:
\begin{itemize}
\item The host language must support a means to intercept variable
  lookup, so names can refer to different objects.
\item The \ac{vm}-based implementation of \langname assumes
  that the \ac{vm} provides access to the program state so solvers can
  ignore encapsulation and modify data structures directly.  In
  contrast, here the extension must enable calling the appropriate
  \ac{api} functions to manipulate data structures.
\item The host language must provide a means to modify interpretation
  of a block of code to implement the constraint construction mode.
\end{itemize}

The first requirement is partially supported in \javascript for object
fields using property accessors. We limit ourselves to constraining
field storage in \langname/JS, but not storage into local variables
(some compiled languages such as, for example, C\# also support
property accessors and other dynamic languages like, for example,
Python or Smalltalk support \emph{method wrappers} to accomplish the
same within the same limitations of only constraining field
access). As in the original design, it does not matter whether the
fields are constrained directly or they are used in the execution of a
method that was constrained to produce a certain result. A property
that is accessed in the execution of a constraint expression is
wrapped with property accessor that intercept lookup and storage.

To execute code in a constraint construction mode, we use a modified
\javascript interpreter written in \javascript and a source code
transformation The transformation is an implementation detail and can
be omitted. In \langname/JS, it merely provides a more convenient
syntax.Languages that provide access to the calling context could
provide this syntax without a transformation.

\subsubsection{Property Accessors for Constrained Objects}
\label{sec:prop-access-constr}
When an object has been used in a constraint, its constrained
properties have been replaced with property accessors. The property
getter is a simple wrapper around the solver variable. Instead of
returning the field value of the object, it returns the value of the
variable in the solver data structure.

The property setter distinguishes two cases.  If the variable is
writable from a solver, an equality constraint for that solver is
created and the updated constraint system is solved, potentially
triggering other solvers.  On the other hand, if 
the variable is not writable (either
because it is of a type that no available solver supports or because
it has been marked as read-only by the programmer), its new
value is stored, and all dependent constraints are recalculated.

\subsubsection{Creating Constraints}
\label{sec:writing-constraints}
As an example of defining constraints, consider an interactive
temperature converter, which maintains the relation between sliders
representing values on the Fahrenheit, Celsius, Rankine, and Kelvin
scales.

\begin{code}
var converter = {},
    cassowary = new CLSimplexSolver();
always({solver:  cassowary}, function() {
    return converter.C * 1.8 == converter.F - 32 &&
           converter.C + 273.15 == converter.K &&
           converter.F + 459.67 == converter.R
});
\end{code}

%% For later: is there a way to write this that isn't a conjunction?
%% It seems more natural to write a series of separate constraints.

Once this code has executed, a change to any one of the
temperature values in the converter object will trigger changes to the
other three values to keep the constraint satisfied through property
accessors described above.

In \langname/JS, the \lstinline{always} function passes the function
expressing the constraint and information about the context into a
custom \javascript interpreter. This interpreter is used to evaluate
expressions in constraint construction mode, which is provided as part
of the \langname/JS library.  The custom interpreter creates property
accessors for the \lstinline{C}, \lstinline{F}, \lstinline{K}, and
\lstinline{R} fields of the \lstinline{converter} object.  Within the
constraint expression, accesses to these fields do not use these
accessors, but instead return \emph{ConstrainedVariable}
objects. Messages are then sent to these objects, and instead of
calculating values, create relations that can be satisfied by a
solver. The \lstinline{always} statement returns a
\lstinline{Constraint} object that provides meta-level access to the
asserted relations, using the protocol described in
\cite{FelgBorningJot2014-submitted}.

In this example, the constraints are on the fields of the
object. However, constraints in \langname can also invoke methods
that perform computations. For example, imagine the converter uses the
\lstinline{getCelsius} method to return a cached temperature value
that is updated in regular intervals from a Web service:
\begin{code}
var converter = {},
    cassowary = new CLSimplexSolver();

converter.getCelsius = function() {
    if (!converter.updater) {
        updateCelsius(converter); // updateCelsius omitted for brevity
        converter.updater = setInterval(5000, function() {
            updateCelsius(converter);
        });
    }
    return converter.C;
}

always({solver:  cassowary}, function() {
    return converter.getCelsius() * 1.8 == converter.F - 32 &&
           converter.getCelsius() + 273.15 == converter.K &&
           converter.F + 459.67 == converter.R
});
\end{code}

By placing the constraint on the result of sending messages rather
than on fields, \langname respects object encapsulation.  The value
returned from the message send in this example is simply a float, but
return values can also be arbitrary objects and computed values. For
example, we could contrive that we want to constrain the maximum
pressure of a volume of dry air with a fixed density.
\begin{code}
converter.pressure = function () {
    var gas_constant_dry_air = 287.058, // J/(kg * K)
        density = 1.293; // kg/m^3
    return density * gas_constant_dry_air * converter.K / 1000;
}

always({solver: cassowary}, function() {
    return converter.pressure() <= 115 // kPa
});
\end{code}
(This will effectively limit the maximum temperature to around
36$^{\circ}$ Celsius)

\subsection{Cooperating Constraint Solvers}
\label{sec:cooperating-solvers}

Note that the above temperature converter has no graphical
representation. Cassowary only works on reals, yet in order to
visualize the temperature scales, we need to convert the values into
strings and update the Web browsers' \ac{dom} using the appropriate
\ac{api}.  This is best done with a local propagation solver, which
can invoke arbitrary methods to satisfy the constraints, in this case
by calling the \ac{api}.  (The constraints that define the temperature
converter are simple enough that we could have used a local
propagation solver for all of them, but this is unsatisfactory for
many problems, since local propagation cannot handle such situations
as simultaneous equations or inequalities.)

There is currently no single solver that can efficiently handle all
constraints that arise in a typical application (and it seems unlikely
that one exists).  To address this, we instead provide an architecture
for cooperating constraint solvers that allows the problem to be
partitioned among multiple solvers.  For this example, we use two
solvers: one for linear arithmetic on the reals, and one for local
propagation constraints.

A huge body of work exists that describes approaches to integrate
different constraint solvers around \ac{smt}
\cite{nelson-oppen-1979}. In the work presented here, we chose to
implement a design for cooperating solvers that partitions constraints
into regions which are connected through read-only variables
\cite{borning2012architectures}.

In this extension to \langname, each constraint belongs to exactly one
solver. All constraints that belong to the same solver 
are in the same
region. While constraints belong to exactly one region, variables may
be shared across regions. This happens if variables occur in multiple
constraints that belong to different regions. These variables are
read-only in all but one of the regions, meaning that the solver 
cannot change the value of these variables to satisfy its
constraints. Read-only variables are represented in a solver-specific
manner, either through \emph{stay constraints} for solvers that
support them, or through required equality constraints.  To support this,
solver libraries should provide a method that makes a variable read-only for
that solver.

In this architecture, the regions must form an acyclic graph so that
solving can simply proceed from the higher to the lower regions,
propagating variable values. To create this graph, the system has to
find an order for the solvers based on the dependencies between the
constraints. The programmer can make this explicitly control the
position of a solver in this graph, or the libraries can provide
information so the system can create the order without the
programmer's support. Applications can use multiple instances of the
same solver type that are used after one another (this can be used,
for example, to break up non-linear constraints into multiple linear
constraints and solve them with Cassowary).

Once the solver regions are sorted, solving proceeds from the topmost
region. Each region will determine values for the variables it can
write to, and the downstream regions will adjust to accommodate the
new values assigned to read-only variables from higher level
regions. Soft constraints are solved by region -- that is, if a soft
constraint in a higher regions restricts a variable to a certain
value, then a lower region must use that value and can in fact not
distinguish if this value was determined by a required or a
preferential constraint. If constraints in a lower region cannot be
solved due to a higher level preferential constraint, we do not
backtrack.

For our temperature converter, we can now provide some graphical
representation. We want the color of a \textsc{div} element to change
when the temperature is above 30$^{\circ}$ C.
\begin{code}
var el = jQuery("#tooHotWarning");

always({solver: deltablue}, function() {
    el.color.formula([converter.getCelsius()],
        function(celsius) {
            var color = celsius > 30 ? "red" : "blue";
            el.setAttribute("class", color);
            return color;
        });
    }
);
\end{code}
Note that for the DeltaBlue local propagation solver, we do not
provide a predicate (although we could --- in that case it would be
run to test whether re-solving is necessary). Instead, the local
propagation solver needs formulas for all writable variables that
state dependencies and how to update the variable. In this case, we
want the Celsius value to be used as input for the color, but not
vice versa, so we only provide one formula. The only dependency here
is the return value of \lstinline{converter.getCelsius()}. The
dependencies are passed as arguments to the formula function, so we
can use them directly to update the \ac{dom} using the browser's
\lstinline{setAttribute} \ac{api} and return the new value.

\subsection{Incremental Re-Solving for Cooperating Constraint Solvers}
\label{sec:coop-incr-resolv}
Some applications involve repeatedly re-satisfying the same set of
constraints with differing input values.  A common such case is an
interactive graphical application with a constrained figure, where we
move some part of the figure with the mouse.  For such applications,
it is important to re-solve the constraints efficiently, and a number
of constraint solvers support this using so-called \emph{edit
  constraints} that allow a new value for a variable to be repeatedly
input to the solver.

The original \langname design did not include support for incremental
re-solving at the language level - it was up to the solver library to
provide access to such functionality. However, to integrate with our
cooperating solvers architecture, \langname/JS includes support for
incremental re-solving through a solver-independent \lstinline{edit}
function that takes the variables to be edited and returns a callback
function. The process that produces new values can use this callback
to input new values into the solvers for the variables to be edited.

The \lstinline{edit} function gathers all constraints the passed
variables participate in. Only variables that occur solely in solvers
that support edit constraints can be edited, otherwise an exception is
raised. All read-only annotations in the solvers for downstream regions are
disabled for these variables, at the same time, they are added to the
solvers' set of edit variables. Finally, the \lstinline{edit} function
creates a callback function and returns it. This callback can then be
used to feed new values into the solvers.

To support incremental re-solving with cooperating solvers, two
restrictions apply: first, all variables that are edited must only be
in regions of solvers that support edit constraints. Second, while the
edit callback is used, no new constraints can be created. These are
required, because edit constraints are an optimization that depends on
the state of the solvers and the graph of connected variables to be
statically known for the duration of the edit.

These restrictions do not limit the generality of the approach, only
the applicability of the optimization of incremental
re-solving. Programs that cannot, for some reason, adhere to these
restrictions can still use normal assignment.

\section{Implementation in Lively Kernel}
\label{sec:implementation}

We have implemented \langname/JS in the Lively Kernel environment. We
provide pure \javascript implementations of DeltaBlue and Cassowary as
constraint solvers and extend the LivelyKernel \javascript interpreter
to evaluate constraint expressions. The code is not Lively specific --
we use the collection \acp{api} and class system of Lively, but this
could be trivially changed. However, when used in the Lively

constraints in the Object Explorer \cite{lively-partsbin-2012} more

\subsection{Assignment}
\label{sec:assignment}

Assignment to objects that are constrained in \langname/JS is the core
concept that binds the declarative constraints and imperative code
together. Whereas in standard imperative code assignment writes a value
to a memory location, assignments in \langname add equality
constraints on constrained objects and trigger re-satisfaction. The new
equality constraint may be unsatisfiable, in which case the assignment
is not executed and a runtime exception is generated.

As in \langname/R, the \langname/JS runtime informs the developer of a
failed assignment by generating a runtime exception.   To
support the cooperating solvers design, assignment in \langname/JS is
a 3-step process:

\paragraph{Set Value}
If the new value is the same as the old, we simply return.  Otherwise,
we disable all read-only constraints on the assigned variable. This
happens if the variable has been marked read-only by the programmer or
automatically, because it appeared in multiple solvers (only one of
which can be allowed write access). Read-only constraints are equality
constraints or required stay constraints (for solvers that support the
latter).

If the assigned value has an external variable, \ie it is constrained
by a solver that can handle its type (for example a real in
Cassowary), the new value is input into the most upstream solver as an
equality constraint and this solver is executed to produce a new
value. If the primary solver cannot satisfy its constraints with the
new value, the read-only constraints are re-enabled and an exception is
generated. Afterwards, the equality constraint for assignment is
removed.

\paragraph{Update Downstream Variables}
For all external variables except the primary one (the one in the most
upstream solver), the new value is input into the solver. If any of
the solvers fail to satisfy their constraints with the new value, an
exception is generated (and all read-only constraints are re-enabled as
above).

For all remaining constraints, the variable is not solvable in their
solvers. Consequently, its value was treated as a constant in their
constraint expressions. With the new value, these have to be
recalculated. To do so, the old variable value is remembered and the
new value is stored into the variable. All remaining constraints are
disabled, their expressions re-run, and then the constraints are
re-enabled. Afterwards, the old value is restored into the variable.
If any constraint in this set fails to run its expression or cannot be
satisfied with the new value, the old value is also restored and an
exception is generated.

\paragraph{Update Connected Variables}
Finally, we have to update the variables connected to the assigned
variable. To do so, we create the transitive closure of all variables
connected to the assignee through constraints. For all these
variables, a new value has already been created for all solvers that
already ran, but their downstream read-only constraints still have to
be updated. These variables have to go through the first two steps of
the assignment process, returning early if their values have not
changed.

Note that at this point, assignment can only fail for variables that
are in solvers that have not run yet. These are only solvers that the
primary assignee is not part of. If any one of these solvers cannot
satisfy their constraints with the new value, no storage of new values
into memory has taken place (we have reverted the only storage of new
values after recalculating constraint expressions in the second
step). So, to cancel assignment at this time, we need to assign the
old value to the primary assignee to revert all solvers' states. While
this may leave the system in a different state than it was in before
assignment (depending on the implementation of the participating
solvers), this new state will be one that satisfies all previously
enabled constraints.

\subsubsection{Assigning Mutable Objects}
\label{sec:assign-compl-objects}
The described semantics do not specify how assignment of mutable
objects should be handled. In our temperature slider example, we only
used the mouse's horizontal location to move the slider along the
horizontal axis. In this case, the assignment is a primitive,
immutable value and the solver has to adjust other variables to
satisfy the constraints. However, if we change the \ac{api} to accept
the mouse location as a point, the expected result is less clear. We
are asking the system to adjust the slider to equal a mutable object
-- in this case the system should not change the mutable object to
satisfy constraints (we still want the slider to follow the mouse, not
vice-versa).

There are situations in which the system should still be allowed to
change assigned objects to satisfy constraints. To use constraints for
input rectification \cite{long-rectification-2012}, programmers may
expect the system to fix the assigned object, rather than reject the
assignment.

To support both scenarios, \langname/JS first marks the assigned
objects as read-only for the solvers and tries to satisfy all
constraints without changing the input data. For example this means
that the slider will continue to follow the mouse as long as the mouse
does not leave the confines of the slider widget. If the assignment of
a mutable object fails, it is re-tried without the read-only
restriction on the object. If we try to drag the slider outside of its
container, the mouse pointer will be adjusted to stay inside,
``sticking'' the mouse to the widget. In any case, after the
assignment has happened, the additional read-only constraints are
removed again.

Note that, if the object marked as read-only has references to other
parts of the system (rather than just immediate values, like a point),
we could accidentally mark parts as read-only that should be modified
for the assignment. In these cases, the programmer might not expect
all objects references by the assigned one to be marked read-only, but
only those that are only reachable through the object. However, we
have found our solution to be useful and meet expectations when
working with the user interface, where objects that are simply
structures of primitive data (such as rectangles, points, ...) are
commonly assigned. For more complex cases, for example, when parts of
an assigned object are shared with other objects, the programmer has
to be explicit.

\subsection{Constraint Construction}
\label{sec:constr-constr}
When a programmer writes a function that contains a constraint
expression, this expression is evaluated using our JavaScript
\emph{ConstraintInterpreter}.  Popular \javascript
\acp{vm}\footnote{http://www.w3schools.com/browsers/browsers\_stats.asp}
(Apple Safari's
SquirrelFish\footnote{http://trac.webkit.org/wiki/SquirrelFish},
Google Chrome's V8\footnote{https://code.google.com/p/v8/} , Mozilla
Firefox's SpiderMonkey \cite{gal-tracejit-2009}, or Microsoft's
Chakra\footnote{http://en.wikipedia.org/wiki/Chakra (JScript engine)})
do not provide direct access to the native interpreter or execution
context of the caller, so our interpreter cannot lookup names used in
the constraint expression in the callers binding. Instead, those names
have to be passed explicitly.

\langname/JS provides a source transformation based on
\emph{UglifyJS}\footnote{http://lisperator.net/uglifyjs/}, that
collects names from the context and modifies the source code to pass
those names into the constraint expression. This source transformation
is enabled automatically when a programmer uses \langname/JS in the
Lively Kernel environments' \emph{Object Editor}. For other
\javascript code, they have to provide a context object explicitly.  I
we only supported constraints that only access fields of objects in
the scope and do not call user defined functions, we could also have
rewritten the source code and evaluated the constraint expression
using \javascript's \lstinline{eval} function, which has access to the
enclosing scope. Using a custom interpreter, however, allows us to
easily instrument the execution of user-defined functions.

Given a context, a function, and a solver, the ConstraintInterpreter
executes the expressions in the function to create the constraint. The
ConstraintInterpreter subclasses a \javascript interpreter, modifying
its behavior in 3 main aspects:
\begin{itemize}
\item Slot accesses are intercepted. For each slot accessed during the
  execution of a constraint expression, property accessors are created
  that delegate access to a \emph{ConstrainedVariable} object. For
  each slot only one ConstrainedVariable is created on first
  access. ConstrainedVariables manage the communication with the
  various solvers and create solver specific representations of the
  slot value.
\item Certain unary (\lstinline{!} and \lstinline{-}) and binary
  operations (arithmetic, equality, inequalities, conjunction) are not
  interpreted as usual if an operand is a ConstrainedVariable or an
  expression involving ConstrainedVariables. In this case, the
  constraint object is sent a message to construct a solver-specific
  expression representing the operation and that expression is
  returned. For example, in Cassowary, the expression
  \lstinline{a.value <= b.value} would return a
  \emph{LinearInequality} object.
\item Functions invoked in the expression are also interpreted in the
  ConstraintInterpreter by default. However, the plain \javascript
  interpreter is used if the receiver is a ConstrainedVariable. In
  that case, the call is executed using normal \javascript execution
  semantics. This is required to avoid creating constraints on the
  state of the solvers themselves.
\end{itemize}

The responsibility of ConstrainedVariables during constraint
construction is to pass calls to the appropriate solver. To that end,
a ConstrainedVariable lazily builds a mapping from solvers to
solver-specific representations of its value. During construction, if
the programmer has explicitly selected a solver, this solver is asked
to provide a value representation by sending the message
\lstinline{constraintVariableFor} with the value as argument. If no
solver was provided, the value is sent the
\lstinline{constraintSolver} message. Solver libraries may override
this message for types that they can operate on. If the value responds
with a solver instance, this solver becomes the active solver for the
currently constructed constraint and is asked to provide a
representation, again by sending \lstinline{constraintVariableFor}.

Whenever a new representation is created in this manner, the solvers
are sorted to determine which region the variable belongs to. Only the
solver responsible for this region may write to the variable, to all
other solvers it is read-only.

\subsection{Determining Cooperating Solver Regions}
\label{sec:determ-inter-solv}
The architecture for cooperating constraint solvers mandates that each
variable must be read-only in all but one of the regions that it
occurs in. Furthermore, the regions and associated solvers must form
an acyclic graph.

In \langname/JS, when a variable appears in a new solver, we gather
the solvers for the variable and sort them into regions. In the
current implementation, the region is simply a property of a solver
instance. This allows, for example, to use multiple instances of the
same solvers in different regions to solve problems that require the
back and forth between types of solvers.

The variable is marked read-only for all solvers except the one in the
highest region, the \emph{defining solver}. This means that new values
are assigned by calling \lstinline{suggestValue} on the defining
solver, and that all other solvers are triggered (in descending order
of regions) once the defining solver has recalculated its constraints,
as described in \autoref{sec:assignment}.

\subsection{Edit Constraints}
\label{sec:edit-constraints}
Since the original \langname design did not include language-level
support for edit constraints, these were supplied by the solver
libraries. In \langname/R, the meta-level protocol for inspecting
constraints was used to support edit constraints in Cassowary and
DeltaBlue. The programmer called the appropriate edit method with the
objects to be edited and a stream that would provide new values. The
Constraint meta-protocol was used to create edit variables, constrain
them to be equal to the supplied variables, and update them from the
stream.

To support cooperating incremental re-solving
(\cf{\autoref{sec:coop-incr-resolv}}) \langname/JS, there are two
changes to this scheme. First, to support edit constraints within a
single thread, the edit method, instead taking a stream of values,
returns a callback to input new values into the solvers. Second, since
the language design now support edit constraints explicitly, the
solvers have to provide a specific edit constraint \ac{api}.

Upon calling the edit method, the following methods are called on the
solvers and the supplied variables, in order:
\begin{description}
\item[prepareEdit] This method is called on each solver variable. In
  this method, variables can prepare themselves for editing. In
  Cassowary, for example, this would call the \lstinline{addEditVar}
  method on the solver with the variable as argument. For DeltaBlue,
  this creates an \lstinline{EditConstraint} on the variable and adds
  it to the list of constraints.
\item[beginEdit] This method is called once for each solver
  participating in the edit before the callback is returned. In
  Cassowary, this initializes the edit constants array and prepares
  the solver for fast re-solving when these constants change. In
  DeltaBlue, the solver generates an execution plan to solve the
  constraints starting with the EditConstraints as input.
\end{description}

Now the callback can be used to input new values into the system and
trigger re-solving. The callback will call
\textbf{\lstinline{resolveArray}} on each solver with the new values
and update the object's storage (so other observers and hooks around
the values still work). Because the solver's execution plan is fixed
for the duration of an edit, we disallow creating new edit callbacks
before the current edit has finished. When new constraints are
created, the execution plan may also become invalid, but we do not
enforce invalidating the edit callback in this case.

To finish editing, the callback is simply called without supplying new
values.
\begin{description}
\item[finishEdit] Called on each solver variable. Cassowary variables
  do nothing here, DeltaBlue variables remove their EditConstraints
  from the solver.
\item[endEdit] Called once for each solver and reset the solver
  state. Afterwards, the solver
\end{description}

Compared to \langname/R, this makes the interface for edit constraints
unified across solvers and also allows it to work with cooperating
solvers. However, each solver now has to provide some support for
this, so more work is required to enable the feature.

\section{Performance Evaluation}
\label{sec:performance}
Our design tries to provide reasonable performance to be useful for
variety of applications. To judge the performance impact, we evaluated
two scenarios: a) how does constraint solving performance compare to
writing imperative code to satisfy constraints, b) how is
object-oriented performance affected by our extension.

For the first problem, we used a Kaleidoscope example as benchmark
\cite{lopez-asi-1994} (the same benchmark was used for
\langname/R). In this example, we simulate a user interaction where
the user drags a slider to adjust the upper end of the mercury in a
thermometer. The constraints are that the mercury should follow the
mouse, but must not go outside the thermometer, and that the graphical
representation of the thermometer and mercury (using a gray and a
white rectangle) as well as a number displaying the current value
should be updated.

We compare the performance of a purely imperative solution using
branches and assignments, a constraint version that assigns new mouse
locations in a loop, and a version with the same set of constraints,
but using edit constraints (\cf{\autoref{sec:app-performance}}). All
numbers are the average execution time in milliseconds $\pm$ the
standard deviation, we ran each set of iterations 10 times.
\begin{table}
  \centering
  \setlength{\tabcolsep}{3pt}
  \begin{tabular}{l|ccc}
    & Imperative & Constrained Assignment & Edit Constraints \\
    \hline\\
    10x & 0.498 $\pm$ 0.2 & 504 $\pm$ 123 & 48.1 $\pm$ 3.69  \\
    100x & 0.6 $\pm$ 0.3 & 5516 $\pm$ 1913 & 64.2 $\pm$ 8.91 \\
    1000x & 0.899 $\pm$ 0.298 & 33397 $\pm$ 6812 & 117 $\pm$ 10.2 \\
  \end{tabular}
\end{table}

To test how purely object-oriented parts of a system are affected if
we pass objects with constraints to them, we measured the overhead of
field access for constrained versus unconstrained fields by repeatedly
reading the same 5 properties from an object first without and then
with equality constraints on each variable.
\begin{table}
  \centering
  \setlength{\tabcolsep}{3pt}
  \begin{tabular}{l|cc}
    & Unconstrained Access & Constrained Access \\
    \hline\\
    1,000x & 0.1 $\pm$ 0.03 & 162 $\pm$ 22.3 \\
    10,000x & 0.79 $\pm$ 0.39 & 2066 $\pm$ 201 \\
    100,000x & 3.7 $\pm$ 1.48 & 23679 $\pm$ 916 \\
  \end{tabular}
\end{table}

These results are comparable to those for \langname/R. These
micro-benchmarks show that, in extreme cases, the object-constraint
versions are many hundred times slower than the purely imperative
solution. However, using edit constraints, repeated solving of
constraints can give acceptable performance. Considering that
\langname/JS is aimed at imperative programmers that want to express
constraints in some parts of their programs, we expect that most of
the time the \ac{vm} will not be solving constraints in tight loops,
but running mostly imperative code intermingled with constraint
re-satisfaction. We think the benefits for comprehensibility, code
size, and robustness justify the performance impact in some system
parts. In our example applications -- the circuit simulation, color
palette chooser, and temperature converter presented above, as well as
a simple particle simulation, an available-to-promise function, and a
layouting example -- the overhead of constraints was much less
pronounced and they provided interactive performance, often even
without using edit constraints.

\section{Open Problems and Future Work}
\label{sec:futurework}
The current \langname/JS implementation has proven useful for a number
of applications. It implements a number of features from the original
\ac{ocp} design, such as unified language constructs for constraint
definition and object-oriented code, automatic maintenance of
constraints, integration with the existing syntax and semantics, an
interface to add new solvers and a constraint solver constructs such
as read-only variables and incremental re-solving. There are a number
of directions for future work.

\paragraph{Constant Read-only Variables}
\label{sec:read-only-constr}
Currently, when variables shared between solver regions are marked
read-only in all but one of the regions, they still appear variable to
the solvers (although constrained to equal one particular, upstream
value). This means that solvers with restrictions on how variables can
be connected may not be able to solve some constraints. For instance,
Cassowary can only solve linear constraints, so it cannot find a
solution to the following expression:
\begin{code}
always(function() { return o.resistance * o.current == o.voltage }
\end{code}
However, if \lstinline{o.current} is determined by an upstream solver
(for example, it is connected to an input field with DeltaBlue), it
should be treated as constant in this constraint and Cassowary should
be able to solve it.

\paragraph{Debugging, Explanation, and Solver Selection}
It is currently difficult to tell why a solver may not be able to
satisfy a given constraint, why it produced an unexpected result, or
why finding a solution is slow. Our ConstraintInterpreter should have
support for reasoning about the built constraint system. Prolog (or
just a direct backtracking algorithm) may be useful as a
``meta-solver'' to find a solver (or set of solvers) for a particular
constraint automatically.

\paragraph{Other \langname/R features}
\label{sec:other-babelsb-feat}
\langname/R included support for more \ac{ocp} features that we have
ignored in this work. Specifically, we should add support for identity
\cite{lopez-ecoop-1994}, class, and message protocol
constraints. Furthermore, to control when solving is invoked,
\langname/R provided multi-assignments to update multiple values
simultaneously before a solver is invoked again. Finally, we don't
provide the convenience methods \lstinline{once} and
\lstinline{assert...during...} to control the duration of constraints,
although these could be trivially added using the meta-protocol of
\lstinline{Constraint} objects.

\paragraph{Color Chooser}
\label{sec:color-chooser}
The entire palette (\lstinline{self}) averages its luminance and hue
values from the colors. The colors are connected by constraints to
create the sum of luminances and hues.
\begin{code}
var previous = undefined;
colors.each(function (ea) {
    always({solver: cassowary}, function() {
         if (previous) {
             return color.lumSum == color.luminance + previous.lumSum &&
                    color.hueSum == color.hue + previous.hueSum
         } else {
             return color.lumSum == color.luminance &&
                    color.hueSum == color.hue;
         }
    });
    previous = ea;
});

always({solver: cassowary}, function() {
     return color.lumSum / pixelCount == self.luminance &&
            color.hueSum / pixelCount == self.hue
});
\end{code}

Each color is represented by a rectangle and has a set of constraints
\begin{code}
// Tell the solver to stay within Lively RGB color range
always({solver: cassowary}, function() {
     var c = rect.getFill();
     return c.r >= 0 && c.g >= 0 && c.b >= 0 &&
            c.r <= 1 && c.g <= 1 && c.b <= 1
});
// Calculate luminance
always({solver: cassowary}, function() {
     var c = rect.getFill();
     return rect.luminance == 0.2126 * c.r + 0.7152 * c.g + 0.0722 * c.b
});
// Approximate hue
always({solver: cassowary}, function() {
     var c = rect.getFill();
     return rect.hue == (c.r + (c.b * 2 + 1) + (c.g * 3 + 2)) / 9.0
});
// Constrain luminance and hue to be close to the palette average
always({solver: cassowary}, function() {
     return self.hue * 0.8 <= rect.hue &&
            self.luminance * 0.8 <= rect.luminance
});
\end{code}

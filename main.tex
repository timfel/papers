\section{Introduction}

Constraints are relations between objects that should hold. This could
be that all parts in an electrical circuit simulation obey the laws of
physics, that the rows in a Sudoku include each digit from 0 to 9, or
that a streamed video play smoothly in the presence of changing CPU or
network load.

\langname\cite{FelgBorningJot2014} proposed an integration of
constraint satisfaction with objects and their methods, building on
the earlier work on constraint-imperative programming in
Kaleidoscope\cite{lopez1994kaleidoscope} and
Turtle\cite{grabmuller2004turtle}. In \langname, constraints are
expressed like assertions using the underlying object-oriented
language. The constraint is that the assertion evaluates to true, and
the system maintains this constraint automatically whenever objects
that particpate in the constraint change.

\langname improves on related approaches to constraint satisfaction in
object-oriented programs, which use
libraries\cite{badros2001cassowary,de2008z3,torlak2007kodkod},
domain-specific languages\cite{AppleCocoaAutoLayout,Enaml}, or (more
recently) functional-reactive
programming\cite{ohshima2012report,meyerovich2009flapjax} to specify
constraints. These approaches do not need special runtime support, but
require the programmer to call specific \acp{api} or follow certain
rules to not accidentally circumvent the constraints.

The initial \langname design described a \ac{vm} extension for Ruby
called \langname/R, but not if the design can be implemented without
\ac{vm} support. In this work, we describe an implementation of
\langname as a \javascript library that we call
\langname/JS. \javascript is currently of great interest in the
industry and research communities and runs in all modern Web
browsers. This enables us to apply Babelsberg/JS to a variety of
existing problems and compare it directly with alternative solutions.

The typical execution environment for \javascript --- the Web browser
--- presents additional challenges the \langname design does not
consider. First, \langname assumes that the environment is open and
solvers can ignore encapsulation and modify data structures
directly. However, some Web browser data structures --- like the
window object --- can only be manipulated using dedicated
\acp{api}. Second, interactive \javascript-based rich web applications
require that the system react quickly to user input --- for example,
dragging a graphical object must be smooth, even if there are
constraints on that objects position.

In this work, we address these shortcomings. To call the browser
\acp{api}, we use DeltaBlue\cite{freeman1989deltablue}, a local
propagation solver. We implement an architecture for interactions
between different constraint solvers\cite{borning2012architectures}
that allows developers to use specialized solvers like
Cassowary\cite{badros2001cassowary} or Z3\cite{de2008z3} in their
domain code, and have the system automatically update the local
propagation constraints via connected variables. To provide
interactive performance, we support incremental solving in combination
with interacting solvers design. Incremental solving is available, for
example, as edit constraints in DeltaBlue and Cassowary.

The contributions of this work thus are:
\begin{itemize}
\item A description of the features a language needs to provide in
  order to support the \langname design without \ac{vm} support and
  its implementation in \javascript
\item A detailed architecture of a design for interacting constraint
  solvers
\item A design to support edit constraints for incremental
  re-satisfaction in interactive settings across multiple interacting
  solvers
\end{itemize}

\section{Background and Related Work}
\label{sec:background}

Programs frequently have some set of constraints that should hold.
For standard imperative languages, the usual approach to dealing with
such constraints is to leave it entirely up to the programmer to
ensure that they are satisfied --- the constraints may be just in
comments and documentation, or perhaps in the form of
machine-checkable assertions.  For the latter case, programmers
typically write assertions to fail early if these constraints are
unexpectedly not satisfied~\cite{rinard2005exploring}. However, some
constraints describe invalid system states that can be automatically
corrected. To deal with such constraints, programmers may write code
that is executed at various times throughout the execution to check
and correct invalid state. In these cases, it is usually clearer to
express and satisfy constraints explicitly, rather than encoding them
with control flow and state changing
operations~\cite{FelgBorningJot2014}.

One approach is to use a library that provides one or more constraint
solvers. A large number of solvers that cover a wide range of type
domains (such as reals, booleans, or finite sets) is available for
imperative languages and can be called from imperative
code~\cite{torlak2007kodkod,de2008z3,badros2001cassowary,freeman1989deltablue}.
For more specialized domains such as user interface layout, some
libraries provide separate \acp{dsl} to express for example minimal
distances between graphical objects. Prominent examples here include
the Mac OS X layout specification language~\cite{AppleCocoaAutoLayout}
and the Qt GUI framework~\todo{cite}.

Another approach, however, is to integrate a means to express and
maintain constraints with the language itself. Some languages such as
Scratch~\todo{cite}, LivelyKernel~\todo{cite}, and
KScript~\cite{ohshima2012report} have built-in support for data flow,
which allows programmers to express unidirectional constraints between
objects. To support a broader set of constraints, some languages
directly integrate one or more solvers into their execution
model. Again, there is a huge body of prior art in this area, examples
include Constraint Logic Programming~\todo{cite}, Constraint
Imperative
Programming~\cite{lopez1994kaleidoscope,grabmuller2004turtle}, and
Object Constraint Programming, which \langname is an instance
of. Object Constraint Programming differs from the former in that it
focuses on object-orientation as the main paradigm. It tries to
integrate declarative constraints in a way that does not compromise
the expectations of imperative object-oriented programmers and to
provide a declarative semantics that is compatible with these
expectations.

\langname is a design for a family of object constraint languages that
integrate constraints with an existing object-oriented language. Its
goals include:
\begin{itemize}
\item a syntax and semantics that are a strict superset and fully
  compatible with the base language
\item performance that is competitive with the base language for
  purely object-oriented code
\item support for required and preferential constraints, constraints
  on object identity, variables that are readonly to solvers or
  imperative code, as well as incremental resolving for use in
  interactive applications
\item an \ac{api} for constraint solvers that makes it straightforward
  to add new solvers and does not privilege the solvers provided with
  the implementation, to make it easy to use different solvers in
  different programs
\end{itemize}
The first implementation of \langname is \langname/R, based on a
modified Ruby \ac{vm}.

\section{\langname/JS}
\label{sec:design}

\javascript is currently of great interest to the research
community. In the industry, it has become the de-facto standard for
Web programming and a huge amount of code exists in the
language. \javascript's unique language design and its execution
environment in the Web browser currently prompt much research to
revise and adapt existing features of other systems\todo{cite
  JSproxies paper from ecoop12, Dart paper, js module system
  paper}.

To provide practical support for object-constraint programming in
\javascript, we adapt the \langname design to not require support from
the underlying \ac{vm}. This enables us to run \langname/JS in modern
browsers and use it in a variety of practical Web applications.

\subsection{Object Constraint Programming without VM Support}
\label{sec:vm-support}

\langname/R was built as an extension to a Ruby \ac{vm}. The extension
is two-fold:
\begin{itemize}
\item The \ac{vm} was extended to support \emph{constrained
    variables}. These variables refer to different objects depending
  on the context they are used in. One is the normal object-oriented
  binding used in the host language execution. The other is a
  constraint object that can be used by a solver for constraint
  construction and solving. Variables become to constrained variables
  only when they are used in a constraint, minimizing the performance
  impact for parts of the program where only unconstrained variables
  are accessed.
\item The \langname/R interpreter distinguishes between different
  execution modes: normal \emph{imperative execution} and
  \emph{constraint construction}. A primitive --- \lstinline{always}
  --- was added to execute a closure in constraint construction
  mode. In this mode, the bytecodes for \load and \store were modified
  to refer to the constraint objects of constrained variables. Normal
  variables are automatically promoted to constrained variables in
  this mode. During imperative execution, assignments to constrained
  variables trigger recalculation of the constraints.
\end{itemize}

We have thus identified the following requirements for implementing
the \langname scheme without \ac{vm} support:
\begin{itemize}
\item The host language must support a means to intercept variable
  lookup, so names can refer to different objects.
\item The host language must provide a means to modify interpretation
  of a block of code to implement the constraint construction mode.
\end{itemize}

The first requirement is partially supported in \javascript for object
fields using property accessors. We limit ourselves to constraining
fields in \langname/JS, but not local variables. In doing so, we can
define property accessors on objects that are used in constraints to
intercept their field lookup and storage.  Second, to execute code in
a constraint construction mode, we use a modified \javascript
interpreter written in \javascript and a source code
transformation,\todo{we could have used just source transformation and
  eval? not really, but the answer is more complicated} because
popular \javascript \acp{vm}~\todo{cite} usually do not provide direct
access to the native interpreter.

\subsection{Interacting Constraint Libraries}
\label{sec:inter-constr-libr}

A huge body of work exists that describes approaches to integrate
different constraint solvers\todo{cite grabmüller,smt}. In this work,
we chose to implement a design for interacting solvers that partitions
constraints into regions which are connected through read-only
variables\cite{borning2012architectures}.

In \langname/JS, each constraint belongs to a particular solver. All
constraints that belong to the same solver are in the same
region. Variables that occur in multiple constraints that belong to
different solvers are read-only in all but one of the
solvers. Read-only variables are represented in a solver specific
manner, either through \emph{stay constraints} for solvers that
support them, or through required equality constraints. We require
solver libraries to provide a method to make a variable read-only for
that solver.

To sort regions, each solver has an associated weight. Solver
libraries define default weights, but the programmer can assign an
instance specific weight to each solver instance. This allows
applications to use multiple instances of the same solver type (this
can be used, for example, to break up non-linear constraints into
multiple linear constraints and solve them with Cassowary).

Once the solver regions are sorted, solving proceeds in order of
descending weight. Each region will determine values for the variables
it can write to, and the downstream regions will adjust to accommodate
the new values assigned to read-only variables from higher level
regions.

In contrast to \langname/R, we cannot defer assigning the values from
the solver to the object-oriented variable. Consider the following two
constraints:

\begin{code}
aCassowarySolver.weight = 10;
aDeltaBlueSolver.weight = 1;
var a, b;

always({solver: aCassowarySolver}, function() {
    return a == b;
});

always({solver: aDeltaBlueSolver, methods: function() {
        a.formula([window.title], function(s) { return parseFloat(s) });
        window.title.formula([a], function(n) { return n + "" });
       }}, function() {
    return a == string;
});
\end{code}

The first constraint uses Cassowary to make \lstinline{a} and
\lstinline{b} refer to the same real value (because Cassowary works
only on reals, \lstinline{a} and \lstinline{b} are coerced into
\javascript floats in the constraint). The second constraint uses
local propagation to make the browser window title reflect the value
of \lstinline{a}. (Note that due to the assigned weights,
\lstinline{a} is read-only for DeltaBlue, so we could also have
omitted the first formula).

If we now assign \lstinline{a = 20}, both solvers will be triggered,
because both have a reference to a constraint that \lstinline{a}
participates in, and both \lstinline{b} and the
\lstinline{window.title} will show the new value on the next
read.

However, if we assign \lstinline{b = 10}, only Cassowary will be
triggered, because \lstinline{b} is only referenced in the Cassowary
constraint. We found that to support the expected behavior that the
window title is updated on either assignment, we have to eagerly
trigger constraint satisfaction for the transitive closure of
variables connected to the variable that is assigned.

In \langname/R, lazy variable was an optimization. We cannot apply
this optimization when assigning to variables that participate in any
constraint that has variables visible in multiple solvers. However,
the optimization can still be applied to variables whose transitive
closure of connected variables is local to one region.

\subsection{Cooperating Incremental Resolving}
\label{sec:coop-incr-resolv}

\emph{The gist here is that we use the edit method. The edit method
  here returns a callback function instead of accepting a stream,
  because this is more in line with the nature of JavaScript.}

\emph{For the edit function, instead of creating new variables plus
  equalities as in Babelsberg/R, we check which solvers the variable
  is in. The algorithm is then:
\begin{itemize}
\item mark the variable as edit variable in all solvers it
  participates in (e.g. beginEdit for cassowary and new
  EditConstraint(var) for DeltaBlue). Remove all read-only
  annotations for the edit variables.
\item create a callback function that, on each call:
  \begin{itemize}
  \item assigns new edit constants
  \item triggers resolving
  \item updates read-only constraints for changed variables in
    downstream regions, triggering those solvers (this part is
    potentially slow. we can optimize it by creating edit
    constraints for those connected variables as well. question is,
    what do we do if we interleave creating new constraints and
    calling the edit callback - do we just disallow that?)
  \end{itemize}
\item on end edit (by calling the callback function without
  arguments), the read-only annotations are put back
\end{itemize}
}

\subsection{Assignment}
\label{sec:assignment}
\emph{During constraint construction, if the variable has an
  interpretation (``is\_solveable'') in the currently active solver,
  an equality constraint is asserted, otherwise it is simply
  stored. Normally, assignment is a 3-step process
  \begin{description}
  \item[Begin Assign]
    \begin{enumerate}
    \item Disable all readonly constraints (equality constraints on
      the current value)
    \item Store the new value
    \item If there are solver-variables, pick the the most upstream
      variable and call begin\_assign on the (usually asserts an
      equality constraint, but solver specific)
    \end{enumerate}
  \item[Assign]
    \begin{enumerate}
    \item If there are solver-variables, pick the most upstream one
      and call assign on that (usually triggers the solver to
      resatisfy its constraints, including the previously asserted
      equality constraint with the new value)
    \item Now call begin\_assign and assign on all
      solver-variables with the new value on all downstream
      solvers
    \end{enumerate}
  \item[End Assign]
    \begin{enumerate}
    \item Call end\_assign on the most upstream solver-variable
      (usually removes the equality constraint created in
      begin\_assign)
    \item Re-enable all the readonly constraints with the new value
    \item For all constraints this variable appears in that have no
      solver-variable for this variable, recalculate the path (this
      will use the new value to re-evaluate the closure in the solver
      - note that this may mean that a solver-variable is subsequently
      created if the variable type changed, but the other way around
      doesn't work. We should probably not allow changing the domain
      of variables that already occured in constraints)
    \end{enumerate}
  \end{description}
}

\emph{we can currently relax this scheme in javascript, because we
  don't support multi-assignment and identity constraints. without
  these, we can do the assignment in one step}

\emph{after assignment, we update all connected variables by assigning
  them the current solver value, if it has changed. this will
  recursively update connected variables until the solvers stop
  changing them. IMPORTANT: I need to explain why this won't

\emph{Complex object assignments (like points) are handled differently
  in JavaScript compared to Babelsberg/R: to behave in an expected
  way, we first try to assign the complex object as-is (that is, the
  rest of the system may change to accomodate the new object, but the
  object itself and its parts are readonly to the solver). We do this
  so the dragging example works, where the x and y values of the
  positions of the mouse and the dragged morph should be equal. when
  we move the mouse, the system should adjust the morph, not the mouse
  pointer. However, if, for example, we have a requirement that the
  morph cannot leave a container, this scheme will fail if we drag
  with the mouse outside of that container (because the new position
  is invalid for the morph, but we made it readonly). As a fallback,
  when assigning complex objects, we remove the readonly
  constraint. This seems to meet expectations when programming user
  interactions via constraints}

\section{Future Work}

\paragraph{Meta-solver}
Prolog (or just a direct backtracking algorithm) may be useful as
meta-solver. Try to find a solver to solve a particular constraint. As
we add constraints, try to always have each constraint handled by a
solver that allows to solve all constraints in the system.
Problem: This means that asserting a new constraint may backtrack
through all constraints in the system (CSP)

\lstinline{once} and \lstinline{assert...during...}, although these

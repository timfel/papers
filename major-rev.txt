More concrete intro
	In the introduction, I am missing a clearer "our debugger is for this scenario" description. It is implicitly said, but for me it got only clear with the example later. Can you explicitly state the use cases for the debugger? The paper does a good job showing the power of the tool for the example, but the introduction does not clearly define which kinds of scenarios it supports.

The EXAMPLE and how concretely we fix the bug
	- Also, while the paper starts with an example, it could go into more details in showing how the approach applies to that example.
	- I would have expected a more concrete discussion of how the proposed approach can be used to solve a bug. While the paper presents a problem in the example application and gives several screenshots of the tool at various steps in the debugging process it's not clear where the bug was nor what exactly is the information that can help a developer pin-point the bug. In several places the paper mentions that developers can use the tool to filter information or understand the failure, but stops short of illustrating these aspects on the example application.
	- Related to this: The paper uses the running example to show how to use the debugger. But at the end, I was a bit lost about what exactly I have to do as a user of the debugger to be able to use it efficiently.
	- I would like to have some kind of summary: needed preconditions / preparation, as well as summary of the interactions with the debugger to find and fix the bug.
	- Section 5) What are the limitations? Can you annotate everything or are the still exceptions? When do I as a user of the debugger need to know/use this?
	- Section 6) (Or maybe before): It is not quite clear what exactly the constraints are when this debugger can be used as-is, and, conversely, if (and how) the techniques could be useful for other contexts. This is I guess future work (or another paper), but I would like to see a bit more discussion here.

The paper is implementation driven
	- the paper heavily mixes conceptual ideas with implementation details and scenario details
	- I have the impression you should make your paper focus on the idea instead of the implementation. Said in other terms, what are the key ingredients that I need to care about if I want to reproduce your approach in a radically different context? 
	
The paper is example driven
	- About the example. It is highly detailed throughout the paper. This makes me wonder whether your application may be efficiently employed in a different setting. By the way, there is a plethora of applications made for Squeak. Why not using one of these as a running example? This flight system seems to be self-made for the paper, which weakens your paper.
	- The nice running example has one weakness: It is not very clear where the example stops and the tool starts and
	if the technique can be used for other setting (the HTTP case). The paper presents to tool as a general debugger, but it seems to be that (out of the box) it is useful for a constraint scenario. Yet it seems to be more general than that in principle.

Related Work
	- expected a better related work
	- As a disadvantage of record-and-replay techniques the paper states that they are hard to understand but does not say why. What makes this approach inherently easier to understand?
	- Regarding the related work, in the introduction the paper dismisses quite quickly post-mortem debugging as it imposes large overheads and record and replay as it provides the wrong level of abstraction. The related work section could go into more details regarding the aforementioned claims.

Diagnosis Scripts and recording
	- the negative side the entry point (e.g., diagnostic scripts) has to reliably reproduce the error. Given the inherent complexity of distributed application writing a script that reproduces a failing scenario might not always be as trivial as making a lot of request to a web server. 
	- An important aspect of the presented approach is that it is based on an image based programming language. By default the debugger/recorder and the application under monitoring will run in the same object space. Hence, the debugger/recorder will anyhow influence the application under analysis. At the very least the debugger/recorder will create objects that will influence the performance of the garbage collector. A more in depth discussion about using in-process or external debuggers/recorders would be welcomed. Some approaches for replay and record use external recorders that require no instrumentation of the system/application.
	- The presented approach starts by executing a diagnostic script against the application until a failing schedule is reproduced. A different approach, when one works in a closed-world case, could be to force different schedules until a problematic one arrises instead of  executing the application with the hope that a failing schedule will occur. Do you have any thoughts, if depending on the particularities of a distributed application, one of these approaches would be a better fit?
	- Can the presented approach find failures caused by timing dependencies between the client and the server or just between different components on the server side? From the way the example is presented the developer that aims to find the cause of the failure will run the script from one of his machines. Other clients would access the server from networks with different latencies. An error that appears only when the client's networks has certain latencies would be difficult to catch. Since the paper states that the approach currently applies only in closed-world cases I guess it does not target this. Making the actual bug from the example more concrete should address this aspect.
	- Also, even if the recording has a small overhead, executing a script 1000 times against a live application might cause a small denial of service attack. Can this be avoided, for example, by executing scripts with a short delay?
	
Evaluation
	- The last paragraph from Section 8 states that the tool was evaluated with actual developers but gives no further information. Is there a publication available? If not, a paragraph summarising the findings would be welcomed.

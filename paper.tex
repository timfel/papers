\section{Introduction and Background}

Programming language implementation frameworks have become more and more popular
as they allow language implementers to use another high-level language and
useful reusable components, such as garbage collectors or caching mechanisms,
to implement virtual execution environments for dynamic languages.
These frameworks, however, often enforce certain implementation styles and are
usually designed to support only one kind of interpretation model.
RPython~\cite{Ancona:2007:RST:1297081.1297091}, a language implementation
framework maintained as part of the PyPy project, for example, is mainly used to
implement bytecode interpreters as it provides a tracing \ac{jit} compiler which
is designed to operate on bytecode.
Oracle's Truffle framework~\cite{Wurthinger:2013:OVR:2509578.2509581}, on the
other hand, is designed for implementing \ac{ast} interpreters and its \ac{jit}
compiler applies \ac{ast} node rewriting and partial evaluation to significantly
increase runtime performance of corresponding interpreters.

Therefore, it is no surprise that most languages implementations in Truffle are
\ac{ast}-based.
In order to be able to interpret LLVM bytecode on top of the GraalVM, for
example, Sulong~\cite{Rigger:2016:BLL:2998415.2998416} has been developed and
Truffle has been extended with optimization mechanisms specifically for bytecode
interpreters.
Nonetheless and at the time of writing, the process of implementing bytecode
interpreters in Truffle was not well documented which is one motivation for this
paper.

\Squeak~\cite{ingalls1997back} is a Smalltalk dialect derived from the
Smalltalk-80 language specification.
Its default virtual machine OpenSmalltalkVM~\cite{openSmalltalkVM} is
bytecode-based and features a mostly handwritten \ac{jit} compiler.
RSqueak/VM~\cite{Felgentreff:2016:BHV:2991041.2991062,Bolz2008} is an
alternative \ac{vm} for \Squeak and is written in RPython.
With SOMns~\cite{Marr:2017:CPCD}, a Smalltalk-like interpreter is already
implemented in Truffle.
However, it operates entirely on \acp{ast} as it is not image-based like
traditional Smalltalk-80 systems and can therefore be well optimized on
GraalVM~\cite{Wurthinger:2013:OVR:2509578.2509581}, the \ac{vm} on which Truffle
language interpreters run.

In this paper, we present and compare the implementations of an \ac{ast}
interpreter and a bytecode interpreter both for \Squeak and written in
the Truffle framework.
We report our experiences implementing the different interpretation models in
Truffle, discuss implementation pitfalls, and compare the performance of the
different interpreters with a micro benchmark.

\paragraph{AST Interpreter}

Since Truffle and the Graal compiler operate on \acp{ast}, the natural way of
implementing a \Squeak interpreter in Truffle is to write an \ac{ast}
interpreter.
However, \Squeak is traditionally bytecode-based, so bytecode streams need to
be transformed into appropriate \ac{ast} nodes.

\begin{figure}
  \centering
  \includegraphics[width=.9\linewidth]{resources/squeak-ast}
  \caption{Architecture of an \ac{ast} interpreter for Smalltalk in Truffle.}
  \label{fig:squeak-ast}
\end{figure}

\autoref{fig:squeak-ast} gives an overview of how the architecture of this setup
can look like.
For each Smalltalk method, Smalltalk code is first parsed into a \Squeak
\ac{ast}.
This \ac{ast} is then compiled to bytecode by \Squeak's compiler.
The Truffle interpreter has no direct access to the original \ac{ast} and can
therefore only see \Squeak bytecode.
In order to transform the bytecode into corresponding nodes again, we have
implemented a custom decompiler which is able to reconstruct the original
\ac{ast} with Truffle nodes.
Finally, Truffle and Graal can execute this \ac{ast} and perform their
performance optimizations.

As it turned out, however, a simple one-to-one node mapping from \Squeak to
Truffle nodes was not sufficient to gain reasonable performance on the GraalVM.
The main reason for this is that \Squeak uses unconditional and conditional
jump bytecodes to realize loops.
In Truffle, on the other hand, there is a dedicated \lstinline{LoopNode} for
which the runtime provides additional optimization strategies.
Therefore, we extended the decompiler in such a way, so that it detects loops in
Smalltalk code and emits appropriate \lstinline{LoopNodes} instead of jump
nodes.

@ExplodeLoop(kind = LoopExplosionKind.MERGE_EXPLODE)
Object executeLoopFast(VirtualFrame frame) {
 CompilerAsserts.compilationConstant(bcNodes.length);
 int pc = 0;
 int backJumpCounter = 0;
 try {
  while (pc >= 0) {
   CompilerAsserts.partialEvaluationConstant(pc);
   AbstractBytecodeNode node = bcNodes[pc];
   if (node instanceof ConJumpNode) {
    ConJumpNode jumpNode = (ConJumpNode) node;
    boolean c = jumpNode.executeCondition(frame);
    if (CompilerDirectives.injectBranchProbability(
         jumpNode.getProbability(JUMP), c)) {
     int successor = jumpNode.getJumpSuccessor();
     if (CompilerDirectives.inInterpreter()) {
      jumpNode.increaseProbability(JUMP);
      if (successor <= pc) backJumpCounter++;
     }
     pc = successor;
     continue;
    } else {
     int successor = jumpNode.getNoJumpSuccessor();
     if (CompilerDirectives.inInterpreter()) {
      jumpNode.increaseProbability(NO_JUMP);
      if (successor <= pc) backJumpCounter++;
     }
     pc = successor;
     continue;
    }
   } else if (node instanceof UncondJumpNode) {
    UncondJumpNode jumpNode = (UncondJumpNode) node;
    int successor = jumpNode.getJumpSuccessor();
    if (CompilerDirectives.inInterpreter()) {
     if (successor <= pc) backJumpCounter++;
    }
    pc = successor;
    continue;
   } else { pc = node.executeInt(frame); }
  }
 } finally {
  LoopNode.reportLoopCount(this, backJumpCounter);
 }
}
\end{lstlisting}


\section{Evaluation}

To assess the performance of our Truffle-based interpreters for \Squeak, we used
\lstinline{tinyBenchmarks} which consists of two micro-benchmarks:
The first one is bytecode-heavy as it allocates, fills, and reads from a large
array.
The other one is a recursive Fibonacci benchmark and therefore send-heavy.
Additionally, \lstinline{tinyBenchmarks} adjusts both benchmarks so that they
run to least one second in order to produce more stable results.
Although the results should be taken with a grain of salt as they do not
represent a wide range of common operations, we believe they are a good
indicator for the overall performance of the different interpreter approaches.

We ran the benchmarks on a 15-inch MacBook Pro from Mid 2015
(CPU: 2.5 GHz Intel Core i7; Memory: 16 GB 1600 MHz DDR3).
For the \ac{ast} interpreter, we used commit \lstinline{8126c1b} of GraalSqueak
and \lstinline{ac530ac} for the bytecode interpreter with loop-reporting.
Moreover, we copied the later version of GraalSqueak and replaced
\lstinline{SqueakMethodNode.executeLoop(VirtualFrame frame)} with the code in
\autoref{fig:loop1} to turn of loop-reporting.
We also ran the benchmarks on other \Squeak \acp{vm}, a recent OpenSmalltalkVM
(tag \lstinline{201804030952}) and RSqueak/VM (commit \lstinline{d33005c}).

\autoref{fig:bytecodes} shows the benchmark results of the bytecode-heavy
micro-benchmark.

The results of the OpenSmalltalkVM can be treated as the baseline as it is the
default \ac{vm} for \Squeak.
It performs relatively stable at around three billion bytecodes per second while
RSqueak/VM is able to process approximately 2.1 billion bytecodes per second.
When we looks at the results of the \ac{ast}-based GraalSqueak implementation,
we notice warmup behavior.
After around two iterations, performance reaches a somewhat stable state.
At the same time, it outperforms the OpenSmalltalkVM by approximately $3.06$x.
The bytecode interpreter, on the other hand, does not show this warmup behavior
and is with an average of ten billion bytecodes per second the fastest \ac{vm}.
Without loop-reporting, however, Truffle is unable to perform its optimizations
due to escaping frames and the otherwise identical interpreter performs very
poorly.

\autoref{fig:sends} shows the recursive Fibonacci benchmark.
RSqueakVM performs much worse compared to the OpenSmalltalkVM.
Although the GraalSqueak interpreters still outperform it, the relative
difference is not as big as in the previous benchmark.
The \ac{ast} interpreter is approximately $1.42$x faster and bytecode
interpreter around $1.47$x.
Again, the performance of the bytecode interpreter with loop-reporting disabled
is very low compared to all other \acp{vm}.

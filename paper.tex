\begin{abstract}

Language implementation frameworks aim to provide everything needed to build
interpreters.
At the same time, they enforce various constraints on language implementations
to be able to perform their optimization techniques.

Truffle, the language implementation framework for the GraalVM, is designed for
building \acrlong{ast} interpreters but it can also be used to implement bytecode
interpreters.

In this paper, we show how we have implemented interpreters using different
approaches for the bytecode-based language \Squeak in Truffle and explain the
measures taken to gain good performance.
Further, we compare the their performance with other \Squeak \acrlongpl{vm} and
discuss the advantages and disadvantages of our different approaches.

\end{abstract}

\section{Introduction and Background}

Programming language implementation frameworks have become more and more popular
as they allow language implementers to use another high-level language and
useful reusable components, such as garbage collectors or caching mechanisms,
to implement virtual execution environments for dynamic languages.
These frameworks, however, often enforce certain implementation styles and are
usually designed to support only one kind of interpretation model.
RPython~\cite{Ancona:2007:RST:1297081.1297091}, a language implementation
framework maintained as part of the PyPy project, for example, is mainly used to
implement bytecode interpreters as it provides a tracing \ac{jit} compiler which
is designed to operate on bytecode.
Oracle's Truffle framework~\cite{Wurthinger:2013:OVR:2509578.2509581}, on the
other hand, is designed for implementing \ac{ast} interpreters and its \ac{jit}
compiler applies \ac{ast} node rewriting and partial evaluation to significantly
increase runtime performance of corresponding interpreters.

Therefore, it is no surprise that most languages implementations in Truffle are
\ac{ast}-based.
In order to be able to interpret LLVM bytecode on top of the GraalVM, for
example, Sulong~\cite{Rigger:2016:BLL:2998415.2998416} has been developed and
Truffle has been extended with optimization mechanisms specifically for bytecode
interpreters.
Nonetheless and at the time of writing, the process of implementing bytecode
interpreters in Truffle was not well documented which is one motivation for this
paper.

\Squeak~\cite{ingalls1997back} is a Smalltalk dialect derived from the
Smalltalk-80 language specification.
Its default virtual machine OpenSmalltalkVM~\cite{openSmalltalkVM} is
bytecode-based and features a mostly handwritten \ac{jit} compiler.
RSqueak/VM~\cite{Felgentreff:2016:BHV:2991041.2991062,Bolz2008} is an
alternative \ac{vm} for \Squeak and is written in RPython.
With SOMns~\cite{Marr:2017:CPCD}, a Smalltalk-like interpreter is already
implemented in Truffle.
However, it operates entirely on \acp{ast} as it is not image-based like
traditional Smalltalk-80 systems and can therefore be well optimized on
GraalVM~\cite{Wurthinger:2013:OVR:2509578.2509581}, the \ac{vm} on which Truffle
language interpreters run.

In this paper, we present and compare the implementations of an \ac{ast}
interpreter and a bytecode interpreter both for \Squeak and written in
the Truffle framework.
We report our experiences implementing the different interpretation models in
Truffle, discuss implementation pitfalls, and compare the performance of the
different interpreters with a micro benchmark.

\section{Implementations}

In this section, we present two different approaches for implementing
\Squeak interpreters in Truffle.
The source code of the GraalSqueak interpreter variations is available on
GitHub~\footnote{\url{https://github.com/...} (will be made public upon publication)}.
% (Short overview of the rest: implementation of bytecodes, primitives, plugins?)

\paragraph{AST Interpreter}

Since Truffle and the Graal compiler operate on \acp{ast}, the natural way of
implementing a \Squeak interpreter in Truffle is to write an \ac{ast}
interpreter.
However, \Squeak is traditionally bytecode-based, so bytecode streams need to
be transformed into appropriate \ac{ast} nodes.

\begin{figure}
  \centering
  \includegraphics[width=.9\linewidth]{resources/squeak-ast}
  \caption{Architecture of an \ac{ast} interpreter for Smalltalk in Truffle.}
  \label{fig:squeak-ast}
\end{figure}

\autoref{fig:squeak-ast} gives an overview of how the architecture of this setup
can look like.
For each Smalltalk method, Smalltalk code is first parsed into a \Squeak
\ac{ast}.
This \ac{ast} is then compiled to bytecode by \Squeak's compiler.
The Truffle interpreter has no direct access to the original \ac{ast} and can
therefore only see \Squeak bytecode.
In order to transform the bytecode into corresponding nodes again, we have
implemented a custom decompiler which is able to reconstruct an \ac{ast} with
Truffle nodes.
Finally, Truffle and Graal can execute this \ac{ast} and perform their
performance optimizations.

As it turned out, however, a simple one-to-one node mapping from \Squeak to
Truffle nodes was not sufficient to gain reasonable performance on the GraalVM.
The main reason for this is that \Squeak uses unconditional and conditional
jump bytecodes for loops.
In Truffle, on the other hand, there is a dedicated \lstinline{LoopNode} for
which the runtime provides dedicated optimization strategies.
Therefore, extending the decompiler so that it detects loops in Smalltalk code
and emits appropriate \lstinline{LoopNodes} instead of jump nodes significantly
improved the performance of the interpreter on the GraalVM.


\paragraph{Bytecode Interpreter}

\begin{figure}
  \centering
  \includegraphics[width=.9\linewidth]{resources/bc-vs-ast}
  \caption{A bytecode stream and a sequence of \ac{ast} nodes.}
  \label{fig:bc-vs-ast}
\end{figure}

\autoref{fig:bc-vs-ast} shows how a stream of bytecode can be represented by a
chain of \ac{ast} nodes.
Each node can only have exactly one or, in the case of a conditional jump, two
successors, because these jumps are the only way to branch in \Squeak.

\begin{lstlisting}[language=Java,caption={A simple loop for interpreting sequences of \ac{ast} nodes.},label=fig:loop1]
Object executeLoop(VirtualFrame frame) {
  int pc = 0;
  while (pc >= 0) {
    pc = bytecodeNodes[pc].executeInt(frame);
  }
}
\end{lstlisting}

Consequently, we can define an interpreter loop as shown in \autoref{fig:loop1}.
However, running this loop with Truffle on the GraalVM will give rather low
performance.
At the same time, Truffle compiler threads report that they fail to optimize
Smalltalk code because of escaping frame objects.
In order to inform Truffle about our bytecode interpreter, we had to add
several annotations and hints which we now explain in more detail.


\begin{lstlisting}[language=Java,caption={Bytecode loop with hints for the Graal compiler.},label=fig:loop2]
@ExplodeLoop(kind = LoopExplosionKind.MERGE_EXPLODE)
Object executeLoopFast(VirtualFrame frame) {
 CompilerAsserts.compilationConstant(bcNodes.length);
 int pc = 0;
 int backJumpCounter = 0;
 try {
  while (pc >= 0) {
   CompilerAsserts.partialEvaluationConstant(pc);
   AbstractBytecodeNode node = bcNodes[pc];
   if (node instanceof ConJumpNode) {
    ConJumpNode jumpNode = (ConJumpNode) node;
    boolean c = jumpNode.executeCondition(frame);
    if (CompilerDirectives.injectBranchProbability(
         jumpNode.getProbability(JUMP), c)) {
     int successor = jumpNode.getJumpSuccessor();
     if (CompilerDirectives.inInterpreter()) {
      jumpNode.increaseProbability(JUMP);
      if (successor <= pc) backJumpCounter++;
     }
     pc = successor;
     continue;
    } else {
     int successor = jumpNode.getNoJumpSuccessor();
     if (CompilerDirectives.inInterpreter()) {
      jumpNode.increaseProbability(NO_JUMP);
      if (successor <= pc) backJumpCounter++;
     }
     pc = successor;
     continue;
    }
   } else if (node instanceof UncondJumpNode) {
    UncondJumpNode jumpNode = (UncondJumpNode) node;
    int successor = jumpNode.getJumpSuccessor();
    if (CompilerDirectives.inInterpreter()) {
     if (successor <= pc) backJumpCounter++;
    }
    pc = successor;
    continue;
   } else { pc = node.executeInt(frame); }
  }
 } finally {
  LoopNode.reportLoopCount(this, backJumpCounter);
 }
}
\end{lstlisting}

\autoref{fig:loop2} shows the revised version of interpreter loop with
appropriate hints for the Graal compiler.
The \lstinline{@ExplodeLoop} annotation instructs the compiler to unroll loops.
In our case, it uses the \lstinline{MERGE_EXPLODE} strategy which is designed
especially for bytecode interpreters as it tries to explode all loops while
merging copies of the loop body that have identical state.
Then we assert that the number of bytecodes is constant per method instance and
ensure that the program counter is reduced to a constant during the partial
evaluation phase.
After fetching the next node for the current program counter, there are three
options how control flow can continue.

First, if the node is a conditional jump node, the condition is being executed.
Each condition jump node maintains a probability value that represents how often
the condition is \lstinline{true} or \lstinline{false}.
Truffle provides an \textsc{API} to inject this values as a branch probability
which further supports the Graal compiler.
Afterwards, the next program counter is determined depending on whether the
condition was \lstinline{true} or \lstinline{false}.
Additionally and only if executed in the interpreter, the corresponding branch
probability is increased and if the successor is smaller than the current
program counter, a \lstinline{backJumpCounter} is incremented.
This \lstinline{backJumpCounter} is reported on method exit in the
\lstinline{finally} block.
This information will be used in Truffle's optimization heuristics to further
improve the compilation process.
Lastly, the successor becomes the current program counter and the interpreter
loops continues with the next bytecode.

Second and in the case of an unconditional jump, the next program counter is
fetched and analyzed for backward jumps if running interpreted.

Otherwise, the current node is fully executed to determine the next program
counter, just like it was in the simple version of the interpreter loop.

The Javadocs for the different Truffle hints provide further information on how
they work or can be used yet are unable to fully explain how to use them in
combination with others or how exactly the Graal compiler benefits from them.


\section{Evaluation}

To assess the performance of our Truffle-based interpreters for \Squeak, we used
\lstinline{tinyBenchmarks} which consists of two micro-benchmarks:
The first one is bytecode-heavy as it allocates, fills, and reads from a large
array.
The other one is a recursive Fibonacci benchmark and therefore send-heavy.
Additionally, \lstinline{tinyBenchmarks} adjusts both benchmarks so that they
run to least one second in order to produce more stable results.
Although the results should be taken with a grain of salt as they do not
represent a wide range of common operations, we believe they are a good
indicator for the overall performance of the different interpreter approaches.

We ran the benchmarks on a 15-inch MacBook Pro from Mid 2015
(CPU: 2.5 GHz Intel Core i7; Memory: 16 GB 1600 MHz DDR3).
For the \ac{ast} interpreter, we used commit \lstinline{8126c1b} of GraalSqueak
and \lstinline{ac530ac} for the bytecode interpreter with loop-reporting.
Moreover, we copied the later version of GraalSqueak and replaced
\lstinline{SqueakMethodNode.executeLoop(VirtualFrame frame)} with the code in
\autoref{fig:loop1} to turn of loop-reporting.
We also ran the benchmarks on other \Squeak \acp{vm}, a recent OpenSmalltalkVM
(tag \lstinline{201804030952}) and RSqueak/VM (commit \lstinline{d33005c}).

The left half of \autoref{fig:benchmark1} shows the benchmark results of the
bytecode-heavy micro-benchmark.

The results of the OpenSmalltalkVM can be treated as the baseline as it is the
default \ac{vm} for \Squeak.
It performs relatively stable at around three billion bytecodes per second while
RSqueak/VM is able to process approximately 2.1 billion bytecodes per second.
When we looks at the results of the \ac{ast}-based GraalSqueak implementation,
we notice warmup behavior.
After around two iterations, performance reaches a somewhat stable state.
At the same time, it outperforms the OpenSmalltalkVM by approximately $3.06$x.
The bytecode interpreter, on the other hand, does not show this warmup behavior
and is with an average of ten billion bytecodes per second the fastest \ac{vm}.
Without loop-reporting, however, Truffle is unable to perform its optimizations
due to escaping frames and the otherwise identical interpreter performs very
poorly.

The other half of \autoref{fig:benchmark1} shows the recursive Fibonacci
benchmark.
RSqueakVM performs much worse compared to the OpenSmalltalkVM.
Although the GraalSqueak interpreters still outperform it, the relative
difference is not as big as in the previous benchmark.
The \ac{ast} interpreter is approximately $1.42$x faster and bytecode
interpreter around $1.47$x.
Again, the performance of the bytecode interpreter with loop-reporting disabled
is very low compared to all other \acp{vm}.

\section{Related Work}

\paragraph{Sulong}
Sulong~\cite{Rigger:2016:BLL:2998415.2998416} is a bytecode-based interpreter
for LLVM bitcode, written in Truffle, and developed by Oracle Labs as part of
the GraalVM project.
Its bytecode loop employs similar Truffle hints to support the compiler in
optimizing runtime performance.

\paragraph{TruffleRuby}
TruffleRuby~\cite{Wurthinger:2017:PPE:3140587.3062381} is Truffle implementation
of the Ruby programming language.
Similar to our \ac{ast}-based GraalSqueak implementation, TruffleRuby uses
a custom parser for directly generating a Truffle \ac{ast}.
The default Ruby runtime MRI~\cite{Flanagan:2008:RPL:1408408}, on the other
hand, operates on bytecode.

\paragraph{OpenSmalltalkVM and Sista}
The OpenSmalltalkVM is the default \ac{vm} for \Squeak and variations of it
include Sista which stands for Speculative Inlining SmallTalk Architecture.
Instead of optimizing code purely on \ac{vm}-level, the \ac{vm} provides an
\textsc{API} which can be used from inside a Smalltalk environment to retrieve
profiling information.
This information can then be used to apply optimizations on image-level which
can also be persisted when saving the image.

\paragraph{RSqueak/VM}
RSqueak/VM is an alternative interpreter for \Squeak and written in the language
implementation framework RPython.
Therefore, it leverages the same meta-tracing \ac{jit} compiler that is also
used in PyPy to optimize its bytecode loop.


\section{Conclusion and Future Work}

In this paper, we presented two different approach for implementing interpreters
for \Squeak in the language implementation framework Truffle.
The \ac{ast}-based interpreter requires a custom decompiler which is able to
generate Truffle \acp{ast} from \Squeak bytecode.
In order to achieve good performance, however, the decompiler needs to detect
loops and emit appropriate \lstinline{LoopNodes}.
The bytecode interpreter, on the other hand, does not need this additional
component which reduces the complexity of the interpreter.
Nonetheless, the bytecode loop needs to be extended with several runtime hints
to allow Truffle and the Graal compiler to successfully apply appropriate
optimizations.
A benchmark shows that the bytecode interpreter can be just as fast or even
faster than the \ac{ast}-based implementation in Truffle.
However, we also measured a performance hit introduced by these Truffle hints
which negatively affects interpreter performance.

In the future, we want to extend GraalSqueak with full support for \Squeak
context objects and more primitives, so that the entire development environment
can be used as intended.
With a complete implementation of \Squeak in Truffle, the GraalVM also allows
for interesting experiments in the area of ployglot programming.

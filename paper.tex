\begin{abstract}
  Language implementation frameworks aim to provide everything that is needed to
  build interpreters, simplify the process by making certain design decisions
  in advance, and suggest implementation strategies to virtual machine creators.
  %
  Truffle, the language implementation framework for the GraalVM, is designed
  for building \acrlong{ast} interpreters and the process of doing so is well
  documented.
  % 
  However, although less documented, Truffle can also be used to implement
  bytecode interpreters.
  %
  This approach requires additional hints to be passed into the compiler to gain
  good performance.
  
  In this paper, we compare two Truffle interpreters for \Squeak, one using an
  \acrshort{ast} implementation approach and the other executing bytecodes.
  %
  While both run at roughly three times the speed of the standard \Squeak
  virtual machine, both represent different trade-offs in implementation
  strategies for interpreters in Truffle.
  %
  We compare these trade-offs and discuss the advantages and disadvantages of
  the different approaches.
\end{abstract}

\section{Introduction and Background}

Programming language implementation frameworks have become more and more popular
as they allow language implementers to use another high-level language and
useful components, such as garbage collectors or caching mechanisms,
to implement virtual execution environments for dynamic languages.
These frameworks, however, often enforce certain implementation styles and are
usually designed to support a specific kind of interpretation model.
RPython~\cite{Ancona:2007:RST:1297081.1297091}, a language implementation
framework maintained as part of the PyPy
project~\cite{Rigo:2006:PAV:1176617.1176753}, for example, is mainly used to
implement bytecode interpreters, because its tracing \ac{jit} compiler is most
suited to operate on bytecode.
Oracle's Truffle framework~\cite{Wurthinger:2013:OVR:2509578.2509581}, on the
other hand, is designed for implementing \ac{ast} interpreters and its \ac{jit}
compiler applies \ac{ast} node rewriting and partial evaluation to significantly
increase runtime performance of corresponding interpreters.
Consequently, most languages implementations in Truffle are \ac{ast}-based.

However, some language specifications include a well-defined bytecode set and
are therefore designed to run on bytecode interpreters.
For this reason, Truffle has optimization mechanisms specifically for building
bytecode-based interpreters. These are used, for example, in
Sulong~\cite{Rigger:2016:BLL:2998415.2998416}, a Truffle-based interpreter for
LLVM bitcode.
The process and pitfalls of implementing bytecode interpreters in Truffle is not
well documented which is one motivation for this paper.

\Squeak~\cite{ingalls1997back} is a Smalltalk dialect derived from the
Smalltalk-80 language specification~\cite{Goldberg:1983:SLI:273}.
OpenSmalltalkVM~\cite{openSmalltalkVM}, the default \ac{vm} for \Squeak, is
bytecode-based and features a mostly handwritten \ac{jit} compiler.
RSqueak/VM~\cite{Felgentreff:2016:BHV:2991041.2991062,Bolz2008} is an
alternative \ac{vm} for it written in RPython.
With SOMns~\cite{Marr:2017:CPCD}, a Smalltalk-like interpreter is already
implemented in Truffle.
However, it operates entirely on \acp{ast} as it is not image-based like
traditional Smalltalk-80 systems and can therefore be well optimized by the
GraalVM~\cite{Wurthinger:2013:OVR:2509578.2509581}, which in turn is the \ac{vm}
on which Truffle language interpreters are designed to run.

In this paper, we present and compare both the Truffle-based implementation of
an \ac{ast} interpreter as well as a bytecode interpreter for \Squeak.
We report our experiences implementing the different interpretation models in
Truffle, discuss implementation pitfalls, and compare the performance of the
different interpreters with two benchmarks.


\section{Implementations}

In this section, we present two different approaches for implementing
\Squeak interpreters in Truffle.
The source code of the GraalSqueak interpreter variations is available on
GitHub\footnote{\url{https://github.com/hpi-swa/graalsqueak/releases}}.
% (Short overview of the rest: implementation of bytecodes, primitives, plugins?)

\paragraph{AST Interpreter}

Since Truffle and the Graal compiler operate on \acp{ast}, the natural way of
implementing a \Squeak interpreter in Truffle is to write an \ac{ast}
interpreter.
However, \Squeak is traditionally bytecode-based, with its compiler written in
Squeak itself and only the bytecodes, not the \acp{ast} or sources stored in the
image, are visible to the \ac{vm}.
Therefore, these bytecode streams need to be transformed into appropriate
\ac{ast} nodes again.

\begin{figure}
  \centering
  \includegraphics[width=.9\linewidth]{resources/squeak-ast}
  \caption{Architecture of an \ac{ast} interpreter for Squeak}
  \label{fig:squeak-ast}
\end{figure}

\autoref{fig:squeak-ast} gives an overview of the architecture of this
implementation.
Each Smalltalk method was first parsed and compiled to bytecode inside the
Smalltalk environment.
Upon loading an image, the Truffle interpreter only has access to compiled code
objects which hold \Squeak bytecode.

To transform the bytecode into Truffle \ac{ast} nodes, we have ported \Squeak's
decompiler to Truffle.
This implementation approach was straightforward, but did not yield great
performance.
The key optimization to gain good performance (and the only deviation from the
Smalltalk decompiler) was for us to reconstruct loop nodes.
By default, the decompiler would turn every loop into a while node with the loop
condition in the body and a break out of the loop if the condition becomes
\lstinline{false}.
In Truffle, on the other hand, there is a dedicated \lstinline{LoopNode} for
which the runtime provides special optimization strategies.
To optimize loops well, we had to modify the decompilation to split the
condition from the body appropriately and use Truffle's \lstinline{LoopNodes}.
This significantly improved the performance of the interpreter on the GraalVM.


\paragraph{Bytecode Interpreter}

\begin{figure}
  \centering
  \includegraphics[width=.9\linewidth]{resources/bc-vs-ast}
  \caption{A bytecode stream and a sequence of \ac{ast} nodes}
  \label{fig:bc-vs-ast}
\end{figure}

Implementing a bytecode interpreter in Truffle is not as intuitive and still
requires generating \ac{ast} nodes.
However, these \acp{ast} are simply linked lists with back pointers.
We create one node for each bytecode and generate a chain of \ac{ast} nodes as
depicted in \autoref{fig:bc-vs-ast}.
In Smalltalk, each of these nodes has either exactly one or, in the case of a
conditional jump, two successors because jumps are the only way to branch in
\Squeak.

\begin{listing}[H]
  \caption{A simple loop for interpreting sequences of \ac{ast} nodes}
  \label{fig:loop1}
  \begin{minted}[
    fontfamily=tt]{java}
void executeLoop(VirtualFrame frame) {
  int pc = 0;
  while (pc >= 0) {
    pc = bytecodeNodes[pc].executeInt(frame);
  }
}
\end{minted}
\end{listing}

Consequently, we can implement an interpreter loop as shown in \autoref{fig:loop1}.
However, running this loop with Truffle on the GraalVM gives rather low
performance.

As Rigger et. al~\cite{Rigger:2016:BLL:2998415.2998416} have shown, the Graal
compiler needs additional information to efficiently execute bytecode loops.
Their optimization encodes the possible successor program counters in an
immutable array of Java primitive integers on each bytecode node.
This way, the compiler knows that most bytecode nodes have exactly one possible
successor node, and can optimize these together.

However, Graal does not automatically detect control-flow cycles in such a
loop.
Instead, it reports escaping frame errors when trying to unroll the loop.
This is also a problem for other bytecode interpreters such as Sulong, but was
not further described by Rigger et. al.
In order to inform Truffle about our bytecode interpreter, we had to add
additional compiler annotations and hints.
These are now explained in more detail.

\begin{figure*}
  \centering

\begin{listing}[H]
  \caption{Bytecode loop with hints for the Graal compiler}
  \label{fig:loop2}
  \begin{minted}[
    linenos=true,
    fontfamily=tt,
    % fontsize=\footnotesize,
    xleftmargin=.16\textwidth]{java}
@ExplodeLoop(kind = ExplodeLoop.LoopExplosionKind.MERGE_EXPLODE)
void executeLoop(VirtualFrame frame) {
 CompilerAsserts.compilationConstant(bytecodeNodes.length);
 int pc = 0; int backJumpCounter = 0;
 try {
  while (pc >= 0) {
   CompilerAsserts.partialEvaluationConstant(pc);
   AbstractBytecodeNode node = bytecodeNodes[pc];
   if (node instanceof ConditionalJumpNode) {
    ConditionalJumpNode jumpNode = (ConditionalJumpNode) node;
    boolean condition = jumpNode.executeCondition(frame);
    if (CompilerDirectives.injectBranchProbability(
         jumpNode.getProbability(JUMP), condition)) {
     int successor = jumpNode.getJumpSuccessor();
     if (CompilerDirectives.inInterpreter()) {
      jumpNode.increaseProbability(JUMP);
      if (successor <= pc) backJumpCounter++;
     }
     pc = successor; continue;
    } else {
     int successor = jumpNode.getNoJumpSuccessor();
     if (CompilerDirectives.inInterpreter()) {
      jumpNode.increaseProbability(NO_JUMP);
      if (successor <= pc) backJumpCounter++;
     }
     pc = successor; continue;
    }
   } else if (node instanceof UnconditionalJumpNode) {
    UnconditionalJumpNode jumpNode = (UnconditionalJumpNode) node;
    int successor = jumpNode.getJumpSuccessor();
    if (CompilerDirectives.inInterpreter()) {
     if (successor <= pc) backJumpCounter++;
    }
    pc = successor; continue;
   } else { pc = node.executeInt(frame); }
  }
 } finally {
  LoopNode.reportLoopCount(this, backJumpCounter);
 }
}
  \end{minted}
  \end{listing}
\end{figure*}

\begin{sloppypar}
\autoref{fig:loop2} shows the revised version of the interpreter loop with
appropriate Truffle hints for the Graal compiler.
The \lstinline{@ExplodeLoop} annotation in line 1 instructs the compiler to
unroll loops.
In our case, it uses the \lstinline{MERGE_EXPLODE} strategy which is designed
especially for bytecode interpreters as it tries to explode all loops while
merging copies of the loop body that have identical state.
Then we assert that the number of bytecodes is constant per method instance
(line 3) and ensure that the program counter is reduced to a constant during the
partial evaluation phase (line 7).
After fetching the next node for the current program counter, there are three
options how control flow can continue.
\end{sloppypar}

First, if the node is a conditional jump node, the condition is being executed
(line 11).
Each conditional jump node maintains a probability value that represents how
often the condition is \lstinline{true} or \lstinline{false}.
Truffle provides an \textsc{API} to inject such values as a branch probability
(line 12 and 13) which further supports the Graal compiler.
Afterwards, the next program counter is determined depending on whether the
condition was \lstinline{true} or \lstinline{false} (line 14 and 21).
Additionally and only if executed in the interpreter, the corresponding branch
probability is increased and if the successor is smaller than the current
program counter, a \lstinline{backJumpCounter} is incremented.
This \lstinline{backJumpCounter} is reported to the compiler through the
\lstinline{LoopNode::reportLoopCount} \textsc{API} on method exit as part of the
\lstinline{finally} block in line 38.
This information will be used in Truffle's optimization heuristics to further
improve the compilation process.
Lastly, the successor becomes the current program counter and the interpreter
loop continues with the next bytecode.

Second and in the case of an unconditional jump, the next program counter is
fetched and analyzed for backward jumps if running interpreted (line 29 to 34).

Otherwise, the current node is fully executed to determine the next program
counter (line 35), just like it was in the simple version of the interpreter
loop.

The Javadocs for the different Truffle hints provide further information on how
they work or can be used, yet are unable to fully explain how to use them in
combination with others or how exactly the Graal compiler benefits from them.


\section{Evaluation}

To assess the performance of our Truffle-based interpreters for \Squeak, we have
implemented all bytecodes and primitives required to run Squeak's
\lstinline{tinyBenchmarks}.
This micro-benchmark suite is often used to measure and compare the performance
of different hardware platforms and Squeak
\acp{vm}~\cite{tinyBenchmarks,Bolz2008} and consists of two benchmarks:
The first one is bytecode-heavy as it allocates, fills, and reads from a large
array.
The other one is a recursive Fibonacci benchmark and therefore send-heavy.
Additionally, \lstinline{tinyBenchmarks} adjusts both benchmarks so that they
run at least one second in order to produce more stable results.
Although the results should be taken with a grain of salt as they do not
represent a wide range of common operations, we believe they are a good
indicator for the overall performance of our different interpreter approaches.

\begin{sloppypar}
We ran the benchmarks on a 15-inch MacBook Pro from Mid 2015
(CPU: 2.5 GHz Intel Core i7; Memory: 16 GB 1600 MHz DDR3).
For the \ac{ast} interpreter, we used commit \lstinline{8126c1b} of GraalSqueak
and \lstinline{ac530ac} for the bytecode interpreter with Truffle hints.
Moreover, we copied the latter version of GraalSqueak and replaced
\lstinline{executeLoop(VirtualFrame frame)} defined on
\lstinline{SqueakMethodNode} with the code from \autoref{fig:loop1} to remove
all compiler hints.
We also ran the benchmarks on other \Squeak \acp{vm}, a recent OpenSmalltalkVM
(tag \lstinline{201804030952}), the fastest stable \ac{vm} for \Squeak,
as well as RSqueak/VM (commit \lstinline{d33005c}).
Please note that, compared to these complete \ac{vm} implementations, our
interpreters do not have an interrupt handler and do not support Smalltalk
\lstinline{Context} objects which will have a negative impact on performance
when implemented.
% When comparing the results with these complete \ac{vm} implementations, please
% note that our interpreters do not have an interrupt handler, which otherwise
% would negatively impact the performance of the benchmarks.
Furthermore, we used 100 iterations per run and all benchmarks took a little
less than an hour to run in total.
Nonetheless, we observed that all results stabilized within the first ten
iterations.
\end{sloppypar}

The left half of \autoref{fig:benchmark1} shows the benchmark results of the
bytecode-heavy micro-benchmark.
The results of the OpenSmalltalkVM can be treated as the baseline as it is the
default \ac{vm} for \Squeak.
It performs relatively stable at around three billion bytecodes per second while
RSqueak/VM is able to process approximately 2.1 billion bytecodes per second.
When looking at the results of the \ac{ast}-based GraalSqueak implementation,
we notice warmup behavior.
After around two iterations, performance reaches a somewhat stable state.
At the same time, it outperforms the OpenSmalltalkVM by approximately $3.06$x.
The bytecode interpreter, on the other hand, does not show this warmup behavior
and is, with an average of ten billion bytecodes per second, the fastest
\ac{vm}.
Without hints, however, Truffle is unable to perform its optimizations
due to escaping frames and the otherwise identical interpreter performs very
poorly.

The other half of \autoref{fig:benchmark1} shows the recursive Fibonacci
benchmark.
RSqueakVM performs much worse compared to the OpenSmalltalkVM.
Although the GraalSqueak interpreters still outperform it, the relative
difference is not as big as in the previous benchmark.
The \ac{ast} interpreter is approximately $1.42$x faster and the bytecode
interpreter with Truffle hints around $1.47$x.
Again, the performance of the bytecode interpreter without hints is very low
compared to all other \acp{vm}.

\section{Related Work}

\paragraph{Sulong}
Sulong~\cite{Rigger:2016:BLL:2998415.2998416} is a bytecode-based interpreter
for LLVM bitcode, written in Truffle, and maintained by Oracle Labs as part of
the GraalVM project.
Its bytecode loop employs similar Truffle hints to support the compiler in
optimizing runtime performance.

\paragraph{TruffleRuby}
TruffleRuby~\cite{Wurthinger:2017:PPE:3140587.3062381} is a Truffle
implementation of the Ruby programming language.
Similar to our \ac{ast}-based GraalSqueak implementation, TruffleRuby uses
a custom parser for generating Truffle \acp{ast}.
Since Ruby 1.9, the default runtime for Ruby is
YARV~\cite{Sasada:2005:YYR:1094855.1094912} which operates on bytecode.

\paragraph{OpenSmalltalkVM and Sista}
The OpenSmalltalkVM~\cite{openSmalltalkVM} is the default \ac{vm} for \Squeak
and variations of it include Sista~\cite{Bera:2017:SSO:3132190.3132201} which
stands for ``Speculative Inlining SmallTalk Architecture''.
Instead of optimizing code purely on \ac{vm}-level, the \ac{vm} provides an
\textsc{API} which can be used from inside a Smalltalk environment to retrieve
profiling information.
This information can then be used to apply optimizations on image-level which
can also be persisted when saving the image.

\paragraph{RSqueak/VM}
RSqueak/VM~\cite{Bolz2008} is an alternative interpreter for \Squeak and written
in the language implementation framework RPython.
Therefore, it leverages the same meta-tracing \ac{jit} compiler that is also
used in PyPy to optimize its bytecode loop.

\paragraph{SOMns}
SOMns~\cite{Marr:2017:CPCD} is an implementation of the Newspeak language in
Truffle.
Since it is completely file-based, it does not provide compatibility with
image-based Newspeak and traditional Smalltalk systems.
Our GraalSqueak interpreters, on the other hand, are designed to be compatible
with existing \Squeak images. This also includes language features such as
sender modifications or support for various \ac{vm} plugins.


\section{Conclusion and Future Work}

In this paper, we presented two different approaches for implementing
interpreters in the Truffle language implementation framework given a language
defined through and/or with bytecode as its interchange format such as \Squeak.

To create an \ac{ast} interpreter for such a language requires a custom
decompiler which is able to generate Truffle \acp{ast} from bytecode.
Besides the decompiler, the main requirement to achieve good performance on
Truffle is that the decompiler needs to detect loops and emit appropriate
Truffle \lstinline{LoopNodes}.

A bytecode interpreter, on the other hand, does not need a decompiler,
which reduces the complexity of the interpreter.
To achieve good execution performance, however, the bytecode loop needs to be
extended with several runtime hints to allow Truffle and the Graal compiler to
successfully apply appropriate optimizations.

Our initial benchmarks show that a bytecode interpreter can be just as fast as
an \ac{ast}-based implementation in Truffle after warmup.
Interpreted performance, on the other hand, is negatively impacted by additional
Truffle hints, suggesting further optimization potential.

In the future, we want to extend GraalSqueak with full support for \Squeak
context objects and more primitives as well as \ac{vm} plugins, so that the
entire programming environment can be used as intended.
% This will also allow a more thorough analysis of the performance of a
% Truffle-based bytecode interpreter.
With a complete implementation of \Squeak in Truffle, the GraalVM also allows
for interesting experiments in the area of ployglot programming.

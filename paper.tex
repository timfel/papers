\begin{abstract}
  Presizing and pretransitioning are run-time optimizations that avoid
  reallocations of resizable arrays. These
  optimizations were previously presented for VMs where the run-time optimizer
  can interact with the garbage collection (GC) system.

  Dynamic language runtimes written for the GraalVM do not have such access to
  the GC. These implementations cannot directly apply the prior work to optimize
  resizable arrays and alternative implementation strategies pose different
  challenges.

  In this paper we explore and analyze one approach on how GraalVM languages
  could incorporate these optimizations using the Python implementation for
  GraalVM as an example. We substantiate these thoughts with rough performance
  numbers taken from a prototype on which we tested different implementation
  approaches.
\end{abstract}

\section{Introduction}
From the programmers perspective, one of the biggest differences between managed
and unmanaged languages is the level of control over when and how memory for an
object is allocated and structured. Beyond that, many dynamic programming
languages offer only high-level, resizable, and untyped array data structures.

The optimization of such data structures can make up a significant portion of
the work of a \ac{jit} compiler and the performance benefits provided by it~\cite{gal2009trace}. One
well-known optimization applied to resizable arrays in multiple dynamic language
\acp{vm} are storage strategies~\cite{bolz2013storage}.

In this paper we focus on two further optimizations that aim to improve the
efficiency of these data structures further: \emph{presizing} and \emph{pretransitioning}. We
use resizable arrays as shorthand for lists and other similar structures, as our
current prototype only works for arrays.  But our findings can also be applied
other collection types, since one can be (and in practice often is) implemented
using the other.
\paragraph{Presizing} As the size of arrays that the \ac{vm}
manages for the programmer changes over the run-time of the program,
part of the execution time is spent growing or shrinking these
structures according to their usage.

In contrast to languages without automatic memory management, the
programmer generally has little influence on the initial size of an
array or on by what factor the arrays size is increased when it is
resized. This is a trade-off between ease of programming and
 performance. Presizing aims to lessen this negative impact on the 
performance by propagating the observed array-sizes back
to their positions in the source code (allocation sites), which we
will expand on in section~\ref{sec:presizing}.
\paragraph{Pretransitioning} The size of an array is not the only
thing that can change over time, the types of the objects stored
inside it can also vary.  Similarly to automatic memory management,
the thus incurred lookup overhead is a performance disadvantage added to improve the
programming experience by allowing for collections of dynamically
typed objects. To reduce the footprint and improve
operations on arrays of numbers, many dynamically typed
object oriented runtimes use storage strategies that only store
numbers unboxed, thereby saving several indirections when performing
computations on them.

The downside of storage strategies is, that they only work as long as
all objects in an array have specific types. If a floating point
number is added to an array of integers, the storage strategy has to
be changed and the entire array has to be converted to a different
format.  Such a conversion is called \emph{transition} and can be a costly
operation on large arrays. Pretransitioning aims to avoid these
transitions, as layed out in section~\ref{sec:pretransitioning}.

In the following, we introduce the basis of
the ideas presented here in section~\ref{sec:related_work}, present
our prototype in section~\ref{sec:prototype}, describe the challenges
of presizing and pretransitioning in section~\ref{sec:presizing}
and~\ref{sec:pretransitioning} respectively, present our findings 
in section~\ref{sec:evaluation}, and end with our conclusion and
future work in section~\ref{sec:conclusion}.  

\section{Allocation-site-based Optimizations}
\label{sec:related_work}
The closest related work we are aware of was done by Clifford et
al.~\cite{clifford2015memento} on the V8 \ac{vm}. They extended
memory management with \emph{Mementos}, short lived objects used to
associate lists with their allocation sites, i.e. the position in the
source code where they were declared. The information gathered this
way would then be used to optimize future allocations of lists
from the same allocation site. Their main focus was on an optimization not
mentioned yet: \emph{pretenuring}. Essentially improving the performance of
the \ac{gc} by using the Memento information to speculate
about objects that were likely to survive the next \ac{gc} cycles and
directly allocating them in the older generation.

GraalVM languages~\cite{wurthinger2013one} do not have this level of access to the \ac{gc}, as we will explain in
section~\ref{sec:prototype}, so we do not consider pretenuring in this
work. However, the other two optimizations discussed by Clifford et
al. are the ones we target in this paper. While pretransitioning was
discussed and evaluated thoroughly, presizing was only discussed
briefly and the evaluation is only anecdotal. The paper mentions that their
prototype ``was able to learn the optimum allocation size for the important
sites in the very sensitive DeltaBlue benchmark without prior knowledge, and preliminary
measurements indicated a slight decrease in the maximum overall heap
size in Octane, with no other performance loss.''~\cite{clifford2015memento} We also found no further
indication that presizing was used in V8.
 
\section{Prototype for GraalPython}
\label{sec:prototype}
Building on the ideas of Mementos (c.f. Section~\ref{sec:related_work}),
we implemented allocation-site tracking in GraalPython allowing us to
link the information of an array resizing operation back to its
allocation site. Based on this information, we did preliminary
experiments with different strategies for determining the presize. Our
code and benchmarks are available on
Github~\footnote{\url{https://github.com/johenning/graalpython/tree/overallocate}}.

In this section, we will discuss the difference in implementation
strategy between our approach and the approach of Clifford et al. and
the limitations of our proposal.

\subsection*{Tracking Allocation-sites}
\label{sec:implementation}
In contrast to the V8 \ac{vm}, we are working within the GraalVM
ecosystem, which relies on a Java \ac{vm} for many of its features, in
particular for memory management and garbage collection. Subsequently,
where Clifford et al. implemented their Mementos by storing
information inside the fields used by the \ac{gc}, getting the information
about a final list size when the \ac{gc} collects it, we
do not have this level of access to the \ac{gc} and cannot easily implement
this strategy.

Instead we opted to instrument list creation and append operations
of Python. We thus can observe the size of an array on every append
that is called on it and use this information to compute the presize
for all other instances sharing its allocation site.

While Clifford et al. payed particular attention to the performance
implications of the book-keeping added by Mementos through their
allocation strategy and \ac{gc} cycles, our approach eliminates its
book-keeping cost by only doing it during interpretation. We do no
book-keeping in compiled code and assume that array sizes are stable by
the time the program is compiled.

We believe that the variables relevant for profiling are:
\begin{itemize}
\item The amount of times the array grows
\item The amount of elements the array contains at most, at least,
  and on average
\item The size of the array when it is garbage collected,
  including actual size and allocated but empty space
\item The types of objects the array contains
\item The primary operations performed on the array, i.e. mostly read or mostly written
\end{itemize}

Whereas the most important ways the performance could be influenced to
approach an optimal solution are:
\begin{itemize}
\item Presize, i.e. initially allocated size
\item Initial storage strategy
\item Growth factor, i.e. by how much does the array grow when it hits
  its limit
\end{itemize}

\subsection*{Limitations of our approach}
As the only information about the allocation site we have is its
position in the source code, our approach does not work for
abstractions build on top of resizable arrays that provide a different
interface. For example, Smalltalk's \texttt{OrderedCollection} type is
written in Smalltalk itself and holds primitive arrays in a field, so the
same allocation site would be seen for all arrays used in OrderedCollections,
regardless of where the OrderedCollection was instantiated. This means that 
high-level collection libraries cannot benefit from our approach.

Secondly, our current approach cannot observe branches in the control
flow of the program after the allocation of an array lead to vastly different
characteristics and requirements for the initial allocation. This, however, is
also a limitation of the prior work that we also have yet to solve.

\section{Presizing}
\label{sec:presizing}
Presizing relies on the assumption that arrays from the same
allocation site will have similar resource consumption over
time. Hence, when a new array is created the runtime environment does
not allocate a predetermined static amount, but instead uses the
previously observed sizes of the array to compute the optimal size to
allocate.

While this optimization should have little to no effect on arrays that
are used infrequently and stay small, it can save a significant amount
of resizing operations for arrays that grow multiple times and are
used in a \emph{hot} portion of the code.  For example, an array
allocated with size 4 that grows by a factor of 2 whenever it hits its
limit will grow 12 times if 10.000 elements are added to it. By adjusting the initial size
or the growth factor, the amount of operations needed to reach the
optimal size can be reduced significantly or even eliminated entirely.

To achieve this we need to answer how, given the history of all sizes a specific
array had during the execution of a program, do we determine the
optimal \emph{presize}? There is no straight forward answer that works
in every scenario.

Presizing works well for arrays whose sizes stabilize over time, as
the presize can approximate the maximum size and eventually eliminate
all resizing operations.

The challenge in determining the optimal presize comes with arrays
that do not reach a stable size. Consider
listing~\ref{listing:presizing_branching} as an example. Whether the
appropriate presize is closer to 1 or 10000 depends on the likelihood
of \lstinline{flag} being true. If we choose to not modify the
presize, for each time \lstinline{flag} is true \lstinline{a} could
grow over 10 times using the example from above. Whereas if we
increase the presize, for each time \lstinline{flag} is false we would
unnecessarily allocate $(presize - 1) * size(1)$ bytes. While the
optimal solution remains an open question, we discuss what we have
found so far in section~\ref{sec:evaluation}.
\begin{figure}[h]
\begin{lstlisting}[language=Python,label={listing:presizing_branching},
  caption={Simple example of branches impacting array-size depending on
  external factors for the same allocation site}]
var a = []
if flag:
    for i in range(0, 10000):
        a.append(1)
else:
    a.append(1)
\end{lstlisting}   
\end{figure}



\section{Pretransitioning}
\label{sec:pretransitioning}
Pretransitioning relies on the same
speculation as presizing: arrays from the same allocation
site will likely contain the same type of objects over time. Thus, for
example, instead of starting out with an \emph{empty} strategy,
transitioning to an \emph{int} strategy when an integer is added, then
transitioning to a \emph{double} strategy when a double is added,
before finally transitioning to an \emph{object} strategy when a
string is added, the array would already be created with the
\emph{object} strategy. While this example is straight forward, the
question remains of how to handle cases where an array only
transitions \emph{sometimes}, but stays homogeneous in other
cases. Which variables should be weighted to make this
decision? 

\begin{figure}
\begin{lstlisting}[language=Python,label={listing:transitions},
  caption={Storage strategy transitions in GraalPython}]
var a = []      # Initialized with Empty strategy
for i in range(0, 10000):
    a.append(1) # Transition to 32-bit Integer strategy 
                # on first execution

a.append(1.0)   # Transition to Double&Integer strategy
a.append('1')   # Transition to Object strategy
    
\end{lstlisting}   
\end{figure}

Listing~\ref{listing:transitions} shows the unoptimized storage
strategy transitions an array might go through in GraalPython. In this example, as
the array will always end up as a general object strategy,
\emph{pretransitioning}, i.e. initializing it with the object strategy
instead of empty, would avoid 3 transitions, with the last 2 in particular
being expensive, as a large arrays needs to be copied in both cases.

While pretransitioning is straight-forward when no branches are
involved, a solution that does not consider branches will have an
adverse effect on performance, as illustrated in 
listing~\ref{listing:pretransition_worstcase}. One way to avoid this
scenario could be to consider branching information collected during
interpretation and pretransitioning to the more likely branch. This is
speculative however, as this has so far proved too complex to implement in
our prototype. 

Another answer to this problem might be to consider this example as
unlikely and sub-optimal practice and thus accept the decrease in performance.



\begin{figure}
\begin{lstlisting}[language=Python,label={listing:pretransition_worstcase},
  caption={Example of pretransitioning adversely affecting performance
    due to branching}]
var a = []
if flag:        # While flag is true    
    a.append(1) # a will use an Integer strategy
else:           # If flag is false once a will use
                # the Object strategy from then on
    a.append(Object())
if flag:
    sum(a)      # Will run fine on the Integer strategy
                # but will be slow on the Object strategy
\end{lstlisting}   
\end{figure}


\section{Performance Analysis and Initial Results}
\label{sec:evaluation}
The first indications on the performance impact of presizing and
pretransitioning look promising. In order to not rely on
micro-benchmarks, we chose the DeltaBlue benchmark, which tests the
performance impact for small and large arrays simultaneously.
\subsection{DeltaBlue}
DeltaBlue is an incremental constraint hierarchy
solver~\cite{freeman1989deltablue} originally developed for Smalltalk
which has been implemented in several languages and thus can be useful
for cross-languages benchmarking, as suggested by Marr et
al~\cite{marr2016cross}.

\subsection{Allocation Sites in DeltaBlue}
As the solver relies on arrays for storing and evaluating its
constraints, there are several performance relevant allocation sites
in the source code. Allocation sites are identified by their line
number in the benchmark source code~\footnote{Available here:
\url{https://git.io/Jve2G}}. Figure~\ref{fig:allocation_sites}
illustrates the array sizes observed through our the instrumentation
of our prototype when running DeltaBlue 30 times with an input size of
5000.

\begin{figure}
    \includegraphics[width=0.49\textwidth]{allocation_sites.png} 
    \caption{DeltaBlue allocation sites and their observed sizes
      excluding arrays that never contain more than 5 elements}
    \label{fig:allocation_sites}
\end{figure}

Figure~\ref{fig:allocation_sites} provides several insights and
illustrates, why there isn't an obvious answer to what the optimal
size for presizing might be. There are several observations we would
like to make:
\begin{itemize}
\item Presizing works fine for arrays that have stable sizes, like 32
  and 360.
\item All other allocations sites have a bottom heavy distribution,
  meaning that there are many small arrays and some very large ones.
\item In particular 445 and 558 have local maxima, where there are
  many large arrays that are still smaller than the maximum size.
\item All arrays other than 32 and 360 approximately reach the maximum
  size given as the benchmark input (5000).
\end{itemize}
As expected, the optimization is straight forward and useful for arrays
that reach a stable size. But arrays that vary widely present an
interesting trade-off: Choosing a small presize limits the usefulness
of the optimizations, but choosing a too large one can explode the
memory usage of the program. In fact, at the time of writing, our
version aborts with an out of memory error, when we run the
benchmark with input sizes larger than 8000. We will explain which
strategies we tested so far for weighing this trade-off below.

\subsection{Optimization Potential}
It is important to point out that transitions as well as resizing involve
copying the array, which entails performance overhead proportional to
the array size. Hence, the performance gains of presizing and
pretransitioning are
proportional to the size of the array and the amount of times it would
have been resized or transitioned.

In addition, avoiding resizing and transitioning can help other
optimizations to be more effective. For example, allocation removal~\cite{bolz2011allocation}
aims to avoid allocations of objects that are only short lived and do
not escape outside the scope of the compilation unit. Graal is able to perform
allocation removal on small arrays, but this is limited by the kind
of operations performed on them. The default size for arrays in
Graal is 4, so any array larger than that will require resizing and
potentially transition operations. These operations make it less
likely that the array will be allocation-removed, because they will create branches in
the resulting compiler graph. With presizing and pretransitioning, however,
we are able to avoid these operations, which removes these branches, which
in turn increases the probability that some lists can be allocation-removed.

\subsection{Tested presizing strategies}
\paragraph{Naive strategy} The easiest solution for testing the
achievable performance with disregard for the increase in memory
consumption is to take each newly observed maximum size as the new
presize. Our naive strategy works similarly, except that we inhibit
the growth of presize by a factor of 8. Hence, we only increase the
presize if the current size has been exceeded 8 times.

Promisingly, we observed a significant impact on performance on the
DeltaBlue benchmark with the size configuration at 5000. The average
run-time speed-up was by a factor for 1.37, the maximum speedup observed
(shortest run-time with optimizations versus shortest run-time without) was
a factor of 3.7. This was at the cost of memory consumption (increased
by a factor of 2) and slower warm-up by a factor of 0.8.

\paragraph{Naive strategy with shrinking}
Without shrinking, our naive strategy approximated the maximum array
size over time and never went back. Our next step was to shrink the
estimate when the list was observed to be smaller, again inhibited by
a factor of 8. This did not produce satisfying results, most likely because we have no
way of observing the final size of the array, but as discussed are
notified of every append operation performed on it. Smaller array
sizes are thus over represented in the history of all sizes.

We experimented with different growth and shrinking factors, but did
not find any way to balance the presize with this approach.

\paragraph{Average size strategy}
When only saving the presize for each allocation site and reducing or
increasing it did not produce balanced results, we decided to record all sizes
encountered at each allocation site to determine the average
size. While figure~\ref{fig:allocation_sites} was created from this
data, we have yet to measure the performance characteristics of this
strategy. To our best knowledge though, it seems like that the average would still be to
large, but the median size looks promising and will be the subject of
our next experiments.


\paragraph{Summary of our current insights}
As observed with the naive strategy, presizing can have a positive
effect on performance, but needs to be considered carefully 
to find the sweet-spot, where we maximize the performance benefits
while minimizing the impact on memory consumption.

Further research is needed for any definite answer in this regard.

\section{Conclusion \& Future Work}
\label{sec:conclusion}
We presented preliminary evidence that pretransitioning and presizing using our
approach can be implemented in GraalVM languages and provide performance
benefits for certain applications. Our naive solution shows a speedup of 37\% in
the DeltaBlue benchmark, at the cost of a 200\% increase in memory
consumption and 20\% longer
warm-up times. Micro benchmarks for the presented code snippets also showed
smaller compiler graphs with fewer allocations. How these findings generalize to
other benchmarks is the subject of ongoing work.

While these initial findings are promising, more work is needed in
order to find an optimal strategy for increasing performance while
decreasing the additional memory consumption. In particular we want to
leverage more of the variables discussed in
section~\ref{sec:implementation} and different heuristics for
determining the presize. Increasing the mentioned growth factor, which
unfortunately is not easily accessible in Java, could be a good way to
avoid exploding memory consumption while still reducing the amount of
resizing operations needed for arrays that infrequently get very large.

Finally, the impact of our optimizations needs to be evaluated with
additional benchmarks.

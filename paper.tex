\begin{abstract}
To improve programming efficiency, the right tools are crucial.
This starts with the choice of the programming language, which often predetermines the libraries and frameworks one can use.
Polyglot runtime environments, such as GraalVM, provide mechanisms for sending messages across language boundaries, which allow developers to combine different languages, libraries, and frameworks with each other.
However, polyglot application developers are obligated to properly use the right interfaces for accessing their data and objects from different languages.
% Especially if multiple languages are involved, it is often not clear which language interface can be expected.

To reduce the mental complexity for developers and let them focus on the business logic, we introduce user-defined target type mappings --
an approach for adapting cross-language messages at run-time to match an expected interface.
Thereby the translation strategies are defined in an exchangeable and easy-to-edit file format.
Thus, different stakeholders ranging from library and framework developers up to application developers can use and extend these strategies for their needs.
\end{abstract}

\section{Introduction}
With the increasing complexity of software, it becomes all the more important to use the right development tools.
By using suitable language constructs, frameworks, and libraries, the development time can be significantly reduced. // ToDo: Source?

To use the most appropriated parts of each programming language for a given problem, polyglot runtime environments such as \productname{GraalVM} provide mechanisms for language interoperability.
Thereby, objects can be accessed across language borders.

In the case of GraalVM, the underlying framework provides interchangeability of primitive types and some selected basic data structures such as lists.
Thereby, this mechanism in deeply integrated into the framework.
And therefore, hard to extend for other objects like maps/dictionaries or even more domain-specific data types like data frames.

To address this issue, this work introduces user-defined target type mappings --
An approach to provide cross-language interface mappings by generating suitable adapters.
Thereby application and library developers can extend the underlying information to generate these adapters to fit there needs and can even share them.

\section{Background/Context}

As part of this work, a prototypical implementation of the represented approach is provided in \productname{GraalVM}~\cite{Wurthinger:2013:OVR:2509578.2509581}.
GraalVM is a Java \ac{VM}, which provides interoperability between different programming language runtimes.
To archive this, the runtimes have to be implemented within a specialized language implementation framework provided by \productname{GraalVM} called \productname{Truffle}.
Thereby objects that can be shared between languages implement the common interface \classname{TruffleObject}.
In this way, all languages have a shared understanding of message communication and messages can be sent to objects across language boundaries~\cite{10.1145/2816707.2816714}.

Furthermore, proxy interfaces are defined, ranging from array interfaces (\classname{ProxyArray}) up to time zone interfaces (\classname{ProxyTimeZone}).
They are defined in the polyglot part of the Graal repository, with the intention that language implementer will use them and provide a common interface between these datastructures.
So the datastructures can be exchanged between languages and the runtime will treat them like objects of the called language.

While this approach provides interconnectivity, it is only limited to specific data structures and hard to extend.
Because new interface has to be integrated for every language seperately, the amount of interfaces is very low and mostly limited to basic datastructures.

A more flexible approach is given by \productname{Custom target type mappings}.
They provide mechanisms to convert object given a custom mapping.
However, these functionality is only provided by the Java embedding \ac{API} and thus not applicable for polyglot programmer outside of Java.

Because our approach tackles these limitations with the goal to provide these functionality, in an easy to use fashion, for more polylglot programmers, it is called ``User-defined Target Type Mappings''.

\section{Approach}

This approach utilizes the adapter design pattern~\cite{Gamma:1995:DPE:186897}.
By wrapping an object from one language with an adapter, it can expose the related interface from another language if it gets called from there.

To build the adapter, the adaptee interface, as well as the desired interface, is needed.
While the first one can be determined by exploring the wrapped object itself, the second part is more critical.
We assume that the desired interface can be derived by the concept represented by the adaptee together with the language, from which the adapter gets called.
The underlying concept can be either expressed by the type of wrapped object, or the user can explicitly define it, as shown in \autoref{lst:interface_first_adapter}.

To share an understanding of concepts and their interfaces, these are defined as a language-independent representation.
For the sake of simplicity, we describe the interface as a set of method names, as shown in \autoref{lst:interface_collection}.

\begin{lstlisting}[caption={Interface definition of Collection}, label={lst:interface_collection}]
add
size
isEmpty
...
\end{lstlisting}

Given that interface definition, the method names are mapped in a mapping file, as shown in \autoref{lst:mapping_file}.
Thereby each line represents one operation.
The first token represents the method identifier in the generic interface definition, followed by the method names of the concrete language object.
Whereas, it is not necessary to provide alias names for wrapped objects, since every translation should lead to the same result,
it is crucial if the mapping is used for the second adapter part.

\begin{lstlisting}[caption={Mapping file between Ruby array and Collection}, label={lst:mapping_file}]
add push <<
size size length
isEmpty empty?
...
\end{lstlisting}

By introducing this intermediate representation of a shared interface, the implementation effort can be reduced.
Through this division, the adapter consists of two parts:
The first part of the adapter maps from the wrapped object to the intermediate representation,
and the second part maps from the intermediate representation to the target interface, as shown in \autoref{fig:adapter_diagram}.
Thus, instead of providing a mapping for each concept between every language implementation, only the mapping to the intermediate representation has to be given to integrating it fully.

\begin{figure*}[]
  \centering
  \includegraphics[width=0.6\textwidth]{images/adapter_diagram.pdf}
  \caption{UML object diagram to illustrate the two part adapter}
  \label{fig:adapter_diagram}
\end{figure*}

\begin{lstlisting}[caption={Example interface to generate the first half of the adapter}, label={lst:interface_first_adapter}, language=python]
from polyglot_ds import PolyglotDS

polyglot_ds = PolyglotDS([], 'Collection')
\end{lstlisting}

Besides the mapping, the creation of the second part also needs the desired language interface.
Thereby determining the desired target language is already a challenge.
During the initialization of the first part, it is not known from which language it will be called.

\begin{figure*}
  \centering
  \includegraphics[width=0.7\textwidth]{images/adapter_behavior.pdf}
  \caption{Adapter Message Resolution (notation UML 2.5 sequence diagram \cite{uml2.5})}
  \label{seq:deployment}
\end{figure*}

To overcome this issue, the user could explicitly state the desired interface if the required information is present.
This can be done either by a explicit call to the adapter, such as \lstinline{polyglot_ds.adapt_to_ruby_array()}, or by utilizing Context-oriented Programming.

While this approach provides fine-granular control by stating everything explicit, it can be quite cumbersome. 
Primarily because, in many cases, the mapping intent is already expressed in the underlying algorithm.
If for example a Collection is passed to a Ruby algorithm, it is pretty clear that the desired interface is at least a Ruby object
and probably also an array-like interface.

Although from a user perspective, the desired language is clear, it is not intended from the Graal framework to find out the language.
While from an application developer view, the transparency between languages is desirable, it limits the design space for tooling developer.

Therefore, as part of the implementation, such functionality was integrated into the Graal framework.

Every time a language context is requested, a newly introduced Graal object saves the corresponding language.
If now, a method is called on one of the adapters, which are internally \classname{RubyObjectTypes}, the currently active language is saved as the last caller language.

Since the adapter is written in \productname{TruffleRuby}, a new primitive function is added to provide an entry point from the language level to access this value and use it to build the desired mapping.

To identify the right data structure interface from the given language,
the language-independent, generic interface can specify default mappings for the different languages. 
Given that information, the adapter can fully automatically adapt to the desired target interface.

From an application programmer's view, the boundary between the languages disappear.

\section{Discussion}

There is always a trade-off between automatization and user control.
By making the interface translation process transparent to the user, it could result in unexpected behavior.
Therefore, this approach tries to balance both sides.
On the one hand, the application developers are in charge of explicitly declaring an adapter with its corresponding concept.
That way, the users are aware of the adapter, and overhead introduced by the adapter is prevented if not needed.
On the other hand, the mapping is determined by predefined configuration files without explicit conversion calls by the user.
Thus, verbosity in using the adapter is reduced and makes it more accessible.
Furthermore, the open nature of the configuration files enables the users to change the adapter behavior for their needs.
Since every stakeholder can create, edit, and combine these configuration files, different kinds of conflicts can occur, for example, if a mapping file relies on a specific interface definition file, that gets changed.
In this case, a dependency and versioning system could help.
For now, the users are responsible for keeping their configuration files consistent.

Besides that, the adapter approach yields some challenges concerning identity, for example, if the adapter is used in a set data structure.
When are two adapters the same? Are they the same if they wrap the same adaptee, even if they have different mappings associated and therefore expose different interfaces?
If not, will an adaption to a new interface, result in a new identity?

\section{Related Work}

The desire to use existing data structures and objects across different runtimes created different approaches.

\paragraph{Serialization}
During serialization, the object is translated into a format that can be stored, transmitted, and later reconstructed.
The advantage of this approach is that it can be integrated into nearly every language as a library.
However, it has its limits by more complex objects.
Since the memory is not shared between the runtimes, the object exists as a separate object in each runtime.
Resulting in different identities, more memory consumption, and performance overhead to transfer the object.
In comparison, our approach preserves the identity by keeping the same object between runtimes and translating the messages accordingly.
Instead of representing a specific instance of an object in a language-independent format, the underlying concept itself is represented that way. 
Thereby, several challenges are shared between these approaches, such as schema evolution.
Although this challenge is not directly addressed in this work, corresponding ideas can be borrowed from this field.
Popular serialization mechanisms are, for example, \productname{Google Protocol Buffers}~\cite{ProtocolBuffers}, \productname{Apache Thrift}~\cite{Thrift}, and \productname{Avro}~\cite{Avro}.

\paragraph{Common Data Layer}
For specialized objects, a standardized, language-independent memory format can be defined.
On top of this language or library, specific interfaces can be defined.
Thereby the memory format is highly specialized for specific data types, and each new interface requires development work.
This approach is implemented in Apache Arrow~\cite{ApacheArrow}.
There, a columnar memory layout is shared between different libraries to provide data frame-like interfaces.

\paragraph{Polyglot Adapters}
The idea to provide adapters for the \productname{GraalVM}, was established by Niephaus et al.~\cite{Niephaus:2019:TPA:3328433.3328458}.
They demonstrated that the adapter pattern is suitable to translate messages between languages and mimic language-specific behavior.
In the course of this, scaling and usability challenges were revealed, which are tackled by this work.
By introducing a language-independent, generic interface representation and splitting the adapter into two parts, the mapping overhead can be drastically reduced.
Further, the language resolution, which creates the second part of the adapter on the fly, improves the overall usability.

\section{Conclusion and Future Work}

In this work, user-defined target type mappings are introduced.
These enable polyglot developers to combine algorithms and data structures from different languages.
Thereby mechanisms are introduced to make the whole process transparent to the user.
There is no need to adjust either the interface from the object or the calls out of the algorithm by hand.
This approach enables the application developer to focus on the domain-specific challenges and using the best-fitted language concepts without being bothered with language boundaries.

Currently, it is an early prototype to test the feasibility.
In a productive environment, the introduced performance overhead should be reduced.
The mechanism to figure out the target language, as well as the creation of the mapping behavior during runtime, introduces additional function calls.
While these can be reduced by utilizing caching and reusing the mapping behaviors, an efficient implementation is part of the future work.

Currently, the creation of the mapping files can be time-consuming.
Therefore it is conceivable to support the user in this process by providing tools.
These can range from providing a specialized editor to explorer and connect different interfaces, up to (fully-)automatic mapping approaches by utilizing data from the underlying source code or test suites.

In addition to the creation of new mappings, the reusing aspect of the mappings was considered.
The file format makes it easy to exchange the data.
However, an infrastructure to upload, download, and explorer these files would be a great addition.

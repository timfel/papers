\section{Introduction}
Managed language runtimes reduce the work a programmer has to do by,
among other things, automatically managing memory including
allocating, deallocating, growing, and shrinking data structures. 
The optimization of data structures makes up a significant portion of
the performance benefits provides by a \ac{jit} compiler. In this
paper we focus on three optimization technologies that aim to optimize
the efficiency of array-like structures: Presizing \&
Pretransitioning. We use arrays as shorthand for lists and other
similar structures, as our current prototype only works for arrays,
but our findings apply to list as well.

\paragraph{Presizing} As the size of arrays that the
runtime system manages for the programmer changes over the execution
time of the program, part of the execution time is spent growing or
shrinking these structures according to the current needs.

In contrast to languages without automatic memory management, the
programmer generally has little influence on the initial size of an
array and by how much an array grows when it needs to. This is a
trade-off between ease of programming and performance. Presizing aims
to equalize the performance degradation by observing the size of all
arrays over time and speculating that an array declared at the same
position in the source code will have similar resource consumption
over time.

Hence, when a new array is created the runtime environment does not
allocate a predetermined static amount, but instead uses the
previously observed size of the array to compute the optimal size to
allocate. While this optimization should have little to no effect on
arrays that are used infrequently and stay small, it can save a
significant amount of growing operations for arrays that get very large
and are used in a \emph{hot} portion of the code.

For example, an array allocated with size 4 that grows by a factor of
2 whenever it hits its limit will grow 12 times if 10.000 elements are
added to it, like in listing~\ref{listing:simple_presizing}. By
adjusting the initial size or the growth factor the amount of
operations needed to reach the optimal size to be reduced
significantly or eliminated entirely.

The open question is: Given a history of all sizes a specific array
had during the execution of a program, how do we determine the
\emph{optimal} size for presizing? There is no straight forward answer
that fits every scenario, we will provide our analysis and examples in
section~\ref{sec:presizing}.

\begin{lstlisting}[language=Python,label={listing:simple_presizing},
  caption={A simple example for the motivation of presizing}]
    var a = []
    for i in range(0, 10000):
      a.append(1)
\end{lstlisting}   
\end{figure}

\paragraph{Pretransitioning} In addition to the size of an array,
what can also change over time is the type of object stored inside
it. This is another performance disadvantage added by dynamically
types programming languages in order to improve the programming
experience. In order to support performant execution of arithmetic
operations on arrays of numbers, many dynamically typed object
oriented runtimes use specialized arrays that only store numbers
unboxed, thereby saving several indirections when performing
computations on them. In Graal these are called storage strategies.

The problem with storage strategies is, that they only work as long as
all objects in an array are of specific types. If a floating point
number is added to an array of integers, the storage strategy has to
be changed and the entire array has to be converted to a different
format. This is true in particular if a non-primitive object is added
to an array that previously only contained primitive values. 

This conversion is called a \emph{transition} and can be a costly
operations on large arrays. Pretransitioning relies on the same
observation as presizing, that the array declared at a specific point
in the source code will likely contain the same type of objects over
multiple iterations. So, for example, instead of starting out with an
\emph{empty} strategy, transitioning to an \emph{int} strategy when an
integer is added, then transitioning to a \emph{float} strategy when an
float is added, before finally transitioning to a \emph{object}
strategy when a string is added, the array would already be created
with the \emph{object} strategy.

The question of interest with this optimization is how to handle cases
where an array only transitions \emph{sometimes}, but stays homogeneous
in other cases. Which variables should be weighted in order to make
this decision? We address this question in
section~\ref{sec:pretransitioning}.

\section{Related Work}
\label{sec:related_work}
\subsection{Memento Mori - Dynamic Allocation-site-based Optimizations}
Our work is closely related to the work of Clifford et
al. ~\cite{clifford2015memento} on the V8
\ac{vm}. Their main focus was on a different optimization:
pretenuring. Essentially using allocation sites to speculate about
objects that were likely to survive the next \ac{gc} cycles and
directly allocating them in the older generation to improve \ac{gc}
performance.

As we have no access to the \ac{gc}, as we will discuss in
section~\ref{sec:prototype}, we do not consider pretenuring in our
work. The other two optimizations discussed by Clifford et al. are the
ones we target in this paper. While pretransitioning was discussed and
evaluated thoroughly, presizing was only discussed briefly and 
how the evaluation was done was not entirely clear:
\begin{quote}
Encouragingly, our prototype was able to learn the optimum
allocation size for the important sites in the very sensitive
DeltaBlue benchmark without prior knowledge, and preliminary
measurements indicated a slight decrease in the maximum overall
heap size in Octane, with no other performance loss. 
\end{quote}
We also found no further mentions of presizing being implemented
inside V8 or any mention in later works. Thus we do believe that there
are relevant and open questions to investigate in this area.

Building on the ideas of Mementos, see section~\ref{sec:related_work},
we implemented 
allocation-site tracking to GraalPython thus allowing to to link the
information of a array growth back to its allocation site. Based on
this information, we did preliminary experiments with different
strategies for determining the optimal size for presizing. Our code
and benchmarks are available on
Github~\footnote{\url{https://github.com/johenning/graalpython/tree/overallocate}}.

In this section we will first discuss the difference in implementation
strategy between our approach and the approach of Clifford et al. We
will then present our observations of the allocation sizes of the
DeltaBlue benchmark and discuss the results of our benchmark
evaluations.

\subsection{Memento Implementation}
\label{sec:implementation}
In contrast to the V8 \ac{vm}, we are working in the Graal
ecosystem, which relies on a Java \ac{vm} for many of its features, in
particular for memory management and garbage collection. Subsequently,
where Clifford et al. implemented their Mementos by storing
information inside the fields used by the \ac{gc}, getting the information
about a final list size when the \ac{gc} collects it, we
do not have access to the \ac{gc} and cannot easily modify it.

Instead we opted to instrument the append and declaration operations
of Python. We thus can store the size of an array on every append that
is called on it and accumulate this information for all invocations of
a list identified by its position in the source code.

While Clifford et al. payed particular attention to the performance
implications of the book-keeping added by Mementos through their
allocation strategy and \ac{gc} cycles, our approach gets rid of its
book-keeping cost by only doing it during interpretation. We do no
book-keeping in compiled code and assume that array sizes are stable by
the time the program is compiled.

We believe that the variables relevant for profiling are:
\begin{itemize}
\item How often does the array grow?
\item How many elements does the array contain at most, at least,
  and on average?
\item What is the size of the array when it is garbage collected,
  including actual size and allocated but empty space?
\item Which types does the array contain?
\item Is the array mostly read or mostly written?
\end{itemize}

Whereas the most important cogs that could be tweaked in order to
approach an optimal solution are:
\begin{itemize}
\item Presize, i.e. initially allocated size
\item Initial strategy
\item Growth factor, i.e. by how much does the array grow when it hits
  its limit
\end{itemize}

\subsubsection{Limitations of our approach}
As the only information about the allocation site we have is its
position in the source code, our approach does not work for
abstractions build on top of array that provide a different
interface. For example, all OrderedCollections would share the same
allocation site in the class definition of OrderedCollection, thereby
making the information collected useless.

\section{Presizing}
\label{sec:presizing}
Presizing uses the collected information at the allocation sites in
order to detemine a likely size for the next array allocated at the
same site. We call this estimate the \emph{presize}. \todo{would
  initial size be a better word?}. Presizing works well for arrays
whose sizes stabilize over time, as the presize will approximate the
maximum size and eventually eliminate all resizing operations.

It is important to point out that transitions, discussed in
section~\ref{sec:pretransitioning}, as well as resizing involve
copying the array, which entails performance overhead proportional to
the array size. Hence, the performance gains of presizing are
proportinal to the size of the array and the amount of times it would
have been resized.

The challenge in determining the optimal presize comes with arrays that
do not reach a stable size. Consider
listing~\ref{listing:presizing_branching} as an example. Whether the
appropriate presize is closer to 1 or 10000 depends on the likelyhood
of \lstinline{flag} being true. For each time it is true,
\lstinline{a} could grow over 10 times using the example from the
introduction. Whereas, for each time it is false we would
unnecessarily allocate $(presize - 1) * size(1)$ bytes. While the
optimal solution remains an open question, we discuss what we have
learned so far in section~\ref{sec:evaluation}.


\begin{figure}
\begin{lstlisting}[language=Python,label={listing:presizing_branching},
  caption={Simple example of branches impacting allocation sizes depending on
  external factors for the same allocation site}]
var a = []
if flag:
    for i in range(0, 10000):
        a.append(1)
else:
    a.append(1)
\end{lstlisting}   
\end{figure}

\section{Pretransitioning}
\label{sec:pretransitioning}
Pretransitioning relies on the language internal optimization of
storage strategies and tries to avoid unnecessary transitions between
such strategies by speculating on the stability of the type of objects
added to arrays bound to an allocation site.

\begin{figure}
\begin{lstlisting}[language=Python,label={listing:transitions},
  caption={Unoptimized transition of storage strategies in GraalPython}]
var a = [] # Initialized with Empty strategy
for i in range(0, 10000):
    a.append(1) # Transition to Integer strategy 
                # on first execution

a.append(1.0)   # Transition to Double strategy
a.append('1')   # Transition to Object strategy
    
\end{lstlisting}   
\end{figure}
Listing~\ref{listing:transitions} shows the unoptimized storage
strategy transitions an array might go through in GraalPython. In this example, as
the array will always end up as a general object strategy,
\emph{pretransitioning}, i.e. initializing it with the object strategy
instead of empty, would avoid 3 transitions, with the last 2 in particular
being expensive, as a large arrays needs to be copied in both cases.

\section{Performance Analysis and Initial Results}
\label{sec:evaluation}
The first indications on the performance impact of presizing and
pretransitioning look promising. In order to not rely on
micro-benchmarks, we chose the DeltaBlue benchmark, which tests both the
performance impacts for small and large arrays simultaneously.
\subsection{DeltaBlue}
DeltaBlue is an incremental constraint hierarchy
solver~\cite{freeman1989deltablue} originally developed for Smalltalk
which has been implemented in several languages and thus can be useful
for cross-languages benchmarking, as suggested by Marr et
al~\cite{marr2016cross}.

\subsection{Allocation Sites DeltaBlue}
As the solver relies on arrays for storing and evaluating its
constraints, there are several performance relevant allocation sites
in the source code~\footnote{Allocation sites are identified by their
  line number in the benchmark source code available here:
  \url{https://git.io/Jve2G}}. Figure~\ref{fig:allocation_sites}
illustrates the array sizes observed through our append instrumentation
when running DeltaBlue 30 times with an input size of 5000. 

\begin{figure}
    \includegraphics[width=0.49\textwidth]{allocation_sites.png} 
    \caption{Allocation sites and their respective observed sizes in
      the DeltaBlue benchmark excluding arrays that never contain more
      than 5 elements}
    \label{fig:allocation_sites}
\end{figure}

Figure~\ref{fig:allocation_sites} provides several insights and
illustrates, why there isn't an obvious answer to what the optimal
size for presizing might be. There are several observations we would
like to make:
\begin{itemize}
\item Presizing works fine for arrays that have stable sizes, like 32
  and 360.
\item All other allocations sites have a bottom heavy distribution,
  meaning that there are many small arrays and some very large ones.
\item In particular 445 and 558 have local maxima, where there are
  many arrays of medium size.
\item All arrays other than 32 and 360 approximately reach the maximum
  size given as the benchmark input (5000).
\end{itemize}
As expected, the optimization is straight forward and useful for arrays
that reach a stable size. But arrays that vary widely present an
interesting trade-off: Choosing a small presize limits the usefulness
of the optimizations, but choosing one too large can explode the
memory usage of the program. In fact, at the time of writing, our
version crashes with and out of memory error, when we run the
benchmark with input sizes larger than 8000. We will explain which
strategies we tested so far for weighing this trade-off in the next
section.

\section{Conclusion}
With have shown that the, so far no implemented, optimization of
presizing can provide performance benefits for certain
applications. Our naive solution implemented in our prototype shows
an average speedup of 37\%, at the cost of increased memory
consumption and longer warm-up times.

While these initial findings are promising, more work is needed in
order to find an optimal strategy for maximizing performance while
minimizing the additional memory consumption.

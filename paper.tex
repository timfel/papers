\begin{abstract}
To improve programming efficiency, the right tools are crucial.
This starts with the choice of the programming language and continues via the choice of libraries up to the choice of frameworks.
Thereby, polyglot runtime environments, such as GraalVM, try to vanish these boundaries. So different languages and their libraries/frameworks can be combined. For example, mechanisms are provided to send messages between language boundaries.
However, the polyglot application developer is obligated to properly use the right interface for the right language.

To reduce the mental effort for the application developer and let them focus on the business logic, we introduce user-defined target type mappings --
an approach to adapt cross-language messages at runtime to match the expected interface. Thereby the translation strategies are defined in an exchangeable and easy to edit file format. Thus different stakeholders ranging from library and framework developer up to application developer can use and extend these strategies for their needs.
\end{abstract}

\section{Introduction}
With the increasing complexity of software, it becomes all the more important to use the right development tools.
By using suitable language constructs, frameworks and libraries the development time can be significantly reduced. // ToDo: Source?

To use the most appropriated parts of each programming language for a given problem, polyglot runtime environments such as GraalVM provide mechanisms for language interoperability.
Thereby, objects can be accessed across language borders.

In the case of GraalVM, the underlying framework provides interchangeability of primitive types and some selected basic data structures such as lists.
Thereby, this mechanism in deeply integrated into the framework.
And therefore, hard to extend for other objects like maps/dictionaries or even more domain-specific data types like data frames.

To address this issue, this work introduces user-defined target type mappings --
An approach to provide cross-language interface mappings by generating suitable adapters.
Thereby application and library developers can extend the underlying information to generate these adapters to fit there needs and can even share them.

\section{Background/Context}

As part of this work a prototypical implementation of the represented approach is provided in GraalVM~\cite{Wurthinger:2013:OVR:2509578.2509581}.
GraalVM is a Java VM, which provides interoperability between different programming language runtimes.
To archive this, the runtimes have to be implemented within a specialized language implementation framework provided by GraalVM called Truffle.
Thereby objects that can be shared between languages, implement the common interface \classname{TruffleObject}.
In this way, all languages have a shared understanding of message communication and messages can be sent to objects across language boundaries~\cite{10.1145/2816707.2816714}.

\section{Approach}

This approach utilizes the adapter design pattern~\cite{Gamma:1995:DPE:186897}.
By wrapping an object from one language with an adapter, it can expose the related interface from another language if it gets called from there.

To reduce the implementation effort and provide an easier entry point for extending, the adapter consists of two parts.
Instead of providing one mapping for each concept, such as a Collection, and language combination, an intermediate, language-independent representation of the interface is used as an intermediate step.
The first part of the adapter maps from the wrapped object to the intermediate representation and the second part maps from the intermediate representation to the target interface as shown in Figure~\ref{fig:adapter_diagram}.
Thus if a new implementation of an existing concept is added, only the mapping to the intermediate representation has to be given to fully integrate it.

\begin{figure*}[]
  \centering
  \includegraphics[width=0.6\textwidth]{images/adapter_diagram.pdf}
  \caption{UML object diagram to illustrate the two part adapter}
  \label{fig:adapter_diagram}
\end{figure*}

To generate the adapter the following information is needed:
\begin{enumerate}
    \item the type and language of the wrapped object
    \item the concept the wrapped object should represent / the generic interface
    \item the interface in the target language    
\end{enumerate}

The first two points can be resolved while creating the adapter.
Therefore the user explicitly specifies which object should be wrapped with which generic Interface as shown in Listing~\ref{lst:interface_first_adapter}.
At this point, the first part of the adapter, which provides the mapping from the wrapped object to the generic interface, can be created.

\begin{lstlisting}[caption={Example interface to generate the first half of the adapter}, label={lst:interface_first_adapter}, language=python]
from polyglot_ds import PolyglotDS

polyglot_ds = PolyglotDS([], 'Collection')
\end{lstlisting}

In order to do so, the mapping has to be specified.
The generic target interface, in this example Collection, is specified in a language-independent, exchangeable file format.
While the development of interface definition languages is an open research topic, %Todo: Source?
for the sake of simplicity we describe the interface as a set of method names as shown in Listing~\ref{lst:interface_collection}.

\begin{lstlisting}[caption={Interface definition of Collection}, label={lst:interface_collection}]
add
size
isEmpty
...
\end{lstlisting}

Given that interface defintion, the method names are mapped in a mapping file as shown in Lisiting~\ref{lst:mapping_file}.
Thereby each line represents one operation.
The first token represents the method identifier in the generic interface definition, followed by the method names of the concrete language object.

\begin{lstlisting}[caption={Mapping file between Ruby array and Collection}, label={lst:mapping_file}]
add push <<
size size length
isEmpty empty?
...
\end{lstlisting}

Whereas, it is not necessary to provide alias names for wrapped objects, since every translation should lead to the same result,
it is crucial if the mapping is used for the second adapter part.

Besides the mapping, the creation of the second part also needs the desired language interface.
Thereby determinating the desired target language is already a challenge.
During the initalization of the first part, it is not known from which language it will be called.

\begin{figure*}
  \centering
  \includegraphics[width=0.7\textwidth]{images/adapter_behavior.pdf}
  \caption{Adapter Message Resolution (notation UML 2.5 sequence diagram \cite{uml2.5})}
  \label{seq:deployment}
\end{figure*}

To overcome this issue, the user could explicitly state the desired interface if the required information is present.
This can be done either by a explicit call to the adapter, such as \lstinline{polyglot_ds.adapt_to_ruby_array()}, or by utilizing Context-oriented Programming.

While this approach provides great control by stating everything explicit, it can be quite cumbersome. 
Especially, in many cases the mapping intent is already expressed in the underlying algorithm.
If for example a Collection is passed to an Ruby algorithm, it is pretty clear that the desired interface is at least an Ruby object
and probably also an array-like interface.

Although from a user perspectiv, the desired language is clear, it is not intended from the Graal framework to find out the language.
While from an application developer view, the transparency between languages is desirable, it limits the design space for tooling developer.
To build the prototype a prototypical language history stack was integrated into the Graal framework.
In addition a new primitive function is added, to provide an entry point from the language level.

Every time a language context is requested, the corresponding language identifier is added to this stack.
By utilizing this stack, it is now possible to determine the language from where the desired method call is emitted.

To identify, the right data structure interface from the given language,
the language-independent, generic interface can specify default mappings for the different languages. 
Given that information, the adapter can fully automatically adapt to the desired target interface.

From an application programmers view, the boundary between the languages disappear.

\section{Related Work}

The desire to use existing data structures and objects across different runtimes, created different approaches.

\paragraph{Serialization}
During serializtion, the object is translated into a format that can be stored, transmitted and later reconstructed.
The advantage of this approach is that it can be integrated in nearly every language as a library.
However, it has its limits by more complex objects.
Since the memory is not shared between the runtimes, the object exists as sperate object in each runtime.
Resulting in different identities, more memory consumption and performance overhead to transfer the object.
In comparison, our approach preserves the identity, by keeping the same object between runtimes and transalting the messages accordingly.
Instead of representing a specific instance of an object in a language-independent format, the underlying conecpt itself is represented that way. 
Thereby, several challenges are shared between these approches, such as schema evolution.
Although this challenge is not directly addressed in this work, correspondig ideas can be borrowed from this field.
Popular serialization mechanism are for example Google Protcol Buffers~\cite{ProtocolBuffers}, Apache Thrift~\cite{Thrift} and Avro~\cite{Avro}.

\paragraph{Common Data Layer}
For specialized objects, a standardized, language-independent memory format can be defined.
On top of this language or library specific interfaces can be defined.
Thereby the memory format is highly specialized for specific data types and each new interface requires development work.
This approach is implemented in Apache Arrow~\cite{ApacheArrow}.
There a columnar memory layout is shared between different libraries to provide data frame-like interfaces.

\paragraph{Polyglot Adapters}
The idea to provide adapters for the GraalVM, was established by Niephaus et al.~\cite{Niephaus:2019:TPA:3328433.3328458}.
They demonstrated that the adapter pattern is suitable to translate messages between languages and mimic language-specific behavior.
In the course of this, scaling and usability challenges were revealed, which are tackled by this work.
By introducing a language-independent, generic interface representation and splitting the adapter in two parts, the mapping overhead can be drastically reduced.
Further, the language resolution, which creates the second part of the adapter on the fly, improves the overall usability.

\section{Conclusion and Future Work}

In this work user-defined target type mappings are introduced.
These enable polyglot developers to combine algorithms and datastrucutre from different languages.
Thereby mechanisms are introduced to make the whole process transparent to the user.
There is no need to adjust either the interface from the object or the calls out of the algorithm by hand.
This enables the application developer to focus on the domain specific challenges and using the best fitted language concepts without being bothered with language boundaries.

Currently, it is an early prototype to test the feasibility.
In a productive environment, the introduced performance overhead should be reduced.
The mechanism to figure out the target language as well as the creation of the mapping behavior during runtime, introduces additional function calls.
While these can be reduced by utiliying caching and reusing of the mapping behaviors, an efficent implementation is part of the future work.

Currently, the creation of the mapping files can be time-consuming.
Therefore it is conceivable to support the user in this process by providing tools.
These can range from providing a specialized editor to explorer and connect different interfaces, up to (fully-)automatic mapping approaches by utilizing data from the underlying source code or test suites.

In addition to the creation of new mappings, the reusing aspect of the mappings was considered.
The file format makes it easy to exchange the data.
However, a infastructure to upload, download and explorer these files would be a great addition.

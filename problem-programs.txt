A Penultimate Plethora of Potentially Problematic Programs

Here is a list of potentially problematic programs in Babelsberg,
usually along with our decisions about what their result should be.
These are classified by language.

____________________________________________________________
BABELSBERG/PRIMITIVE_TYPES

x := 3;
x := "hello";
/* Assignment can change the type of a variable.  (If we are modeling
a dynamically typed language, this should certainly work.) */

x := 3;
always y=x;
x := "hello";
/* This will work if the solver allows it.  After the second
assignment, we would have a weak stay on y that it be an int, along
with the required constraint that forces it to be a string.  If the
solver can handle constraints that ask x to be of different types,
then it works.  Note that we will be a bit inconsistent with
Babelsberg/Records, in which an analogous program will *not* be legal.
A rationale for this is that we are treating all the primitive types
as similar -- they are atomic -- and what we are doing with our type
checking rules is avoiding changing *structure*.  If we did want to
disallow this program, we could add some suitable type checking rules.
*/

x := 3;
always weak x=5;
always weak x="hello";
/* This is also legal if the solver accepts it.  Here the solver is
free to choose either an int or a string for x.  Arguably this
nondeterminism isn't any worse than allowing the solver to select
either 3 or 5 as the value for a variable (and certainly we allow
that). */

x := 3;
always y=x+x;
x := "Hello";
/* Similarly, legal if the solver can accommodate it and if + is
overloaded to mean string concatenation as well as addition.  First we
would have y=6, then y="HelloHello". */

/* This program is intended to illustrate coercion issues.  Suppose we 
have both integers and floats as primitive types */
x := 5;  
y := 10;  
always y=x+3.1416;
/* Similarly, legal if the solver can accomodate it (in this case by
doing a coercion from int to float) */


____________________________________________________________
BABELSBERG/RECORDS

a := {x:1};
a := {y:10};
/* this is OK - again, assignment can change the type of a variable */

once a = {x:1};
once a = {y:10};
/* Not legal - the type check (which is a structural check) fails.
This is in contrast to the similar examples with primitive types,
which work if the solver can handle the resulting constraints. */

a := {x: 4};
always a.x=10;
b := {x: 0};
always a=b;
a := {y:30, x:4};
/* Not legal - the assignment to a at the end gives it a different type
than b, so the equality constraint fails to typecheck */

a := {x:1};
b := {y:1};
always medium a=b;
/* Not legal, because either a or b would have to change their structure */

a := {x:2};
always a.y = 100;
/* Not legal, since a doesn't have a y field (the system doesn't add
one spontaneously) */

a := {x:1};
b := {};
always a.x=b.x
/* Not legal- the system won't assign a record to b with an x field */

a := {x:1};
always b=a;
a := {};
/* Not legal - b is uninitialized at the point we encounter the
always constraint. */

About the last program: requiring that variables be initialized before
equating them with something is annoying for the programer.  We
decided that indeed the above program is illegal in the formal
semantics.  However, in practical implementations, we can have a hack
to allow it.  It only works for = constraints where one side is
uninitialized.  (Perhaps the semantics is that it first assigns the
other side to the uninitialized variable, and then adds the always
constraint.)

BABELSBERG/UID

p := new {x:0, y:0}; 
q := new {z:0}; 
always p == q; 
/* Legal - identity constraints don't include the structural
compatibility checks.  To satisfy the final constraint the solver will
make p and q be idential.  It is nondeterministic whether p will be set
to q or vice versa, but the system will use one or the other (it won't
create a new object). */

p := new {x:0}; 
q := new {x:0}; 
always medium p.x = 0; 
always medium q.x = 1; 
always weak p == q; 
/* This is not allowed, because explicit soft identity constraints are
not allowed on the program level. This allows us to solve for
identities first.  (If this were legal, either we would violate a
medium priority constraint in favor of a weak one, or else we would
need to change identities in response to value constraints.)  In the
semantics we do have weak identity stay constraints, but these are
implicit rather than written explicitly by the programmer. */

a := new {x:1, y:2};
b := new {ref:a};
always b.ref.x = 2;
c := new {x:2}
once b.ref==c && b.ref.x=2
/* Not allowed.  We don't want to allow identity constraints and
constraints on values to be intermingled.  Even though this would work
for conjunction, we'd want to allow disjunction as well, and short of
eagerly selecting a branch (as in the current implementations, which
arguably don't implement the correct semantics) this would prevent
separately satisfying identity and value constraints. */

BABELSBERG/OBJECTS

x := 3;
always y=x;  /*uses an equality constraint */
x := "hello";
/* This is the same as one of the Babelsberg/PrimitiveTypes programs.
It is legal as far as the semantics is concerned.  If the = method for
String can accept an integer as the argument, then the program
succeeds with x and y both bound to "hello"; and otherwise it fails. */

x := 3;
always y==x;  /*uses an identity constraint */
x := "hello";
/* This is again legal as far as the semantics is concerned, but in
this case we also know that it must succeed with x and y both bound to
"hello", since we are using an identity constraint (which for
uniformity we also allow for primitive types). */

x := stack.pop;
/* This works, because the RHS of the assignment is evaluated first, and 
then we set up a once constraint using the value popped from the
stack.  (The RHS of an assignment can have side effects, in contrast
to always or once constraints.) */

once x = stack.pop;
/* not allowed, since we don't allow side effects in constraints */

always x = stack.pop;
/* definitely not allowed! */

s := Rectangle.new( ...);
always a = s.area
s := Circle.new( ...);
/* Legal.  Note that the class of s changes, but both have an area
method */

p1 := Point.new(2,3);
p2 := Point3d.new(0,0,0);
always p1=p2;
/* If = for 2D points is written in a reasonable way (i.e., = just
calls the the x and y methods of the argument and checks them for
equality with the result of calling its own x and y methods), this
should succeed with p1.x=p2.x and p1.y=p2.y; there are no constraints
on p2.z.  This is a bit weird, but no more weird than the standard OO
definition of = for points.  (It would seem less weird if we weren't
overloading =, but instead called it two_d_point_equals.) */

p1 := Point.new(2,3);
p2 := Point3d.new(0,0,0);
always p2=p1;
/* This fails, assuming p1 has no z method */


We decided that constraints cannot call methods that create other
constraints.  This would be easy to check in a practical
implementation if we wanted to do so.  Note that this is not the same
as having a method, called in the ordinary way, that creates
constraints.  That seems useful and is fine.

In some cases, creating a constraint is a kind of side effect, and
would be forbidden under our restriction that methods called by
constraints must be side-effect-free.  (There is an example of this
below.)  There are other examples that could be made to work, but we
don't have any good use cases.  So for simplicity let's just not allow it.

For the record, here are some examples (even though we are forbidding it).

def test(x)
  always y=x+2;
  return y;
end;
a := 10;
b := 10;
always b=test(a);
/* Note that the effects of the y=x+2 constraint persist after the
method returns. */


If we allowed using such methods in constraint expressions, we would
need to solve their constraints eagerly rather than just accumulating
the constraints and solving all at once.  Here's an example that shows
the need to solve the constraints eagerly.

def test(x)
  always y=x;
  if y>10 then return 1 else return 0;
end;
a := 5;
always b=test(a);
/* If we don't solve eagerly, y doesn't have a value when we evaluate the
test in the 'if' statement. */

The following program is not allowed, and illustrates why adding
constraints in methods called from constraints can have side effects.
Suppose we are using a least-squares solver that supports soft
constraints.

def test(x)
  always medium x=5;
  return x+1;
end;
a := 0;
b := 0;
always medium a=10;
always b=test(a);
/* Every time we evaluate the expression b=test(a), we add another
medium constraint that a=5.  Since we are finding a least squares
solution, this nudges a more toward 5 each time, diminishing the
influence of the a=10 constraint. */

Finally, if we did allow this, what if the method adds soft
constraints, and is itself invoked by a soft constraint?  For example,
suppose that in the above program we instead had "always weak b=test(a)".
We would need an algebra for combining priorities, for example, take
the minimum of the priorities, but this just seems like one more
complication.

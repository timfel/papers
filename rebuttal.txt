We first address high-level questions and concerns regarding our
evaluation and the applicability of our work to other languages, and
then respond to more specific concerns.

Reviewers 1, 2, and 5 note that we should give more information on the
evaluated programs. We have provided the companion TR as supplementary
material with the submission, and it should be available to the
reviewers. It explains the test cases in more detail. In addition, all
programs as well as the executable semantics are available on GitHub
(github.com/babelsberg/babelsberg-rml,
github.com/babelsberg/babelsberg-js/tree/semantics-compat). We will
add links to the code and the TR to the paper. We also plan to submit
an artifact. We will nonetheless add additional detail about size,
complexity, and purpose of the evaluated programs as well as the test
cases to the main paper.

Reviewer 2 asks whether the problem we address is specific to
Babelsberg. To our knowledge, any language that supports references or
methods in constraints has the same issues. Kaleidoscope, for example,
allowed some of the same surprising solutions that we address in this
paper where types of variables may be determined to satisfy value
constraints. Kaplan and Turtle address the second issue by evaluating
non-constraint methods and variables eagerly and then use them as
constants in the constraint expression. Our work would allow these
languages to support references and object-oriented methods in
constraints. Kaplan does not support soft constraints for specifying
that the solution should be close to the prior state of the system,
and programmers have to take explicit steps if they desire such
solutions.

Reviewer 4 asks what the differences would be for statically typed
languages, in particular regarding identity constraints. Our typing
rules can re-use the typing rules from the underlying language, which
may already include knowledge about object fields. However, the issue
of identity constraints remains. Kaplan does not address this issue,
as it does not include a facility to require two variables to always
point to the same object. Kaplan uses Z3, and requires programmers to
wrap variables to use them in constraints. When passed to the solver,
everything is regarded as a value, and there is no notion of making
references be equal. Our notion of identity constraints would work in
Kaplan as well, thus allowing the integration of identity constraints
with a statically typed language.

Reviewer 3 notes that "optimal solution" is not clearly defined. By
this we mean whatever the used solver considers "optimal", allowing us
to draw on the extensive prior work on optimizing solvers. Our work
treats the solver as a black box - the function to determine an
optimal solution is solver-specific. The solver interface is treated
in more detail in Reference 1.

Both reviewers 3 and 4 note that H(x)\uparrow has not been defined. We
will clarify that this indicates that H is undefined for x, i.e., that
no binding for x exists on the heap. Both reviewers also note that
L!=x => E,H|- L:T was confusing in the S-Asgn and S-AsgnNew rules. It
means that if L is not simply a variable (x), then L must be well
typed under E and H (i.e, have a type T through our typing judgment
for the current heap and environment). This requirement ensures that
we do not generate fields in assignments. We will make this clearer.

Reviewers 2 and 4 note that "once" was not defined. We will correct
this. A "once" constraint is created, solved, and then immediately
retracted.

Reviewer 2 raises a concern that we do not sufficiently introduce
object-constraint programming (OCP) with Babelsberg. Constraints in
OCP provide a tool to add and maintain invariants regardless of where
a change that invalidates them comes from. Babelsberg/JS implements a
design for cooperating solvers, which handles constraints over reals,
integers, booleans, strings, and finite domains. As per the semantic
model, enabled constraints continue to be satisfied, and when
satisfaction fails, the program halts, leaving heap and environment
unaffected. In the practical implementations, this generates an
exception the programmer can handle.

Regarding our omission of method and class definitions, we do provide
a full object-oriented semantics in the companion TR. (Due to space
limitations we were unable to include the entire semantics in the
ECOOP paper itself, and chose to concentrate on the semantic issues of
object identity rather than methods and class definitions, since the
issues of object identity were subtle and complex; method dispatch was
more straightforward.) The main additional challenge is how methods in
constraints are translated to the solver. Method dispatch in
constraints works normally by looking up the method on the receiver's
class according to the host language's semantics.

The formalization uses reals rather than ints simply because it seemed
clearer to use them in our examples (e.g., for the solution to
simultaneous linear equations). In the theory, solving is precise;
round-off issues that occur in practical languages are not relevant
for the semantics. Adding more primitive types is straightforward and
the practical implementations do support a variety of such types.

Most standard rules are not given (such as rules for method and class
definitions). The rules that are standard include those for control
structures. Non-standard rules are our rules for declaring
constraints, assignments, and type-checking.
 
The E;H \models C judgment is used in the assignment rules, as well as
the S-Once rule.

The stay and i-stay rules ensure that the environment and heap change
as little as possible. The stay rules allow changes to identities, as
these can change during assignments. The i-stay rules assert that
identities stay the same, and thus ensure that the solver cannot
change object identities to satisfy a constraint that only involves
primitive types.

In S-Asgn, C_I is the result of translating the set of identity
constraints. The stay rules already return a suitable representation
and thus do not need to be translated. The full rules for the
translation are given in the companion TR, but since they are
relatively straightforward we did not include them in the main paper.

The S-OnceIdentity rule asserts that both the LHS and RHS of the
identity expression evaluate to the same value. Thus, they must
already be identical before the constraint can be added.

The website noted by the reviewer is primarily a useful list of
constraint solvers with APIs in popular languages. These APIs offer
none of the language integration that OCP provides, leaving it to the
programmer to deal with the issues of expressing references and
translating methods to the solver. These constraint solvers are of
interest for use with Babelsberg, but the work reported here is
largely agnostic with respect to the particular solver (we treat it as
a black box). On the other hand, for practical implementations the
choice of solver can be very significant. We will clarify that there
are many other solvers available that could be used with our design
and use this website as a reference for that.


----------------------- REVIEW 1 ---------------------
PAPER: 3
TITLE: Squeak Makes a Good Python Debugger
AUTHORS: Fabio Niephaus, Tim Felgentreff, Tobias Pape and Robert Hirschfeld

Overall evaluation: 3

----------- Overall evaluation -----------
I'd like to start to say that I was very impressed with the technology
described in the paper.  I can see that this would stir wider,
including commercial, interest beyond the language research community.
Under that light, the paper could be written for an audience other
than a small subset of the community of language researchers, who are
presumed to know about the inner worksing of Squeak, PyPy, RSqueak,
etc., well.  For regular Python coders, why hot-swapping, doIts in a
workspace, etc. are more useful than printf debugging could be useful.
Perhaps the last line in the abstract could be more strongly stated.

As for language researchers, it would be good if there were a few
paragraphs on how the Squeak image is represented at runtime (as I
understand it, there is no contiguous memory region for Squeak objects
but a Squeak object is represented in a way RPython expects) etc.,
before delving into how frames are organized.  Even though the other
papers are referenced, it is worthwhile to mention them to make the
paper more readable.

One piece of important information is how much code (for RSqueak and
PyPy in RPython, I presume) was needed to be modified/added to make it
work.  The paper mentions that it was "comparatively low", but I'd
like to know some numbers.

In regards to the sequencing of explanation, I was confused why you'd
have to chain different kind of contexts in the same process.  On page
3, it mentions that interpreters for different languages are running
in separate processes.  That initially lead me to think that a new
Python process would be launched when a Python interpreter is started,
and Squeak process would operate on the process.  Later on, the notion
of doits from workspaces and evaluating expressions are mentioned and
I gather that that is why we'd need the mixed frames in a process (if
I'm not mistaken).

A technical question: Can primEval:filename:mode: primitive take some
variable bindings?  In the Squeak Debugger, a very powerful feature is
to be able to evaluate a code snippet in the right context.  The
temporary variables and instance variables of the receiver can be used
in the code snippet to explore.  From the paper, I got the impression
that it is not supported (but even if that is the case, perhaps it is
not so hard?)

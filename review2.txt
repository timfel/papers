PAPER: 3
TITLE: Squeak Makes a Good Python Debugger
AUTHORS: Fabio Niephaus, Tim Felgentreff, Tobias Pape and Robert Hirschfeld

Overall evaluation: 3

----------- Overall evaluation -----------
This paper describes an experimental hosting of the execution of Python programs in a Smalltalk virtual machine environment and extends the Smalltalk debugger and other develop tool to operate upon such Python programs.
The paper offers a good description of an interesting experiment but it’s not clear that that it actually breaks any new ground.  Most, if not all, of the techniques described have been used in many  multi-language runtimes and debuggers. But the literature seldom describes such techniques in detail. The techniques tend to be craft skills of practitioners working in this specialized area. They are either rediscovered or passed down from generation to generation of runtime/debugger implementors.

Overall, this is a good paper and revisiting this area seems quite appropriate for this workshop.

Things you may want to address at the workshop and in future versions of the paper:

Figure 1 and the accompanying text seems to be arguing that using an “debugging API” places limitations upon live programming support and that Smalltalk/Squeak has an advantage because it does not have such an API.  But, aren’t the Smalltalk runtime objects (contexts, CompiledMethods, instvarAt: methods, etc.) in fact an API that is used for inspecting and manipulating the execution state of the VM? The real difference between systems with a formalized debugging API and the classic Smalltalk approach is that the Smalltalk debugging API has not been abstracted.  Instead the API is the actual implementation entities of the runtime.  The problem with this approach is that it make clients of the API (the tools) highly dependent upon the implementation details of the runtime. This subsequently constrains improvement to the runtime that might have the effect of breaking the tooling. A solution to this problem is Mirrors (Ungar and Bracha, http://bracha.org/mirrors.pdf ). The commercial scale feasibility (and pitfalls) of using a Smalltalk environment to host both the tools and execution of another language was demonstrated by IBM’s VisualAge for Java product (https://en.wikipedia.org/wiki/IBM_VisualAge ftp://ftp.lotus.com/pub/lotusweb/product/devtools/redbook/SG242232.pdf). VAJ’s tooling was implemented in Smalltalk with both the Smalltalk and Java code running on a single “universal virtual machine” https://books.google.com/books?id=mRBg-8B0WCsC&pg=PT9&lpg=PT9&dq=visualage+uvm&source=bl&ots=pxOYpJv8T-&sig=kZ-wtoCCXUqnxXtHXlx2FTGD29s&hl=en&sa=X&ved=0ahUKEwi4u8iP-KnSAhXFsVQKHdyWCfsQ6AEIHjAA#v=onepage&q=visualage%20uvm  

Finally, since this is a submission to a “programming experience” workshop it would be interesting to have a bit more exploration of actual Python programmer’s experience of using this system. Smalltalk=style extensible live development tooling is clearly applicable to other dynamic languages such as Python.  But, do Python programmers really want Smalltalk=based tools? Much of the perceived power of Smalltalk (and Lisp) environments seem to raise from the fact that both application code and tool code is written in the same language operating in the same process. Will Python programmers be empowered or disenfranchised by the necessity of using Smalltalk to extend the tools. The anecdotal experience from VisualAge for Java (http://wiki.c2.com/?VisualAgeJavaGripes) suggests non-Smalltalk programmers have a hard time adapting to Smalltalk inspired tools.

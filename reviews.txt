# Reviews

Review #6A
===========================================================================

Overall merit
-------------
3. Weak accept

Reviewer expertise
------------------
2. Some familiarity

Paper summary
-------------
This paper presents a framework for language developers to produce
IDE features for performance-oriented dynamic languages. It consists
of making the Language Server Protocol automatically available 
to all language implementations based on the Truffle framework.

The frameworks makes a number of features available such as 
code completion of globals and locals, code completion of
properties, documentation, signature help, among others.

The basic approach consists of executing code in order to obtain
dynamic type information, making the above mentioned features
possible in the absence of static types.

The evaluation shows which of these IDE features are available
for a collection of Truffle based languages.

Comments for author
-------------------
In general, this paper is well written and presents its ideas clearly.
It demonstrates that this technique can be helpful in providing
some useful IDE features automatically to language developers in
Truffle.

The paper is very forthcoming about its limitations. For instance
that only one syntax error can be reported in a file that potentially
has more (it stops at first syntax error).

It seems that executing code to obtain type information has
its limitations. First, it requires an adequate test suite to bootstrap
the code. This means that the test suite needs to not only have
good coverage but be correct. A bogus test (which can happen during
early development stages) would lead to incorrect runtime type
information and potentially wrong code completion.
Second, the ability to execute code assumes that the code is in
good enough shape. For example, the developer might first write the
overall logic with mock function calls before filling those out.
In this case, executing the code will not help in obtaining type
information. Finally the code has to be free of syntax errors. 
IDEs for statically typed languages manage to provide such features
even in the face of syntax errors (unless there are too many), which is helpful in the
early stages of development. Finally, executing code could be
side-effecting. The paper needs to discuss this limitation a bit
more. The developer may use a library which has a REST call deep
inside. Executing the code over and over from the IDE may result
in external undesirable side-effects (and potentially costly).

The paper needs to discuss a bit better what a language developer needs
to provide in terms of hooks to be able to use this framework. A complete
example on a small language might help (or a general discussion). How
much more work do they have to do?

The caching aspect needs a bit of clarification. The paper states
the user needs to initiate it at appropriate times. How does the user
know when to initiate caching? Does this require knowledge of how
the IDE works (which would not be ideal)?

Review #6B
===========================================================================

Overall merit
-------------
3. Weak accept

Reviewer expertise
------------------
2. Some familiarity

Paper summary
-------------
The authors propose the use of a Language Server Protocol for communicating between runtimes and tools such as IDEs. By using an LSP, tooling is able to interrogate a code base and provide tool features that are normally difficult or impossible to implement for dynamic languages (such as on-the-fly code completion). By targetting RPython and Truffle/Graal, it is possible to implement LSP and related tooling for a number of programming languages at once.

Comments for author
-------------------
This is an interesting paper, and in many ways it represents an obvious "next step" in making RPython / Truffle/Graal languages practical for developers. The main approach of the paper is described well and the example IDE features are interesting. 

The major drawback of this paper is in its evaluation. IDE use in particular, is an area where "lag" can make the difference between a practical implementation of an idea that has a chance of adoption, and an idea that has no hope of ever being useful. To be useful to the wider community, you really need to give a clear indication of how responsive your implementation is. Some benchmarks and results would help to convince the reader that your approach is worth pursuing. 

On page 9 you say "Unfortunately, the performance depends on the one hand on the execution time of the source code, which can be reduced by caching run-time information, but on the other hand it depends on the creation time of Truffle language contexts. We create a new one for each execution, which is quite cheap for SL, but for GraalPython, it takes a noticeable time. Reusing those contexts improves the performance, but introduces problems with cache invalidation and memory usage.". From this description, it is not clear at all how scalable or practical your approach is -- this is exactly where experimental data would help your case.

Review #6C
===========================================================================

Overall merit
-------------
3. Weak accept

Reviewer expertise
------------------
3. Knowledgeable

Paper summary
-------------
The paper deals with the implementation of a language agnostic server for the LSP protocol (language server protocol), that can be used with Truffle based dynamic languages. Issues of collecting meta-information from the IR (intermediate representation) of Truffle and from run-time information are discussed with accompanying suggestions for a possible solution.

Comments for author
-------------------
I have mixed feelings about this paper. Providing editor support almost out of the box in language design frameworks such as Truffle, is indeed a very worthy cause. Unfortunately there are a number of problems with the current status of the paper and my general suggestion is to refactor it and submit it in the "Experience Papers" category defined as: "describe insights gained from substantive practical applications that should be of a broad interest". The problem is that the submission does not currently read as a research paper:

a) Abstract + Intro: You are not presenting properly the context of your contribution when you are speaking about "tools" in general that are lacking when building new languages, the LSP provides a lot of editing assistance, but is not meant as a replacement for "tooling in general". This is the reason that projects such as the "Debug Adapters Protocol" where also introduced (to cover additional needs such as debuggers, but again not "tooling in general"). You can keep the general problem as a motivation but quickly explain to your readers what is the scope of your contribution.

b) Sec 2. Context: This is very introductory material that can be also found online, try to give concrete examples for a "Problem Statement" with some implementation details (ie we have Python on top of Truffle, running faster/better and can do polyglot, but we do not have the following editing facilities that are available through LSP with the standard python distribution). Then state your goal (ie a single language server for all truffle-based dyn. languages) and pick a state-of-the-art baseline (mainstream eg https://urldefense.proofpoint.com/v2/url?u=https-3A__code.visualstudio.com_docs_languages_python&d=DwIBaQ&c=RoP1YumCXCgaWHvlZYR8PZh8Bv7qIrMUB65eapI_JnE&r=tYnE93QcmCN_OA1iNJ02mecvaDZCC1hHyQm5HiiHuIk&m=hf5AFqJXOVpqzY1gNTjupEYhRESOMZqllBBwMcLyg-w&s=WUWFVF2m05QsvgRCdcxZdpPF5AHMqUX8hw-myFnalkM&e= ), that you can use for your evaluation later. Even if you show us a fraction of the features covered compared to your baseline BUT on top of Truffle it is still a WIN.

c1) Sec 3. Approach: Try to extract a model/design pattern from the textual description of page 4 and walk-us through some "idealized" code/pseudo-code for your solution. Imagine that we are implementors  to whom you are suggesting a general solution by giving them an idealized example and not only textual "guidelines".

c2) Sec 3. Approach: The "Obtaining run-time information" challenge for dynamic languages in order to do code completion is an orthogonal/independent problem to the one that you already introduced (ie out of the box language-agnostic editor support). Again set here a base-line and check what the current state-of-the-art is (a mainstream eg again could be: https://urldefense.proofpoint.com/v2/url?u=https-3A__code.visualstudio.com_docs_languages_python&d=DwIBaQ&c=RoP1YumCXCgaWHvlZYR8PZh8Bv7qIrMUB65eapI_JnE&r=tYnE93QcmCN_OA1iNJ02mecvaDZCC1hHyQm5HiiHuIk&m=hf5AFqJXOVpqzY1gNTjupEYhRESOMZqllBBwMcLyg-w&s=WUWFVF2m05QsvgRCdcxZdpPF5AHMqUX8hw-myFnalkM&e= )

c3) Sec 3. Approach: You need to organize your material / challenges / solutions in a table, give examples and tell us how your proposed model solves the problem (related to c1). Giving textual general guidelines is ok but only for corner cases that you judge as "implementation specific", the rest should be linked with a concrete description (UML and code) of a proposed solution.

d) Sec 4. Impem. + Validatiion: What is the baseline ? Where are the implementation details ? What resources are being used by your proposal, compared to other solutions ? What are the trade-offs ?

Paper summary
-------------
This paper describes a generic implementation of Microsoft's language
server protocol for the Truffle framework on the Graal VM.

Comments for author
-------------------

This paper has two main content sections:

Section 3 "Approach" outlines possible techniques for implementing the
LSP. This is written in the conditional tense, and without any
examples or code examples or really any details.  Section 4
"Implementation and Evaluation" really does little more than the
content in Table 1: there are a bunch of partial implementations which
have different feature sets.  Unfortunately neither the screen dumps
or the text discussion really any more usable information than that. 

Given these presentation issues, I consider this paper too premature
for publication at this time.

Possibly the issue is really the paper structure: the paper takes
Table 1 in Row-major order (working per feature) whereas a
presentation in Column-major would work better.

That's to say: make 2.1 more grounded, detailed, precise,

then for a new section merging 3 and 4, start with a subsection for
the simplest language (SL?), describe the salient features of the
implementation, then describe how it supports whichever features.  The
the next subsection tackles the next least complex language,
describing how the implementation differs from the previous one, and
the how the features differ, and so on.  Perhaps language 4 mixes
techniques from 3 previous ones, well that's fine, again, point back
to the concrete descriptions of those features or implementations,
describe differences.


Writing: fine, a little clumsy in places

Questions:

line 454 - how can you "try executing the current source code"

for that matter, can an implementation really run a whole batch of
unit tests in response to a code completion request?  the suggestions
on unsaved changes seem even less practical (459)
Actually page 5 gets more and more far-fetched - is this implemented???

the solution of course has been well known from Smalltalk: do all
development in a running instance of the program.  An IDE could always
not offer code completion until the program had executed far enough to
gather useful information.

I don't think section 3, written mostly in the conditional tense works
at all well. Instead of presenting a high-level "approach" that is too
high-level or provisional to be reliable, why not start with the LSP
for SimpleLanguage, then work through that showing how actual problems
in an actual implementation can be resolved?

792 - "implemented in an instrument" ??

816 seems SL implementation just builds a bridge from it's existing 

834 FastR impelemntation is very incomplete - why report it

867 FastR errors???

926 missing annotation?? so what?

table 1, pick better symbols (tick / start / questionmark / blank?)

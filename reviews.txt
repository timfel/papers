TITLE: Object Versioning to Support Recovery Needs: Using Proxies to Preserve Previous Development States in Lively
AUTHORS: Bastian Steinert, Lauritz Thamsen, Tim Felgentreff and Robert Hirschfeld
OVERALL EVALUATION: 2 (accept)
REVIEWER'S CONFIDENCE: 5 (expert)
----------- REVIEW -----------
Summary: The authors present a system to support versioning in a live programming system, Lively, that emulates Smalltalk on top of JavaScript. Proxies are used to manage multiple object versions, to preserve access to previous development and application states.  The approach is based on the following ideas:
- objects are immutable and as the state of an object changes a new version of the object is created
- objects are referenced via version aware links (realized through proxies)

Pros:
- interesting, provocative idea
- a prototype exists
- detailed performance analysis
Cons:
- use case is not highly motivating or convincing
- performance is abysmal
The paper addresses the very relevant problem of managing a history of a program, in this case focused on Lively Kernel Environment. The authors approach to using version-aware references is interesting and opens a lot of space for memory and performance optimizations.
The proposal is intriguing, but I am worried about the ability to cherry-pick versions. Is this really useful?  Normally it is not individual versions of objects that are of interest, but a collection of mutually dependent versions. For a very different approach to object versioning for dynamic updates, you should look at "Incremental Dynamic Updates with First-class Contexts", E. Wernli et al. http://dx.doi.org/10.5381/jot.2013.12.3.a1 Although the motivation is quite different, many of the same technical issues are addressed.
Also relevant is other work by Wernli on proxies: "Delegation Proxies: The Power of Propagation", http://dx.doi.org/10.1145/2577080.2577081. Wernli's approach to wrapping objects with proxies is very similar to yours, but he reports only 1 order of magnitude performance loss (8x slower), not 3 orders, within a Smalltalk environment. That suggests that your approach could as well be made to scale much better than in your current prototype.

Observations
- The paper describes well the problems with an implementation in JavaScript
- The paper evaluates well the memory and performance overhead of the implementation
- In general, paper is well written, easy to follow and easy to read
- The paper needlessly spends too much time on introduction and background

----------------------- REVIEW 2 ---------------------
PAPER: 13
TITLE: Object Versioning to Support Recovery Needs: Using Proxies to Preserve Previous Development States in Lively
AUTHORS: Bastian Steinert, Lauritz Thamsen, Tim Felgentreff and Robert Hirschfeld
OVERALL EVALUATION: 1 (weak accept)
REVIEWER'S CONFIDENCE: 4 (high)
----------- REVIEW -----------
Develops ubiquitous object versioning in the Lively implementation of Squeak Smalltalk in the browser. This is done at the JavaScript level using object proxies as proposed in ES6. The goal is to add version-control capabilities to the program development environment. For example to easily and safely rollback to a prior state of development. The crucial ability to fork and merge is largely left to future work.
Unfortunately the results of this experiment are mixed. Performance decreases by a factor of 180! It also turns out that proxies are supported incompatibly and incompletely by the main browsers, so as yet the experiment has not gotten Lively completely working. Although this experiment could be considered a failure it is about an important problem and so deserves to be reported.
I was bothered by the lack of discussion of the design decision to implement object versioning at the JavaScript level rather than inside the Lively Kernel itself. The Lively Kernel is a Smalltalk VM written in JavaScript. Surely the natural place to implement ubiquitous versioning of Smalltalk objects would be in the Smalltalk VM itself rather than in the underlying implementation language. I can imagine a number of plausible reasons for this design decision but I thought it should have been discussed. 
I felt this paper failed to highlight its main contribution, perhaps because it is one the Smalltalk community feels uncomfortable talking about. This paper is really about trying to fix one of the fundamental weakness of Smalltalk’s image-based development model, which some people blame as a primary reason for Smalltalk failing in the marketplace. Developing with textual source files may be less flexible and exploratory, but in compensation provides overwhelming advantages for managing industrial-scale development and deployment. This paper is attempting to provide image-based developers with the version-control capabilities that have been taken for granted for decades in file-based programming. Version control is not an advanced experimental feature that would be nice to have - it is an absolute requirement for any serious modern programming language. In my opinion a major contribution of the paper is to argue that providing source version control while maintaining the s!
 pirit of image-based development requires ubiquitous versioning of objects. I believe this paper could be made more relevant and discussion-sparking if it were recast as an attack on a key weakness of Smalltalk in order to enable its wider adoption.
I sign all my reviews - Jonathan Edwards <edwards@csail.mit.edu>

TITLE: Object Versioning to Support Recovery Needs: Using Proxies to Preserve Previous Development States in Lively
AUTHORS: Bastian Steinert, Lauritz Thamsen, Tim Felgentreff and Robert Hirschfeld
OVERALL EVALUATION: 1 (weak accept)
REVIEWER'S CONFIDENCE: 5 (expert)
----------- REVIEW -----------
The paper discusses an extension to Lively, a live development system for Javascript, that supports object versioning. The basis for this are versioned references: object references that maintain a version history for an object.  The implementation of versioned referenced is based on ES6's proposed proxy mechanism. The system does not require changes to application code or the programming language, and enables full undo and redo on arbitrary Lively applications. Unfortunately, the performance overhead is massive (1000x) and so the system is not practical at this stage.
Pros:
The paper is quite clearly written.
I think it would be wonderful if a mechanism like this became practical, and the value of the paper is in exploring this idea. 
Cons:
Unfortunately, the work gives no indication that a practical solution is remotely at hand. You blame much of the problems on poor implementations of proxies in JS.  That is probably true, but if things go from a 200x overhead on proxies to 10x you'll be very lucky. At that point, if your versioning overhead were zero, you would probably be in the practical range for a development environment (albeit very slow, and for demanding applications, much too slow). However, your overhead is not zero, and you devote scant attention to it.

 REVIEW #1 
The paper presents a new design of an object-oriented
language that extends Ruby with constraints. Constraints
make give more freedom to express and enforce properties
(e.g. assertions) that an application should satisfy.
Compared to systems based on functional and logic
constraints, important expressive power here is
re-establishment of constraints in case of changes, which is
useful or many applications, including user interface
layout. The edit constraints that directly support
re-establishing a constraint in case of a localized change
are useful, and give notable performance gain.
Another important aspect is soft constraints; these
are helpful in practice because there is in general
no guarantee that constraints would be satisfiable
in a hard sense.
Being able to indicate when a constraint should hold within
a piece of code is useful.
Some of these features are present in earlier systems such
as Kaleidoscope, but the current design appears practical
and is built on a reasonably high-performance infrastructure
PyPy (as far as dynamic languages are concerned).
The system has 1.5 slowdown even if constraints are not
used.  Could this be eliminated using an extension of PyPy's
type inference to detect variables that are not involved in
constraints?
The system has not been evaluated on solvers that find
entire data structures such as arrays or strings. The
constraint solving is only applied to numerical domains in
the two example benchmarks presented.
Assessment and suggestions:
I like this paper and the work done, but have a few
concerns that justify a revision request.
First, there are only two constraint solving benchmarks
presented, and that the presentation and the design mix the
programming model and its implementation.  It is my opinion
that one of the main factors holding back progress in
constraint solving support in languages is the lack of good
challenge benchmarks, so the paper could do more to
contribute to this.
Second, the paper mixes the presentation of the programming
model and the implementation. In a clean language, the
programmer should not need to know how the feature is
implemented. Currently, the presentation up and not
including section 4 is implementation-independent, but it
does not cover all features. Some more interesting and novel
features, like edit constraints, are explained essentially
as implementation concepts. Is there a friendlier way for
programmers to use edit constraints? Overall, I would have
spent a little more on the description of the programming
model than on some of the implementation details.
Third, I would have also liked to see a performance
comparison with other recent systems, such as Kaplan system
presented in POPL 2012 paper "Constraints as Control" and
available (for an older version of Scala) here:
http://lara.epfl.ch/w/kaplan
The performance comparison is interesting because Kaplan
uses Scala, which is statically typed, and interoperates
with Z3 reasonably efficiently. 
Fourth, the authors gloss over the questions of finite
precision of numbers used by some solvers.  Z3 does not
support floating points, only real numbers, whose semantics
is very different than floating points. SMT solvers that
support floating points are only beginning to emerge.  I
wonder how the system enforces equality constraints on
floating point values, given round-off errors.  Does it
assume some tolerance? If so, how does it ensure that the
tolerance is well-chosen for the particular domain?
Fifth, as far as I can see, the presented system does not
support enumeration of solutions. It is possible to find all
solutions when the set is finite?
I was also wondering if identity constraints are useful for
finding data structures?  Could the authors provide a
reference to the DeltaBlue library and examples where they
used it?

Summary
=======
The paper describes the language Babelsberg, and its implementation.
Babelsberge is Ruby, extended with primitives for expressing constraints
between program variables. Babelsberg serves as an interface between
an OO language and constraint solvers: different constraint sovers can
be plugged in to solve particular constraints.
Evaluation
==========
As the athors do, I too believe there's value in integrating OO widely used
OO language and constraint solving, so the authors are working towards a worhty
contribution. This paper is an attempt to explain that contribution.
It is, however, inadequate. 
The biggest problem with the paper is that the language is _only_
explained through examples. The semantics, not even syntax, of the
extensions are explained in any general level, so it is really not
possible to know what Babelsberg is.  There is a section on
implementation, but that, on the other hand, is too detailed, and
vague at the same time. I don't believe that it is possible to infer
the semantics, or even syntax, from that description either.
In general, the writing is not precise and unambiguous enough.  Too
many details are crammed into the paper, leaving many (most)
unsatisfactorily explained. Terms are used without explanation, new
ones invented, etc. I give many detailed examples below on such
problems, and how to possibliy improve.  Please note that going
through the list of my recommendations below and following them
would not (yet) make this paper accetable.

This paper is about adding constraints in the Constraint Imperative Programming
(CIP) style to an OO language, namely, Ruby, and this is called Babelsberg/R.
The contribution is mainly about a modern refresh of ideas in Constraint
Inmperative Programming mainly Kaleidoscope within a modern OO language
and the paper focuses on the implementation in Ruby. I like the thesis
of the paper of embedding constraint solvers in a non-solver specific
fashion as this is an old idea which deserves a modern implementation.
That said, I found it hard to identify what is the novel research
contribution. Most the paper is written in mostly in an informal way
without much details. I wonder how important is the particular OO language,
and the specific importance of Ruby. While the authors have picked Ruby,
and they probably need to pick a specific language, can't this be done to
other OO languages or dynamic languages. While the authors are focusing
on the CIP paradigm, there are also a number of existing constraint
OO libraries. The one which comes to mind which has some careful OO integration
is Ilog Solver (nowadays called IBM Ilog Solver) which takes specific
advantage of C++ making it easy to write semi-declarative programs in C++
including handling of backtracking.
The authors should compare the OO features of Babelsberg/R with Ilog Solver
eventhough the CIP focus does make this paper different.
Notice that Ilog Solver does not need to have different execution modes
like what is done here because of the use of overloading.
Very few constraint solvers are designed for CIP as it requires specific
treatment of soft constraints. Its not clear how those solvers, e.g.,
Z3 will fit well. It would be better to have a clearer treatment of
solver semantics combined with language semantics. 
For example, by having a formalization which can encompass several solvers
and their different features, this can then be clearly mapped to both
syntax, semantics and implementation in Babelsberg/R.
Note that in S2.1, the Z3 example is quite different from the other examples.
Because the paper is quite informal, I wonder if there are issues with
variables, what happens if an object is no longer live 
(and hence can be deleted) but the constraints interact with another 
constraint in another live object. Normally the variables in the dead object
can be garbage collected and also the data structures but this may not
be correct with constraints. Because there is little treatment of the
interaction between language semantics and constraints, examples like this
one raises questions about their language integration.
I also wonder if there are other garbage collection issues with constraints.
The contribution of the CIP part of the paper is mentioned only briefly.
Is it mainly the implementation?
 
It is unclear to me in the evaluation section that the imperative version
is behaviorally equivalent to the object-constraint version. Shouldn't
the constraint version be more general than the imperative version?
If so the comparison may not be totally fair for the constraint version.
Overall it seems to me that this paper is interesting but a bit rough and
could benefit from more precision and perhaps also generalizability.
Why is Ruby chosen anyway? Why not other OO languages? Why not Java even?
Overall the motivation of the paper is good but I feel that the paper
needs a more careful treatment of the semantics, language issues and
implementation.

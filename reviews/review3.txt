----------------------- REVIEW 3 ---------------------
PAPER: 2
TITLE: GraalSqueak: A Fast Smalltalk Bytecode Interpreter Written in an AST Interpreter Framework
AUTHORS: Fabio Niephaus, Tim Felgentreff and Robert Hirschfeld

Overall evaluation: 2 (accept)

----------- Overall evaluation -----------
This is a nice and short paper.
The paper compares and evaluates Truffle-based AST and bytecode interpreters for the Smalltalk/Squeak language.
The AST is actually decompiled from the bytecode, and loops are recovered for better performance.
The paper details the bytecode interpretation loop and the needed annotations in Truffle.

It is not clear to me why the source Smalltak code is not available to the VM, and only the bytecode is.
The text mentions the sources are in the image, so why the VM cannot access it?

Using a decompiler has the advantage the source->bytecode compiler is used in both cases, but relies heavily on how faithful the decompiler is.
Could you show what the decompiled code look like for those benchmarks?
Is it very similar to the original source code or rather different?

Using only 2 tiny benchmarks is disappointing.
They also seems to exclusively use primitive methods and not exercise any Smalltalk code beyond the benchmark method itself.
Aren't there more small Smalltalk benchmarks which do not require much compatibility?

In Section 2, you mention you maintain your own branch profile counters in ConditionalJumpNode.
Why not using a CountingConditionProfile in the bytecode loop instead?

Do you have any insight why Truffle doesn't optimize the original loops emitted by the decompiler as well as when using a LoopNode? Is it due to OSR?

You mention LoopNode, but I don't see how that integrates with the bytecode loop in Listing 2.
Also, what is backJumpCounter for if the loops are already translated to LoopNode during decompilation?

I could not understand this paragraph:
"To further compare the performance of the bytecode interpreter without hints, we additionally ran the two bytecode
interpreter variations of GraalSqueak on a standard JDK 1.8.0 144 and without the Graal compiler".
This is extremely confusing, please clarify.
What does unoptimized means here? The graph actually shows one configuration with hints. Which two variations?

The figure 4 is also confusing.
The text says the simple bytecode loop is faster, which the figure confirms.
But it seems odd that GraalVM without Truffle PE and without hints would perform very similar to GS+hints+JDK8, and not similar to GS-hints+JDK8.
Did you write "GS-hints" instead of "GS+hints" in the legend maybe?

It would be interesting to mention the performance gap between interpreter and JIT code, it looks fairly large.
Figure 4 should start the y axis at 0 to avoid confusing the reader (GS-hints+JDK8 is not 2x faster even though it looks like it).

The paper mentions the code is available on GitHub but actually the link is not provided.
Making it available during submission would help to clarify some details, and ensure it is available after publication.

Typos/Clarifications:
* 1. "with a benchmark" => with two benchmarks
* 2. the decompiled loops seem to be like `while(true) { if (!cond) break; body }`, it would be nice to clarify this.
* 2. The explanation of the code is hard to follow, I suggest to refer to line numbers in the text and use vertical spacing in the code.
* Listing 2 could benefit from better syntax highlighting (e.g., with the `minted` package)
* 3. There is no reference for tinyBenchmarks. Could you add one or maybe even show the code since it is so small?
* 3. The first tinyBenchmark looks like a Sieve of Eratosthenes, it would be good to mention it.
* 3. "so that they run -to- *at* least one second" 
* 3. It would be useful to precise the processor generation.
* 4. "*a* Truffle implementation of the Ruby programming language."
* 4. TruffleRuby doesn't directly generate Truffle ASTs. It uses a parser generating syntatic nodes and then translate them to Truffle nodes.
* 4. It would be better to cite "YARV: Yet Another RubyVM: Innovating the Ruby Interpreter." K. Sasada., OOPSLA Companion, 2005, for the reference Ruby implementation, since that is the name of the bytecode interpreter.
* Figure 3 should use different symbols for each line.
* 5. "the language implementation framework Truffle" => "the Truffle language implementation framework"

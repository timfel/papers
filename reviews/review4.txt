----------------------- REVIEW 4 ---------------------
PAPER: 2
TITLE: GraalSqueak: A Fast Smalltalk Bytecode Interpreter Written in an AST Interpreter Framework
AUTHORS: Fabio Niephaus, Tim Felgentreff and Robert Hirschfeld

Overall evaluation: 2 (accept)

----------- Overall evaluation -----------
This paper examines the use of Truffle/Graal to implement bytecode interpreters, and compares the implementation of a Squeak / Smalltalk bytecpde interpreter to that of an AST interpreter. Because Graal is intended to be used to create AST interpreters, bytcode interpreter implementations need to give the underlying system some extra hints to improve performance, some of which are described in the paper.

The paper is interesting and well-explained, and the evaluation will be of interest to attendees of the workshop. It would be nice to have a clearer motivation for writing bytecode interpreters in Graal. The authors note that some languages have well defined bytecode semantics, but are there languages or circumstances in which a bytecode interpreter is preferable to an AST interpreter? Is there some reason for a VM engineer to choose to implement a bytecode interpreter, other than that it's possible? There are some hints in the conclusions, but it would be nice to have more motivation in the introduction of the paper.

The AST and bytecode interpreter implementations were compared using a number of standard micro-benchmarks. It would also be interesting to see the results from some larger benchmarks. 

The performance charts shown in the paper give data for all the VMs under test over the first ten iterations of the benchmark. This is a surprisingly small number of iterations, and although the first iterations of a benchmark may be interesting, longer term results would be more convincing. The paper claims that some of the executions reached a steady state, but it is difficult to give this credence without seeing the longer term trend. It would also be interesting to see the timing results of the benchmarks, as well as the bytecode/second, send/second data (clearly the two are related, but timing data would help the reader situate the results within the wider literature).

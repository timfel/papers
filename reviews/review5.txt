Hi Fabio,

the paper looks nice, and I think that it will get accepted. However, I think there is a problem with the red thread through the paper. It’s somewhat unclear what you want to tell your readers.

In the abstract, the first paragraph basically says that the problem is that the bytecode interpreter mechanism is not clear documented. This sets the expectation that the paper is about better describing this mechanism. However, the abstract’s second paragraph states that you compare the two possible approaches to implement control flow in Truffle. The problem description that I would have expected before is that it’s unclear which control-flow mechanism yields better performance. Both do not obviously fit to the title, which promises me that you show me how to a implement a fast Squeak implementation. The ambiguity of a main topic continues throughout the paper.

I would suggest that you concentrate your paper on one main problem and show how you tackled it, and potentially include the other subtopics only to assist the main one:
Documentation: Truffle’s bytecode interpreter approach is badly documented. In this paper, we show you how it works.
GraalSqueak: There are several small-talk like implementations, including a Truffle one, but nobody has explored the design space. We explored the design space and show how different tradeoffs affect performance.
Control-flow approaches: Truffle language implementations can be implemented using either a pure AST approach or by using a bytecode-interpreter-like approach. We present the design tradeoffs and a performance evaluation on GraalSqueak.

I think that the Documentation problem (i.e., showing how to use Truffle’s APIs) is scientifically not that interesting. It would work if you explained the mechanisms behind them; however, I think that except Christian Wimmer not many people know how everything works together on an implementation level. The paper also stays very fuzzy on why certain parts of code are needed or what they mean:
“In Truffle, on the other hand, there is a dedicated LoopNode for which the runtime provides special optimization strategies” → What are these optimization strategies? Truffle uses the LoopNode to implement On-Stack Replacement to replace a running interpreter loop by a compiled version. 
“However, this alone is not enough for the compiler, as it will still fail to optimize Smalltalk code because of escaping frame objects.” → Why is it not enough? What are escaping frame objects? Why do they escape? If you want to stay general, I would propose something like this: “This simple loop does not work, since the compiler expects a more elaborate representation of the loop to reconstruct loops present in the bytecode.” The escaping frame objects are only a symptom of Graal looping endlessly since it cannot determine that it already expanded a path.
“Truffle provides an API to inject this values as a branch probability which further supports the Graal compiler.” → How does it support the Graal compiler? In what?
“This information will be used in Truffle’s optimization heuristics to further improve the compilation process.” → For what is this information used?
It’s also a bit of a problem that the approach is explained in the VMIL Sulong paper. Maybe you can stress what you do better than it? For example: “Rigger et al. described the implementation of the bytecode-interpreter approach only on an abstract, simplified level without going into detail about the actual implementation.”

The GraalSqueak topic would be interesting for a workshop. However, the paper does not actually talk much about the Squeak-specific aspects of the implementation.

The Control-flow approaches topic seems to be the best fit in my opinion, also because it is the most interesting one scientifically. The main research questions could be “How can control-flow be efficiently represented in Truffle?” The problem statement would then be, that two approaches exist in Truffle but that it's unclear which ones language implementers should use. To investigate this, you implemented both approaches in GraalSqueak. In this case I would keep the explanation a bit on a higher level and balance the description of both approaches a bit more; now, you mainly talk about the bytecode interpreter loop. You could for example put the control-flow code next to each other and explain the key differences. You could also mention the general advantages and disadvantages, for example, that using a bytecode-interpreter-like approach means that you cannot use Truffle’s OSR facilities. An evaluation of interpreter performance would also be interesting. (I just realized that the submission deadline is already over, so I guess you cannot make such big changes, but I would encourage you to pursue this direction and make a conference paper out of it. Given the work that you have already done, this would look like a low-hanging fruit to me.)

Removing compiler hints would be okay, but a code structure like the one in Listing 1 is not supported by Graal, so it will simply not compile it. In order to make it work, you could have a loop over each possible successor index (you can browse the Sulong history to find that).
Related Work: It’s unclear how it relates to your work. Motivate it for the reader. For example, why do you discuss TruffleRuby? Only because it is also using an AST approach? What about the other implementations that use an AST approach?
“good performance”: What does this mean? Sometimes, you mention good performance when talking about warmup performance (i.e., by using LoopNodes) and sometimes about peak performance.
In the bibliography, don’t use “SIGPLAN Not” citations. If you download ACM references, there is always a second citation with the real venue, where the paper was published.
Delete non-canonical bibliography parts such as “URL http://doi.acm.org/.”

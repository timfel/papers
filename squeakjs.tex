\begin{abstract}
  We report our experience in implementing SqueakJS, an implementation
  of Squeak/Smalltalk in pure JavaScript. Our implementation runs at
  usable speed in the browser, allowing Squeak/Smalltalk applications
  to run on any platform with a recent JavaScript VM. In contrast to
  an automatic translation of an existing Squeak VM using an
  tool-chain such as Emscripten, our implementation is a full
  re-implementation which exposes each Squeak object also as a
  JavaScript object, allowing rich interactions between Smalltalk and
  JavaScript code.

\section{Introduction}

Javascript has become the de-facto standard for Web programming, and
a huge amount of code exists in the language.  This fact, along with
Javascript's unique design and its execution environment in a Web
browser, also make it of great interest to the research community,
motivating work to provide various languages in the browser\cite{?}.

Recently, automatic translation tool-chains such as Emscripten\cite{?}
and improved Javascript performance in general have enabled libraries
and language VMs written in C/C++ to be performantly executed in the
browser.

- used mostly for whole-system translations (stand-alone applications)

- no interaction with Javascript and DOM

To provide practical support for Smalltalk in Javascript, we instead
implement a Squeak VM entirely in Javascript. This enables us to run
Squeak in modern browsers and allow Javascript applications to
interact with the VM.

\emph{Contributions}

- squeak objects as JS objects

- GC design

- demonstration of interaction through a Lively part that interacts with
the VM

\section{Stuff}

\todolist{Object Representation}{
\item Squeak objects are Javascript objects with direct object references.
\item SmallIntegers are represented as Javascript numbers, there is no need for tagging. typeof check


\item Instance variables and indexable fields are held in a single Array named "pointers".
\item Word and byte binary objects store their data in Typed Arrays named "bytes" or "words". \lstinline|Uint32Array| and \lstinline|Uint8Array|.
\item CompiledMethod instances have both "pointers" (for literals) and "bytes" (for bytecodes). Simplifies access. PC = zero is the first bytecode. 
\item Float instances are not stored as two words as in Squeak, but have a single "float" property that stores the actual number. The words are generated on-the-fly when needed.
}

\todolist{Garbage Collection}{
\item A hybrid scheme. The bulk of the work is delegated to the Javascript garbage collector. Only in relatively rare circumstances is a "manual" garbage collection needed. This hybrid GC is a semi-space GC with an old space and a new space. Old space is a linked list of objects, but newly allocated objects are not added to the list, yet. Therefore, unreferenced new objects will be automatically garbage-collected by Javascript. This is like Squeak's incremental GC, which only looks at objects in new space. The full GC is a regular mark-and-sweep: it's marking all reachable objects (old and new), then unmarked old objects get removed (a very cheap operation in a linked list), and new objects (identified by their missing link) are added to the old-space list. One nice feature of this scheme is that its implementation does not need weak references, which Javascript currently does not support.
\item This scheme also trivially supports object enumeration (Squeak's nextObject/nextInstance primitives): If the object is old, the next object is just the next link in the list. Otherwise, if there are new objects (newSpaceCount > 0) a GC is performed, which creates the next object link. But if newSpaceCount is 0, then this was the last object, and we're done.
\item OOPS are maintained as in regular Squeak VM. Simplifies image saving. New objects get negative temp oops. When compacting, oops of old objects are adjusted. When tenuring, actual oops are assigned: obj.oop = endOfMemory; endOfMemory += obj.totalBytes(). Objects are tenured in allocation order (sorted by temp oop) to maintain same order as Slang VM.
\item Todo: implement weak refs
}

\todolist{UI}{
\item The UI for now copies the Squeak display bitmap pixel-by-pixel to a typed array and shows it on the HTML 2D canvas using putImageData(). Clipboard copying injects a synthetic CMD-C keyboard event into the VM, then runs the interpreter until it has executed the clipboard primitive in response, then answers that string. This is because the web browser only allows clipboard access inside the copy/paste event handlers.
\item Lively UI: 
  bytecode disassembler, debugger, inspector. Makes VM debugging fun.
}
\todolist{Files}{
\item You can drag files from your disk into the Lively world (including Squeak image files). Files are stored in indexedDB and directory entries in \lstinline|localStorage['squeak:/']|.
}

\begin{abstract}
  We report our experience in implementing SqueakJS, an implementation
  of Squeak/Smalltalk in pure JavaScript. Our implementation runs at
  usable speed in the browser, allowing Squeak/Smalltalk applications
  to run on any platform with a recent JavaScript \ac{VM}. In contrast to
  an automatic translation of an existing Squeak \ac{VM} using an
  tool-chain such as Emscripten, our implementation is a full
  re-implementation which exposes each Squeak object also as a
  JavaScript object, allowing rich interactions between Smalltalk and
  JavaScript code.

\section{Introduction}


JavaScript has become the de-facto standard for Web programming, and
a huge amount of code exists in the language.  This fact, along with
JavaScript's unique design and its execution environment in a Web
browser, also make it of great interest to the research community,
motivating work to provide various languages in the browser\cite{?}.

Recently, automatic translation tool-chains such as
Emscripten\cite{zakai:2011:emscripten:-llvm-to-javascript} and
improved JavaScript performance in general have enabled libraries and
language \acp{VM} written in C/C++\footnote{Or at least translatable
  to LLVM bytecode} to be performantly executed in the
browser\footnote{See for example \url{http://www.repl.it}, retrieved
  \today}. However, a number of common themes among such ports emerge:

\begin{itemize}
\item These translations are mostly used to provide a whole system in
  the browser, to be used as a stand-alone application. The browser
  acts merely as the underlying runtime.
\item The translation mechanism is oblivious to the browser platform,
  and this cannot provide interactions with the host Javascript
  \ac{VM} or the \ac{DOM}.
\item Translation toolchains such as Emscripten provide a C semantics
  and use various low-level Javascript mechanisms to achieve good
  performance, so the resulting code cannot be easily inspected and
  instrumented as normal Javascript objects.
\end{itemize}

\dan{Many reasons to want Squeak and especially EToys to run
in browsers, but...}
\topa{potential goal: get Etoys and Scratch to the web with good
  backwards compat}
SqueakJS aims to provide a fully backwards-compatible Squeak/Smalltalk
system in the browser, able to run wide-spread applications such as
Etoys\cite{?} and Scratch\cite{?} directly in the browser. To achieve
this goal, an automatic translation would suffice.

However, SqueakJS also aims to allow existing Javascript code to
interact and instrument Squeak objects, in order to not only be a
``Squeak in the browser'', but also provide practical support for
using Smalltalk in a Javascript environment. To achieve these goals,
we implemented a Squeak \ac{VM} entirely in JavaScript. This enables
us to run Squeak in modern browsers and allow JavaScript applications
to interact with the \ac{VM}.

In this paper, we report our experience with this implementation,
highlighting the following items in particular:
\begin{itemize}
\item Our mapping of Squeak objects in the VM to Javascript objects
  with direct references
\item Our hybrid garbage collection scheme to allow Squeak GC semantics
  while delegating as much work as possible to the Javascript GC
\item Interaction with Javascript for clipboard access, image loading,
  file system access, debugging, and inspecting Squeak objects
\end{itemize}

\subsection{Object Representation}

Reimplementation of a Smalltalk virtual machine is facilitated by the
relatively clean separation between the byte code interpreter, the object
memory and the graphics system. As noted above, JSqueak departed significantly
from the Squeak object implementation without introducing any major
perturbations in the rest of the virtual machine. All Squeak objects were
mapped to Java objects with slots for

\begin{itemize}
	\item 	Squeak hash (short)
	\item 	Squeak format code (short)
	\item 	class (pointer)
	\item 	pointer fields (array of pointers)
	\item 	indexable binary data fields (array of bytes or ints)
\end{itemize}

SmallIntegers were the only exception, they were represented by
\lstinline|Integer| objects. This is similar to the tagged pointers in other
Squeak VMs which are used to represent immediate SmallInteger values. In
contrast, Floats are represented by full objects, but their binary data slot
is set to a Java \lstinline|Double| so it can be accessed more quickly in
arithmetic primitives.

Essentially the same scheme is used in SqueakJS. Since the layout of
JavaScript objects does not have to be declared in advance, slots are added
only when needed. That means the pointers, bytes, and words slots are only
present if the object actually needs them. SmallIntegers are directly
represented by JavaScript numbers.

For making common tests more efficient, SqueakJS also adds flags to special
objects. For example, the \lstinline|isNil| property is added to the
\lstinline|nil| object so that a test for being nil can be written without
having to compare it to the VM's \lstinline|nil| object. Floats are marked by
an \lstinline|isFloat| property, and the numeric value is stored directly in
another property. The conversion to words happens on-the-fly, and only when
the image tries to index individual words of the Float object.

\subsection{Object Enumeration and Garbage Collection}

For object enumeration and finding all instances of a class Squeak uses a
primitive to answer the ``next object'' for a given object, or the next
instance given a particular instance. The next object is easily found since
all objects are contiguous in main memory, so simply adding the size of an
object to the object's address gives the address of the next object. This is
not possible for JSqueak or SqueakJS.

Since Java provides no facility for enumerating objects, JSqueak used an
object table for the sole purpose of enumeration, as required by Squeak's
enumeration facility as well as to support object mutation which involves
enumeration implicitly. By making use of weak pointer objects in the object
table, it was possible to leave the task of garbage collection entirely up to
the Java runtime, a key to this Hobbes-style port.

Unfortunately the JavaScript engines of our time provide no support for weak
pointers, so this means that the use of an object table for enumeration was
out of the question. It would have prevented all objects from being
garbage-collected by the JavaScript runtime. An important innovation in the
SqueakJS object memory is the use of enumeration links in a subset of Squeak
objects that corresponds to long-lived objects, or what is commonly referred
to as ``old space''.

When loading an object snapshot, objects are created as outlined above.
Additionally, each object is assigned a \lstinline|nextObject| slot pointing
to the next object. The first and last object in this linked list is held in
the VM, constituting the ``old space''. When a new object is allocated at
runtime, it is not added to that list immediately. Instead, it is only held by
references from other objects and released automatically when no longer
referenced.

For old objects, the ``next object'' primitive can simply return the object's
\lstinline|nextObject|. But for a new object, which does not have the
\lstinline|nextObject| slot yet, a full garbage collection is triggered. This
adds the object (and all other surviving new objects) to the old-space list,
setting the \lstinline|nextObject|, so the enumeration can continue.

The full GC is a vanilla mark-and-sweep: In the first phase, all objects
reachable from the roots are marked. If a new object is found in this phase,
it is added to a temporary collection. In the second phase, the old-space
linked list is traversed, unmarked objects are unlinked, and the mark of
remaining objects is cleared. Finally, the new objects from the first phase
are linked to the end of the old-space list. For a typical object memory of
300,000 objects this takes about 300 milliseconds.

\subsection{Main loop}

In most Squeak VMs, the VM itself has a main loop that executes
byte codes until the system quits. Not so in SqueakJS: The VM needs to
regularly break out of its interpreter loop, because only then will the web
browser update the screen or provide new input events.

The interpreter has two entry points: \lstinline|interpretOne()| for executing
a single byte code (which is used only when single-stepping in the VM
debugger), and \lstinline|interpret()| for executing multiple byte codes. The
latter loops for a certain time, or until a primitive requests an immediate
return of control to the browser. This happens e.g. after drawing to the
screen: to minimize the delay between drawing and the change being visible to
the user, the drawing primitive requests to exit the interpreter loop
immediately.

Also, break points can be set for various conditions, e.g. when a certain
method is executed or returns. When the condition is met, the interpreter loop
exits to let the debugger show that state.

To support using asynchronous functions in primitives that need to appear
synchronous to the Squeak runtime, we implemented a feature to ``freeze'' the
VM. A primitive can call the VM's \lstinline|freeze()| function, which returns
a callback function for unfreezing. All subsequent calls to
\lstinline|interpret()| are ignored until the unfreeze function was called by
the primitive's asynchronous event handler. That means the VM's state remains
unchanged until the unfreeze, so the primitive is allowed to defer pushing a
return value onto the stack until the asynchronous operation is done. This is
used for example to support asynchronous file access (see below).

\subsection{Files}

While Squeak can work without a file system, a lot of functionality
would be missing if SqueakJS did not have the ability to permanently store
files. This presents a challenge to a system designed to run in a browser. One
option would be to upload and retrieve files to a server. But this would
require constant connectivity, and we very much want SqueakJS to be usable
offline. \bert{move rationale to other section?}

Persistent offline storage is a relatively new feature for web browsers. The
most common way is the browser's \lstinline|localStorage|, which is
synchronous, and very easy to use, but only supports storing strings, and is
usually limited in size to 5 Megabytes. Fortunately, all major browsers now
support the \lstinline|indexedDB| client-side storage (Firefox x.y, Chrome
x.y, Safari x.y, IE ?/?) which stores arbitrary Javascript objects, and has
more generous size quotas, but is an asynchronous API.

The FilePlugin is implemented with a combination of \lstinline|localStorage|
and \lstinline|indexedDB|. Directory entry information (name, size, directory
flag, creation date, modification date) is serialized as a JSON string per
directory and saved in \lstinline|localStorage|. It is accessed very often so
the ability to access it synchronously is helpful. Also, it takes a relatively
small amount of space. Due to idiosyncrasies of Squeak, often files are opened
and closed without actually accessing the file contents.

The file contents is put into the \lstinline|indexedDB|. When the file
contents is needed, it is loaded from the database into memory. Since every
database access is an asynchronous operation, the VM is frozen until this read
operation is finished. Write operations are performed in memory only. It is
stored to the database only when the file handle is closed or explicitly
flushed. The VM does not need to wait until the write finishes (similar for
deleting a file). A single copy of the file contents in memory is shared for
all open file handles of the same file. The file handles are
reference-counted, and the memory is released when the last handle is closed.

A potential drawback of this scheme is that the two storages could get out of synch.
This has not been a problem so far. If it becomes a problem, a file system
check could restore consistency, or directory information could be stored in
\lstinline|indexedDB|, too.

\subsection{Embedding}

While SqueakJS is developed inside Lively, the VM takes care to
not depend on Lively. It is implemented in a single JavaScript file. For
demonstration purposes we have written a simple harness that runs Squeak
without Lively. It consists of a 10 line HTML page, 30 lines of JavaScript to
emulate the Lively module and class system, and 200 lines to download an
image, set up input and output, and run the VM. Because the overhead of that
harness is considerably lower than the full Lively environment, it works
nicely even on mobile devices such as an iPad.

\subsection{Extensions}

The SqueakJS VM can be extended with modules, just like most
regular Squeak VMs. There is an internal and an external modules interface.
Internal modules are part of the VM itself, they simply expose primitives by
name instead of by index. An example for an internal module is the FilePlugin.

External modules are implemented outside the core VM. The interface is purely
object-based. Which module is implemented in which file is unknown to the VM.
A module object is simply registered by name:
\begin{lstlisting}[numbers=none,columns=fixed]
Squeak.registerExternalModule('ModuleName',
                              moduleObject);
\end{lstlisting}

The module object needs to have a field named \lstinline|exports| which
references all provided primitive functions by name. If a function is exported
as \lstinline|initializeModule| then it will be executed when loading the
module, passing the VM's primitive handler as argument. This is similar to
passing the \lstinline|interpreterProxy| in C-based VMs, it allows the
module's primitive functions to interact with the VM, foremost to read
arguments from the stack and push a result back. An example external module is
\lstinline|SimplePlugin.js| as shown in \autoref{lst:simpleplugin}.
\begin{lstlisting}[float,caption={A simple Squeak Plugin},label=lst:simpleplugin]
var SimplePlugin = function() {
    var proxy;
    function initializeModule(interpreterProxy) {
        proxy = interpreterProxy;
    };

    function primitiveNavigatorInfo(argCount) {
        if (argCount !== 1) return false; // fail
        var which = proxy.stackInteger(0);
        if (!proxy.success) return false; // fail
        var result;
        switch (which) {
            case 1: result = navigator.userAgent; break;
            case 2: result = navigator.language; break;
        }
        if (!result) return false; // fail
        var resultObj = proxy.makeStString(result);
        proxy.vm.popNandPush(1 + argCount, resultObj);
        return true; // success
    };

    return {
        exports: {
            initializeModule:
                initializeModule,
            primitiveNavigatorInfo:
                primitiveNavigatorInfo,
        }
    }
};

// register plugin in global Squeak object
Squeak.registerExternalModule('SimplePlugin',
                                  SimplePlugin());

\end{lstlisting}

The root for all Squeak implementations is the original Squeak
\ac{VM}~\cite{Ingalls+:1997:Back-to-the-future:-the-story}, that aims to
provide an open Smalltalk-80 system. Initially, the original \ac{VM} did only
provide an interpreter-based execution, hence it is sometimes called
interpreter \ac{VM}. Although projects like
Exupery\footnote{\url{http://wiki.squeak.org/squeak/Exupery}} aim to provide a

Another well-known Squeak \ac{VM} is Miranda's
Cog\ac{VM}~\cite{Miranda2011:The-Cog-Smalltalk-Virtual-Machine:}, providing a

Potato\footnote{\url{http://sourceforge.net/projects/potatovm/}} and its

inspiration for \SqueakJS.

SPy~\cite{Bolz+2008:Back-to-the-Future-in-One-Week}, or RSqueakVM, is an

\todolist{Object Representation}{
\item Squeak objects are JavaScript objects with direct object references.
\item SmallIntegers are represented as JavaScript numbers, there is no need for tagging. typeof check


\item Instance variables and indexable fields are held in a single Array named "pointers".
\item Word and byte binary objects store their data in Typed Arrays named "bytes" or "words". \lstinline|Uint32Array| and \lstinline|Uint8Array|.
\item CompiledMethod instances have both "pointers" (for literals) and "bytes" (for bytecodes). Simplifies access. PC = zero is the first bytecode. 
\item Float instances are not stored as two words as in Squeak, but have a single "float" property that stores the actual number. The words are generated on-the-fly when needed.
}

\todolist{Garbage Collection}{
\item A hybrid scheme. The bulk of the work is delegated to the JavaScript garbage collector. Only in relatively rare circumstances is a "manual" garbage collection needed. This hybrid \ac{GC} is a semi-space \ac{GC} with an old space and a new space. Old space is a linked list of objects, but newly allocated objects are not added to the list, yet. Therefore, unreferenced new objects will be automatically garbage-collected by JavaScript. This is like Squeak's incremental \ac{GC}, which only looks at objects in new space. The full \ac{GC} is a regular mark-and-sweep: it's marking all reachable objects (old and new), then unmarked old objects get removed (a very cheap operation in a linked list), and new objects (identified by their missing link) are added to the old-space list. One nice feature of this scheme is that its implementation does not need weak references, which JavaScript currently does not support.
\item This scheme also trivially supports object enumeration (Squeak's nextObject/nextInstance primitives): If the object is old, the next object is just the next link in the list. Otherwise, if there are new objects (newSpaceCount > 0) a \ac{GC} is performed, which creates the next object link. But if newSpaceCount is 0, then this was the last object, and we're done.
\item OOPS are maintained as in regular Squeak VM. Simplifies image saving. New objects get negative temp oops. When compacting, oops of old objects are adjusted. When tenuring, actual oops are assigned: \lstinline|obj.oop = endOfMemory; endOfMemory += obj.totalBytes()|. Objects are tenured in allocation order (sorted by temp oop) to maintain same order as interpreter \ac{VM}.
\item Todo: implement weak refs
}

\begin{abstract}
  We report our experience in implementing \SqueakJS, a bit-compatible
  implementation of \SqueakST in pure JavaScript that runs
  entirely in the browser with a virtual file system that can be
  directed to any server.  Our implementation is notable for
  simplicity and performance gained through adaptation to the host
  object memory, and deployment leverage gained through the Lively Web
  development environment.  We present several novel techniques and
  present performance figures for the resulting virtual machine.  Much
  of this experience is potentially relevant to preserving other
  dynamic language systems and making them available in a
  cloud/browser environment.

\section{Motivation}

A number of interesting applications have been built in the \SqueakST
development environment, with this environment itself being very
interesting itslef. However, educational applications such as
Etoys\citet{cite} and early versions of Scratch\citet{cite}, suffer
from restrictions on installing native software in many school
environments. To address this limitation, Web browsers, which are
ubiquitous today, have become a strongly desired target for deploying
those applications; Scratch has been rewritten in Flash and for Etoys,
a browser plugin for major Web browsers could be used for a several
years now. Yet, both approaches still need either software alien to
the browser or a complete rewrite.

With JavaScript as the de-facto standard for Web programming, a
browser-native JavaScript-based implementation of Squeak's \ac{VM} is
desirable.
% This fact, along with JavaScript's unique design and its execution
% environment in a Web browser, also make it of great interest to the
% research community, motivating work to provide various languages in
% the browser\cite{?}.
With \SqueakJS, we aim to provide a fully compatible \SqueakST system
in the Web browser, able to directly run applications like Etoys or
Scratch.

Dynamic languages like Python or Ruby have successfully been
translated into Javascript\cite{?} using the automatic translation
tool-chain
Emscripten~\cite{zakai:2011:emscripten:-llvm-to-javascript}. In
contrast to such language implementations that host much of its core
functionality inside of the \ac{VM}, Squeak implements most of its
kernel in Smalltalk itself. Also, Squeak is a graphical programming
system and so, to run in the browser, requires a certain level of
interaction with the browser's \ac{DOM}.

Recent attempts at re-implementing or re-engineering the Squeak
\ac{VM} have shown that good performance is difficult to
achieve~\cite{roarvm,spyvm,rsqueakvm}. To us, Squeak appeared to be
too slow to be emulated in JavaScript, and too complex to be divided
into an interpreter and a browser graphics layer. However, a smaller
project to emulate ALTO machine code to run a Smalltalk 72 \ac{VM}
showed promising performance.

Potato, a small Squeak \ac{VM} experiment written in Java, served as
basis for the \SqueakJS design in many respects. For example the
mapping of Squeak objects to JavaScript objects or the separation of
the \ac{VM} into the interpreter and a primitive handler are exactly
as done in Potato.

The fact that \SqueakJS represents Squeak objects as plain JavaScript
objects and integrates with the JavaScript \ac{GC} allows existing
JavaScript code to interact with Squeak objects. This has proven
useful during development as we could re-use existing JavaScript tools
to inspect and manipulate Squeak objects as they appear in the
\ac{VM}.  This means that \SqueakJS is not only a ``Squeak in the
browser'', but also provide practical support for using Smalltalk in a
JavaScript environment.

In this paper, we report our experience with this implementation,
highlighting the following items in particular:
\begin{itemize}
\item our mapping of Squeak objects in the \ac{VM} to JavaScript objectsa
  with direct references,
\item a hybrid garbage collection scheme to allow Squeak object
  enumeration without a dedicated object table, while delegating as
  much work as possible to the Javascript \ac{GC},
\item a cloud-appropriate adaption of file and image-file management
  to load and store Squeak images, and
\item the interaction with JavaScript for clipboard access, graphics,
  debugging, and providing plugins, that allowed use to use a
  rapid-prototyping approach to \ac{VM} development.
\end{itemize}

The rest of this paper is structured as follows: We describe our
rationale for various issues that arise when trying to implement a
Squeak \ac{VM} in the browser. A description of the implementation
details \SqueakJS, highlighting its innovative approaches, follows in
\autoref{sec:impl}. We evaluate our findings in \autoref{sec:eval} and
put \SqueakJS into perspective with other work in
\autoref{sec:related}. Finally, \autoref{sec:conclusion} presents some
lessons learned and concludes.


\section{Concept}
\label{sec:concept}

The core of \SqueakJS is very much inspired by Potato, a Squeak \ac{VM} written
in Java. The sources of its precursor, Dan Ingalls' 2008 original ``JSqueak'',
served as reference. Fundamental design decisions, like the mapping of Squeak
objects to JavaScript objects or the separation of the VM into the interpreter
and a primitive handler are exactly as in Potato. Some parts of the
interpreter were transcribed literally, just removing the Java type
annotations. Even some bugs were faithfully transcribed and only fixed later.

Apart from using another language, there are also differences in the
\SqueakJS implementation. For example, there is no object table, a
WeakReference array that is used in Potato for object
enumeration.

These implementation differences, however, are less important than the
context for which \SqueakJS is intended. JavaScript applications are
more amendable than Java applications to direct manipulation
development, where objects are inspected and manipulated with
developer tools. Rapid prototyping environments such as the Lively
Kernel allow developers to extend and continuously improve their
tools. In this context, the properties inherited from Potato are
beneficial and allowed us to develop the \ac{VM} using Lively tools in
a very short time and with immediate feedback.

\subsection{Getting it Going}
\label{sec:getting-it-going}

Re-implementing Squeak has been done a number of times by now. To get
going, it roughly consists of the steps indicated by
\cite{Ingalls+:1997:Back-to-the-future:-the-story}:
\begin{itemize}
\item Produce a new image reader and writer
\item Produce a new interpreter and essential plugins such as BitBlt
  and FilePlugin
\item Compile the interpreter to make it practical
\end{itemize}

Of these steps, only the first two apply to our context. We decided
early on to transcribe our implementation from the Potato sources.
The original Squeak VM is written in ``Slang'', a subset of Smalltalk
with C semantics, which can be translated to C easily. It does not use
any of C's structured data types to describe objects. Instead, Slang
operates on words in memory, much like machine code would. The
Slang-to-C translater could be retargeted to produce Java or
JavaScript, but that would keep these low-level semantics, which does
not map well to a high-level language. That is why Potato and
\SqueakJS are not based on the Slang implementation.

\paragraph{Representing Objects}
\label{sec:object-model}
Potato's object representation represents a significant departure from
Squeak's. All Squeak objects appeared as plain Java objects, with
slots that stored the information required by the \ac{VM} such as
instance variables, class, format code, and indexable data. The same
scheme can be used for \SqueakJS.  In the Lively Kernel, this means
that we can easily adapt existing JavaScript tools to work on Squeak
objects. The Lively Kernel is a self-supporting development
environment, which means that the system itself and its tools are
continuously developed and improved with themselves. In Lively, most
tools are \emph{parts}\cite{partspaper} -- parts are compositions of
\emph{morphs}\cite{morphs} with associated, instance-specific
behavior. Once the image loader began working, we could compose
various Lively tools to create a virtual machine inspector, as shown
in \autoref{fig:virtualmachineinspector}.

Because stack frames and threads (Contexts and Processes in Squeak
parlance) are Squeak objects as well, we can use the inspector to
watch the \ac{VM} stack while it is executing and debug any problems
directly. This was useful early on to verify that the image loader and
scheduler work correctly, and that dispatch actually worked when the
\ac{VM} started executing. Additionally, the debugging support as
available in Squeak -- to break at, step into, and to disassemble
methods -- is available to the inspector as well.

\subsection{Drawing to the Screen}
Besides the interpreter, some way of drawing to the screen is
required. Squeak uses a BitBlt plugin to render into bitmaps, which is
fairly well separated from the rest of the interpreter. Potato only
supports 1 bit per pixel color depths and a minimal set of graphics
features. To support full color and all graphics features used in
modern Squeak and Etoys image, the much larger Slang code
for the BitBlt and WarpBlt plugins has to be transcribed to
JavaScript.

Both BitBlt and WarpBlt can be simulated in Squeak, so conceivably,
the Smalltalk code could be executed directly to render graphics. The
RSqueakVM (originally implemented as SpyVM by
\cite{Bolz+2008:Back-to-the-Future-in-One-Week}) is an RPython-based
implementation of Squeak that uses this
scheme\cite{larswassermann}. However, even with RPython's tracing
\ac{JIT}, the performance of pure-Smalltalk BitBlt is still about one
order of magnitude slower than a C-based implementation, indicating
that a native (which in our case means JavaScript) implementation is
still preferable to achieve good performance.

\SqueakJS exposes a module interface similar to that of regular Squeak
\acp{VM}, and BitBlt is implemented as an internal module, i.\,e., one
that comes with the \ac{VM}. A simple HTML5 canvas can be used to
mirror the contents of the Squeak display object, a bitmap object that
contains an array of bytes. Whenever an update to the display is
needed, the Squeak system calls a primitive, which we use to update
the HTML5 canvas.


\subsection{Cleaning up Garbage}

Many core functions in Squeak built upon the ability to enumerate
objects of a specific class using the \lstinline{firstInstance} and
\lstinline{nextInstance} primitive methods. In Squeak, this is easily
implemented since all objects are contiguous in memory, so we can
simply scan from the beginning and return the next available
instance. This not possible in a hosted implementation, including
Potato or \SqueakJS. Potato used a weak-key object table to keep track
of objects to enumerate them. Other implementations, like RSqueakVM,
use the RPython garbage-collection to trigger a full \ac{GC} and yield
all objects of a certain type. These are then temporarily kept in a
list for enumeration. In JavaScript, neither weak references, nor
access to the \ac{GC} is generally available, so neither option was
possible for \SqueakJS. Instead, we designed a hybrid \ac{GC}
scheme.

\SqueakJS manages objects in an \emph{old} and \emph{new} space, akin
to a semi-space \ac{GC}. When an image is loaded, all objects are
created in the old space. Because an image is just a snapshot of the
object memory when it was saved, all objects are consecutive in the
image. When we convert them into JavaScript objects, we create a
linked list of all objects. This means, that as long as an object is
in the \SqueakJS old-space, it cannot be garbage collected by the
JavaScript \ac{VM}. New objects are created in a virtual \emph{new}
space. However, this space does not really exist for the \SqueakJS
\ac{VM}, because it simply consists of Squeak objects that are not
part of the old-space linked list. New objects that are dereferenced
are simply collected by the JavaScript \ac{GC}.

When a full \SqueakJS \ac{GC} is triggered (for example because the
\lstinline{nextInstance} primitive has been called on an object that
does not have a next link) a full two-phase collection is started. Any
new objects that are referenced from surviving objects are added to
the end of the linked list. Any objects in the linked list that were
not found to survive are removed from the list, and thus become
eligible for ordinary JavaScript \ac{GC}. Note also, that we append
objects to the old list in the order of their creation, simply by
ordering them by their object ids. In Squeak, these are the memory
offsets of the object. To be able to save images that can again be
opened with the standard Squeak \ac{VM}, we generate object ids that
correspond to the offset the object would have in an image. This way,
we can serialize our old object space and thus save binary compatible
Squeak images from \SqueakJS.

To implement Squeak's weak references, a similar scheme can be
employed: any weak container is simply added to a special list of root
objects that do not let their references survive. If, during a full
\ac{GC}, a Squeak object is found to be only referenced from on of
those weak roots, that reference is removed, and the Squeak object is
again garbage collected by the JavaScript \ac{GC}.

\subsection{Making Squeak Happy in the Cloud}
\label{sec:making-it-happy}

A general problem when running Squeak in a browser is the asynchronous
nature of JavaScript. While most \acp{VM} are implemented as a main
loop that simply executes until the \ac{VM} is stopped, \SqueakJS at
least needs access to input events that are generated by the browser,
and has to give the browser time to update the \ac{DOM}. Our solution
to this problem is that we have \SqueakJS regularly break out of its
interpreter loop, and schedule a timeout function to continue running
after events have been processed.

Another common problem of running JavaScript applications is the
question of file system access.  While Squeak can work without a file
system, a lot of functionality would be missing if \SqueakJS did not
have the ability to permanently store files. This presents a challenge
to a system designed to run in a browser. One option would be to
upload and retrieve files to a server. But this would require constant
connectivity, and we very much want \SqueakJS to be usable offline.

Three options are available to store data in a browser. The oldest are
Cookies. On top these, simple key-value stores can be
implemented. However, cookies are limited to 4 Kilobytes and are not a
good fit to emulate a file system, considering that just to save a
modern Squeak image requires from ten to hundreds of Megabytes. The
second option is the browsers local storage\cite{todo}. Like cookies,
the amount of local storage per web page is limited, in most browsers
to 5 Megabytes. Again, this prevents us from saving most modern Squeak
images. The third and most recent way to store files in a browser is
the IndexedDB\cite{todo}. It can store arbitrary JavaScript objects
and allows to store more data.

IndexedDB is the only viable option that provides enough storage to be
useful as a file system for \SqueakJS. However, it only provides an
asynchronous API, whereas Squeak expects file system calls to work
synchronously. While breaking out of the interpreter loop allows the
browser to process asynchronous events, access to the IndexedDB may
take longer than one event loop. To be able to simulate a synchronous
API, we additionally need to be able to freeze the \ac{VM} -- instead
of scheduling the next interpretation step, the main loop simply
stores a continuation to continue running when it is unfrozen. When a
file primitive is called, the \ac{VM} is frozen, and the callback that
receives the IndexedDB unfreezes the \ac{VM}. The same scheme can be
used to synchronize any asynchronous JavaScript API that we want to
expose. This is useful even for network operations, so that only
\SqueakJS waits for a response, and not the entire browser.

\section{Implementation}
\label{sec:impl}

Our implementation closely follows the Potato \ac{VM} in its basic
approach, but deviates to accomodate JavaScript's execution
environment. It is publicly available on
GitHub\footnote{\url{https://github.com/bertfreudenberg/SqueakJS}}.

\subsection{Object Representation}
\label{sec:objrep}

Reimplementation of a Smalltalk virtual machine is facilitated by the
relatively clean separation between the byte code interpreter, the object
memory and the graphics system. As noted above, Potato departed significantly
from the Squeak object implementation without introducing any major
perturbations in the rest of the virtual machine. All Squeak objects were
mapped to Java objects with slots for

\begin{itemize}
	\item 	Squeak hash (short)
	\item 	Squeak format code (short)
	\item 	class (pointer)
	\item 	pointer fields (array of pointers)
	\item 	indexable binary data fields (array of bytes or ints)
\end{itemize}

SmallIntegers were the only exception, they were represented by
\lstinline|Integer| objects. This is similar to the tagged pointers in other
Squeak VMs which are used to represent immediate SmallInteger values. In
contrast, Floats are represented by full objects, but their binary data slot
is set to a Java \lstinline|Double| so it can be accessed more quickly in
arithmetic primitives.

Essentially the same scheme is used in \SqueakJS. Since the layout of
JavaScript objects does not have to be declared in advance, slots are added
only when needed. That means the pointers, bytes, and words slots are only
present if the object actually needs them, that is, they have at least one
element. SmallIntegers are directly represented by JavaScript numbers. In
places where the VM needs to distinguish SmallIntegers from other objects it
uses a \lstinline|typeof| check.

For making common tests more efficient, \SqueakJS also adds flags to special
objects. For example, the \lstinline|isNil| property is added to the
\lstinline|nil| object so that a test for being nil can be written without
having to compare it to the VM's \lstinline|nil| object. Floats are marked by
an \lstinline|isFloat| property, and the numeric value is stored directly in
another property. The conversion to words happens on-the-fly, and only when
the image tries to index individual words of the Float object.

An \lstinline|oop| numeric property is maintained mainly for identifying
objects when saving a snapshot. It also serves as key when objects need to be
added to a hash map temporarily (e.g. during ``become'' operations) because
JavaScript does not provide an object-keyed hash map. New objects are assigned
consecutive negative oops. A real oop is assigned when the object survives a
full garbage collection, and during compaction oops are adjusted to account
for released objects. This emulates the consecutive memory layout of the C
Squeak VMs which is manifested in the snapshot format. The oop also helps in
distinguishing objects while debugging.

\begin{itemize}
	\item hash (\lstinline|number|)
	\item format (\lstinline|number|)
	\item class (\lstinline|object|)
	\item oop (\lstinline|number|)
	\item pointers (\lstinline|Array|, optional)
	\item words (\lstinline|Uint32Array|, optional)
	\item bytes (\lstinline|Uint8Array|, optional)
	\item mark (\lstinline|false|, present after surviving GC)
\end{itemize}

The implementation takes advantage of JavaScript idiosyncrasies like treating
a non-existing property as \lstinline|false|. E.g., a newly allocated object
does not have the \lstinline|mark| property, while an old object might have it
set to \lstinline|true| or \lstinline|false| during GC. But the test can
simply be written as ``\lstinline|if (obj.mark) ...|'' because both cases test
equally.

\subsection{Object Enumeration and Garbage Collection}

For object enumeration and finding all instances of a class Squeak uses a
primitive to answer the ``next object'' for a given object, or the next
instance given a particular instance. The next object is easily found since
all objects are contiguous in main memory, so simply adding the size of an
object to the object's address gives the address of the next object. This is
not possible for Potato or \SqueakJS.

Since Java provides no facility for enumerating objects, Potato used
an object table for the sole purpose of enumeration, as required by
Squeak's enumeration facility as well as to support object mutation
which involves enumeration implicitly. By making use of weak pointer
objects in the object table, it was possible to leave the task of
garbage collection entirely up to the Java runtime, a key to this
port. In this regard, it is similar to Hobbes, a \ac{VM} for the
original Smalltalk-80 written for VisualWorks Smalltalk (see
\autoref{sec:dynam-lang-impl}.)

Unfortunately the JavaScript engines of our time provide no support for weak
pointers, so this means that the use of an object table for enumeration was
out of the question. It would have prevented all objects from being
garbage-collected by the JavaScript runtime. An important innovation in the
\SqueakJS object memory is the use of enumeration links in a subset of Squeak
objects that corresponds to long-lived objects, or what is commonly referred
to as ``old space''.

When loading an object snapshot, objects are created as outlined above.
Additionally, each object is assigned a \lstinline|nextObject| slot pointing
to the next object. The first and last object in this linked list is held in
the VM, constituting the ``old space''. When a new object is allocated at
runtime, it is not added to that list immediately. Instead, it is only held by
references from other objects and released automatically when no longer
referenced.

For old objects, the ``next object'' primitive can simply return the object's
\lstinline|nextObject|. But for a new object, which does not have the
\lstinline|nextObject| slot yet, a full garbage collection is triggered. This
adds the object (and all other surviving new objects) to the old-space list,
setting the \lstinline|nextObject|, so the enumeration can continue.

The full GC is a variation on mark-and-sweep: In the first phase, all objects
reachable from the roots are marked recursively. If a new object is found in
this phase, it is added to a temporary collection. In the second phase, the
old-space linked list is traversed, unmarked objects are unlinked, and the
mark of remaining objects is cleared. Finally, the new objects from the first
phase are linked to the end of the old-space list. The discovery of new
objects from the ``virtual'' new space during the mark phase is what sets this
GC apart. For a typical object memory of 300,000 objects this takes about 300
milliseconds.

\subsection{Snapshotting}

The Potato implementation, being a proof of concept only, did not support
saving object images that could be stored and resumed elsewhere. The \SqueakJS
implementation provides this function in the following manner.

A Squeak object image consists of a few words file header for basic parameters
followed by a literal memory dump of the object memory. Objects are laid out
consecutively. Each object consists of one to three header words followed by
zero or more body words, as determined by bits in the header words. Object
references (oops) are one word wide direct pointers to the address of the
always-present ``last'' object header word immediately preceding the object
body. That means the actual starting address of the object may be smaller than
its oop, in the cases where it has a two ore three word header.

Strictly speaking, oops matching the C VM memory layout are only needed while
snapshotting. The \SqueakJS runtime does not need them. They could be generated
before taking a snapshot by walking the old-space list and accumulating object
sizes. But for the reasons mentioned in \autoref{sec:objrep} they are kept
up-to-date by the garbage collector, so after doing a full GC we can rely on
all objects having accurate oops. The total number of bytes needed is
maintained by the GC, too.

Snapshotting then means invoking a fullGC which updates oops and sets the
nextObject links. An \lstinline|ArrayBuffer| of the needed size is allocated
and wrapped in a \lstinline|DataView| for typed access. The image header
fields are written. The linked list of objects is traversed and each object
writes a representation of itself to the memory buffer: one to three header
words encoding the class oop, format, hash, and size, followed by the pointers
(tagged for SmallIntegers and oops for all other objects), words, or bytes.
The finished snapshot is stored as file in the browser's \lstinline|indexedDB|
(see \autoref{sec:files}). It can be resumed later in \SqueakJS, or be exported to
the user's disk and resumed in another Squeak VM.

\subsection{Graphics System}

As mentioned above the Squeak graphics system is relatively well separated
from the rest of the virtual machine by the BitBlt and WarpBlt APIs. While
the Potato proof-of-concept implementation did include BitBlt, it only
supported the simplest 1 bit per pixel format and the simplest combination
functions. While \SqueakJS benefits from the similar syntax of C and
JavaScript, the accurate and complete port of Squeak's BitBlt and WarpBlt
functions was a significant part of the overall implementation task.

The implementation currently closely follows Squeak's, using the same approach
of having various optimized variants of main loops for different arguments, or
handling the start and end words of a line separately so the inner-most loop
can be executed without conditionals. Pretty much everything needs to be done
word-by-word, which is most efficient for 1 bit graphics because each word
stores 32 pixels. The only place where more than one word can be processed at
a time is when copying pixels without the need for shifting or color mapping.
In that special case we use \lstinline|Uint32Array|'s \lstinline|subarray()|
and \lstinline|set()| functions to copy a full line at once. This optimization
helps with scrolling, in particular.

The final stage of rendering the screen bitmap to an HTML5 canvas
object uses the \lstinline|putImageData()| drawing call. The image
data is assembled in a \lstinline|Uint32Array| by mapping each
individual pixel of 1, 2, 4, 8, 16, or 32 bits to a single 32 bit ABGR
pixel as required by the Canvas API. This needs to be done even in the
32 bit case because the order of color components differs between
Squeak and HTML. These conversions incur additional overhead compared
to the standard Squeak \ac{VM} (something that we share with
e.\,g. RSqueakVM, which outputs to
SDL\footnote{\url{http://www.libsdl.org/}, retrieved \today}.) In
\autoref{sec:eval}, this additional overhead is visible in the higher
slowdown that actually drawing to the screen versus just blitting
bitmaps incurs.

\subsection{Main loop}

In most Squeak VMs, the VM itself has a main loop that executes
byte codes until the system quits. Not so in \SqueakJS: The VM needs to
regularly break out of its interpreter loop, because only then will the web
browser update the screen or provide new input events.

The interpreter has two entry points: \lstinline|interpretOne()| for executing
a single byte code (which is used only when single-stepping in the VM
debugger), and \lstinline|interpret()| for executing multiple byte codes. The
latter loops for a certain time, or until a primitive requests an immediate
return of control to the browser. This happens e.g. after drawing to the
screen: to minimize the delay between drawing and the change being visible to
the user, the drawing primitive requests to exit the interpreter loop
immediately.

Also, break points can be set for various conditions, e.g. when a certain
method is executed or returns. When the condition is met, the interpreter loop
exits to let the debugger show that state.

To support using asynchronous functions in primitives that need to appear
synchronous to the Squeak runtime, we implemented a feature to ``freeze'' the
VM. A primitive can call the VM's \lstinline|freeze()| function, which returns
a callback function for unfreezing. All subsequent calls to
\lstinline|interpret()| are ignored until the unfreeze function was called by
the primitive's asynchronous event handler. That means the VM's state remains
unchanged until the unfreeze, so the primitive is allowed to defer pushing a
return value onto the stack until the asynchronous operation is done. This is
used for example to support asynchronous file access (see below).

\paragraph{Input Events}
Whenever \SqueakJS breaks out of the interpreter loop, the JavaScript
runtime has the chance to deliver new input events. The canvas object
that draws the Squeak display registers to receive the available input
events, such as \lstinline|onMouseMove|, \lstinline|onMouseDown|,
\lstinline|onKeyDown| and so on. In older Squeak images, two
primitives regularly check the state of the input devices. To support
that behavior, whenever \SqueakJS receives an input event, we store it
in a queue. When the image calls the stateful input primitives, states
are popped from the front of the queue, so all events are processed in
order. Newer Squeak and Etoys images use an ``event-driven'' approach:
they call a primitive that, instead of checking the \emph{current}
state of the input devices, releases an appropriate \lstinline|Event|
instance. However, if this primitive fails, all newer images can fall
back to using the stateful primitives, so \SqueakJS only implements
these.

\subsection{Files}
\label{sec:files}

As mentioned in \autoref{sec:making-it-happy}, a goal for \SqueakJS
was to provide some way offline storage. Persistent offline storage is
a relatively new feature for web browsers. The most common way is the
browser's \lstinline|localStorage|, which is synchronous, and very
easy to use, but only supports storing strings, and is usually limited
in size to 5 Megabytes. Fortunately, all major browsers now support
the \lstinline|indexedDB| client-side storage (Firefox x.y, Chrome
x.y, Safari x.y, IE ?/?) which stores arbitrary Javascript objects,
and has more generous size quotas, but is an asynchronous API.

The FilePlugin is implemented with a combination of \lstinline|localStorage|
and \lstinline|indexedDB|. Directory entry information (name, size, directory
flag, creation date, modification date) is serialized as a JSON string per
directory and saved in \lstinline|localStorage|. It is accessed very often so
the ability to access it synchronously is helpful. Also, it takes a relatively
small amount of space. Due to idiosyncrasies of Squeak, often files are opened
and closed without actually accessing the file contents.

The file contents is put into the \lstinline|indexedDB|. When the file
contents is needed, it is loaded from the database into memory. Since every
database access is an asynchronous operation, the VM is frozen until this read
operation is finished. Write operations are performed in memory only. It is
stored to the database only when the file handle is closed or explicitly
flushed. The VM does not need to wait until the write finishes (similar for
deleting a file). A single copy of the file contents in memory is shared for
all open file handles of the same file. The file handles are
reference-counted, and the memory is released when the last handle is closed.

A potential drawback of this scheme is that the two storages could get out of synch.
This has not been a problem so far. If it becomes a problem, a file system
check could restore consistency, or directory information could be stored in
\lstinline|indexedDB|, too.

To interact with the host file system, \SqueakJS handles drag and drop
of files from the disk into the Lively world -- Squeak image files are
loaded and run, graphics are read in-image and loaded as
Bitmaps. Files can also be stored into the host file system, by
generating a data uri in the HTML page, which can be saved to the file
system by the user.

\subsection{Embedding}

While \SqueakJS is developed inside Lively, the VM takes care to
not depend on Lively. It is implemented in a single JavaScript file. For
demonstration purposes we have written a simple harness that runs Squeak
without Lively. It consists of a 10 line HTML page, 30 lines of JavaScript to
emulate the Lively module and class system, and 200 lines to download an
image, set up input and output, and run the VM. Because the overhead of that
harness is considerably lower than the full Lively environment, it works
nicely even on mobile devices such as an iPad.

\subsection{Extensions}

The \SqueakJS VM can be extended with modules, just like most
regular Squeak VMs. There is an internal and an external modules interface.
Internal modules are part of the VM itself, they simply expose primitives by
name instead of by index. An example for an internal module is the FilePlugin.

External modules are implemented outside the core VM. The interface is purely
object-based. Which module is implemented in which file is unknown to the VM.
A module object is simply registered by name:
\begin{lstlisting}[numbers=none,columns=fixed]
Squeak.registerExternalModule('ModuleName',
                              moduleObject);
\end{lstlisting}

The module object needs to have a field named \lstinline|exports| which
references all provided primitive functions by name. If a function is exported
as \lstinline|initializeModule| then it will be executed when loading the
module, passing the VM's primitive handler as argument. This is similar to
passing the \lstinline|interpreterProxy| in C-based VMs, it allows the
module's primitive functions to interact with the VM, foremost to read
arguments from the stack and push a result back. An example external module is
\lstinline|SimplePlugin.js| as shown in \autoref{lst:simpleplugin}.
\begin{lstlisting}[float,caption={A simple Squeak Plugin},label=lst:simpleplugin]
var SimplePlugin = function() {
    var proxy;
    function initializeModule(interpreterProxy) {
        proxy = interpreterProxy;
    };

    function primitiveNavigatorInfo(argCount) {
        if (argCount !== 1) return false; // fail
        var which = proxy.stackInteger(0);
        if (!proxy.success) return false; // fail
        var result;
        switch (which) {
            case 1: result = navigator.userAgent; break;
            case 2: result = navigator.language; break;
        }
        if (!result) return false; // fail
        var resultObj = proxy.makeStString(result);
        proxy.vm.popNandPush(1 + argCount, resultObj);
        return true; // success
    };

    return {
        exports: {
            initializeModule:
                initializeModule,
            primitiveNavigatorInfo:
                primitiveNavigatorInfo,
        }
    }
};

// register plugin in global Squeak object
Squeak.registerExternalModule('SimplePlugin',
                                  SimplePlugin());

\end{lstlisting}

\section{Related Work}
\label{sec:related}

\paragraph{Squeak \acp{VM}}
\label{sec:squeakvms}

The root for all Squeak implementations is the original Squeak
\ac{VM} by~\citet{Ingalls+:1997:Back-to-the-future:-the-story}, that aims to
provide an open Smalltalk-80 system. Initially, the original \ac{VM} did only
provide an interpreter-based execution, hence it is sometimes called
interpreter \ac{VM}; it serves as the reference implementation for other Squeak
\acp{VM}. A \emph{Squeak Web Plugin} based on this \ac{VM} has been available
for several years; however, the plugin runs completely isolated from the
browser, thus, not providing any interaction from within the browser, let alone
JavaScript.


Another well-known Squeak \ac{VM} is the Cog\ac{VM}
by~\citet{Miranda2011:The-Cog-Smalltalk-Virtual-Machine:}, providing a fully
functional \ac{JIT} compiler for Squeak. Cog's primary concern is performance.
Both are written in \emph{Slang}, a Smalltalk subset that directly translates
to C.

The RoarVM by~\citet{Ungar+2009:Hosting-an-object-heap} implements Squeak with
a focus on exploiting manycore hardware. It is written directly in C++.

Potato\footnote{\url{http://sourceforge.net/projects/potatovm/}} and its
ancestor, JSqueak, are implementations of Squeak in Java, originally by
Ingalls. SPy, or RSqueakVM, by~\citet{Bolz+2008:Back-to-the-Future-in-One-Week}
is an implementation of Squeak in the PyPy framework. It is implemented in a
subset of Python, RPython, to test the variability of their \ac{VM} platforms.

NaClSqueak\footnote{\url{https://github.com/yoshikiohshima/NaClSqueak}}
by Ohshima is a deviation of the \emph{interpreter} Squeak \ac{VM}
modified to run natively on the NativeClient framework of the Chrome
browser family. Emscripten provides a similar option to NaCl,
compiling C code directly into JavaScript. While, to our knowledge, no
Squeak \ac{VM} compiled with Emscripten exists, PyPy, which is based
on the same RPython translation toolchain that RSqueakVM uses, has
been successfully compiled using Emscripten, and the same might work
for RSqueakVM. However, both NaCl and Emscripten focus on whole-system
translation, implement a C semantics, and are not intended to interact
with the JavaScript environment. In this regard, NaClSqueak and a
hypothetical Emscripten-compiled Squeak \ac{VM} come closest to the
Squeak Web plugin. Their most direct advantage is near native
performance through highly optimized JavaScript code, but they are
difficult to debug and instrument from JavaScript. Additionally,
NativeClient is only available to Chrome browsers.

\paragraph{Dynamic Languages on Dynamic Languages}
\label{sec:dynam-lang-impl}

Squeak itself can be run ontop of Squeak whithin the \emph{Simulator}. While
being slow, this provides means of introspection into the Squeak \ac{VM}.
However, these means are limited to the C-oriented view of Slang; objects of
the guest Squeak cannot be accessed as such. In \SqueakJS, the objects of the
guest Squeak are readily available.

Self includes Smalltalk~\citep{wolczko:1996:self-includes:}, as a bytecode
simulation, since version 4.0.\tim{One sentence more}

Amber\footnote{\url{http://amber-lang.net}} by Petton et al. is a Smalltalk
dialect from the Squeak family implemented JavaScript. It includes a complete
development environment and Smalltalk-to-JavaScript compiler.

Hobbes is a \ac{VM} for the original Smalltalk-80 written in VisualWorks
Smalltalk by Bykov, later ported to \SqueakST by Ingalls.

Whalesong by~\citet{yoo+:2013:whalesong:-running} [Racket],
Biwa\footnote{\url{http://www.biwascheme.org}} [Scheme], and
Skulpt\footnote{\url{https://github.com/skulpt/skulpt}} [Python], among
otheres, are JavaScript implementations of \acp{VM} for dynamic languages.

\paragraph{Other Languages ontop of JavaScript}
\label{sec:other-lang-ontop}

O'Browser by~\citet{canou+:2008:obrowser:-objective} [OCaml],
BicaVM\footnote{\url{https://github.com/nurv/BicaVM}} [Java], and
Doppio\footnote{\url{http://int3.github.io/doppio/about.html}} [Java], among
otheres, are JavaScript implementations of \acp{VM} for static languages.

For a plethora of languages, including Dart, CoffeScript, TypeScript, the
Google Web Toolkit (Java) and others, source-to-source compilers exists that
emit JavaScript code as result of the compilation process. Hence, not code of
the source language is actually run but JavaScript instead.


\section{Conclusion and Future Work}
\label{sec:conclusion}
\secmissing{Conclusion}

\emph{Things we learned}

- Small kernels make for (relatively) easy ports and emulations

- JSqueak was small enough to be a tractable experiment, yet complete enough to be motivating

- Performance is usable, and will only improve with technology

Good idea to make VM actually provide a virtual environment: no FFI, no direct
exposure of platform libraries. Instead, plugin interface implementable even
in completely different environments.

Would be nice if all non-essential primitives had working fallback code in
image. Would serve to get image up and running on a new platform much sooner.
